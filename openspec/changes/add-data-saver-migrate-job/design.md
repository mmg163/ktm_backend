# Design

## Context

Мотивация - `proposal.md`, требования - `specs/data-saver/schema-migration/spec.md`. Решение расширяет ADR-0004
(раздел 5 «Автоматический накат»); стек и роли - ADR-0001, `docs/04-ролевая-модель.md`. Исходное состояние: скрипты
`db/init` (суперпользователь, вручную) и `db/migrations/V*.sql` (идемпотентные, без метакоманд, под `ktm_migrator`),
накат вручную.

Ограничения: `ktm_app` без DDL; пароли не в репозитории, не в `.env`, не в argv; только бесплатные компоненты;
файлы конфигурации не тестируются (тест - на поведение скрипта).

## Goals / Non-Goals

**Goals:** накат миграций автоматически и воспроизводимо при `docker compose up`; сервис не стартует на
немигрированной базе; защита от параллельного наката; ошибка видна и останавливает развёртывание.

**Non-Goals:** автоматизация `db/init` (роли, расширение, схема, пароли ролей) - остаётся за администратором БД;
таблица истории версий и откаты (`down`-скрипты); накат на prod-контуре (решается с инфраструктурой); накат из
Data Saver или API.

## Decisions

### Р-1. Разовый контейнер, а не накат при старте сервиса

Контейнер `migrate` под `ktm_migrator`; `data-saver` ждёт `service_completed_successfully`. Накат при старте сервиса
отвергнут: требует DDL у `ktm_app` (ADR-0001 стр. 24, `docs/04`). Побочное следствие: `depends_on` действует при
`docker compose up`, но не при перезапуске контейнеров демоном Docker (`restart: unless-stopped` после перезагрузки
хоста) - тогда `data-saver` поднимется без прогона `migrate`; это допустимо, схема уже накачена. Поведение
`docker compose up -d` на уже завершённом `migrate` (повторный запуск контейнера или нет) разработчик проверяет и
фиксирует в руководстве (задача 3.2); критичного влияния нет, так как прогон идемпотентен.

### Р-2. Образ: официальный `postgres:16-alpine`, без собственного образа

Нужен только клиент `psql` 16 (метакоманда `\getenv` требует 15+; `pg_dump` для проверки идемпотентности тоже есть в
образе). Лицензия: PostgreSQL License (разрешительная, MIT-подобная), образ официальный, Docker Hub, бесплатно; базовая
система Alpine (musl, MIT/GPL-компоненты не распространяются нами). Размер порядка сотен МБ в распакованном виде
(точное значение разработчик фиксирует замером `docker images` в задаче 3.1 и записывает в design/руководство) - для
разового контейнера на dev приемлемо. Тег фиксируется конкретный (`16.<минор>-alpine<версия>`), не `latest` и не
плавающий `16-alpine`, как и для TimescaleDB (ADR-0004). Скрипт - POSIX `sh` (busybox в образе есть, `bash` в alpine
нет), монтируется `ro` из `deploy/data-saver/migrate/migrate.sh`.

Альтернативы: (1) `timescale/timescaledb:*-pg16` как образ клиента - тянет серверный образ ради клиента, лицензия
TimescaleDB смешанная (Apache/TSL), отвергнуто; (2) собственный образ `alpine` + `apk add postgresql16-client` -
меньше размер, но добавляет сборку и зависимость от `apk`-репозитория при сборке, выигрыш не оправдывает; (3) образ
с .NET и Npgsql - противоречит правилу «V-файлы выполняются тем же `psql`, что на вручную» и требует кода; отвергнуто.

### Р-3. Один сеанс `psql` на файл + отдельный сеанс-держатель блокировки

Требования «один сеанс на файл» и «блокировка на весь прогон» совместимы только через отдельный сеанс: сессионный
`pg_advisory_lock` живёт, пока жив сеанс, поэтому его держит выделенный фоновый `psql`, а файлы идут своими сеансами.

- Ключ: постоянная bigint-константа, объявленная в скрипте (например, `hashtextextended('ktm:schema-migration', 0)`
  либо литерал); один ключ на базу.
- Держатель: `psql` (фоновый процесс, стандартный ввод - из именованного канала/файла-дескриптора, открытого
  скриптом) выполняет `pg_advisory_lock`, затем ждёт EOF ввода. Скрипт узнаёт о получении блокировки по маркеру в
  выводе держателя и ждёт не дольше таймаута (`MIGRATE_LOCK_TIMEOUT_SECONDS`, по умолчанию 120); альтернатива -
  опрос `pg_try_advisory_lock` с паузой. Выбор механики - за разработчиком в границах требований spec; обязательные
  свойства: (а) блокировка не снимается раньше конца прогона, (б) снимается при любом завершении скрипта (`trap` на
  EXIT/INT/TERM и обрыв соединения), (в) перед каждым файлом проверяется, что держатель жив, иначе выход с ошибкой.
- Файл: `psql -X -v ON_ERROR_STOP=1 -f <file>`; `-X` исключает `psqlrc`. Сеанс на файл - потому что файл
  самодостаточен, и ошибка, остановившая один сеанс, не оставляет открытой транзакции следующего.
- Метакоманды: только в обёртке (держатель), в V-файлах - нет (ADR-0004). Нужны ли `-1`/`--single-transaction`: нет,
  файлы сами управляют транзакциями (`create_hypertable` и компрессия требуют отдельных ограничений); не добавлять.

Альтернатива «один сеанс на все файлы через `\i` под одним локом» проще, но нарушает требование изоляции файлов и
ломает диагностику (при ошибке вторая половина прогона зависит от состояния сеанса). Отвергнуто.

### Р-4. Порядок и проверки состава

`LC_ALL=C`, перебор `V*.sql` с сортировкой по имени. Проверки до первого файла: каталог содержит файлы; имя
соответствует `V<число>__<смысл>.sql`; номера уникальны (числовое сравнение: `V1` и `V001` считаются одним номером).
Пустая маска - ошибка, а не «нечего делать»: чаще всего это неверный монтаж. Лог: строка на файл «apply <name>» и
итог «done N files».

### Р-5. Секрет: файл -> `PGPASSFILE` в tmpfs

Секрет подключён только к сервису `migrate` (сервис `data-saver` его не получает; решение лида 2026-11-21). Пароль читается из `/run/secrets/ktm_migrator_password` (путь переопределяется `MIGRATE_PASSWORD_FILE`; хранить
пароль ни в какой переменной окружения compose нельзя). Скрипт строит файл `.pgpass` формата
`host:port:db:user:password` в tmpfs (`/tmp`, `umask 077`, права `0600`), экранируя `\` и `:` в значении (требование
формата libpq), отбрасывая завершающий перевод строки, и удаляет файл в `trap`. `PGPASSFILE` указывает на него; в
argv и в окружение пароль не попадает, `set -x` не используется (либо отключается на время работы с паролем). Контейнер
запускается с `read_only: true`, `tmpfs: /tmp`, пользователем `1654:1654` (как у `data-saver`, поэтому `chown
1654:1654` + `0400` для `ktm_migrator_password` совпадает с текущим решением для `ktm_app_password`). Проверка:
`psql` под uid без записи в passwd работает при явном `-U`/`PGPASSFILE` (разработчик подтверждает в 3.1).
Альтернативы: `PGPASSWORD` из файла в entrypoint (проще, но значение видно в `/proc/<pid>/environ` процесса и
наследуется всеми дочерними; библиотека документирует его как нежелательный) - отвергнуто в пользу passfile;
`\getenv` - тоже требует переменной окружения, отвергнуто.

### Р-6. Подключение и SSL

`PGHOST`, `PGPORT`, `PGDATABASE` из `DataSaver__Postgres__{Host,Port,Database}` (общий `env_file: .env` для обоих
сервисов); порт по умолчанию 5432. Пользователь - константа `ktm_migrator` (необязательное переопределение
`MIGRATE_USERNAME` допустимо для тестов, но не из `DataSaver__Postgres__Username`: там `ktm_app`). `PGSSLMODE` из
`DataSaver__Postgres__SslMode`: Disable->`disable`, Prefer->`prefer`, Require->`require` (по умолчанию),
VerifyCA->`verify-ca`, VerifyFull->`verify-full`; иное - ошибка. Корневой сертификат для `verify-*` (`PGSSLROOTCERT`) -
вне объёма (решение лида: `Verify*` и сертификаты не рассматриваются). `.env` в `migrate` попадает целиком (там только несекретные значения -
правило `.env.example`).

### Р-7. Остановка при ошибке и видимость

`set -eu`; любая ошибка - ненулевой код (1 - ошибка миграции/состава, 2 - ошибка конфигурации/секрета, 3 - таймаут
блокировки/потеря сеанса; точные значения - в руководстве). Вывод `psql` идёт в stdout/stderr контейнера без
фильтрации (ошибки SQL видны в `docker compose logs migrate`); пароль в вывод не попадает. `restart: "no"`.

### Р-8. Идемпотентность и триггер пересмотра ADR-0004

Пока все файлы идемпотентны, повторный прогон при каждом `up` безопасен и дёшев. Таблицы истории нет, поэтому
каждый запуск перебирает все файлы. Условие пересмотра (ADR-0004, раздел 5): первый неидемпотентный V-файл (`ALTER
TABLE ... ADD COLUMN` без `IF NOT EXISTS`, `INSERT` справочника без `ON CONFLICT` и т.п.) - тогда вводится таблица
истории и готовый инструмент DbUp/Flyway. Проверка автором файла и ревью: двукратный прогон нового файла на пустой и
на мигрированной базе (метатест, задача 2.3, прогоняет так все файлы каталога).

### Р-9. Тесты: минимум автотестов, остальное вручную

Решение лида: автотестов немного. Автоматически (Testcontainers, `Ktm.DataSaver.IntegrationTests`): (1) двукратный
прогон скрипта на TimescaleDB `2.32.1-pg16` после `db/init` - оба раза код 0, схема `ktm` создана и неизменна;
(2) заведомо неверный SQL во временной копии каталога - ненулевой код и ошибка в выводе; (3) метатест: каждый
`db/migrations/V*.sql` проходит двукратный прогон (охрана условия ADR-0004), если он дёшев. Скрипт запускается во
втором контейнере с тем же образом, что в compose (общая сеть, `db/` смонтирован `ro`, пароль файлом); допустимое
упрощение - `exec` скрипта внутри DB-контейнера (в нём тоже есть `psql`). Тест проверяет поведение скрипта, не
compose-файл и не конфиги (правило проекта).

Один раз вручную, с записью в `docs/test-protocols/data-saver-migrate-job.md`: порядок файлов, параллельный запуск и
ожидание блокировки, таймаут блокировки, `SslMode` (по умолчанию `require`, отказ без SSL), секрет (пароль со
спецсимволами подключается, в `docker compose logs`/`ps` не виден), остановка `up` при ошибке миграции, проверки состава
каталога.

## Risks / Trade-offs

- **R-1. Накат при каждом `up`.** Всегда прогоняется весь набор файлов; растёт со временем. Приемлемо при единицах
  файлов; смена на историю версий - по триггеру ADR-0004.
- **R-2. Пароль мигратора на `dev-backend`.** Расширяет поверхность: файл с паролем роли-владельца схемы рядом с
  сервисом. Смягчение: `0400`, uid контейнера, отдельный от `ktm_app` файл, подключён только к `migrate`, нет в `.env` и
  образе. Решение принято лидом (А2).
- **R-3. Потеря сеанса-держателя.** Сессионная блокировка исчезает при обрыве соединения незаметно; закрыто
  проверкой живости перед каждым файлом (но не посреди файла). Окно гонки на время одного файла остаётся и допустимо
  при идемпотентных файлах.
- **R-4. `depends_on` не действует при рестарте демоном.** См. Р-1.
- **R-5. Версия `psql` и сервера.** Клиент 16, сервер 16: проверено дизайном, подтверждается на dev (А4).
- **R-6. Скачивание образа.** Docker Hub с `dev-backend` доступен (подтверждено лидом).

## Migration Plan

1. ADR-0004 дополнен; задачи 1-4 в ветке `feature/data-saver-migrate-job`, ревью `reviewer` по группам.
2. Администратор создаёт файл пароля `ktm_migrator` (`secrets/ktm_migrator_password`) и задаёт пароль роли (`db/README.md`).
3. Деплой на `dev-backend`: `docker compose up -d`; `migrate` - код 0, `data-saver` стартует; повторный запуск - код 0,
   `pg_dump --schema-only -n ktm` не меняется (5.2).
4. Откат: убрать сервис `migrate` и `depends_on` из compose (накат снова ручной, `db/README.md`); схема не затрагивается.
