# Proposal

## Why

Миграции схемы `ktm` сейчас накатываются вручную (`db/README.md`, ADR-0004 п. 4: «оператор следит за порядком
сам»). На dev это означает, что `docker compose up` может поднять Data Saver на базе без миграций (сервис получит
`42P01`, «конфигурационная» ошибка записи, и будет повторять её бесконечно) либо на базе с частично применёнными
файлами. Одновременный ручной накат с двух машин не защищён. Пока файл один (`V001`), это терпимо; со вторым файлом
порядок и полнота наката становятся источником ошибок развёртывания.

Накат при старте самого сервиса отвергнут: `ktm_app` не имеет DDL (ADR-0001, стр. 24; `docs/04-ролевая-модель.md`,
принцип минимальных прав), а выдача DDL приложению разрушает защиту неизменяемости журнала. Нужен отдельный
исполнитель под ролью `ktm_migrator`.

## What Changes

- Разовый контейнер `migrate` в `deploy/data-saver/docker-compose.yml`: выполняет `db/migrations/V*.sql` скриптом-обёрткой
  через `psql` под `ktm_migrator` и завершается. Образ - официальный `postgres:16-alpine` (фиксированный тег),
  собственного образа нет, `db/` и скрипт монтируются только на чтение.
- Сервис `data-saver` получает `depends_on: migrate: condition: service_completed_successfully`: стартует только после
  успешной миграции; при ошибке миграции сервис не стартует, причина видна в `docker compose logs migrate`.
- Скрипт: порядок по возрастанию имени, один сеанс `psql` на файл с `ON_ERROR_STOP=1`, глобальная защита от
  параллельного наката (`pg_advisory_lock` на весь прогон), пароль только из файла Docker secret
  (`secrets/ktm_migrator_password`), SSL-режим как у сервиса.
- Немного автотестов (Testcontainers): двукратный прогон, неверный SQL с ненулевым кодом, метатест идемпотентности
  `V*.sql`; порядок, параллельный накат, `SslMode` и секрет проверяются один раз вручную и фиксируются в протоколе
  `docs/test-protocols/data-saver-migrate-job.md`.
- ADR-0004 дополняется (не заменяется); `db/README.md` и `docs/manuals/data-saver.md` описывают новый порядок.

Не меняется: `db/init` (роли, расширение, схема `ktm`, пароли ролей) остаётся ручным шагом администратора БД под
суперпользователем; содержимое `V001`; роль и права `ktm_app`; контракты API и Kafka; код Data Saver.

Ломающих изменений нет. Побочный эффект: `docker compose up` теперь требует секрет `ktm_migrator_password` (без него
compose не стартует) - обновляется инструкция запуска.

## Impact

- **Код/конфигурация**: `deploy/data-saver/docker-compose.yml` (сервис `migrate`, `secrets`, `depends_on`),
  `deploy/data-saver/migrate/migrate.sh` (новый), `.env.example` (без секретов; при необходимости переменная таймаута
  блокировки), тестовый проект `Ktm.DataSaver.IntegrationTests` (новый тест). Код Data Saver не меняется.
- **Данные**: схема не меняется. `ktm_migrator` получает пароль (ручной шаг администратора, как и для `ktm_app`).
- **Документация**: ADR-0004 (раздел 5), `db/README.md`, `docs/manuals/data-saver.md`.
- **Эксплуатация**: `dev-backend` получает ещё один секрет-файл `0400` (как у `ktm_app`, подключён только к `migrate`); образ
  `postgres:16-alpine` тянется из Docker Hub (доступен, внутренний реестр не нужен).
- **Приёмка**: усиливает «развёртывание воспроизводимо»; NFR не затрагивает.

## Dependencies

- `add-data-saver-core`: `db/migrations/V001`, `deploy/data-saver/docker-compose.yml` (задачи 9.1/9.4), ADR-0004, интеграционные
  тесты и фикстура Testcontainers. Ветка `feature/data-saver-migrate-job` создана от `feature/data-saver-core`;
  порядок слияния: сначала core.

## Assumptions

- (А1) **Подтверждено лидом.** На dev-data суперпользователя для автоматизации нет: `db/init` выполняет администратор
  БД вручную. Этот change init не автоматизирует и от суперпользователя не зависит.
- (А2) **Решено лидом.** Пароль `ktm_migrator` - Docker secret файлом `secrets/ktm_migrator_password` (`chown
  1654:1654`, `0400`), как у `ktm_app`; подключён только к `migrate`, сервис его не получает; в `.env`, образе и
  репозитории пароля нет. Это не вопрос, а принятое решение.
- (А3) Все существующие `V*.sql` идемпотентны (ADR-0004); таблицы истории применённых версий нет.
- (А4) `psql` 16 совместим с сервером PostgreSQL 16 (TimescaleDB) на `dev-data`; подтверждается ручной проверкой (5.3).
