# Proposal

## Why

Адаптеры СКУД и видеоаналитики разработаны, но в Kafka не пишут; формат сообщения
(`docs/api/kafka-event-format.md`), топики (`infra/kafka`) и схема журнала
(`docs/design/Схема_БД_ER.md`) уже определены. Нет компонента, который доставляет
события из Kafka в неизменяемый журнал. Без него уровень 1 (`docs/03-архитектура.md`,
п. 3.2) не работает, а требования п. 5.1 ТЗ (идемпотентность по составному ключу,
отбраковка ошибочных данных, продолжение работы при сбоях) и п. 7.1 (пик 500
событий/с, задержка до отражения не более 5 минут) нечем проверить. Data Saver —
ядро приёма: все остальные части уровней 1-3 зависят от того, что события попали в
журнал ровно один раз и не потерялись при сбоях БД, перезапусках и масштабировании.

## What Changes

- Новый сервис **Data Saver** (.NET Worker, Confluent.Kafka + Npgsql): читает единый топик
  `ktm.events.raw` в группе `ktm-data-saver`, пишет пачками в `ktm.events` одним
  `INSERT ... ON CONFLICT DO NOTHING`, фиксирует offset только после commit в БД.
- Корректирующие сообщения сохраняются в `ktm.event_corrections` (с записью в `events`
  как обычного события, как в схеме B3; исходное событие не меняется; сохраняются и
  при отсутствии исходного). **Расхождение с постановкой - см. design.md, Open Questions.**
- Устойчивость к сбоям: при недоступности БД - pause партиций, повтор с нарастающей
  паузой (backoff), потерь нет; graceful shutdown дописывает пачку и фиксирует offset.
- Масштабирование копиями (общая группа потребителей), настройки только из окружения,
  эндпоинты `/health/live` и `/health/ready`.
- Конвейер стадий (разбор и проверка формата, порт проверки событий C5, порт
  обработки ошибок записи C6, отбраковка в `ktm.events.rejected`) с **точкой
  расширения** под будущий движок правил отбраковки; сам движок правил - вне объёма.
- ADR: `docs/adr/0001-backend-stack.md`, `0002-data-saver-ingestion.md`,
  `0003-data-saver-validation-pipeline.md`, `0004-db-migrations.md`.
- Dockerfile, пример `docker compose` для dev, интеграционные тесты на Testcontainers
  (Kafka + TimescaleDB), замер событий/с, протокол испытаний.

Ломающих изменений нет: публичный REST API (`Ktm.Api`) и контракт сообщения Kafka не
меняются (кроме фиксации имени топика `ktm.events.raw` в `kafka-event-format.md`); схема БД
не меняется: миграция создаётся по DDL `Схема_БД_ER.md` п. 9 как есть (`db/migrations/`, ADR-0004).

## Capabilities

### New Capabilities
- `data-saver/event-ingestion`: чтение событий из Kafka и запись в журнал:
  пакетирование, идемпотентность, модель commit offset, корректировки, поведение при
  сбое БД, остановка, масштабирование, конфигурация, health.
- `data-saver/ingestion-pipeline`: стадии разбора и отбраковки, порты C5/C6, учёт
  offset для отбракованных сообщений, требования к расширению под движок правил.

## Impact

- **Код**: новые проекты в `src/Ktm/` (`Ktm.DataSaver.Core`, `Ktm.DataSaver.Infrastructure`,
  `Ktm.DataSaver`, два тестовых). `Ktm.Api` не затрагивается.
- **Данные**: запись в `ktm.events`, `ktm.event_corrections` под ролью `ktm_app`
  (`SELECT, INSERT`); миграции приложением не применяются.
- **Kafka**: читает `ktm.events.raw`, пишет в `ktm.events.rejected`. В `infra/kafka` три топика
  `ktm.events.raw.*` заменены одним `ktm.events.raw` (9 партиций, хранение 7 суток).
- **БД**: новые каталоги `db/init`, `db/migrations` (ADR-0004).
- **Эксплуатация**: новый контейнер на `dev-backend`; переменные окружения и секреты
  (доступ к БД) задаются вне репозитория.
- **Приёмка**: закрывает критерии «событие в БД за секунды», «дубли не создают записей»,
  «остановка без потерь», «сбой БД без потерь», замер пропускной способности (dev -
  ориентир, НФТ подтверждается на целевом контуре).

## Dependencies

- **A1** (инфраструктура/топики), **B3** (схема журнала и роли), **C2** (формат
  сообщения) - готовы как документы; скрипт миграции создаётся в этом change (группа 4A).
- **C5** (проверка событий), **C6** (обработка ошибок записи) - подключаются через порты;
  до них работают заглушки.

## Assumptions

- Топики и ключ сообщения - как в `infra/kafka` (ключ `<источник>:<sourceEventId>`).
- Схема сообщения v1 - единственная поддерживаемая версия (`{1}`).
- Привязка события к сотруднику (Процессор привязки) - отдельная задача, не здесь.
- Коэффициенты доверия источников пока не хранятся; временная реализация берёт значение
  из окружения и подлежит замене.
