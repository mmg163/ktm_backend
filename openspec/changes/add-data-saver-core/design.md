# Design

## Context

Мотивация - `proposal.md`. Требования - `specs/data-saver/*/spec.md`. Подробное
обоснование решений - ADR: `docs/adr/0001-backend-stack.md`,
`0002-data-saver-ingestion.md`, `0003-data-saver-validation-pipeline.md`; здесь -
сжатая сводка, связь с задачами и риски.

Конструктивные ограничения:

- **Нагрузка:** пик 500 соб/с, средняя 100, 15 млн в месяц (`docs/07`, п. 7.1);
  доля Data Saver в «5 минут до отражения» - секунды.
- **Идемпотентность - в схеме БД:** `UNIQUE (source, source_event_id, occurred_at)`
  (`docs/05`, п. 5.1; `Схема_БД_ER.md`). У `ktm_app` только `SELECT, INSERT`.
- **Kafka на dev:** один брокер, RF=1, 3 топика по 3 партиции, хранение 7 суток.
- **dev не подтверждает НФТ:** замеры на нём - ориентир (`add-infrastructure-topology`).

## Goals / Non-Goals

**Goals:**

- Доставка «минимум один раз» с идемпотентной записью, т.е. эффект «один раз» в журнале,
  без потерь при сбое БД, остановке и ребалансировке.
- Конвейер, в который без переделки цикла встают проверка формата, C5, C6 и будущий
  движок правил отбраковки.
- Каждый критерий приёмки задачи имеет автоматический тест.

**Non-Goals:**

- Движок правил отбраковки (только точка расширения и тесты на неё).
- Содержимое правил C5 и политика C6 (порты и заглушки).
- Процессор привязки, цифровой профиль, уровни 2-3, REST API журнала.
- Топики и брокер (A1). DDL, роли и миграции БД в объём **входят** (группа 4A, ADR-0004), но только для журнала событий.
- Канал уведомлений администратору, экспорт метрик в Prometheus/OTel.
- Параллельная запись внутри экземпляра (только по результату замера).

## Decisions

### Р-1. Npgsql + `unnest` на горячем пути; EF Core не используется (ADR-0002 D-2)

Одна транзакция на пачку, `INSERT ... SELECT FROM unnest(...) ON CONFLICT (natural key)
DO NOTHING`. *Почему:* EF Core не умеет пакетный `ON CONFLICT DO NOTHING`; один
round-trip на пачку; число вставленных строк = результат команды (счётчик дублей).
*Альтернативы:* EF Core + перехват конфликта, Dapper, `COPY` (оставлен как путь
оптимизации по замеру).

### Р-2. Commit offset после COMMIT в БД и публикации отбракованных (D-6)

`EnableAutoCommit=false`, ручной `Commit` с `offset+1` по партициям; в расчёт входят и
отбракованные сообщения. Порядок после записи: `Resume`, затем commit (D-7 п. 5); дубли в `rejected` при
частичном сбое публикации - осознанный at-least-once (D-6); `DeadLetter` от C6 - только после durable-сохранения.
Контракты портов цикла - ADR-0002 D-8а. *Почему:* «ничего не терять»; идемпотентность БД делает повтор
безвредным. *Альтернативы:* автокоммит (потеря), offset в БД (две точки правды).

### Р-3. Pause + продолжение опроса + backoff (D-7)

Недоступность БД -> `Pause(Assignment)`, `Consume` с коротким таймаутом (держим
членство в группе), повтор той же пачки с паузой 1 с, x2, потолок 30 с, джиттер 20 %.
Ошибки делятся на Transient / Fatal-config / Data; повтор без лимита для первых двух.

### Р-4. Корректировки: две записи в одной транзакции (D-4)

Как в B3: строка в `events` + строка в `event_corrections`, `correction_event_id` берётся
выборкой по натуральному ключу. *Почему:* схема B3 не вмещает исправленные значения в
`event_corrections`. Исходное событие не читается и не меняется; при его отсутствии
`original_event_id = NULL`. *Это расхождение с формулировкой задачи - Open Question 1.*

### Р-5. Конвейер стадий и точка расширения (ADR-0003)

`Decode -> IIngestionStage[] -> Classify -> Batch -> Write + Publish rejects -> Commit`.
Вердикт `Accept | Reject(RejectionInfo{Kind, Reason, RuleId?, TargetTopic?})`; отбракованное
сообщение продвигает offset. Правила - только качества данных (граница уровней).

### Р-6. Структура solution (ADR-0001)

`Ktm.DataSaver.Core` (без Kafka/Npgsql) <- `Ktm.DataSaver.Infrastructure` <- `Ktm.DataSaver`
(host). Домен не ссылается на инфраструктуру; цикл тестируется на fake-портах.

### Р-7. Health и остановка (D-8, D-10)

`ShutdownTimeout` отсчитывается от сигнала stop и ограничивает in-flight операции; остановка во время backoff - одна
немедленная попытка записи.

`/health/live` - heartbeat цикла (не зависит от БД), `/health/ready` - есть назначение
партиций, нет `Degraded`, брокер доступен (активный запрос метаданных, кэш 5 с, предел 2 с, не на потоке цикла - D-10),
БД доступна. SIGTERM: дописать пачку, закоммитить offset,
`Close()`, не позже `Shutdown__TimeoutSeconds`.

### Р-8. Конфигурация (D-11)

Окружение (`DataSaver__*`), секреты - переменные или файлы, валидация на старте;
в репозитории - только `.env.example` с заглушками.

### Р-9. Тесты (D-12)

Unit без контейнеров + интеграционные на Testcontainers (`apache/kafka`, TimescaleDB
pg16; приложение под ролью `ktm_app`). Сбой БД - остановка контейнера с фиксированным
host-портом; 15 с в обычном прогоне, 2 минуты в категории `Long`. Замер - категория `Perf`.

### Р-10. Граница Core обеспечивается структурой ссылок и ревью (задача 1.2)

Автоматического теста на границу Core нет: по решению лида проекта тесты на конфигурационные файлы и метафайлы
(`csproj`, `deps.json`, props) не пишутся (ADR-0001, раздел тестов). Граница обеспечивается тем, что
`Ktm.DataSaver.Core.csproj` не содержит `PackageReference`/`FrameworkReference` на Confluent.Kafka, Npgsql, EF Core, ASP.NET и
`ProjectReference` на `Infrastructure`/`Ktm.DataSaver`/`Ktm.Api`; соответствие ссылок проектов ADR-0001 проверяет
`reviewer` при каждом ревью изменений проектов. Остаточный риск: нарушение замечено только на ревью, а не сборкой.

### Р-10а. Сборка образа: контекст - корень репозитория

`Ktm.DataSaver.Core.csproj` встраивает схему из `..\..\..\docs\api` (одна копия правды). Поэтому контекст сборки
Docker-образа - корень репозитория, и он включает `docs/api` (в `.dockerignore` каталог `docs/api` не исключается);
`docker build` из `src/Ktm` или `deploy/data-saver` Core не соберёт. Касается задачи 9.1.

### Р-11. Правила C# в `.editorconfig` не вводятся

`.editorconfig` содержит только базовые форматные настройки (кодировка, окончания строк, отступы). Правила стиля и
анализаторов C# (`dotnet_diagnostic.*`, `csharp_style_*`) не добавляются в этом change: вместе с
`TreatWarningsAsErrors` они превращают вкусовые замечания в ошибки сборки и расширяют объём без связи с критериями
Data Saver. Если команда решит ввести - отдельная задача с прогоном по существующему коду.

## Risks / Trade-offs

- **R-1. Один брокер, RF=1, хранение 7 суток.** Потеря диска Kafka теряет ещё не
  принятые события; простой БД более 7 суток теряет хвост.
  -> Алерт на лаг группы `ktm-data-saver`; в целевом контуре 3 брокера
  (`add-infrastructure-topology`).
- **R-2. Пропускная способность dev не подтверждает НФТ** (БД и Kafka на одной ВМ).
  -> Замер на dev - ориентир; приёмка НФТ - на целевом контуре. Если на dev не набирается
  500 соб/с, сначала `COPY`-вариант записи, затем параллельная запись по партициям.
- **R-3. Скрипт миграции пишется в этом change** (ADR-0004, группа 4A) по черновику
  `Схема_БД_ER.md` п. 9. -> Риск расхождения с замыслом владельца схемы снимается ревью и
  тестом идемпотентности/прав (4A.2); тесты применяют те же файлы (7.1).
- **R-4. Двойной учёт исходного и исправляющего события на уровне 2.** Корректирующая
  строка лежит в `events` как обычное событие. -> Требование к ЧТЗ уровня 2: действующая
  версия определяется join'ом по `event_corrections`.
- **R-5. Нет проверки окна `occurredAt`.** Событие из 1970 или 2999 года создаёт чанки
  hypertable. -> Правило в зоне C5; пока риск принят.
- **R-6. Блокирующая заглушка C6.** Ошибка данных, не пойманная проверкой формата,
  останавливает партицию (потерь нет, но поток стоит). -> Лог Error, `ready = false`;
  политика C6 - следующая задача.
- **R-7. Идемпотентность зависит от детерминированного `occurredAt` у адаптеров.**
  -> Добавить в `kafka-event-format.md` (согласуется с владельцами адаптеров).
- **R-8. Ключ сообщения расходится между форматом и инфраструктурой** (`{source}:{externalPersonId}`
  против `<source>:<sourceEventId>`). Порядок по человеку не гарантируется; Data Saver
  корректен при любом порядке. -> Вопрос к владельцам адаптеров.
- **R-9. Интеграционные тесты требуют Docker.** На машине разработчика Docker есть, тесты
  запускаются локально (проверить командой `docker run hello-world`, задача 0.3). Открыт только
  вопрос CI: без Docker в CI автоматическая приёмка там невозможна; до решения - локальный
  прогон с протоколом.
  **Результат проверки 0.3 (2026-11-20):** `docker run --rm hello-world` выполнен сессией
  (Claude Code) на машине разработчика - успешно, Docker 29.9.3. Проверка разовая, на этой машине;
  на CI и на `dev-backend` не проверялась.

## Migration Plan

1. Merge ADR и этого изменения; подтвердить Open Questions 1-2.
2. Реализация по `tasks.md` в ветке `feature/data-saver-core` (код - роль `developer`,
   ревью - `reviewer` по группам задач).
3. Деплой на `dev-backend` (docker compose), `ktm_app` создан B3, топики существуют;
   смоук: тестовое сообщение (`source = skud`) в `ktm.events.raw` -> строка в `ktm.events`.
4. Откат: остановить контейнер; Kafka хранит сообщения 7 суток, повторный запуск
   дочитает с закоммиченного offset; журнал не затрагивается (только вставка).

## Open Questions

1. **(Решён, 2026-11-20.)** Постановка: «корректировка -> `event_corrections`,
   не `events`». Схема B3 требует и строку в `events` (исправленные `eventType`/`payload`
   негде хранить, `correction_event_id NOT NULL`). **Решено (лид проекта, 2026-11-20): вариант B3** (запись в `events` + `event_corrections`); изменение схемы B3 не требуется.
2. (Снят.) Скрипт миграции создаётся в этом change: `db/migrations/`, ADR-0004, группа 4A.
3. Какой ключ сообщения считать утверждённым (R-8)? Влияет на пересборку упорядочивания
   на уровне 2, не на Data Saver.
4. Нужна ли политика C6 «после N попыток - в `ktm.events.dlq`» вместо блокировки
   (R-6)? Не блокирует; решается в C6.
5. Откуда брать `trust` до появления хранилища настроек (временно - значение из окружения,
   по умолчанию 100)? Подтвердить шкалу 0..100 (`Схема_БД_ER.md` п. 7.1).
