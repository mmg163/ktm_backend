# Tasks

Код пишет роль `developer`; после каждой группы - `reviewer`. Чекбокс отмечается, когда поведение реализовано целиком и
проверка из задачи проходит. Запуск тестов - `$run-tests`. Тесты - только на поведение кода и БД (не на csproj, compose, `.env`, документы).
Решения и формулировки - `docs/adr/0006-data-saver-dlq-and-reprocessing.md` (ссылки «ADR п. X» - на него), структура - `design.md` (Р-n).
Ветка: `feature/add-data-saver-dlq-reprocessing`.

Объём: бюджет попыток (`MaxAttempts`) и изоляция ядовитого сообщения для **любой ошибки, привязанной к сообщению, на любой стадии** (разбор, C5, правила, запись; стадии `mapping` нет - JSON->событие = `parse`, событие->SQL = `write`; неожиданное исключение - туда же), `ktm.events.dlq` с заголовками `ktm-dlq-stage`/`ktm-dlq-exception-type`, повторная обработка (`dlq`, `rejected`, `raw` за период) через **HTTP admin-API `/admin/v1/reprocessing/...`** (асинхронные задачи, ProblemDetails, OpenAPI/Swagger, `.http`) и **админка `/admin/ui/`** на порту health, метрики и логи, документация.
Не входит: `dlq` для ошибок инфраструктуры (БД недоступна, таймауты, права, сеть - повтор без предела), CLI-режим `reprocess`, аутентификация и отдельный порт admin (решение лида: без них, защита сетевая), аудит-таблица, dry-run, публикация результатов обратно в топики, изменения схемы БД/compose/Dockerfile (design: Non-Goals).

Порядок групп: 0 -> 1 -> 2 -> 3 (ядро DLQ, критерии 1-3 лида); 4 -> 5 (повторная обработка: ядро, admin-API, админка; критерии 4-5); 6 (интеграционная приёмка); 7 (документация, критерий 6); 8 (закрытие).
Группы 4-5 не зависят от 3 по коду (общие `PoisonIsolator` и классификатор - из группы 1) и могут идти параллельно после группы 2.

## 3. Цикл приёма: повторы, изоляция, DLQ, предохранитель (`IngestionLoop`, unit на fake-портах `IngestionHarness`)

- [x] 3.1 Бюджет попыток в `WriteStageAsync` (design Р-3): ошибка `Data`/`Unexpected` - `dataFailures++`, для `Data` порт `IWriteFailureHandler` вызывается как сейчас, затем при `dataFailures < MaxAttempts` - Degraded, backoff, повтор пачки; `Transient`/`FatalConfig` - ветка без изменений (без предела); проверка - unit: Data-ошибка один раз, затем успех -> `dlq` пуст, offset зафиксирован, `Running`; `Unexpected` в записи на `MaxAttempts` -> изоляция и `dlq` (`unexpected_error`, `stage=write`); Transient N > MaxAttempts раз -> нет изоляции и нет `dlq`; FatalConfig - то же + `NotifyFatalConfig`; `Enabled=false` - повтор без предела (регрессия на прежние тесты)

- [x] 3.2 Изоляция и публикация в `dlq`: после исчерпания бюджета вызывается `PoisonIsolator`, записанное исключается из повторной записи (`written`), ядовитые (записи и стадий конвейера) публикуются в `dlq` одним шагом с повтором при отказе (`Retry("dlq_publish")`, Degraded, backoff без предела, результат изоляции не пересчитывается), затем попадают в `deadLettered`; commit offset по всей пачке только после подтверждения; проверка - unit: порядок вызовов (запись остальных -> публикация dlq -> commit), commit включает offset ядовитых, отказ публикации -> нет commit, затем успех -> commit, повторная запись остальных не вызывается (нет раздувания `duplicates`), число попыток записи ядовитого не растёт при повторах публикации
- [x] 3.3 Прерывание и границы: ошибка инфраструктуры при изоляции -> обычный путь без нового расхода бюджета и с продолжением изоляции; отозванные партиции не публикуются в `dlq`; остановка (`IoToken`) во время изоляции/публикации -> `false` без commit; `received_at` один для всех подзаписей; `Touch()` после каждой подзаписи и подтверждения публикации; проверка - unit на каждую ветвь (в т.ч. `StopAlreadySignalled...`-аналог, ребаланс во время публикации)
