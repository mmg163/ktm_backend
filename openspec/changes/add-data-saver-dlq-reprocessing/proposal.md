# Proposal

## Why

Корректное по формату сообщение, которое БД не принимает (нарушение ограничения, недопустимое значение), сегодня блокирует партицию
бесконечно: заглушка C6 (`BlockingWriteFailureHandler`) всегда отвечает «повторить» (`add-data-saver-core`, ADR-0003 п. 2.3). Топик
`ktm.events.dlq` создан, но не используется (ADR-0002 G-7); повторно обработать сообщения из `rejected` и `dlq` или перечитать `raw`
за период после сбоя нечем: `kafka-event-format.md` п. 3 называет это «ручной операцией администратора». События терять нельзя
(`docs/05` п. 5.1), а один «ядовитый» пакет не должен останавливать приём (NFR `docs/07` п. 7.1: 500 соб/с, 5 минут до отражения).

Зависит от C4 (запись, `add-data-saver-core`) и C5 (отбраковка, `add-data-saver-rules-engine`): оба реализованы и в `main`.
Решения и обоснование - `docs/adr/0006-data-saver-dlq-and-reprocessing.md` (статус «принят»; В-1 и В-2 изменены лидом 2026-11-24, раздел 9).

## What Changes

- **Бюджет попыток для любой ошибки, привязанной к сообщению** (решение лида, ADR-0006 В-1). Ошибка стадии разбора, C5, правил или записи в БД (отдельной стадии «маппинг» нет: JSON->событие = `parse`, событие->SQL = `write`) (SQLSTATE `22/23`, исключения сериализации, **любое неожиданное исключение**) повторяется
  с нарастающей паузой `DataSaver__Dlq__MaxAttempts` раз (3), затем сообщение изолируется и уходит в `dlq`; временный сбой, после которого обработка удалась, в `dlq` не попадает. **Без предела повторяются только ошибки инфраструктуры**
  (БД/сеть недоступны, таймауты, права/объекты). `rejected` не меняется (не JSON, не по схеме, отказ C5/правила - отбраковка, не `dlq`).
- **Изоляция ядовитого сообщения.** Для записи - деление пачки пополам до одиночных сообщений (`PoisonIsolator`); для стадий конвейера - повтор по конкретному сообщению; остальные сообщения обрабатываются, партиция не блокируется.
- **`ktm.events.dlq`.** Ядовитое сообщение публикуется с подтверждением брокера (исходные ключ и тело) и заголовками `ktm-dlq-reason` (`write_data_error`, `write_value_error`, `unexpected_error`), **`ktm-dlq-stage`**, **`ktm-dlq-exception-type`**,
  `ktm-dlq-detail`, `ktm-dlq-attempts`, `ktm-dlq-failed-at`, `ktm-source-topic|partition|offset|timestamp`; только после подтверждения offset коммитится. Стадия и тип исключения позволяют после починки кода повторно обработать `dlq`.
  Недоступный `dlq` = Degraded, повтор публикации без предела, без commit (ADR-0006 п. 2.5).
- **Предохранитель** (`DataSaver__Dlq__BreakerThreshold`, 20, сохранён): подряд уходящие в `dlq` сообщения без единой успешной записи означают системную проблему или баг кода (исключение на каждом сообщении); `dlq` отключается до первой успешной записи.
- **Повторная обработка через HTTP admin-API** (решение лида, В-2): `POST /admin/v1/reprocessing/jobs` (`dlq|rejected|raw`; для `raw` обязательны `from`/`to` UTC; `maxRate`) -> `202` + id задачи, одна задача одновременно (`409`), статус/прогресс/отчёт/отмена,
  ProblemDetails, OpenAPI и Swagger для `/admin`, `.http`-файл. Логика - сервис в Core, эндпоинты - тонкий слой; отдельный consumer без группы и commit (группа `ktm-data-saver` не трогается); аудит запуска в структурный лог. Область `/admin/v1/<раздел>/` расширяема.
- **Админка** `/admin/ui/` (решение лида): статическая страница, раздаваемая самим Data Saver (встроенные ресурсы, без сборки, без CDN, без зависимости от `ktm_revisor`): форма запуска, подтверждение, задачи, прогресс, отчёт, отмена; разделы добавляются модулями.
- **Без аутентификации (решение лида, принятый риск).** `/admin` работает на порту health, без ключа и отдельного порта: эндпоинты, способные массово переписывать данные, доступны любому, кто достучался до порта сервиса. Защита сетевая: внешний периметр/ingress
  не должен публиковать `/admin` - требование к деплою и пункт протокола приёмки (ADR-0006 п. 2.6, R-8).
- Метрики (`messages.dead_lettered{reason,stage}`, `write.isolations`, `dlq.breaker_open`, стадии `dlq_publish` и `pipeline` в `retries`), структурные логи без тел и текстов исключений.
- Контракт Kafka `docs/api/kafka-event-format.md`: раздел `ktm.events.dlq`; аддитивный заголовок `ktm-source-timestamp` в `rejected`. Контракт admin-API - `docs/api/data-saver-admin.openapi.json`.
- Документация: раздел «Топик `dlq` и повторная обработка» в `docs/manuals/data-saver.md`, раздел с `curl`-примерами в `src/README.md`, `.env.example`, сверка `docs/test-protocols/data-saver-scenario-coverage.md`.

Не меняется: схема журнала и права `ktm_app`, миграции, формат сообщения `schemaVersion = 1`, `Dockerfile`, `docker-compose.yml`, основной REST API и контракт с фронтендом.
Ломающих изменений нет: заголовки, топик и admin-область добавляются аддитивно; фронтенд не затрагивается.

## Capabilities

### New Capabilities
- `data-saver/dead-letter`: классификация ошибок (любая стадия), бюджет попыток, изоляция ядовитого сообщения, `ktm.events.dlq` (формат, подтверждение,
  недоступность), предохранитель, наблюдаемость.
- `data-saver/reprocessing`: admin-API и админка повторной обработки `dlq`/`rejected`/`raw`: источники, период, идемпотентность, задачи, защита рабочего потока, отчёт, аудит, сетевая защита.

### Modified Capabilities
- `data-saver/event-ingestion`: «Устойчивость к недоступности БД» (граница: ошибки, привязанные к сообщению, ограничены бюджетом, без предела - только инфраструктура),
  «Фиксация offset только после записи» (и после подтверждённой публикации в `dlq`), «Наблюдаемость приёма» (метрики и лог `dlq`).
- `data-saver/ingestion-pipeline`: «Порт обработки ошибок записи (C6)» (политика вместо заглушки; порт сохраняется).
- `data-saver/schema-migration`, `data-saver/rules-engine`: не меняются.

## Impact

- **Код**: `Ktm.DataSaver.Core` (`Resilience`: классификатор, бюджет, `PoisonIsolator`; `Ingestion`: порт `IDeadLetterPublisher`, правки `IngestionLoop`;
  `Reprocessing`: раннер, отчёт), `Ktm.DataSaver.Infrastructure` (`KafkaDeadLetterPublisher`, `KafkaReplaySource`, наблюдаемость), `Ktm.DataSaver`
  (опции, регистрация, режим `reprocess` в `Program.cs`, разделение composition root), тесты `Ktm.DataSaver.Tests` и `Ktm.DataSaver.IntegrationTests`.
  Новых NuGet-пакетов нет.
- **Данные**: схема БД не меняется; `ktm.events` пополняется восстановленными событиями (`received_at` = момент повторной обработки).
- **API/контракты**: Kafka - аддитивно; новая admin-область Data Saver (`/admin/v1/...`) на порту health; основной HTTP не затрагивается; фронтенд (`ktm_revisor`) не уведомляется.
- **Эксплуатация**: новая операция администратора (admin-API/админка), требование к деплою «не публиковать `/admin`», новый алерт на `dead_lettered`, регламент разбора `dlq` (30 суток хранения).
- **NFR**: нормальный путь записи без изменений; стоимость - только на ошибке Data (ADR-0006 п. 2.10); замер `Perf` с долей ядовитых сообщений - tasks 6.7.
