# Spec Delta

## Purpose

Капабилити описывает автоматический накат миграций схемы журнала событий (`db/migrations/V*.sql`) разовым контейнером
`migrate` под ролью `ktm_migrator` перед стартом Data Saver: порядок применения, защиту от параллельного запуска,
обращение с паролем, поведение при ошибке и повторном запуске. Создание ролей, расширения и схемы (`db/init`) в
капабилити не входит.

## ADDED Requirements

### Requirement: Миграции применяются разовым контейнером до старта сервиса

Развёртывание `deploy/data-saver/docker-compose.yml` ДОЛЖНО содержать разовый сервис `migrate` (без перезапуска), а сервис
`data-saver` ДОЛЖЕН зависеть от него условием `service_completed_successfully`. Сервис `data-saver` НЕ ДОЛЖЕН
выполнять DDL и применять миграции и ДОЛЖЕН работать под ролью `ktm_app`. Каталог `db/` ДОЛЖЕН монтироваться в контейнер
`migrate` только на чтение.

#### Scenario: Успешная миграция запускает сервис

- **WHEN** выполняется `docker compose up -d` на базе с выполненным `db/init` и заданным паролем `ktm_migrator`
- **THEN** контейнер `migrate` завершается с кодом 0, после чего стартует `data-saver`

#### Scenario: Ошибка миграции не даёт стартовать сервису

- **WHEN** один из `V*.sql` завершается ошибкой
- **THEN** контейнер `migrate` завершается с ненулевым кодом, `data-saver` не запускается, текст ошибки `psql` и имя
  файла видны в `docker compose logs migrate`

### Requirement: Порядок и состав файлов

Скрипт ДОЛЖЕН применять файлы `V*.sql` в порядке возрастания имени (сортировка не зависит от локали). Один файл
ДОЛЖЕН выполняться в одном сеансе `psql` с `ON_ERROR_STOP=1`; прогон ДОЛЖЕН прекращаться на первой ошибке, следующие
файлы НЕ ДОЛЖНЫ выполняться. Скрипт ДОЛЖЕН завершаться кодом 1, если файлов нет, если имя не соответствует
`^V[0-9]{1,9}__[A-Za-z0-9_.-]+\.sql$` (ASCII), если номер встречается дважды (`V1` и `V001` - один номер) или если порядок
по числовому номеру не совпадает с порядком по имени (`V2` и `V10` отвергаются, нужны ведущие нули). Метакоманды `psql` в `V*.sql` НЕ ДОПУСКАЮТСЯ (ADR-0004);
метакоманды допустимы только в обёртке.

#### Scenario: Файлы идут по порядку имени

- **WHEN** в каталоге `V001__a.sql`, `V002__b.sql`, `V010__c.sql`
- **THEN** выполнение идёт в порядке `V001`, `V002`, `V010`, имя каждого файла записано в лог

#### Scenario: Ошибка прекращает прогон

- **WHEN** `V002` содержит неверный SQL
- **THEN** код выхода ненулевой, `V003` не выполняется

#### Scenario: Номера без ведущих нулей

- **WHEN** в каталоге `V2__a.sql` и `V10__b.sql`
- **THEN** код выхода 1, причина названа в логе, ни один файл не выполнен

#### Scenario: Метакоманда psql в файле

- **WHEN** в `V*.sql` есть строка, начинающаяся (после пробелов) с обратной косой черты (`\i`, `\set` и т.п.)
- **THEN** код выхода 1, причина и имя файла названы в логе, ни один файл не выполнен

#### Scenario: Пустой или некорректный каталог

- **WHEN** по маске `V*.sql` нет файлов, либо два файла имеют один номер, либо имя не соответствует шаблону
- **THEN** код выхода 1, причина названа в логе, ни один файл не выполнен

### Requirement: Защита от параллельного наката

Скрипт ДОЛЖЕН на всё время прогона удерживать `pg_advisory_lock` с постоянным ключом в отдельном сеансе, время жизни
которого не превышает время жизни процесса скрипта (сервер снимает блокировку при любом завершении, в том числе
аварийном). Ожидание блокировки ДОЛЖНО быть ограничено настраиваемым временем (по умолчанию 120 с) с кодом выхода 3 по
истечении. Живость сеанса ДОЛЖНА проверяться запросом к серверу, а не только наличием процесса. Если сеанс блокировки потерян во время прогона, скрипт ДОЛЖЕН завершиться ошибкой до следующего
файла.

#### Scenario: Два запуска одновременно

- **WHEN** два экземпляра скрипта стартуют одновременно на одной базе
- **THEN** файлы выполняет один экземпляр, второй ждёт снятия блокировки, затем проходит все файлы повторно
  (идемпотентно) и завершается с кодом 0; два файла миграции одновременно не выполняются

#### Scenario: Блокировка не снимается

- **WHEN** блокировку удерживает другой сеанс дольше таймаута ожидания
- **THEN** скрипт завершается кодом 3 с сообщением о таймауте блокировки, ни один файл не выполнен

#### Scenario: Потеря сеанса блокировки

- **WHEN** сеанс, удерживающий блокировку, разорван между файлами
- **THEN** следующий файл не выполняется, код выхода 3

### Requirement: Пароль мигратора только секретом-файлом

Пароль `ktm_migrator` ДОЛЖЕН передаваться только файлом Docker secret `secrets/ktm_migrator_password` (права `0400`,
владелец - uid пользователя контейнера, как у `ktm_app_password`). Пароль НЕ ДОЛЖЕН находиться в `.env`, в образе
сервиса, в переменных окружения compose, в аргументах процесса и в выводе скрипта (включая режим `set -x`).
Завершающий перевод строки в файле ДОЛЖЕН отбрасываться. Недоступность файла ДОЛЖНА давать ненулевой код выхода с
сообщением, называющим путь, но не содержимое.

#### Scenario: Пароль не виден в процессах и логах

- **WHEN** скрипт выполняется с паролем, содержащим `:`, `\` и пробел
- **THEN** подключение успешно, пароль отсутствует в `docker compose logs migrate`, в `docker inspect` и в аргументах
  процессов контейнера

#### Scenario: Секрета нет

- **WHEN** файл пароля отсутствует или не читается
- **THEN** код выхода ненулевой, сообщение называет путь к файлу

### Requirement: Подключение теми же параметрами, что у сервиса

Скрипт ДОЛЖЕН брать хост, порт и имя базы из `DataSaver__Postgres__Host`, `DataSaver__Postgres__Port`,
`DataSaver__Postgres__Database`, режим SSL - из `DataSaver__Postgres__SslMode` (по умолчанию `Require`; значения
сопоставляются с режимами libpq, неизвестное значение - ошибка). Пользователь - всегда `ktm_migrator`;
`DataSaver__Postgres__Username` (роль `ktm_app`) и `DataSaver__Postgres__PasswordFile` скрипт НЕ ДОЛЖЕН использовать.
Отсутствие обязательной переменной ДОЛЖНО давать ненулевой код с названием переменной.

#### Scenario: SSL по умолчанию

- **WHEN** `DataSaver__Postgres__SslMode` не задан
- **THEN** соединение устанавливается с `sslmode=require`; при сервере без SSL подключение отклоняется, код выхода 1

#### Scenario: Роль приложения не используется

- **WHEN** в окружении `DataSaver__Postgres__Username=ktm_app`
- **THEN** миграции выполняются под `ktm_migrator`

#### Scenario: Ошибка подключения

- **WHEN** сервер недоступен для подключения (неверный пароль, SSL, хост)
- **THEN** код выхода 1, ни один файл не выполнен, пароль в сообщении отсутствует

### Requirement: Идемпотентность и повторный запуск

Повторный запуск `migrate` на уже мигрированной базе ДОЛЖЕН завершаться кодом 0 без изменения схемы. Таблицы истории
применённых версий нет: каждый файл `V*.sql` ДОЛЖЕН быть идемпотентным. Появление первого неидемпотентного файла
ЯВЛЯЕТСЯ условием пересмотра ADR-0004 (таблица истории и готовый инструмент DbUp/Flyway); такой файл НЕ ДОЛЖЕН
добавляться без этого пересмотра.

#### Scenario: Двукратный прогон

- **WHEN** `migrate` выполнен дважды подряд на базе после `db/init`
- **THEN** оба раза код 0, `pg_dump --schema-only -n ktm` до и после второго запуска совпадает
  (без строк `\restrict`/`\unrestrict`)

#### Scenario: Перезапуск сервиса

- **WHEN** выполняется `docker compose up -d` на уже мигрированной базе
- **THEN** `migrate` проходит с кодом 0 и `data-saver` стартует
