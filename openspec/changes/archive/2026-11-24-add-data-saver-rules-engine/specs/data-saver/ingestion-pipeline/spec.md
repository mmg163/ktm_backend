# Spec Delta

Изменяет требования капабилити `data-saver/ingestion-pipeline` (`openspec/specs/data-saver/ingestion-pipeline/spec.md`)
в связи с появлением движка правил (`rules-engine`, ADR-0005). Раздел `## Purpose` основной спеки (фраза «сам движок -
вне объёма этого изменения») механизмом дельт не меняется: правится при синхронизации (задача 8.4).

## MODIFIED Requirements

### Requirement: Проверка формата и отбраковка

Data Saver ДОЛЖЕН разбирать каждое сообщение и проверять его по схеме
`docs/api/kafka-event.schema.json` для поддерживаемых версий (сейчас `{1}`).
Сообщение, не являющееся JSON, с неизвестной, отсутствующей или нечисловой
`schemaVersion`, не прошедшее схему (включая время не в UTC), превышающее предел размера
(64 КиБ) или содержащее символ `\u0000`, ДОЛЖНО быть опубликовано в
`ktm.events.rejected` с оригинальным телом и ключом и заголовками `ktm-reject-reason`,
`ktm-reject-detail`, `ktm-source-topic`, `ktm-source-partition`, `ktm-source-offset`.
Если отбраковавшая стадия вернула непустой идентификатор правила, сообщение ДОЛЖНО
дополнительно нести необязательный заголовок `ktm-reject-rule-id` (значение не длиннее
128 символов, усекается); при отбраковке без правила заголовка НЕ ДОЛЖНО быть. Для отбраковки правилом
(`rules-engine`) сообщение ДОЛЖНО также нести необязательные заголовки `ktm-reject-rule-name` и
`ktm-reject-rule-version`; при отбраковке по формату или стадией C5 этих заголовков НЕ ДОЛЖНО быть.
Такое сообщение НЕ ДОЛЖНО попадать в журнал, ДОЛЖНО записываться в лог, а его
offset ДОЛЖЕН фиксироваться. Уровень записи в лог: Error для отбраковки по формату и стадией C5; Warning для отбраковки
правилом (требование `rules-engine`: «Отбраковка события правилом»). Причины отбраковки по формату - `unknown_schema_version`,
`invalid_schema`, `malformed_json`; иные случаи относятся к `invalid_schema` с пояснением в `detail`. Причина отбраковки
правилом - `reason_code` правила, он не совпадает ни с одной из причин формата. Корректирующее сообщение, ссылающееся на
собственный ключ, ДОЛЖНО отбраковываться как `invalid_schema`.

#### Scenario: Неизвестная версия

- **WHEN** приходит сообщение с `schemaVersion = 2`
- **THEN** оно публикуется в `ktm.events.rejected` с `ktm-reject-reason =
  unknown_schema_version` и нужными заголовками, в `events` строки нет, offset зафиксирован,
  чтение партиции продолжается

#### Scenario: Не JSON

- **WHEN** приходит сообщение с телом, не являющимся JSON
- **THEN** оно публикуется в `ktm.events.rejected` с `malformed_json`, чтение не блокируется

#### Scenario: Пачка из одних отбракованных

- **WHEN** пачка состоит только из отбракованных сообщений
- **THEN** обращения к таблицам журнала нет, отбракованные опубликованы, offset зафиксирован

#### Scenario: Ошибка публикации в rejected

- **WHEN** публикация отбракованного сообщения не удалась
- **THEN** offset пачки не фиксируется, попытка повторяется по правилам нарастающей паузы

#### Scenario: Отбраковка правилом несёт данные правила

- **WHEN** сообщение отбраковано правилом
- **THEN** в `ktm.events.rejected` у него есть `ktm-reject-rule-id`, `ktm-reject-rule-name`, `ktm-reject-rule-version`,
  `ktm-reject-reason` равен `reason_code` правила, остальные заголовки те же, что у отбраковки по формату

### Requirement: Точка расширения под правила отбраковки

Конвейер ДОЛЖЕН состоять из упорядоченного списка стадий, каждая из которых возвращает
по сообщению вердикт «принять» либо «отбраковать» (с видом, причиной, необязательными
идентификатором правила и целевым топиком). Отбракованное любой стадией сообщение НЕ
ДОЛЖНО записываться в журнал и ДОЛЖНО учитываться при расчёте фиксируемого offset
наравне с записанными. Публикация отбракованных ДОЛЖНА маршрутизироваться по целевому
топику вердикта, по умолчанию - `ktm.events.rejected`. Стадия НЕ ДОЛЖНА обращаться к БД
журнала синхронно на каждое сообщение и НЕ ДОЛЖНА изменять тело сообщения. Добавление
новой стадии НЕ ДОЛЖНО требовать изменения цикла чтения, записи и фиксации offset.
Движок правил отбраковки (`rules-engine`) ДОЛЖЕН быть реализован как такая стадия, вызываемая после проверки формата и
порта C5 и до записи; сообщение, отбракованное форматом или C5, правилами НЕ ДОЛЖНО вычисляться.

#### Scenario: Тестовая стадия отбраковывает часть сообщений

- **WHEN** в конвейер подключена тестовая стадия, отбраковывающая каждое третье сообщение
  в отдельный топик с идентификатором правила
- **THEN** такие сообщения не попадают в `events`, публикуются в указанный топик с
  идентификатором правила в заголовке `ktm-reject-rule-id` (и только в нём), а фиксируемый
  offset равен последнему сообщению пачки плюс один независимо от вердиктов

#### Scenario: Отбраковка без правила не несёт идентификатор

- **WHEN** сообщение отбраковано по формату (например, `malformed_json`)
- **THEN** в `ktm.events.rejected` у него нет заголовка `ktm-reject-rule-id`

#### Scenario: Стадия не знает о цикле

- **WHEN** разработчик регистрирует новую стадию в DI
- **THEN** цикл чтения и записи остаётся без изменений, а изменения ограничиваются
  стадией, её регистрацией и тестами

#### Scenario: Порядок стадий

- **WHEN** сообщение не прошло проверку формата либо отбраковано портом C5, а условие правила ему «подошло бы»
- **THEN** стадия правил для него не вызывается, причина в `rejected` - форматная либо причина C5
