# Spec Delta

## Purpose

Определяет запуск REST API и фоновых обработчиков ядра и гарантии конфигурации, хранения и совместимости развёртывания Data Saver.

## ADDED Requirements

### Requirement: Способ запуска компонентов ядра

Публичный REST API должен (MUST) запускаться отдельным процессом. Единый фоновый хост должен поддерживать независимый выбор Data Saver, Binding и Interpretation. Запуск Binding и Interpretation сам по себе не должен требовать Kafka. Фоновая обработка бизнес-событий Binding и Interpretation вводится последующими изменениями.

#### Scenario: Отдельный запуск API

- **WHEN** оператор запускает публичный REST API
- **THEN** API не активирует Data Saver, Binding или Interpretation

#### Scenario: Выбор обработчиков в локальном контуре

- **WHEN** оператор запускает фоновый хост с выбранными Binding и Interpretation
- **THEN** фоновый хост регистрирует каркасы этих обработчиков без запуска Data Saver
- **AND** отсутствие Kafka и параметров Data Saver не препятствует запуску

### Requirement: Совместимость развёртывания Data Saver

Действующее развёртывание Data Saver должно (MUST) сохранять имя сервиса, разовую миграцию как условие запуска, права `ktm_app`, параметры `DataSaver__*`, служебные HTTP-маршруты и контракты Kafka. Профиль этого развёртывания должен активировать только Data Saver.

#### Scenario: Обновление действующего развёртывания

- **WHEN** оператор запускает существующее развёртывание с действующей конфигурацией Data Saver и новым образом фонового хоста
- **THEN** после успешного выполнения миграционной задачи Data Saver запускается с прежними настройками и предоставляет действующие health и административные маршруты
- **AND** обработчики Binding и Interpretation не активируются

### Requirement: Проверка конфигурации и чтение секретов

Хосты должны (MUST) принимать настройки из переменных окружения и поддерживать секреты через параметры с суффиксом `_FILE`. Обязательные параметры хоста и активированных обработчиков должны проверяться до начала их работы. Диагностика не должна содержать значения секретов.

#### Scenario: Секрет из файла

- **WHEN** оператор задаёт параметр секрета через поддерживаемую переменную `*_FILE` с путём к читаемому файлу
- **THEN** настроенный компонент использует секрет из файла

#### Scenario: Неверная конфигурация

- **WHEN** обязательная настройка активированного компонента отсутствует или заданный файл секрета недоступен
- **THEN** процесс завершается с ненулевым кодом до начала его работы
- **AND** диагностика называет проблемную настройку и не содержит значения секрета

#### Scenario: Два источника нового секрета

- **WHEN** для нового параметра секрета заданы и значение, и путь через соответствующую переменную `*_FILE`
- **THEN** процесс завершается с ошибкой конфигурации до начала работы и не раскрывает значение секрета

### Requirement: Запуск с минимальными правами базы данных

Процессы ядра должны (MUST) использовать общую БД PostgreSQL со схемой `ktm` и подключаться с правами, необходимыми для активированных модулей. Версионируемые SQL-миграции должны выполняться отдельной задачей под ролью мигратора.

#### Scenario: Запуск каркаса на подготовленной БД

- **WHEN** оператор подготовил схему и запускает REST API и фоновый хост под прикладными ролями
- **THEN** процессы запускаются без прав мигратора и без самостоятельного применения миграций

#### Scenario: Изоляция таблиц ядра от Data Saver

- **WHEN** в схеме создаётся таблица ядра, к которой Data Saver не обращается
- **THEN** роль `ktm_app` не получает права чтения и записи этой таблицы

### Requirement: Локальный запуск

Инструкция разработчика должна (MUST) описывать команды сборки и тестирования solution и запуск локального контура с PostgreSQL/TimescaleDB и Kafka через Docker Compose.

#### Scenario: Запуск на чистом локальном контуре

- **WHEN** разработчик следует инструкции и задаёт перечисленные обязательные настройки
- **THEN** Compose поднимает БД и брокер, выполняет миграции и позволяет запустить REST API и фоновый хост
