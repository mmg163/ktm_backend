# Design

## Context

Мотивация - `proposal.md`, требования - `specs/data-saver/rules-engine/spec.md`, решения и их обоснование -
`docs/adr/0005-data-saver-rules-engine.md` (редакция 3; ссылки Р-n ниже указывают на его пункты). Здесь - как решение
встраивается в код `add-data-saver-core` (архив: `openspec/changes/archive/2026-11-22-add-data-saver-core`), порядок работ и риски реализации.

Исходное состояние (проверено по коду): `IngestionPipeline(FormatStage, IEnumerable<IIngestionStage>)`, стадия
`IIngestionStage.Evaluate(ConsumedMessage, ParsedEvent) -> IngestionVerdict` синхронная и чистая; `RejectionInfo(Kind, Reason,
Detail, RuleId, TargetTopic)`; `KafkaRejectionPublisher.ToMessage` пишет заголовки `ktm-reject-*`; `ObservedRejectionPublisher`
логирует Error и считает `messages.rejected{reason}`; `ParsedEvent.Body` - `JsonElement` всего тела; опции с проверкой при
старте (`AddOptions<T>(..., DataSaverChecks.*)`); `DataSaverWorker` запускает цикл; готовность - `HealthSignals`/`HealthEvaluator`;
`ISchemaValidator` (`LateApexEarlySpeed.Json.Schema`) - за интерфейсом, сейчас под схему события; `StartupErrors` - код выхода 78;
`BackoffPolicy` - нарастающая пауза.

## Goals / Non-Goals

**Goals:** правила качества данных в таблице БД (урезанной: одна таблица и миграции, `ktm_app` только `SELECT`), меняемые без
перезапуска опросом; запись условия в нотации JsonLogic при собственном вычислителе; отбраковка до записи с понятным выводом в
`rejected`; ошибочное правило и сбой чтения БД правил не ломают приём; все операции и узлы покрыты тестами; документ для человека;
шов под отложенную обвязку БД (аудит, `NOTIFY`) без переписывания движка.

**Non-Goals:** триггер версии, таблица и триггер аудита, `LISTEN/NOTIFY`, перечитывание «по команде» (отложены, ADR, приложение A);
операторы `in`, `missing`-подобный, регэксп, без учёта регистра (отложены, архитектурой допускаются); библиотека JsonLogic и
семантическая совместимость со стандартным JsonLogic (совместима только запись); JSON-файл правил; REST API и UI управления
правилами; уведомления администратору; правила интерпретации (роли, смены, оценки, привязка к сотруднику) - они уровня 2;
ретроактивная отбраковка уже записанного; повторная автоматическая обработка `rejected`; относительное время и функции в
условиях («старше суток»); экспорт метрик (Prometheus/OTel); проверка правил «на сухую» утилитой (в документе - ручной способ).

## Decisions

### Р-1. Структура в коде (ADR-0005 п. 2.1)

```
Ktm.DataSaver.Core/Rules/
    RuleDefinition            определение правила в терминах модели (Id, Name, Description, Source|null, Enabled, Priority, Version, ReasonCode, Condition: JsonElement)
    FieldPath                 разбор и вычисление пути к полю тела (грамматика `var`, п. 2.5)
    OperatorRegistry          реестр операторов: ==, !=, <, <= (2 и 3 операнда), >, >=; расширяется регистрацией
    ConditionCompiler         JSON-условие -> скомпилированные узлы; собирает список ошибок правила, ничего не бросает
    CompiledRule / Node       Evaluate(JsonElement body) -> bool; Trace(...) -> перечень сработавших листьев (только для сработавшего)
    RuleSnapshot              неизменяемо: индекс источник -> CompiledRule[] (общие правила уже слиты), ошибочные правила, ревизия
    RuleSnapshotBuilder       RuleSourceResult -> RuleSnapshot (проверка, лимиты, порядок, сравнение с прежним снимком для журнала изменений)
    IRuleSource               ReadAsync(previousRevision, ct) -> RuleSourceResult (Unchanged | набор); бросает RuleSourceException
    IRuleChangeSignal         WatchAsync(ct) -> поток подсказок «возможно, изменилось» (необязателен; реализации нет)
    IRuleSnapshotHolder       Current (volatile), Replace(snapshot); HasSnapshot
    RuleRejectionStage        IIngestionStage: берёт Current один раз, вычисляет по порядку, возвращает Reject(RejectionInfo{Kind=Rule,...})
Ktm.DataSaver.Infrastructure/Postgres/
    NpgsqlRuleSource          SELECT ... FROM ktm.rejection_rules; хэш выборки как ревизия; 42P01/42501 -> Configuration
    RuleRefreshService        IHostedService: первая загрузка (блокирует старт, повтор с backoff), таймер, журнал изменений
Ktm.DataSaver.Infrastructure/Observability/
    DataSaverMetrics (+)      метрики правил; ObservedRejectionPublisher: Warning для Kind=Rule, reason="rule_matched" в метрике
Ktm.DataSaver.Infrastructure/Kafka/KafkaRejectionPublisher (+)   заголовки ktm-reject-rule-name, ktm-reject-rule-version; детали до 1024
db/migrations/
    V002__rejection_rules.sql         таблица, CHECK-и, права
    V003__rejection_rules_examples.sql  выключенные примеры
```

`RejectionInfo` расширяется необязательными `RuleName` и `RuleVersion` (аддитивно, существующие конструкторы и тесты не
меняются). Стадия регистрируется после `EventValidationStage` (порядок регистрации в DI = порядок конвейера).

Схема условия `docs/api/rejection-condition.schema.json` в рантайме не используется (компилятор - единственный авторитет); тест
сверки загружает её через `ISchemaValidator` (нужен выбор схемы по имени, при этом библиотека JSON Schema остаётся известной только
`Core/Decoding`, ADR-0001).

### Р-2. Условие компилируется один раз, вычисление без аллокаций

`ConditionCompiler` превращает JSON-условие в дерево узлов с предразобранными путями, `decimal`/`DateTimeOffset` для сравнений и границ
диапазона. Операторы берутся из реестра (интерфейс: ключ, разбор операндов и проверка при загрузке, вычисление, имя для трассировки);
в первой итерации зарегистрированы `==`, `!=`, `<`, `<=` (две формы: два операнда и три - диапазон, обе границы включительно), `>`,
`>=`. Запись - нотация JsonLogic (`{"<": [{"var": "path"}, 0.3]}`), узлы `and`/`or`/`!`. Отложенные операторы добавляются классом и
регистрацией, без правок узлов, стадии и порта источника. Литерал слева (`[5, var]`) компилируется в зеркальное сравнение;
вычисление строгое, в отличие от стандартного JsonLogic (ADR п. 2.4). Вычисление на сообщение - обход дерева по `JsonElement` без
создания строк (кроме `GetString()` там, где без него не обойтись). Трассировка листьев - отдельный проход, только для сработавшего правила.

### Р-3. Снимок и первая загрузка

`RuleRefreshService` регистрируется до `DataSaverWorker`; его `StartAsync` делает первую загрузку и только затем возвращает
управление, так что цикл приёма не стартует без снимка. Kafka-подписка ленивая (решение лида): consumer создаётся и подписывается
после первой успешной загрузки правил, а не при старте процесса (реализовано). БД недоступна - повтор с `BackoffPolicy`, отмена по остановке host; в это
время `/health/ready` = 503 (Kestrel к тому времени уже слушает; порядок старта hosted-сервисов и Kestrel проверить на практике: если
Kestrel стартует позже `StartAsync`, readiness недоступна вместо «не готова» - допустимо для оркестратора, фиксируется в руководстве).
`RuleSourceException(Configuration)` (`42P01`, `42501`) на первой загрузке - ошибка конфигурации с кодом выхода 78 через
`StartupErrors`; после первой загрузки - обычная недоступность (прежний снимок). Пустая таблица - успешная загрузка с пустым набором
(Info). Ошибки отдельных правил на старте только логируются.

### Р-4. Опрос и «по команде»

Только таймер (`TimeProvider`; тесты с `FakeTimeProvider`): последовательная загрузка, тики не пересекаются. Выбран опрос без
`LISTEN/NOTIFY`: триггер и выделенное соединение убраны из первой итерации (отступление от постановки, подтвердить у лида).
`RuleRefreshService` принимает необязательный `IRuleChangeSignal` и ведёт общий `Channel` ёмкостью 1 (`DropWrite`) для таймера и сигнала с
паузой 1 с на склейку; без реализации сигнала работает только таймер. Цена опроса: один небольшой `SELECT` за интервал на экземпляр;
для быстрого применения администратор ставит интервал 5 с.

### Р-5. Порядок проверок при загрузке одного правила

Поля строки (`source` из `skud`/`cv`/`1c-do`/`*`, `reason_code` не из зарезервированных) -> для включённого: структура узлов (один ключ из
`and`/`or`/`!`/оператор сравнения) -> лимиты (глубина, узлы) -> оператор из реестра -> форма и типы операндов (для диапазона - `var`
посередине, два литерала одного вида, нижняя не больше верхней) -> путь (грамматика, первый сегмент) -> дата-значение (с зоной).
Первая найденная ошибка описывается как `<путь по дереву>: <причина>` (например `condition.or[1]: оператор "in" не поддерживается`) -
в лог попадает именно этот текст. Тексты ошибок не содержат значений из сообщений (их при загрузке нет).

### Р-6. Метаданные правила в вердикте и логе

`ktm-reject-detail` строит стадия (она знает правило и листья) по шаблону ADR-0005 п. 2.9; значения полей сообщения в текст не
входят. Лог пишет `ObservedRejectionPublisher` после подтверждённой публикации: Warning для `Kind = Rule`, Error для остальных
(поведение формата не меняется); `IAdminNotifier` не вызывается ни для одной из этих отбраковок. Журнал применённых наборов (Info при
замене снимка: ревизия, число правил, добавленные/изменённые/удалённые `rule_id` с `version`) пишет `RuleRefreshService`; изменение
содержимого без увеличения `version` - Warning (замена триггера версии).

### Р-7. Миграции

`V002` - таблица, CHECK-и, права; `V003` - выключенные примеры (`INSERT ... ON CONFLICT (rule_id) DO NOTHING`). Оба проходят
метатест «дважды» (ADR-0004 п. 5) и выполняются под `ktm_migrator`. Примеры в отдельном файле, чтобы правка набора примеров не
затрагивала файл схемы; следствие - удалённый пример возвращается при `migrate` (выключать, не удалять). Набор примеров - на операторах
первой итерации (ADR п. 2.3, tasks 1.2); перечислен в `docs/rules-engine.md`; проверяется тестом на компилятор и схему условия (защита от
примеров, которые сервис не принимает; тест на поведение загрузчика, а не на файл как конфигурацию).

### Р-8. Тесты

Unit (`Ktm.DataSaver.Tests`): на каждый оператор первой итерации (положительный и отрицательный случаи, отсутствует/`null`/другой тип;
диапазон - обе границы включительно, внутри, вне диапазона), на каждый узел (`and`, `or`, `!`) и вложенность, на пути, на компилятор
(каждая причина ошибки правила), на порядок и первый сработавший, на стадию (вердикт, заголовки, detail без значений), на недоступность
источника (последний снимок сохраняется), на журнал изменений, на счётчики; сверка схемы условия и компилятора на образцах.
Интеграционные (`Ktm.DataSaver.IntegrationTests`, Testcontainers Kafka + TimescaleDB, миграции из репозитория; правила вставляются
SQL): схема и права, 100/95/5, перезагрузка без рестарта (`UPDATE`, короткий интервал опроса), ошибочное правило, недоступность БД правил,
старт без таблицы (код 78). Перф - категория `Perf`, как существующие (Skip без `KTM_PERF_*`).

## Risks / Trade-offs

- **R-1. Критерии брака не получены у предприятия.** Примеры - иллюстрация, выключены. Закрыть этап «правила отбраковки
  настроены на данных предприятия» нельзя без владельцев источников; технически этап закрывается по критериям готовности.
- **R-2. Опечатка в пути внутри `payload` не ловится при загрузке** (структура `payload` не описана в `docs/api`). Смягчение:
  документ + ручная проверка правила на примере сообщения; по мере фиксации `payload` по источникам - ужесточение проверки.
- **R-3. Правка делает правило ошибочным -> фильтр выключается, брак идёт в журнал.** Алерт - на `rules.invalid` (канал вне
  объёма); в логе Error на каждое изменение, повтор раз в час.
- **R-4. Нет аудита изменений правил** (`docs/04` п. 4.4) - отступление, принятое лидом как временное; триггер возврата обвязки БД
  (триггер версии, аудит, `NOTIFY`) - первое реальное правило либо потребность в аудите.
- **R-5. Нет перечитывания «по команде»:** задержка до интервала опроса (по умолчанию 60 с; минимум 5 с). Отступление от постановки.
- **R-6. Отбракованное правилом - необратимая потеря «для журнала».** Смягчение: исходное сообщение в `rejected`, предупреждение
  в лог, метрика; повтор вручную. Срок хранения `rejected` на брокере (`kafka-event-format.md` п. 6 - не определён) влияет на
  то, как долго отбраковку можно разобрать: уточнить у владельца инфраструктуры.
- **R-7. Рост журнала `rejected`.** Слишком широкое правило отправит в `rejected` весь поток (до 500 соб/с). Нагрузка на
  публикацию `rejected` - существующий идемпотентный producer; замер в перф-проверке (задача 6.5) на 100 % отбраковки.
- **R-8. Согласованность экземпляров.** Несколько экземпляров могут краткое время работать на разных наборах (в пределах интервала
  опроса). Допустимо: правило отбраковки не требует транзакционной согласованности между экземплярами.
- **R-9. Правки идут под `ktm_migrator` без аудита:** роль DDL используется для DML (временно).
- **R-10. `version` ведётся вручную:** забытый инкремент искажает `ktm-reject-rule-version`; смягчение - Warning сервиса.
- **R-11. Первая версия нотации** фиксирует имена операторов и форму условия как стабильный контракт; переименование - миграция данных.

## Migration Plan

1. `migrate` накатывает `V002`, `V003` до старта `data-saver` (ADR-0004 п. 5); `ktm_app` получает `SELECT` на таблицу правил.
2. Сервис выкладывается с `DataSaver__Rules__Enabled=true`; примеры выключены, таблица содержит только выключенные правила - поведение
   приёма не меняется.
3. Администратор включает нужные правила `UPDATE ... SET enabled = true, version = version + 1` после согласования критериев.
4. Откат: `DataSaver__Rules__Enabled=false` (перезапуск) либо `UPDATE ... SET enabled = false` (без перезапуска). Таблица не удаляется.
5. Возврат обвязки БД (аудит, `NOTIFY`) - отдельный change по триггеру ADR-0005 п. 6: добавляются `V004` и `IRuleChangeSignal`;
   движок и контракт `rejected` не меняются.

## Open Questions

Решены по умолчанию, ждут подтверждения лида: ADR-0005 п. 9. Дополнительно:

- Срок хранения `ktm.events.rejected` и потребитель (R-6 выше): ответ от владельца инфраструктуры/потребителя.
- Кто правит правила на стенде и под какой ролью (до отдельной роли-редактора; сейчас `ktm_migrator`).
- Уведомление потребителей `ktm.events.rejected` (задача 7.2): потребитель топика не определён и не подтверждён, вопрос открыт
  (кому сообщать - решит лид). Изменение контракта аддитивно:
  необязательные заголовки `ktm-reject-rule-name`, `ktm-reject-rule-version` (и `ktm-reject-rule-id` при отбраковке правилом),
  новые значения `ktm-reject-reason` (`reason_code` правил), `schemaVersion` не меняется (`docs/api/kafka-event-format.md`, п. 3).
  Требование к любому потребителю (когда он будет определён): терпеть неизвестные заголовки `ktm-reject-*` и обрабатывать
  незнакомый `ktm-reject-reason` как «прочее»; отличать отбраковку правилом по наличию `ktm-reject-rule-id`; быть идемпотентным
  по `topic/partition/offset`. Предупреждение: при включении правил часть сообщений уходит в `rejected` не по причине формата,
  критерии брака согласуются до включения правил (все примеры выключены). Статус: уведомление не отправлено, адресат не определён;
  пока не подтверждено, совместимость потребителя считать недоказанной.
- Решено лидом: число вне `decimal` в литерале условия - ошибка загрузки этого правила (остальные работают, `rules.invalid`,
  `Error` с `RuleId`), ADR п. 2.6; Kafka-подписка ленивая - consumer создаётся после первой успешной загрузки правил (реализовано,
  ADR п. 2.10); `RuleRefreshService` остаётся в `Ktm.DataSaver/Hosting` (нужны internal `StartupErrors` и `DataSaverWorker`, ADR п. 2.1).
- Не решено: лимит условия 16 КиБ реализован `pg_column_size` (размер хранения, не логический), компилятор размер не проверяет;
  зафиксировано в документации как текущее поведение.
