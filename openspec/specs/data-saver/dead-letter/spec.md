# data-saver/dead-letter Specification

## Purpose

Капабилити описывает обработку сообщений, которые не удалось обработать из-за причины, привязанной к самому сообщению: что считается такой ошибкой (любая стадия: разбор, C5, правила, запись в БД; ошибка отображения JSON в событие - `parse`, события в параметры SQL - `write`),
сколько раз обработка повторяется, как «ядовитое» сообщение изолируется и уходит в `ktm.events.dlq`, формат сообщения в `dlq` (включая стадию и тип исключения), поведение при недоступном
`dlq` и предохранитель. Отличие от `ktm.events.rejected`: в `rejected` - штатная отбраковка (не JSON, не прошло схему, отказ C5/правила; решение о данных принято), в `dlq` - обработать сообщение не удалось
(отказ записи или неожиданное исключение стадии). Решения - `docs/adr/0006-data-saver-dlq-and-reprocessing.md` (В-1 изменено решением лида 2026-11-24).

## Requirements

### Requirement: Классификация: что уходит в DLQ

Data Saver ДОЛЖЕН направлять в `ktm.events.dlq` сообщение, обработка которого не удалась из-за ошибки, привязанной к сообщению, после `DataSaver__Dlq__MaxAttempts` попыток с нарастающей паузой, на любой стадии: разбор, валидация (C5),
движок правил, запись в БД. Отдельной стадии «маппинг» НЕТ: ошибка отображения JSON в событие относится к стадии `parse`, ошибка отображения события в запись журнала (параметры SQL) - к стадии `write`. К таким ошибкам относятся: отказ записи с SQLSTATE `22xxx`/`23xxx` (причина `write_data_error`), исключение сериализации значения при записи (`InvalidCastException`, `FormatException`,
`OverflowException`, `ArgumentOutOfRangeException`; причина `write_value_error`) и **любое иное неожиданное (неизвестное) исключение стадии, не относящееся к инфраструктуре** (причина `unexpected_error`).
Без ограничения числа попыток ДОЛЖНЫ повторяться **только ошибки инфраструктуры**: недоступность БД и сети, таймауты, взаимоблокировки, нехватка ресурсов, исчерпание пула, ошибки прав и отсутствия объектов, прочие ошибки БД с иным SQLSTATE
(по требованию «Устойчивость к недоступности БД», `event-ingestion`). Классификация ДОЛЖНА начинаться с проверки инфраструктурных признаков (цепочка исключений, SQLSTATE) и только затем относить исключение к ошибке сообщения.
Штатная отбраковка (не JSON, не прошло схему, отказ C5/правила) НЕ ДОЛЖНА уходить в `dlq` и НЕ ДОЛЖНА расходовать бюджет попыток: она остаётся в `ktm.events.rejected`.

#### Scenario: Недоступность БД не порождает DLQ

- **WHEN** БД недоступна дольше, чем `MaxAttempts` пауз повтора, затем восстанавливается
- **THEN** ни одно сообщение не опубликовано в `ktm.events.dlq`, после восстановления все события записаны по одному разу

#### Scenario: Ошибка прав или объектов БД

- **WHEN** запись отвергнута SQLSTATE `42501` или `42P01`
- **THEN** сообщения не уходят в `dlq`, поведение - как у ошибок конфигурации (повтор без предела, Error-лог, `ready = 503`)

#### Scenario: Неожиданное исключение в записи

- **WHEN** запись бросает исключение, не относящееся ни к инфраструктуре, ни к SQLSTATE `22/23`
- **THEN** обработка повторяется `MaxAttempts` раз с паузами, затем сообщение изолируется и уходит в `dlq` (`ktm-dlq-reason = unexpected_error`, `ktm-dlq-stage = write`), остальные записаны

#### Scenario: Неожиданное исключение в валидаторе

- **WHEN** валидатор (C5) бросает исключение для одного сообщения пачки
- **THEN** обработка этого сообщения повторяется `MaxAttempts` раз с паузами, затем оно уходит в `dlq` (`ktm-dlq-stage = validation`, `ktm-dlq-exception-type` = тип исключения), в `rejected` не попадает, остальные записаны

#### Scenario: Неожиданное исключение в правилах

- **WHEN** движок правил бросает неожиданное исключение для одного сообщения
- **THEN** сообщение после `MaxAttempts` попыток уходит в `dlq` со стадией `rules`, партиция не блокируется

#### Scenario: Ошибка отображения значения в запись журнала

- **WHEN** значение события не ложится в параметр записи (например, `OverflowException` при построении параметров SQL)
- **THEN** ошибка относится к стадии `write` (`ktm-dlq-reason = write_value_error`, `ktm-dlq-stage = write`), после `MaxAttempts` попыток сообщение уходит в `dlq`

#### Scenario: Неожиданное исключение при разборе

- **WHEN** разбор бросает исключение, не являющееся штатным признаком «не JSON/не по схеме»
- **THEN** сообщение уходит в `dlq` со стадией `parse`; штатно отвергнутое («не JSON», не по схеме) - в `rejected`

#### Scenario: Инфраструктурное исключение в стадии обработки

- **WHEN** исключение стадии обработки является недоступностью инфраструктуры (сеть, таймаут)
- **THEN** повтор без ограничения числа попыток, в `dlq` ничего не уходит

#### Scenario: Временное неожиданное исключение

- **WHEN** неожиданное исключение возникает один раз и при повторе обработка удаётся
- **THEN** сообщение обработано, в `dlq` ничего нет

### Requirement: Повторы записи с нарастающей паузой и бюджет попыток

При ошибке записи, привязанной к сообщению (класс «данные» и неожиданное исключение), Data Saver ДОЛЖЕН повторять запись той же пачки (одна транзакция, один `receivedAt`) с нарастающей паузой по политике
`DataSaver__Backoff__*` не более `DataSaver__Dlq__MaxAttempts` раз (по умолчанию 3; допустимо 1..20; ошибка значения - отказ запуска, код 78). Если запись
удалась в пределах бюджета, ни одно сообщение пачки НЕ ДОЛЖНО попадать в `dlq`. Во время повторов партиции ДОЛЖНЫ стоять на паузе, опрос consumer
продолжаться, состояние - `Degraded` (поведение по требованию `event-ingestion`). При неожиданном исключении стадии конвейера (разбор, C5, правила) повтор относится к конкретному сообщению (до `MaxAttempts` попыток, с паузами), остальные сообщения пачки обрабатываются и записываются.
Порт `IWriteFailureHandler` ДОЛЖЕН вызываться на каждой ошибке записи класса «данные» (SQLSTATE `22/23`) до расходования бюджета; принятое им решение `DeadLetter` имеет приоритет над бюджетом. `DataSaver__Dlq__Enabled=false` ДОЛЖЕН возвращать прежнее поведение (повтор без предела, в том числе при исключениях стадий конвейера, `dlq` не используется).

#### Scenario: Ошибка исчезла со второй попытки

- **WHEN** первая попытка записи пачки падает ошибкой класса «данные», вторая успешна
- **THEN** пачка записана, `dlq` не использовался, offset зафиксирован, счётчик попыток сброшен

#### Scenario: Пауза растёт

- **WHEN** запись пачки падает ошибкой класса «данные» несколько раз подряд
- **THEN** паузы между попытками следуют политике backoff (рост до потолка, джиттер), число попыток не превышает `MaxAttempts`

#### Scenario: Отключение

- **WHEN** `DataSaver__Dlq__Enabled=false` и запись падает ошибкой класса «данные»
- **THEN** партиция блокируется, повтор без предела, `dlq` не используется

### Requirement: Изоляция «ядовитого» сообщения

После исчерпания бюджета записи Data Saver ДОЛЖЕН определить сообщения, вызывающие ошибку, делением пачки пополам: каждая часть записывается отдельной
транзакцией с тем же `receivedAt`; успешно записанные части не пишутся повторно и не учитываются как дубли; упавшая часть делится до одиночных
сообщений; одиночное сообщение, упавшее ошибкой, привязанной к сообщению, признаётся ядовитым. Число записей при одном ядовитом сообщении в пачке из N
сообщений НЕ ДОЛЖНО превышать `2 * ceil(log2 N) + 1`. Если во время изоляции возникает ошибка инфраструктуры, изоляция ДОЛЖНА прерываться и
продолжаться после восстановления без нового расхода бюджета и без повторной записи уже записанного. Сообщения партиций, отозванных при ребалансе, НЕ ДОЛЖНЫ
публиковаться в `dlq`. Остальные сообщения пачки ДОЛЖНЫ быть записаны, чтение ДОЛЖНО продолжиться без остановки партиции.

#### Scenario: Одно ядовитое в пачке из 500

- **WHEN** в пачке из 500 сообщений одно нарушает ограничение БД
- **THEN** 499 записаны, ровно одно опубликовано в `dlq`, offset всей пачки зафиксирован, партиция не заблокирована

#### Scenario: Несколько ядовитых

- **WHEN** в пачке два ядовитых сообщения в разных частях
- **THEN** оба в `dlq`, остальные записаны, каждое сообщение записано не более одного раза

#### Scenario: БД упала во время изоляции

- **WHEN** во время изоляции запись отвергается как недоступная БД, затем БД восстановлена
- **THEN** изоляция завершается, ядовитое попадает в `dlq`, записанное ранее не дублируется, бюджет не расходуется заново

#### Scenario: Исправление и исходное в разных частях

- **WHEN** корректирующее сообщение и его исходное событие при делении оказываются в разных частях
- **THEN** оба записаны, связь корректировки создана (порядок не важен, `event-ingestion`: «Корректирующие сообщения»)

### Requirement: Публикация в DLQ

Data Saver ДОЛЖЕН публиковать ядовитое сообщение в топик `DataSaver__Kafka__DlqTopic` (по умолчанию `ktm.events.dlq`) с исходными ключом и телом
и заголовками (UTF-8): `ktm-dlq-reason` (`write_data_error` для SQLSTATE `22/23`, `write_value_error` для исключений сериализации, `unexpected_error` для прочих неожиданных исключений),
`ktm-dlq-stage` (стадия, на которой возникло исключение: `parse`, `validation`, `rules`, `write`; других значений нет), `ktm-dlq-exception-type` (полное имя типа исключения; без текста и стека),
`ktm-dlq-detail` (тип ошибки, SQLSTATE, имя ограничения и таблицы при наличии; не длиннее 1024 символов; без текста исключения и значений из
сообщения), `ktm-dlq-attempts` (целое число неудачных попыток обработки), `ktm-dlq-failed-at` (RFC 3339, UTC, `Z`), `ktm-source-topic`,
`ktm-source-partition`, `ktm-source-offset`, `ktm-source-timestamp` (RFC 3339, UTC, `Z`) и при известном SQLSTATE `ktm-dlq-sqlstate`. Публикация
ДОЛЖНА ждать подтверждения брокера (`acks=all`, идемпотентный producer). Offset сообщения ДОЛЖЕН фиксироваться только после подтверждения;
до него сообщение НЕ ДОЛЖНО исключаться из пачки. Заголовки `ktm-reject-*` в `dlq` НЕ ДОЛЖНЫ присутствовать; в `rejected` не публикуются сообщения
с отказом записи или исключением стадии; заголовки `ktm-dlq-stage` и `ktm-dlq-exception-type` ДОЛЖНЫ присутствовать всегда, чтобы после исправления кода выбрать сообщения для повторной обработки.

#### Scenario: Постоянная ошибка записи

- **WHEN** сообщение нарушает ограничение БД и все попытки исчерпаны
- **THEN** в `ktm.events.dlq` одно сообщение: ключ и тело совпадают с исходными, `ktm-dlq-reason = write_data_error`, `ktm-dlq-attempts` не меньше `MaxAttempts`, `ktm-dlq-stage = write`, `ktm-dlq-exception-type` заполнен,
  координаты `ktm-source-*` совпадают с исходными, в журнале события нет

#### Scenario: Заголовки не содержат данных события

- **WHEN** сообщение ушло в `dlq`
- **THEN** ни `ktm-dlq-detail`, ни `ktm-dlq-exception-type`, ни лог не содержат значений полей сообщения и текста исключения

#### Scenario: Различие rejected и dlq

- **WHEN** одно сообщение отбраковано правилом, а другое корректно, но не записано (или ломает код стадии)
- **THEN** первое только в `ktm.events.rejected` с `ktm-reject-*`, второе только в `ktm.events.dlq` с `ktm-dlq-*`

### Requirement: Недоступность топика DLQ

Если публикация в `dlq` не подтверждена (брокер недоступен, топика нет, нет прав, таймаут `Kafka__ProducerMessageTimeoutMs`), Data Saver ДОЛЖЕН
оставаться в состоянии `Degraded`, повторять публикацию с нарастающей паузой без ограничения числа попыток, НЕ ДОЛЖЕН фиксировать offset сообщений пачки и НЕ ДОЛЖЕН
терять сообщения или записывать их повторно. Результат изоляции НЕ ДОЛЖЕН пересчитываться между повторами публикации. Каждая неудача ДОЛЖНА учитываться в `retries{stage="dlq_publish"}`; для
неповторяемых ошибок (нет прав на топик, слишком большое сообщение) ДОЛЖЕН записываться Error в лог.

#### Scenario: DLQ недоступен, затем восстановлен

- **WHEN** ядовитое сообщение определено, а публикация в `dlq` не подтверждается, затем подтверждается
- **THEN** offset не зафиксирован до подтверждения, после подтверждения зафиксирован, остальные события записаны ровно по одному разу, число попыток записи ядовитого не растёт

#### Scenario: Остановка при недоступном DLQ

- **WHEN** во время ожидания публикации в `dlq` получен сигнал остановки и предел остановки вышел
- **THEN** процесс завершается без commit offset, после перезапуска сообщения читаются снова

### Requirement: Предохранитель DLQ

Если подряд `DataSaver__Dlq__BreakerThreshold` сообщений (по умолчанию 20; 1..10000; любой стадии и причины) направлены в `dlq` без единой успешной записи события между ними,
Data Saver ДОЛЖЕН прекратить направлять сообщения в `dlq`: перейти в `Degraded`, писать Error в лог на каждой попытке, вызывать `IAdminNotifier`, повторять запись без
ограничения и вернуться к обычной работе после первой успешной записи события. Состояние ДОЛЖНО быть видно в `ktm.datasaver.dlq.breaker_open` (1 - открыт).
Это правило ДОЛЖНО действовать и для сбоя стадии конвейера (разбор, C5, правила): при открытом предохранителе сообщение с постоянным стадийным сбоем НЕ уходит в `dlq`, consumer блокируется на повторе этого сообщения без предела,
состояние - `Degraded`, на каждой попытке - Error-запись цикла и вызов `IAdminNotifier`. Предохранитель хранится в памяти процесса: перезапуск сервиса сбрасывает его, после чего сообщение уходит в `dlq` за `MaxAttempts` попыток.
Счёт предохранителя по стадийным сбоям ведётся в пределах пачки до её записи: `BreakerThreshold` и более стадийных ядовитых сообщений в одной пачке открывают предохранитель, даже если в той же пачке есть валидные сообщения
(известное ограничение; такая доля ядовитых - проблема источника или кода, а не штатный поток).

#### Scenario: Системная проблема под видом ошибки данных

- **WHEN** каждое из подряд идущих сообщений отвергается ограничением БД либо вызывает исключение в стадии обработки (например, дефект нового кода)
- **THEN** после `BreakerThreshold` сообщений в `dlq` приём останавливается в `Degraded`, дальнейшие сообщения в `dlq` не уходят, `breaker_open = 1`

#### Scenario: Стадийный сбой при открытом предохранителе

- **WHEN** предохранитель открыт, а обработка сообщения в стадии конвейера постоянно завершается неожиданным исключением
- **THEN** сообщение в `dlq` не уходит, повтор идёт без предела, состояние `Degraded`, на каждой попытке вызван `IAdminNotifier`, offset не фиксируется; после перезапуска сервиса (предохранитель сброшен) сообщение уходит в `dlq` за `MaxAttempts` попыток

#### Scenario: Закрытие предохранителя

- **WHEN** после открытия предохранителя причина устранена и запись события удалась
- **THEN** `breaker_open = 0`, счётчик подряд идущих сброшен, приём продолжается

### Requirement: Наблюдаемость DLQ

Data Saver ДОЛЖЕН публиковать счётчик `ktm.datasaver.messages.dead_lettered` с тегами `reason` и `stage` (после подтверждения брокера), счётчик
`ktm.datasaver.write.isolations`, измерение `ktm.datasaver.dlq.breaker_open`. Уход сообщения в `dlq` ДОЛЖЕН записываться в лог уровня Error с именованными
`Topic`, `Partition`, `Offset`, `Source`, `SourceEventId`, `Reason`, `Stage`, `ExceptionType`, `Attempts`, `SqlState`, `ConstraintName`, `TableName`; тело сообщения, значения полей и
текст исключения в лог НЕ ДОЛЖНЫ попадать. Уход в `dlq` - технический инцидент записи и НЕ ДОЛЖЕН влиять на оценку сотрудников.

#### Scenario: Метрика и лог

- **WHEN** ядовитое сообщение подтверждено в `dlq`
- **THEN** `dead_lettered{reason,stage}` увеличен на 1, в логе одна запись Error с перечисленными полями, тела в ней нет

### Requirement: Конфигурация DLQ

Настройки `DataSaver__Kafka__DlqTopic`, `DataSaver__Dlq__Enabled`, `DataSaver__Dlq__MaxAttempts`, `DataSaver__Dlq__BreakerThreshold` ДОЛЖНЫ читаться из
окружения, иметь указанные умолчания и проверяться при старте: пустое имя топика и значения вне диапазонов - отказ запуска с кодом 78 и сообщением, называющим настройку (без
секретов). Правило согласованности `Health__LiveStaleSeconds` ДОЛЖНО учитывать ожидание публикации в `dlq` (то же значение `Kafka__ProducerMessageTimeoutMs`); цикл ДОЛЖЕН
отмечать heartbeat после каждой записи изоляции и после подтверждения публикации в `dlq`.

#### Scenario: Неверное значение

- **WHEN** `DataSaver__Dlq__MaxAttempts=0`
- **THEN** запуск отклоняется с кодом 78, сообщение называет `DataSaver__Dlq__MaxAttempts`

#### Scenario: Изоляция не роняет liveness

- **WHEN** изоляция пачки из 500 сообщений длится дольше одной обычной записи, но каждая запись укладывается в предел
- **THEN** `/health/live` остаётся 200
