# data-saver/rules-engine Specification

## Purpose

Капабилити описывает движок правил отбраковки Data Saver: хранение правил в таблице БД, язык условий, вычисление над событием,
перенаправление отбракованного в `ktm.events.rejected` вместо записи в журнал, загрузку и перезагрузку правил (опросом) без
перезапуска, поведение при ошибочных правилах и недоступности хранилища, лог и метрики. Проверка формата (JSON, версия, схема)
относится к `ingestion-pipeline` и правилами не является. Решения - `docs/adr/0005-data-saver-rules-engine.md` (редакция 3;
обвязка БД - триггеры версии и аудита, `LISTEN/NOTIFY` - и расширенный набор операций отложены и в эту капабилити не входят).

## Requirements

### Requirement: Правило отбраковки и его хранение

Правила ДОЛЖНЫ храниться в таблице `ktm.rejection_rules` со столбцами: `rule_id` (первичный ключ, `[A-Za-z0-9._:-]{1,128}`),
`name`, `description` (необязательный), `source` (`skud`, `cv`, `1c-do` или `*` - все источники; без значения по умолчанию),
`condition` (jsonb-объект до 16 КиБ), `reason_code` (`[a-z][a-z0-9_]{0,63}`, кроме `malformed_json`, `unknown_schema_version`,
`invalid_schema` - их отвергает БД, и системного `rule_eval_timeout` - его отвергает загрузчик правил: правило с этим кодом ошибочно), `enabled` (без значения по умолчанию), `priority` (0..10000, по умолчанию 100), `version` (1..1 000 000, по
умолчанию 1; увеличивается автором при правке, без триггера). Таблица ДОЛЖНА создаваться одной миграцией
`V002__rejection_rules.sql` (идемпотентной, под `ktm_migrator`), выключенные примеры для `skud`, `cv`, `1c-do` и общего правила -
миграцией `V003__rejection_rules_examples.sql`, выключенные примеры оператора `regex` - отдельной миграцией
`V004__rejection_rules_examples_regex.sql` (применённая `V003` не правится). Роль `ktm_app` ДОЛЖНА иметь на таблицу только `SELECT`. Правила НЕ ДОЛЖНЫ быть
зашиты в код. Аудита изменений правил, триггера версии и уведомлений об изменении в этой итерации НЕТ.

#### Scenario: Схема создаётся миграцией идемпотентно

- **WHEN** `V002__rejection_rules.sql`, `V003__rejection_rules_examples.sql` и `V004__rejection_rules_examples_regex.sql` применяются дважды под `ktm_migrator`
- **THEN** оба раза без ошибок, состав таблицы и примеров после второго раза не меняется

#### Scenario: Примеры выключены и принимаются загрузчиком

- **WHEN** загружаются примеры `V003` и `V004`
- **THEN** все выключены, условия проходят и компилятор, и JSON Schema условия без ошибок

#### Scenario: Приложение не может менять правила

- **WHEN** под ролью `ktm_app` выполняется `INSERT`/`UPDATE`/`DELETE` в `ktm.rejection_rules`
- **THEN** БД отвечает ошибкой `insufficient_privilege`, а `SELECT` выполняется

#### Scenario: Код причины формата для правила запрещён

- **WHEN** вставляется правило с `reason_code = 'invalid_schema'`
- **THEN** БД отклоняет вставку

#### Scenario: Системный код таймаута для правила запрещён

- **WHEN** в таблице включено правило с `reason_code = 'rule_eval_timeout'` (БД такую строку принимает: CHECK `V002` содержит три кода формата)
- **THEN** правило ошибочно и не применяется, в лог - Error с `RuleId` и причиной «код причины зарезервирован», `ktm.datasaver.rules.invalid` растёт, остальные правила работают

#### Scenario: Обязательные значения

- **WHEN** вставляется правило без `enabled` или без `source`
- **THEN** БД отклоняет вставку (значения по умолчанию нет)

#### Scenario: Изменение условия без пересборки

- **WHEN** администратор обновляет `condition` правила SQL-командой
- **THEN** изменение действует без пересборки и перезапуска сервиса (требование «Загрузка и перезагрузка»)

### Requirement: Язык условий

Условие (поле `condition`) ДОЛЖНО быть записано в нотации JsonLogic: узел - объект ровно с одним оператором из `and`, `or`, `!`,
`==`, `!=`, `<`, `<=`, `>`, `>=`, `regex`. `{"and": [узел, ...]}` и `{"or": [узел, ...]}` ДОЛЖНЫ быть логическими (не побитовыми)
операциями над результатами вложенных узлов с вычислением до первого определяющего результата; массивы ДОЛЖНЫ быть непустыми.
`{"!": узел}` (допустима запись `{"!": [узел]}`) ДОЛЖЕН быть отрицанием результата узла. Сравнение - `{"<оп>": [операнд, операнд]}` с
ровно двумя операндами, один из которых `{"var": "путь"}`, другой - литерал (порядок любой, литерал слева читается зеркально).
Диапазон - `{"<=": [нижняя, {"var": "путь"}, верхняя]}`: `нижняя <= поле <= верхняя`, обе границы включительно; нижняя не больше
верхней, обе - числа либо обе - даты. Любой иной оператор или форма (в том числе трёхаргументные `<`, `>`, `>=`, `var` со значением
по умолчанию или с выражением, `in`, `missing`, `if`, арифметика) ДОЛЖНЫ делать правило ошибочным. Вложенность ДОЛЖНА
поддерживаться в пределах: глубина 8, узлов-операторов 64. Путь (`var`) ДОЛЖЕН адресовать поле тела сообщения как оно получено, в
том числе внутри `payload` (`payload.confidence`, `payload.items.1.code`), сегменты через точку, сегмент из цифр у массива - индекс,
и начинаться с имени поля конверта формата v1. Типы НЕ ДОЛЖНЫ приводиться друг к другу (`"5"` не равно `5`), `==`/`!=` ДОЛЖНЫ быть
строгими. Числа ДОЛЖНЫ сравниваться как десятичные (`1` равно `1.0`). `<`, `<=`, `>`, `>=` и границы диапазона с числовым значением
ДОЛЖНЫ применяться к числовому полю; со строковым значением (дата RFC 3339 с обязательной зоной) - к строковому полю,
содержащему такую дату, сравнение по моменту времени. Для отсутствующего поля, `null` и несовпадения типов все сравнения, кроме
`!=`, ДОЛЖНЫ давать ложь; `!=` ДОЛЖЕН быть отрицанием `==` (отсутствующее поле «не равно» любому значению). Регулярное выражение - узел
`{"regex": [{"var": "путь"}, "шаблон"]}` с ровно двумя операндами в **фиксированном порядке** (первый `var`, второй - строковый литерал
от 1 до 512 символов): истинно, только если значение поля - строка и шаблон находит в ней совпадение **в любой части** (как
`Regex.IsMatch`; якоря задаёт автор шаблона); отсутствующее поле, `null`, число, булево, объект и массив дают ложь, типы не
приводятся; внутри `!` ложь листа даёт истину (как `!=`). Шаблон ДОЛЖЕН компилироваться один раз при загрузке правила
встроенным движком .NET в режиме линейного времени (`NonBacktracking`, `CultureInvariant`); регистр игнорируется встроенным в шаблон
`(?i)` (отдельного оператора и флага нет). Операции `contains`/`in`, пусто/заполнено (`missing`) и сравнение `==`/`in` без учёта
регистра на этой итерации НЕ ДОЛЖНЫ приниматься (правило с ними ошибочно); их добавление НЕ ДОЛЖНО менять формат условия и узлы
`and`/`or`/`!`. Число `regex`-узлов ДОЛЖНО быть не более 8 в правиле и не более `DataSaver__Rules__MaxRegexNodes` (по умолчанию 64) в
наборе; узел `regex` ДОЛЖЕН учитываться в лимитах глубины и 64 узлов правила наравне с сравнением. В трассировке листьев
(`ktm-reject-detail`) лист `regex` описывается как `путь regex`, без шаблона и без значений сообщения.

#### Scenario: Сравнение чисел

- **WHEN** условие `{"<": [{"var": "payload.confidence"}, 0.5]}` и `payload.confidence = 0.3`
- **THEN** условие истинно; для `payload.confidence = "0.3"` (строка) - ложно; для отсутствующего поля - ложно

#### Scenario: Литерал слева

- **WHEN** условие `{"<": [5, {"var": "payload.x"}]}` и `payload.x = 7`
- **THEN** условие истинно (читается как `x > 5`); для `payload.x = 5` - ложно

#### Scenario: Сравнение дат

- **WHEN** условие `{"<": [{"var": "payload.dueAt"}, "2026-01-01T00:00:00Z"]}` и значение `"2025-12-31T23:00:00+00:00"`
- **THEN** условие истинно (сравнение по моменту времени)

#### Scenario: Дата без зоны в правиле

- **WHEN** значение операции сравнения - строка-дата без зоны (`"2026-01-01"`)
- **THEN** правило ошибочно и не применяется

#### Scenario: Диапазон включает границы

- **WHEN** условие `{"<=": [0.2, {"var": "payload.confidence"}, 0.8]}`
- **THEN** истинно для 0.2, 0.5 и 0.8; ложно для 0.19, 0.81, строки `"0.5"` и отсутствующего поля

#### Scenario: Некорректный диапазон

- **WHEN** диапазон задан с нижней границей больше верхней, с числом и датой, либо трёхаргументным `<`
- **THEN** правило ошибочно и не применяется

#### Scenario: Равно и не равно

- **WHEN** условие `{"==": [{"var": "eventType"}, "test_event"]}` и `eventType = "test_event"`
- **THEN** истинно; `!=` на том же сообщении - ложно, на сообщении без поля - истинно
- **WHEN** условие `{"==": [{"var": "payload.count"}, 5]}` и `payload.count = "5"`
- **THEN** условие ложно (типы не приводятся)

#### Scenario: Логическое И и ИЛИ

- **WHEN** условие `or(payload.confidence < 0.3, and(source == "cv", payload.confidence > 0.99))`
- **THEN** результат равен логическому значению выражения для каждой комбинации входов (по тесту на ветвь), вложенность в
  пределах лимитов принимается, глубина 9 - ошибка правила

#### Scenario: НЕ

- **WHEN** условие `{"!": {">=": [{"var": "payload.confidence"}, 0.5]}}` и поле отсутствует
- **THEN** условие истинно (отрицание ложного сравнения); `{"<": [{"var": "payload.confidence"}, 0.5]}` на том же сообщении - ложно

#### Scenario: Оператор вне первой итерации

- **WHEN** в правиле указан оператор `in`, `iregex` или `missing`, либо `var` со значением по умолчанию
- **THEN** правило ошибочно («оператор не поддерживается»), в лог - Error, остальные правила действуют

#### Scenario: Регэксп совпадает в части строки

- **WHEN** условие `{"regex": [{"var": "deviceId"}, "TEST"]}` и `deviceId = "MY-TEST-1"`
- **THEN** условие истинно; для `"PROD-1"` - ложно

#### Scenario: Якоря задаёт автор

- **WHEN** условие `{"regex": [{"var": "deviceId"}, "^TEST-\\d+\\z"]}`
- **THEN** истинно для `"TEST-42"`; ложно для `"MY-TEST-42"`, `"TEST-42x"` и `"TEST-42\n"` (`\z` не пропускает завершающий перевод строки)

#### Scenario: Регэксп без учёта регистра

- **WHEN** условие `{"regex": [{"var": "eventType"}, "(?i)^test_event\\z"]}`
- **THEN** истинно для `"test_event"` и `"TEST_EVENT"`; ложно для `"test_events"`

#### Scenario: Регэксп на поле не-строке и отсутствующем поле

- **WHEN** условие `{"regex": [{"var": "payload.code"}, "^\\d+$"]}` и `payload.code` - число `123`, `null`, булево, объект, массив либо поля нет
- **THEN** условие ложно во всех случаях (типы не приводятся), ошибки нет

#### Scenario: Регэксп под НЕ, И, ИЛИ

- **WHEN** условие `{"!": {"regex": [{"var": "deviceId"}, "^TEST-"]}}`
- **THEN** истинно для `"PROD-1"` и для сообщения без `deviceId`, ложно для `"TEST-1"`
- **WHEN** условие `{"and": [{"regex": [{"var": "deviceId"}, "^"]}, {"!": {"regex": [{"var": "deviceId"}, "^TEST-"]}}]}`
- **THEN** истинно только для строкового `deviceId`, не начинающегося с `TEST-` (идиома «поле есть и не подходит»)

#### Scenario: Недопустимая форма регэкспа

- **WHEN** оператор `regex` записан с тремя операндами, с шаблоном первым (`[шаблон, var]`), с шаблоном-`var`, с шаблоном-числом, с пустым шаблоном или шаблоном длиннее 512 символов
- **THEN** правило ошибочно и не применяется (по отдельной причине на каждый случай), в лог - Error с `RuleId`

#### Scenario: Невалидный или неподдерживаемый шаблон

- **WHEN** шаблон синтаксически неверен (`(`, `[z-a]`) либо использует просмотр вперёд/назад (`(?=a)`), обратную ссылку (`(a)\\1`), атомарную группу или слишком большие счётчики повторений (`(a{1000}){1000}`)
- **THEN** правило ошибочно и не применяется, остальные правила и сервис работают, в лог - Error с `RuleId` и причиной (код ошибки и позиция), без шаблона целиком и без значений сообщений, `rules.invalid` растёт

#### Scenario: Лимиты regex-узлов

- **WHEN** в правиле 9 узлов `regex`, либо суммарное число `regex`-узлов включённых правил превышает `MaxRegexNodes`
- **THEN** ошибочным становится правило, на котором лимит исчерпан (набор - в порядке `priority`, `rule_id`); остальные правила действуют

#### Scenario: Поле внутри payload

- **WHEN** условие `{"==": [{"var": "payload.zone"}, "A"]}` и событие без `payload.zone`
- **THEN** условие ложно, ошибки нет

### Requirement: Отбраковка события правилом

Для каждого сообщения, прошедшего проверку формата и C5, Data Saver ДОЛЖЕН вычислить включённые правила его источника и правила
со `source IS NULL` в порядке `priority`, затем `rule_id`, и остановиться на первом сработавшем. Если правило сработало,
событие НЕ ДОЛЖНО записываться в `ktm.events`, а ДОЛЖНО быть опубликовано в `ktm.events.rejected` с исходными ключом и телом и
заголовками `ktm-reject-reason` (= `reason_code`; при таймауте регулярного выражения - системный `rule_eval_timeout`, см. требование «Безопасность регулярных выражений и таймаут совпадения»), `ktm-reject-rule-id`, `ktm-reject-rule-name`, `ktm-reject-rule-version`,
`ktm-reject-detail` (не длиннее 1024 символов, без значений из сообщения), `ktm-source-topic`, `ktm-source-partition`,
`ktm-source-offset`; offset ДОЛЖЕН фиксироваться после подтверждения публикации так же, как у любого отбракованного.
В лог ДОЛЖНО писаться предупреждение (Warning) с `RuleId`, `RuleVersion`, `ReasonCode`, `Source`, `SourceEventId` и координатами
сообщения, без тела; `IAdminNotifier` НЕ ДОЛЖЕН вызываться. Если не сработало ни одно правило, событие ДОЛЖНО записываться в
журнал, как до появления правил. Правила НЕ ДОЛЖНЫ обращаться к данным о сотрудниках, ролях, сменах и оценках.

#### Scenario: Сработало правило своего источника

- **WHEN** событие `skud` подпадает под включённое правило с `source = 'skud'`
- **THEN** в `ktm.events` его нет, в `ktm.events.rejected` есть сообщение с исходным телом и заголовками `ktm-reject-rule-id`,
  `ktm-reject-rule-name`, `ktm-reject-reason`, `ktm-reject-detail`, в логе - Warning

#### Scenario: Правило другого источника не применяется

- **WHEN** событие `cv` подпадает по условию под правило с `source = 'skud'`
- **THEN** событие записывается в журнал

#### Scenario: Общее правило применяется ко всем источникам

- **WHEN** правило со `source IS NULL` подпадает событие любого из источников
- **THEN** событие отбраковывается этим правилом

#### Scenario: Сработали два правила

- **WHEN** событию соответствуют правила `A` (`priority` 10) и `B` (`priority` 20)
- **THEN** в `rejected` одна запись с `ktm-reject-rule-id = A`

#### Scenario: Выключенное правило не применяется

- **WHEN** правило подходит событию, но `enabled = false`
- **THEN** событие записывается в журнал

#### Scenario: 100 сообщений, 5 бракованных

- **WHEN** в настроенный входящий raw-топик поступает 100 корректных по формату сообщений, 5 из которых подпадают под включённые правила
- **THEN** в `ktm.events` записано 95, в `ktm.events.rejected` - 5, и offset входящего топика зафиксирован на конце

#### Scenario: Сообщение, не прошедшее формат, правила не видит

- **WHEN** сообщение не прошло проверку формата и условие правила ему «подошло бы»
- **THEN** причина в `rejected` - форматная (`invalid_schema` и т. д.), заголовка `ktm-reject-rule-id` нет, правило не вычислялось

### Requirement: Загрузка и перезагрузка правил без перезапуска

Правила ДОЛЖНЫ быть загружены при старте до начала чтения Kafka, затем перечитываться периодически (по умолчанию раз в 60 секунд,
`DataSaver__Rules__RefreshIntervalSeconds`, допустимо 5..3600). Изменение ДОЛЖНО определяться по хэшу содержимого выборки; при
отсутствии изменений набор НЕ ДОЛЖЕН пересобираться. Набор правил ДОЛЖЕН заменяться целиком и атомарно; одно сообщение ДОЛЖНО
обрабатываться по одному набору. Перезапуск сервиса для применения изменений НЕ ДОЛЖЕН требоваться. Включение, выключение, изменение
и добавление правила ДОЛЖНЫ вступать в силу для сообщений, начатых обработкой после замены набора, не позднее чем через интервал
опроса. Перечитывание «по команде» (внеочередное) в этой итерации НЕ реализуется; порт источника ДОЛЖЕН допускать необязательный
сигнал об изменении без правок движка. Пустая таблица правил и набор без включённых правил - штатные состояния (набор без правил, запись
Info). Если БД недоступна на первой загрузке, сервис ДОЛЖЕН повторять загрузку с нарастающей паузой, не читать Kafka и быть не готов;
если чтение таблицы завершается ошибкой `42P01` (таблицы нет) либо `42501` (нет прав) на первой загрузке, сервис ДОЛЖЕН завершиться с
кодом 78 и сообщением без значений секретов; та же ошибка при уже загруженном наборе код выхода не даёт и обрабатывается как
недоступность источника. Неверные значения `DataSaver__Rules__*` ДОЛЖНЫ приводить к завершению с кодом 78. При каждой замене набора в
лог ДОЛЖНА писаться запись (Info) со списком добавленных, изменённых и удалённых правил (`rule_id`, `version`) и ревизией; изменение
содержимого правила без увеличения `version` ДОЛЖНО давать предупреждение.

#### Scenario: Правило выключено без рестарта

- **WHEN** сервис отбраковывает события правилом, администратор выполняет `UPDATE ... SET enabled = false`, затем в Kafka приходит
  подходящее событие
- **THEN** не позднее чем через интервал опроса событие записывается в журнал, процесс не перезапускался

#### Scenario: Добавлено новое правило

- **WHEN** в таблицу вставлено правило `enabled = true`
- **THEN** оно начинает действовать не позже чем через интервал опроса

#### Scenario: Набор не изменился

- **WHEN** очередной опрос находит ту же выборку (тот же хэш)
- **THEN** набор не пересобирается, `rules.reloads{result="unchanged"}` растёт

#### Scenario: Изменение без увеличения версии

- **WHEN** условие правила изменено `UPDATE`, а `version` осталась прежней
- **THEN** набор применяется, в лог пишется предупреждение с `rule_id`

#### Scenario: Пустая таблица

- **WHEN** сервис стартует при пустой `ktm.rejection_rules`
- **THEN** сервис готов, правил нет, в логе Info, все события записываются в журнал

#### Scenario: Первая загрузка не удалась

- **WHEN** при старте БД правил недоступна
- **THEN** сервис не читает Kafka и не готов (`/health/ready`), повторяет загрузку; после успешной загрузки начинает работу

#### Scenario: Нет таблицы или прав при первой загрузке

- **WHEN** при старте чтение `ktm.rejection_rules` завершается ошибкой `42P01` (миграция `V002` не применена) или `42501`
- **THEN** сервис завершается с кодом 78 (ошибка конфигурации) и сообщением без значений секретов

#### Scenario: Неверная настройка

- **WHEN** `DataSaver__Rules__RefreshIntervalSeconds=1`
- **THEN** процесс завершается с кодом 78 с сообщением о допустимом диапазоне

### Requirement: Ошибочные правила и недоступность хранилища правил

Каждое включённое правило ДОЛЖНО проверяться при загрузке: структура условия, имена операторов и формы операндов, типы значений,
пути (имя верхнего уровня - поле конверта v1), даты, границы диапазона, регулярные выражения (шаблон компилируется при загрузке;
синтаксис, конструкции, не поддерживаемые линейным режимом, длина, лимиты regex-узлов), лимиты (глубина, число узлов), допустимость `source`.
Ошибочное правило НЕ ДОЛЖНО применяться и НЕ ДОЛЖНО влиять на остальные правила и на работу сервиса; в лог ДОЛЖНА писаться ошибка
(Error) с `RuleId`, `RuleVersion` и причиной (повтор для той же версии и причины - с ограничением частоты). Условие выключенного
правила НЕ ДОЛЖНО проверяться на семантику. При ошибке чтения набора правил после успешной первой загрузки сервис ДОЛЖЕН
продолжать работу по последнему валидному набору, писать предупреждение в лог (с ограничением частоты) и увеличивать
`ktm.datasaver.rules.reloads{result="failed"}`; приём НЕ ДОЛЖЕН прерываться.

#### Scenario: Неизвестный оператор среди корректных правил

- **WHEN** в таблице включено правило с неподдерживаемым оператором (например `in`) и несколько корректных правил
- **THEN** сервис работает, корректные правила применяются, ошибочное - нет, в логе Error с `RuleId` ошибочного правила,
  `ktm.datasaver.rules.invalid` = 1

#### Scenario: Неверный путь

- **WHEN** правило ссылается на поле `unknownField` верхнего уровня
- **THEN** правило ошибочно (в лог - Error), события им не отбраковываются

#### Scenario: Невалидный регэксп среди корректных правил

- **WHEN** в таблице включено правило с шаблоном `(` и несколько корректных правил (в том числе с `regex`)
- **THEN** сервис работает и принимает сообщения, корректные правила применяются, ошибочное - нет, в логе Error с `RuleId` ошибочного правила и причиной без значений сообщений и без шаблона целиком, `ktm.datasaver.rules.invalid` = 1; после исправления `UPDATE` правило действует без рестарта

#### Scenario: Недоступность БД при работе

- **WHEN** после успешной загрузки чтение таблицы правил завершается ошибкой
- **THEN** действует прежний набор, в лог пишется предупреждение, `rules.reloads{result="failed"}` растёт, приём не прерывается;
  после восстановления набор обновляется

#### Scenario: Правило исправлено без рестарта

- **WHEN** ошибочное правило исправлено `UPDATE`
- **THEN** оно начинает действовать со следующего набора, `rules.invalid` уменьшается

### Requirement: Метрики правил

Data Saver ДОЛЖЕН считать отбракованные правилами сообщения по источникам и правилам: счётчик
`ktm.datasaver.rules.rejected` с тегами `source` (`skud`, `cv`, `1c-do`) и `rule_id` (только из загруженного набора);
счётчик `ktm.datasaver.messages.rejected` для отбраковки правилом ДОЛЖЕН использовать `reason = "rule_matched"`, а для отбраковки по таймауту регулярного выражения - `reason = "rule_eval_timeout"` (`rules.rejected` считает и её). ДОЛЖНЫ
публиковаться также `ktm.datasaver.rules.active`, `ktm.datasaver.rules.invalid`, `ktm.datasaver.rules.reloads`
(теги `result` - `changed`/`unchanged`/`failed`, `trigger` - `timer`/`startup`) и `ktm.datasaver.rules.snapshot_age`, а также счётчик `ktm.datasaver.rules.eval_errors` (теги `kind` - `regex_timeout`,
`rule_id` - только из загруженного набора): вычисление правила прервано таймаутом, сообщение отбраковано (требование «Безопасность регулярных выражений и таймаут совпадения»).
Теги НЕ ДОЛЖНЫ зависеть от содержимого сообщений.

#### Scenario: Счётчик по правилу и источнику

- **WHEN** правило `skud-test-event` отбраковало 3 сообщения
- **THEN** `rules.rejected{source="skud", rule_id="skud-test-event"}` = 3

### Requirement: Расширяемость источника правил и набора операций

Движок (компиляция условий, снимок, стадия, вывод в `rejected`, метрики) ДОЛЖЕН получать правила только через порт
источника правил, не зная формата хранилища; порт ДОЛЖЕН передавать правила в виде определений (поля правила и условие как
JSON) и непрозрачную ревизию, отличать ошибку всего источника от ошибки отдельного правила и допускать необязательный
сигнал об изменении. Замена источника НЕ ДОЛЖНА требовать изменений стадии, компилятора условий и контракта `rejected`. Операторы
условий ДОЛЖНЫ быть реализованы реестром (в том числе `regex`), добавление нового (`in`, `missing`-подобный, сравнение без учёта регистра) НЕ
ДОЛЖНО менять стадию, узлы `and`/`or`/`!`, порт источника и контракт `rejected`.

#### Scenario: Движок работает с подменённым источником

- **WHEN** в тесте вместо `NpgsqlRuleSource` подставлен источник, возвращающий определения правил из памяти
- **THEN** загрузка, отбраковка, перезагрузка по смене ревизии и сохранение прежнего набора при сбое источника работают так же

### Requirement: Документация правил

Документ `docs/manuals/rules-engine.md` ДОЛЖЕН описывать для читателя, не знающего кода: что такое правило и его столбцы; синтаксис
условия (`var`, в том числе внутри `payload`; операторы первой итерации с семантикой отсутствующего поля и типов; оператор `regex`:
частичное совпадение, якоря и `\z`, экранирование `\\` в JSON, `(?i)`, ограничения движка (без просмотра вперёд/назад и обратных ссылок),
лимиты, ловушка `!regex` на отсутствующем поле и идиома `^`; диапазон
трёхаргументным `<=` с включительными границами; значения и даты; `and`/`or`/`!` с вложенностью; соответствие нотации JsonLogic и
отличия); привязку к источнику или ко всем; как добавить, изменить, выключить правило SQL-командами (с `version`) и как быстро оно
вступит в силу (опрос, настройка интервала; «по команде» не реализовано); что видно в `rejected` и в логе; готовые примеры для
СКУД, видео и 1С:ДО; типичные ошибки (неизвестный оператор, неверный путь, дата без зоны, перевёрнутый диапазон) и реакцию
сервиса; какие операции отложены (с оператором JsonLogic, если он есть в стандарте); почему JsonLogic-библиотека не используется;
что означает отсутствие аудита и права ролей.

#### Scenario: Примеры в документе совпадают с миграцией

- **WHEN** сравниваются примеры `docs/manuals/rules-engine.md` и `V003__rejection_rules_examples.sql`, `V004__rejection_rules_examples_regex.sql`
- **THEN** все примеры миграций описаны в документе, а условия в документе принимаются загрузчиком без ошибок

### Requirement: Безопасность регулярных выражений и таймаут совпадения

Регулярные выражения ДОЛЖНЫ выполняться за время, линейное по длине входа (режим `NonBacktracking`): катастрофический откат (ReDoS)
НЕ ДОЛЖЕН быть возможен. Для каждого совпадения ДОЛЖЕН действовать таймаут `DataSaver__Rules__RegexTimeoutMs` (по умолчанию 200 мс,
допустимо 1..1000; неверное значение - завершение с кодом 78; `DataSaver__Rules__MaxRegexNodes` - 1..1000, по умолчанию 64, неверное
значение - код 78). При превышении таймаута сообщение ДОЛЖНО отбраковываться (публиковаться в `ktm.events.rejected`, в журнал не
записываться) **сразу**, независимо от формы правила (в том числе когда `regex` стоит под `!`): остальные правила для этого сообщения НЕ
ДОЛЖНЫ вычисляться. Причина (`ktm-reject-reason`) - системный код `rule_eval_timeout`, который НЕ ДОЛЖЕН использоваться автором правила
(правило с этим `reason_code` ошибочно); `ktm-reject-rule-id`, `ktm-reject-rule-name`, `ktm-reject-rule-version` - правило, на котором
вышло время; `ktm-reject-detail` - текст о таймауте с пределом в миллисекундах, без значения поля, шаблона и совпавшего фрагмента.
Каждая такая отбраковка ДОЛЖНА увеличивать `ktm.datasaver.rules.eval_errors{kind="regex_timeout", rule_id}` и учитываться как отбраковка
правилом (`rules.rejected`, `messages.rejected{reason="rule_eval_timeout"}`); в лог ДОЛЖЕН писаться Warning с `RuleId`, `RuleVersion`,
`Source`, координатами сообщения и пределом таймаута - без тела и значений полей, не чаще раза в 10 минут на правило (повторные
подавляются, счётчик растёт на каждое). Таймаут повторного прохода трассировки НЕ ДОЛЖЕН отменять уже принятую отбраковку правилом: её
причина остаётся `reason_code` правила, `detail` строится без перечня листьев. Иные исключения вычислителя НЕ ДОЛЖНЫ превращаться в
отбраковку. Публичные типы вердикта и отбраковки НЕ ДОЛЖНЫ меняться.

#### Scenario: Враждебный шаблон не вешает поток

- **WHEN** правило `{"regex": [{"var": "payload.s"}, "^(a+)+$"]}` вычисляется на `payload.s` из 40 символов `a` и `!`
- **THEN** вычисление завершается быстро (линейное время), результат - ложь

#### Scenario: Таймаут отбраковывает с системным кодом (форма с `!`)

- **WHEN** совпадение превышает таймаут в правиле `{"!": {"regex": [{"var": "deviceId"}, "^TEST-"]}}`
- **THEN** сообщение не записывается в журнал, в `ktm.events.rejected` - с `ktm-reject-reason = rule_eval_timeout`, `ktm-reject-rule-id`/`-rule-name`/`-rule-version` этого правила и `ktm-reject-detail` с пределом в мс, без значения поля и шаблона; `rules.eval_errors{kind="regex_timeout", rule_id}` растёт; в лог пишется Warning без значений сообщения; повтор в течение 10 минут по тому же правилу в лог не пишется, счётчик растёт

#### Scenario: Таймаут отбраковывает с системным кодом (форма без `!`)

- **WHEN** совпадение превышает таймаут в правиле `{"regex": [{"var": "deviceId"}, "^TEST-"]}`
- **THEN** результат тот же: отбраковка с `rule_eval_timeout` и заголовками правила; различия между формами с `!` и без нет

#### Scenario: Остальные правила не вычисляются после таймаута

- **WHEN** правило с меньшим `priority` завершилось таймаутом, а следующее правило сработало бы на этом сообщении
- **THEN** в `rejected` одна запись с `rule_eval_timeout` и идентификатором первого правила, второе правило не вычислялось

#### Scenario: Таймаут повторного прохода трассировки

- **WHEN** правило сработало штатно, а повторный проход для перечня листьев `detail` завершился таймаутом
- **THEN** отбраковка сохраняется с `reason_code` правила, `detail` без перечня листьев, код `rule_eval_timeout` не выставляется

#### Scenario: Неверная настройка регэкспа

- **WHEN** `DataSaver__Rules__RegexTimeoutMs=0` либо `DataSaver__Rules__MaxRegexNodes=1001`
- **THEN** процесс завершается с кодом 78 с сообщением о допустимом диапазоне
