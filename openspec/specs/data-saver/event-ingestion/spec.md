# data-saver/event-ingestion Specification

## Purpose
Капабилити описывает приём событий из Kafka в неизменяемый журнал событий: чтение
топиков источников, пакетную идемпотентную запись, порядок фиксации offset, хранение
корректирующих сообщений, поведение при сбоях БД и остановке, масштабирование,
конфигурацию и проверки состояния сервиса Data Saver.

## Requirements

### Requirement: Чтение входящего топика

Data Saver ДОЛЖЕН читать единый входящий топик `ktm.events.raw` (события всех источников;
источник определяется полем `source` в теле) в группе потребителей `ktm-data-saver`.
Имя группы и имя топика ДОЛЖНЫ настраиваться. Одно
сообщение Kafka ДОЛЖНО соответствовать одному событию. При первом запуске группы чтение
ДОЛЖНО начинаться с самого раннего доступного сообщения.

#### Scenario: Событие доходит до журнала

- **WHEN** валидное событие опубликовано в `ktm.events.raw` (`source = skud`)
- **THEN** строка с соответствующим `(source, source_event_id, occurred_at)` появляется
  в `ktm.events` не позднее чем через 5 секунд при настройках по умолчанию

#### Scenario: Несколько источников в одном топике

- **WHEN** в `ktm.events.raw` опубликованы события с `source` `skud`, `cv` и `1c-do`
- **THEN** все они попадают в журнал

### Requirement: Пакетная идемпотентная запись

Data Saver ДОЛЖЕН накапливать сообщения в пачку и записывать её одной транзакцией
командой `INSERT ... ON CONFLICT DO NOTHING` по ключу `(source, source_event_id,
occurred_at)`. Пачка ДОЛЖНА закрываться по достижении настраиваемого размера (по
умолчанию 500) либо настраиваемого максимального времени ожидания (по умолчанию
1000 мс) с момента получения первого сообщения. Уникальность ДОЛЖНА гарантироваться
схемой БД, а не проверкой в приложении. Повторная доставка НЕ ДОЛЖНА создавать дубликат
и НЕ ДОЛЖНА считаться ошибкой. Запись НЕ ДОЛЖНА выполнять `UPDATE` и `DELETE`.
Значение `occurredAt` ДОЛЖНО усекаться до микросекунд детерминированно. Время получения
(`received_at`) ДОЛЖНО быть единым для пачки и не пересчитываться при повторе записи пачки.

#### Scenario: Дубли внутри потока

- **WHEN** в топик опубликованы 100 событий, из которых 10 - повторы ранее
  опубликованных (тот же ключ)
- **THEN** в журнале ровно 90 строк по этим ключам, ошибок в логе записи нет, метрика
  дублей равна 10

#### Scenario: Закрытие пачки по размеру и по времени

- **WHEN** поступает поток, превышающий размер пачки, а затем одиночное событие в
  простое
- **THEN** первые пачки закрываются по размеру, одиночное событие записывается по
  истечении максимального времени ожидания

#### Scenario: Повторная доставка после сбоя

- **WHEN** сообщения, уже записанные в журнал, доставляются повторно
- **THEN** новые строки не создаются, `UPDATE` не выполняется, роль `ktm_app` не
  получает ошибок прав

### Requirement: Фиксация offset только после записи

Data Saver ДОЛЖЕН фиксировать offset только после успешного commit транзакции БД (и
после подтверждённой публикации отбракованных сообщений пачки). Автоматическая
фиксация offset ДОЛЖНА быть отключена. Фиксируемый offset по партиции ДОЛЖЕН быть
максимальным offset сообщений пачки плюс один, с учётом отбракованных сообщений.
Ошибка фиксации offset (потеря партиции) НЕ ДОЛЖНА останавливать сервис.

#### Scenario: Сбой записи

- **WHEN** запись пачки завершилась ошибкой
- **THEN** offset не фиксируется, сообщения пачки будут повторены, в журнале нет
  частично записанной пачки

#### Scenario: Падение между записью и фиксацией offset

- **WHEN** процесс аварийно завершён после commit в БД, но до фиксации offset
- **THEN** после перезапуска сообщения читаются повторно, дубликатов в журнале нет

### Requirement: Корректирующие сообщения

Сообщение с объектом `correction` ДОЛЖНО сохраняться в `ktm.event_corrections` (связь
по `source` и `correction.correctsSourceEventId` / `correctsOccurredAt`) и, как задано
схемой журнала, отдельной строкой в `ktm.events` со своим `sourceEventId`, в одной
транзакции. Исходное событие НЕ ДОЛЖНО читаться или изменяться. Если исходного
события ещё нет, сообщение ДОЛЖНО сохраняться с пустым `original_event_id` и НЕ ДОЛЖНО
блокировать партицию. Идентификатор корректирующей записи в `event_corrections` ДОЛЖЕН
браться из строки `events` по натуральному ключу корректирующего события. Повторная
доставка корректирующего сообщения НЕ ДОЛЖНА создавать дубликат.

#### Scenario: Корректировка существующего события

- **WHEN** в журнале есть исходное событие, затем приходит корректирующее сообщение на него
- **THEN** создаётся запись `event_corrections` со ссылкой на исходное (`original_event_id`
  заполнен), строка исходного события в `events` не изменена (значения всех колонок
  совпадают с прежними)

#### Scenario: Корректировка раньше исходного

- **WHEN** корректирующее сообщение прочитано до исходного события
- **THEN** запись `event_corrections` создаётся с `original_event_id = NULL`; после
  прихода исходного события оно записывается как обычно; ссылка разрешается чтением
  по натуральному ключу

#### Scenario: Повтор корректировки

- **WHEN** то же корректирующее сообщение доставлено дважды
- **THEN** в `event_corrections` и в `events` по его ключу по одной строке

### Requirement: Устойчивость к недоступности БД

При недоступности БД (и иных временных ошибках записи) Data Saver ДОЛЖЕН ставить
назначенные партиции на паузу, продолжать вызывать опрос consumer для сохранения
членства в группе, повторять запись той же пачки с нарастающей паузой (по умолчанию
начальная 1 с, множитель 2, потолок 30 с, джиттер до 20 %, значения настраиваются) без
ограничения числа попыток и после успеха фиксировать offset и возобновлять чтение.
События НЕ ДОЛЖНЫ теряться и дублироваться. Партиции, назначенные во время сбоя, ДОЛЖНЫ
сразу ставиться на паузу. Недоступность БД ДОЛЖНА трактоваться как технический сбой и
НЕ ДОЛЖНА влиять на оценку сотрудников. Ошибки отсутствия прав и объектов БД ДОЛЖНЫ
повторяться так же, но с логом уровня Error на каждой попытке.

#### Scenario: БД остановлена на 2 минуты

- **WHEN** во время потока событий БД недоступна 2 минуты, затем становится доступной
- **THEN** после восстановления все события потока присутствуют в журнале ровно по одному
  разу, процесс не перезапускался, consumer не покидал группу

#### Scenario: Нарастающая пауза

- **WHEN** БД остаётся недоступной несколько попыток подряд
- **THEN** интервалы между попытками растут от начального значения до потолка и не
  превышают потолок с учётом джиттера; после успешной записи отсчёт начинается заново

### Requirement: Корректная остановка

При получении сигнала остановки Data Saver ДОЛЖЕН прекратить чтение новых сообщений,
дописать текущую пачку, зафиксировать offset, покинуть группу и завершиться в пределах
настраиваемого времени (по умолчанию 30 с). Если БД недоступна и время вышло, сервис
ДОЛЖЕН завершиться без фиксации offset.

#### Scenario: Остановка посреди обработки

- **WHEN** сервис останавливается во время потока событий, затем запускается снова
- **THEN** все события потока присутствуют в журнале ровно по одному разу, а при
  штатной остановке повторно прочитанных сообщений нет (offset закоммичен)

#### Scenario: Остановка при недоступной БД

- **WHEN** сервис останавливается, пока БД недоступна
- **THEN** процесс завершается не позднее предельного времени остановки без фиксации
  offset, события не потеряны

### Requirement: Масштабирование копиями

Несколько экземпляров Data Saver с одной группой ДОЛЖНЫ делить партиции средствами
Kafka без дополнительной координации. Ребалансировка НЕ ДОЛЖНА приводить к потере или
дублированию событий в журнале.

#### Scenario: Два экземпляра

- **WHEN** запущены два экземпляра, и в топик опубликован поток событий
- **THEN** каждая партиция обслуживается одним экземпляром, все события в журнале по
  одному разу

#### Scenario: Остановка одного экземпляра

- **WHEN** один из двух экземпляров останавливается во время потока
- **THEN** второй принимает его партиции, все события в журнале по одному разу

### Requirement: Конфигурация и секреты

Все настройки ДОЛЖНЫ задаваться переменными окружения. Секреты (пароли БД, учётные
данные Kafka) НЕ ДОЛЖНЫ храниться в репозитории и НЕ ДОЛЖНЫ попадать в логи; ДОЛЖНА
поддерживаться передача секрета через файл. Неверная или неполная конфигурация ДОЛЖНА
приводить к отказу запуска с понятным сообщением без значений секретов.

#### Scenario: Отсутствует обязательная настройка

- **WHEN** сервис запускается без `DataSaver__Kafka__BootstrapServers`
- **THEN** запуск завершается ошибкой с указанием имени настройки

#### Scenario: Проверка репозитория на секреты

- **WHEN** выполняется поиск паролей и строк подключения в репозитории
- **THEN** реальных значений секретов нет; присутствует только `.env.example` с заглушками

### Requirement: Проверки состояния

Data Saver ДОЛЖЕН предоставлять `GET /health/live` и `GET /health/ready`. Liveness ДОЛЖЕН
возвращать 200, пока цикл обработки работает (в том числе в состоянии паузы при
недоступной БД), и 503 при остановившемся цикле. Readiness ДОЛЖЕН возвращать 200 только
при назначенных партициях, доступной БД и доступном брокере, а при включённом движке правил
(`DataSaver__Rules__Enabled`, по умолчанию включён) - только после первой успешной загрузки набора правил (пустая таблица
правил - успешная загрузка), иначе 503. Последующие неудачные перечитывания правил (при уже загруженном наборе) готовность НЕ ДОЛЖНЫ
менять. Доступность
брокера ДОЛЖНА определяться активной проверкой связи с брокером с ограниченным временем
ожидания (не наличием назначения в памяти клиента) и НЕ ДОЛЖНА выполняться на потоке
цикла приёма. Ответы НЕ ДОЛЖНЫ содержать секретов, адресов брокера и содержимого событий.

#### Scenario: БД недоступна

- **WHEN** БД недоступна
- **THEN** `/health/ready` возвращает 503, `/health/live` возвращает 200

#### Scenario: Брокер недоступен

- **WHEN** брокер Kafka недоступен, а назначение партиций у клиента ещё числится
- **THEN** `/health/ready` возвращает 503 с причиной `broker_unavailable` не позднее чем через
  интервал кэша проверки плюс её предел ожидания, `/health/live` возвращает 200

#### Scenario: Топик отсутствует

- **WHEN** брокер доступен, но читаемого топика в кластере нет
- **THEN** `/health/ready` возвращает 503 с причиной `no_partitions_assigned`, а не `broker_unavailable`

#### Scenario: Брокер восстановлен

- **WHEN** брокер снова доступен
- **THEN** `/health/ready` возвращает 200 не позднее чем через интервал кэша проверки плюс её предел
  ожидания (при условии, что остальные условия готовности выполнены)

#### Scenario: Штатная работа

- **WHEN** сервис работает, партиции назначены и правила загружены
- **THEN** оба эндпоинта возвращают 200

#### Scenario: Правила ещё не загружены

- **WHEN** при старте первая загрузка правил не завершена (например, БД правил недоступна)
- **THEN** `/health/ready` возвращает 503, чтение Kafka не начато

#### Scenario: Таблица правил пуста

- **WHEN** первая загрузка завершилась успешно, но в `ktm.rejection_rules` нет строк
- **THEN** `/health/ready` определяется остальными условиями готовности (пустой набор правил её не ухудшает)

#### Scenario: Правила отключены настройкой

- **WHEN** `DataSaver__Rules__Enabled=false`
- **THEN** готовность не зависит от правил

### Requirement: Наблюдаемость приёма

Data Saver ДОЛЖЕН публиковать счётчики и измерения: прочитано сообщений, записано
событий, дублей, корректировок, отбраковано (по причинам, включая `rule_matched` для отбракованных правилами), длительность
записи пачки, размер пачки, число повторов, текущее состояние (`Running` / `Degraded`). События
отбраковки и сбои ДОЛЖНЫ попадать в лог со структурными полями `topic`, `partition`,
`offset`, `source`, `sourceEventId`. Поля ДОЛЖНЫ быть именованными параметрами записи лога
(не частью текста сообщения); в .NET - `Topic`, `Partition`, `Offset`, `Source`, `SourceEventId`.
`source` и `sourceEventId` берутся из конверта события, прошедшего разбор формата; для сообщения,
не прошедшего разбор формата, они равны `null` (содержимое недоверенного сообщения в лог не
копируется). Для записи пачки `offset` - первый offset группы сообщений одной партиции, дополнительно
указываются `lastOffset` и `count`; `source` и `sourceEventId` - первое принятое событие группы.
Для сбоя записи класса «данные» текст исключения (может содержать значения из строки) в лог НЕ
ДОЛЖЕН попадать: фиксируются тип исключения и код состояния БД (`sqlState`). Отбраковка правилом
(`rules-engine`) логируется уровнем Warning, а не Error, и не вызывает оповещения администратора; метрики правил описаны
в `rules-engine`.

#### Scenario: Отбраковка разобранного события

- **WHEN** событие прошло разбор формата, но отбраковано стадией конвейера, не являющейся правилом (например, C5)
- **THEN** запись лога уровня Error содержит именованные `Topic`, `Partition`, `Offset`, `Source`,
  `SourceEventId` из конверта события

#### Scenario: Отбраковка правилом

- **WHEN** событие прошло разбор формата и отбраковано правилом
- **THEN** запись лога уровня Warning содержит именованные `Topic`, `Partition`, `Offset`, `Source`, `SourceEventId`,
  `RuleId`, `RuleVersion`, `ReasonCode`; тела и значений полей события в записи нет

#### Scenario: Отбраковка неразобранного сообщения

- **WHEN** сообщение отбраковано на разборе формата (не JSON, неверная `schemaVersion` и т.п.)
- **THEN** запись лога содержит `Topic`, `Partition`, `Offset`, а `Source` и `SourceEventId` равны
  `null`; тело сообщения в логе отсутствует

#### Scenario: Сбой записи пачки

- **WHEN** запись пачки завершилась ошибкой
- **THEN** для каждой группы сообщений одной партиции в логе есть запись с именованными `Topic`,
  `Partition`, `Offset` (первый), `LastOffset`, `Count`, `Source`, `SourceEventId` (первое принятое
  событие группы); при ошибке класса «данные» в записях нет текста исключения

#### Scenario: Измерение пропускной способности

- **WHEN** выполняется нагрузочный прогон (категория `Perf`)
- **THEN** протокол содержит число записанных событий в секунду по устойчивому
  интервалу и задержку «публикация -> строка в БД» (p50 и p99)
