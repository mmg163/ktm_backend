# data-saver/reprocessing Specification

## Purpose

Капабилити описывает повторную обработку Data Saver: прогон сообщений из `ktm.events.dlq`, `ktm.events.rejected` и перечитывание
`ktm.events.raw` за выбранный период через тот же конвейер и ту же идемпотентную запись. Повторная обработка запускается асинхронной задачей через
административные HTTP-эндпоинты `/admin/v1/reprocessing/...` на порту Data Saver (расширяемая область `/admin/v1/<раздел>/`) и из админки `/admin/ui/`;
режима командной строки нет. Аутентификации нет по решению лида: защита сетевая. Решения - `docs/adr/0006-data-saver-dlq-and-reprocessing.md`, пп. 2.6-2.8, раздел 9.

Решение о способе проверки (2026-11-25): admin-область, включая HTTP-эндпоинты, Swagger/OpenAPI и UI, не тестируется в рамках изменения. Соответствие требованиям проверяется ревью кода и контрактных артефактов. Сценарии ниже описывают требуемое поведение и не предписывают создание или выполнение тестов admin-области. Проверки ядра повторной обработки и сетевой изоляции развёртывания сохраняются; существующие тесты не удаляются.

## Requirements

### Requirement: Admin-API повторной обработки

Data Saver ДОЛЖЕН предоставлять на **том же порту, что и health** (`DataSaver__Health__Port`; отдельного порта и аутентификации нет), эндпоинты версии `/admin/v1/reprocessing`:
`POST /jobs` (запуск; тело `source = dlq|rejected|raw`, `from`, `to`, `reason`, `maxRate`), `GET /jobs` (последние 10 задач), `GET /jobs/{id}` (состояние и прогресс),
`GET /jobs/{id}/report` (отчёт с пагинацией), `POST /jobs/{id}/cancel`. Запуск ДОЛЖЕН быть асинхронным: ответ `202 Accepted` с заголовком `Location` и описанием задачи (`id`);
одновременно активна одна задача, запуск при активной задаче - `409 Conflict` (ProblemDetails с `activeJobId`); если источник недоступен при открытии (брокер не ответил, топика источника нет) - `503 Service Unavailable`, задача не создаётся. Ошибки ДОЛЖНЫ возвращаться как `application/problem+json`
(RFC 9457); ошибки аргументов - `400` с перечнем полей, до создания задачи и без чтения/записи данных. Время в запросах и ответах - RFC 3339, UTC с `Z`. Маршруты и схемы ДОЛЖНЫ быть
описаны в документе OpenAPI (`/admin/openapi/v1.json`, Swagger UI `/admin/swagger`, отключаются `DataSaver__Admin__SwaggerEnabled=false`) и в `.http`-файле. Эндпоинты НЕ ДОЛЖНЫ быть доступны на порту,
отличном от порта сервиса, а их логика ДОЛЖНА находиться в сервисе уровня Core, эндпоинты - только разбор запроса и маппинг ответа. Режим командной строки `reprocess` НЕ ВВОДИТСЯ.
Перезапуск сервиса теряет задачи и историю (состояние в памяти); повторный запуск безопасен благодаря идемпотентности.

#### Scenario: Запуск возвращает 202

- **WHEN** `POST /admin/v1/reprocessing/jobs` с `{ "source": "dlq" }`
- **THEN** ответ `202`, `Location: /admin/v1/reprocessing/jobs/{id}`, в теле `id` и `state`; `GET` по этому `id` возвращает состояние

#### Scenario: Вторая задача одновременно

- **WHEN** задача активна и поступает ещё один `POST /jobs`
- **THEN** ответ `409` ProblemDetails с `activeJobId`, новая задача не создана

#### Scenario: Неверные аргументы

- **WHEN** указан неизвестный источник, `from` без `Z`, `from` не раньше `to`, `reason` для `raw`, не заданы оба `from` и `to` для `raw`, либо `maxRate` вне `1..MaxRateLimit`
- **THEN** ответ `400` ProblemDetails, поле `errors` называет каждое неверное поле, задача не создана, ничего не прочитано и не записано

#### Scenario: Недопустимое значение причины

- **WHEN** `reason` длиннее 64 символов либо содержит управляющие символы
- **THEN** ответ `400`, поле `errors` называет `reason`, значение в лог не попадает

#### Scenario: Источник недоступен

- **WHEN** брокер не отвечает при открытии либо топика источника не существует
- **THEN** ответ `503` ProblemDetails (не `400`), задача не создана, слот единственной задачи свободен, топик не создан

#### Scenario: Неизвестная задача

- **WHEN** `GET /jobs/{id}` с неизвестным `id` (в том числе после перезапуска сервиса)
- **THEN** ответ `404` ProblemDetails

#### Scenario: Отчёт до завершения

- **WHEN** `GET /jobs/{id}/report` для активной задачи
- **THEN** ответ `409` ProblemDetails; после завершения - `200` со страницей (`limit`, `offset`, `total`)

#### Scenario: Отмена

- **WHEN** `POST /jobs/{id}/cancel` для активной задачи
- **THEN** ответ `202`, задача после текущей пачки переходит в `Cancelled` с достигнутым прогрессом; для завершённой - `409`

#### Scenario: Работа рабочего потока

- **WHEN** задача выполняется
- **THEN** `/health/live` и `/health/ready` отвечают по состоянию рабочего цикла, задача не переводит его в `Degraded`

### Requirement: Состояние и итог задачи

Задача ДОЛЖНА иметь состояние `Queued`, `Running`, `Completed`, `Failed`, `Cancelled` и итог `outcome` для завершённой: `Succeeded` (все сообщения записаны, признаны дублями или снова отбракованы с занесением в отчёт - только если нет не записанных),
`CompletedWithFailures` (часть сообщений снова не записана из-за ошибки, привязанной к сообщению), `Failed` (инфраструктурный сбой: `error.code` = `db_unavailable`, `source_unavailable` или `internal`; задачу можно запустить заново; отказ записи класса FatalConfig - нет прав/таблицы - завершает задачу сразу кодом `internal`, без ожидания `MaxUnavailableSeconds`),
`Cancelled`. Статус ДОЛЖЕН содержать параметры, счётчики (`read`, `skippedByFilter`, `written`, `duplicates`, `rejectedAgain` по `reason`, `failedAgain`), прогресс по партициям, `startedAt`, `finishedAt`.

#### Scenario: Итог запуска

- **WHEN** обработано 10 сообщений: 7 записаны, 2 дубля, 1 отбракован правилом
- **THEN** статус содержит `read = 10`, `written = 7`, `duplicates = 2`, `rejectedAgain = {rule_code: 1}`, `outcome = Succeeded`

#### Scenario: Снова не записано

- **WHEN** сообщение по-прежнему нарушает ограничение БД
- **THEN** оно не публикуется обратно в `dlq`, попадает в отчёт с координатами, стадией и кодом причины, `outcome = CompletedWithFailures`

#### Scenario: Нет прав на запись

- **WHEN** запись отвечает ошибкой класса FatalConfig (например, нет прав)
- **THEN** задача сразу `Failed`, `error.code = internal`, слот свободен, прогресс сохранён, в логе Error с типом исключения и SQLSTATE без текста

#### Scenario: БД недоступна дольше предела

- **WHEN** БД недоступна дольше `DataSaver__Reprocess__MaxUnavailableSeconds` (по умолчанию 600)
- **THEN** состояние `Failed`, `error.code = db_unavailable`, статус содержит достигнутый прогресс, повторный запуск продолжает безопасно

### Requirement: Прохождение через рабочий конвейер

Сообщения повторной обработки ДОЛЖНЫ проходить те же стадии, что и рабочий поток (формат, C5, правила отбраковки по набору правил, действующему в сервисе в момент обработки сообщения; снимок на старте не фиксируется, смена правил во время задачи действует со следующего сообщения, ADR-0006 R-10), те же коэффициенты доверия и ту же идемпотентную запись
(`ON CONFLICT DO NOTHING` по `(source, source_event_id, occurred_at)`), пачками `DataSaver__Batch__MaxSize`, с тем же разделением ошибок (временные ошибки инфраструктуры - ожидание с нарастающей паузой; ошибки, привязанные
к сообщению, - изоляция сообщения). Для сообщений `dlq` и `rejected` ДОЛЖНЫ использоваться исходные тело и ключ из сообщения и исходные координаты из `ktm-source-*` (при отсутствии заголовков - фактические координаты с пометкой
в отчёте). Результат ДОЛЖЕН быть неотличим от обработки рабочим потоком, кроме `received_at` (момент повторной обработки).

#### Scenario: После исправления причины событие записывается

- **WHEN** сообщение из `dlq` не записывалось из-за ограничения БД (или из-за дефекта кода стадии), причина исправлена, запущена задача `dlq`
- **THEN** событие присутствует в журнале ровно один раз, `outcome = Succeeded`

#### Scenario: Повторный запуск не создаёт дублей

- **WHEN** задача `dlq` запущена второй раз с теми же параметрами
- **THEN** новых строк в журнале нет, `written = 0`, `duplicates` равен числу сообщений, `outcome = Succeeded`

#### Scenario: Отбракованное исправлено правилом

- **WHEN** сообщение из `rejected` было отбраковано правилом, правило выключено, запущена задача `rejected`
- **THEN** событие записано; если правило всё ещё включено - сообщение в отчёте как «отбраковано снова», в журнал не попадает

### Requirement: Источники и период

Задачи `dlq` и `rejected` ДОЛЖНЫ читать топики `DataSaver__Kafka__DlqTopic` и `DataSaver__Kafka__RejectedTopic` от начала до конечных offset, снятых при старте задачи (новые сообщения не догоняются), либо в пределах периода.
Задача `raw` ДОЛЖНА читать `DataSaver__Kafka__Topic` и требовать оба параметра `from` и `to`. Период ДОЛЖЕН задаваться по Kafka-timestamp сообщения как полуинтервал `[from, to)` в UTC и определяться без полного чтения
топика (поиск offset по времени). Если начало периода нельзя подтвердить как покрытое сохранёнными данными, запуск ДОЛЖЕН быть отклонён `400` (поле `from`), а не читать молча с начала: для партиции с очищенным retention началом (low watermark > 0) допустим только `from` не раньше времени её первого сохранённого сообщения (ответ называет самое раннее допустимое время); для целиком очищенной партиции (low = high > 0) и для первого сообщения без timestamp начало подтвердить нельзя - `400` с понятным сообщением. Отсутствие топика источника - не ошибка аргумента, а отказ источника (`503`). Сообщения без Kafka-timestamp при заданном периоде ДОЛЖНЫ включаться в чтение. Открытие источника ДОЛЖНО быть ограничено по времени и прерываться токеном.
`reason` ДОЛЖЕН отбирать сообщения `dlq`/`rejected` по `ktm-dlq-reason`/`ktm-reject-reason`; остальные учитываются как пропущенные фильтром. Чтение ДОЛЖНО идти отдельным consumer без подписки на группу.

#### Scenario: Граница периода

- **WHEN** в `raw` лежат сообщения с timestamp `t-1мс`, `t`, `t2-1мс`, `t2`, запущена задача `raw` с `from = t`, `to = t2`
- **THEN** обработаны сообщения с `t` и `t2-1мс`; сообщения с `t-1мс` и `t2` не прочитаны

#### Scenario: Перечитывание raw после потери записи

- **WHEN** события за период опубликованы в `raw`, но в журнале отсутствуют, запущена задача `raw` за этот период
- **THEN** все события периода записаны ровно по одному разу; события вне периода не затронуты

#### Scenario: Период раньше retention

- **WHEN** в партиции с очищенным началом `from` раньше первого сохранённого сообщения (в другой партиции с таким же началом - позже, берётся самое позднее время)
- **THEN** ответ `400`, сообщение называет самое раннее допустимое время

#### Scenario: Партиция целиком очищена retention

- **WHEN** в топике есть партиция с `low = high > 0` и задан `from`
- **THEN** ответ `400`, сообщение называет партицию и причину; молчаливого пропуска нет

#### Scenario: Партиция без удалений

- **WHEN** low watermark партиции 0 (в том числе пустой), `from` любое
- **THEN** партиция не ограничивает период

#### Scenario: Фильтр причины

- **WHEN** задача `dlq` с `reason = unexpected_error`
- **THEN** обрабатываются только сообщения с этой причиной, остальные сосчитаны как пропущенные

### Requirement: Защита рабочего потока и источников

Задача НЕ ДОЛЖНА изменять offset группы `DataSaver__Kafka__GroupId` (в том числе не состоять в ней), НЕ ДОЛЖНА фиксировать offset вообще (идемпотентность вместо чекпоинта), НЕ ДОЛЖНА публиковать сообщения в `rejected`
или `dlq` и НЕ ДОЛЖНА изменять и удалять сообщения исходных топиков. Скорость ДОЛЖНА ограничиваться `maxRate` (умолчание `DataSaver__Reprocess__MaxRatePerSecond` = 200 сообщений в секунду, верхний предел
`DataSaver__Reprocess__MaxRateLimit` = 400; ошибка значения настройки - отказ запуска сервиса, код 78) так, чтобы приём рабочим потоком 500 событий/с не деградировал. При недоступности БД задача ДОЛЖНА ждать с нарастающей паузой
не дольше `DataSaver__Reprocess__MaxUnavailableSeconds`.

#### Scenario: Рабочая группа не затронута

- **WHEN** выполняется задача `raw` одновременно с работающим приёмом
- **THEN** offset группы `ktm-data-saver` не меняется задачей, лаг рабочего потока не растёт из-за задачи сверх нормы

#### Scenario: Скорость ограничена

- **WHEN** `maxRate = 100`, обрабатывается 1000 сообщений
- **THEN** обработка занимает не менее 9 секунд (допуск на округление)

#### Scenario: Скорость выше предела

- **WHEN** `maxRate` больше `MaxRateLimit`
- **THEN** ответ `400`, задача не создана

### Requirement: Отчёт и аудит запуска

Отчёт задачи (`GET /jobs/{id}/report`) ДОЛЖЕН содержать для сообщений, не записанных и отбракованных снова, координаты (`topic`, `partition`, `offset`), стадию и код причины. Начало, отмена и завершение задачи ДОЛЖНЫ записываться
в лог структурными записями: идентификатор задачи, время UTC, параметры, адрес клиента (`RemoteIp`), необязательное имя из заголовка `X-Requested-By` (не доверенное, до 64 печатных символов), итоговые счётчики. Запуск и итог (с `Outcome`, в том числе `Cancelled`) пишет сервис задач Core; запрос отмены (кто, когда, результат вызова) и адрес клиента пишет `AdminAudit` admin-слоя. Тела сообщений,
значения полей и тексты исключений НЕ ДОЛЖНЫ попадать в лог, статус и отчёт.

#### Scenario: Аудит запуска

- **WHEN** задача запущена и завершена
- **THEN** в логе есть запись о запуске (с `JobId`, параметрами, `RemoteIp`) и запись об итоге со счётчиками

#### Scenario: Отчёт без данных

- **WHEN** сформированы отчёт, статус и лог
- **THEN** в них нет тел сообщений и значений полей

### Requirement: Админка повторной обработки

Data Saver ДОЛЖЕН раздавать статическую страницу `/admin/ui/` на том же порту (встроена в сборку, без внешних CDN и шрифтов, без зависимости от `ktm_revisor`), использующую admin-API того же origin. Меню ДОЛЖНО строиться по `GET /admin/v1/sections`;
новый раздел добавляется модулем и записью в реестре без изменения каркаса. Раздел `reprocessing` ДОЛЖЕН давать: форму запуска (источник, `from`/`to`, `reason`, `maxRate`), диалог подтверждения с итоговыми параметрами перед запуском, список задач,
прогресс активной задачи, отчёт, отмену с подтверждением, понятный вывод ошибок ProblemDetails. Ответы страницы ДОЛЖНЫ содержать `Content-Security-Policy` с `default-src 'self'`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`; данные
в браузере НЕ ДОЛЖНЫ сохраняться.

#### Scenario: Страница отдаётся с защитными заголовками

- **WHEN** `GET /admin/ui/`
- **THEN** ответ `200`, `text/html`, заголовки CSP/nosniff/no-store присутствуют, внешних ссылок в разметке нет

#### Scenario: Запуск из админки

- **WHEN** оператор заполняет форму и подтверждает диалог
- **THEN** выполняется `POST /jobs`, страница показывает прогресс и итог задачи, без подтверждения запрос не отправляется

### Requirement: Сетевая защита admin-области (принятый риск)

Admin-API и админка НЕ ИМЕЮТ аутентификации (решение лида, ADR-0006 п. 2.6, R-8): они доступны любому, кто достучался до порта сервиса. Поэтому развёртывание ДОЛЖНО не публиковать `/admin` через внешний периметр/ingress и не открывать порт
Data Saver наружу; это ДОЛЖНО быть описано в руководстве и проверяться в протоколе выкладки.

#### Scenario: Проверка деплоя

- **WHEN** выполняется приёмка выкладки
- **THEN** запрос `/admin/v1/sections` из внутренней сети возвращает `200`, из внешнего контура недоступен

### Requirement: Документация повторной обработки

В `src/README.md` и `docs/manuals/data-saver.md` ДОЛЖНЫ быть описаны: порядок действий оператора (найти причину по `ktm-dlq-stage`/`ktm-dlq-exception-type`, исправить, запустить задачу), готовые примеры `curl` для `dlq`, `rejected`, `raw` за период, запуск, статус,
отчёт и отмену, работа в админке и Swagger UI, значения `outcome`, проверка результата, ограничения (период по Kafka-timestamp, retention `raw` 7 суток и `dlq`/`rejected` 30 суток, нагрузка, `received_at`, состояние в памяти, одна задача
одновременно) и требование к деплою (не публиковать `/admin`). Описание ДОЛЖНО быть проверено выполнением на стенде либо явно помечено «не проверено».

#### Scenario: Оператор по инструкции

- **WHEN** оператор, не читавший код, следует README
- **THEN** он запускает повторную обработку `dlq` (curl или админка) и находит результат (счётчики, события в журнале) без обращения к исходникам
