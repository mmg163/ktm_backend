# Протокол замера пропускной способности Data Saver (задачи 8.1, 8.2)

Дата замера: 2026-11-20. Требование: НФТ п. 7.1 - пиковая нагрузка не менее 500 событий/с, средняя не менее 100,
задержка получения события до отражения в профиле не более 5 минут.

> **Замер выполнен на локальном Docker машины разработчика, а не на dev-стенде. НФТ этот протокол не подтверждает:
> цифры - ориентир. Замер на dev (`dev-backend`/`dev-data`) - отдельный шаг, вместе с 9.2.**

## 1. Стенд

| Параметр | Значение |

## 2. Устойчивая нагрузка 500 соб/с, 15 минут (450 000 событий)

| Показатель | Результат |
|---|---|
| Опубликовано | 500,0 соб/с (450 000 за 900,1 с), ошибок доставки 0 |
| Записано, устойчивый интервал 60-889 с | 500,9 соб/с (счётчик `ktm.datasaver.events.written`); по минутам: 485, 514, 495, 504, 499, 498, 501, 500, 495, 504, 504, 497, 502, 499, 496 |
| Задержка «публикация -> строка в БД», устойчивый интервал (415 000 событий) | p50 = 782 мс, p95 = 1260 мс, p99 = 1370 мс, max = 2745 мс |
| Задержка, все события | p50 = 788 мс, p99 = 1416 мс, max = 2876 мс; не наблюдено опросом: 0 |
| Лаг группы (опубликовано - committed offset) | средний в первой трети 1434, в последней трети 1462, максимум 2943 сообщений: **рост отсутствует**; лаг определяется пачкой и ожиданием `MaxWaitMs` |
| Хвост после окончания генерации | все 450 000 строк, offsets зафиксированы; остаток дописан за 1,6 с |
| Записей в БД | 450 000 строк, дублей ключа 0 |
| Пачки | 901, средний размер 499; время записи пачки p50 = 79 мс, p99 = 344 мс, max = 1639 мс |
| Записи лога Warning и выше | 0; вызовов завершения процесса 0 |

Ресурсы:

| Компонент | CPU | Память |
|---|---|---|
| Процесс теста (Data Saver + генератор + клиенты) | в среднем 12% одного ядра (макс. 55%) | рабочий набор 136 МБ в среднем, 146 МБ максимум |
| Контейнер Kafka | около 3-8% (одиночный пик 67%) | 308 -> 611 МБ (растёт с объёмом лога) |
| Контейнер TimescaleDB | около 15-35%, пики до 58% | 628 МБ -> 1,15 ГБ (кэш буферов) |

Измерение: задержка получена опросом журнала каждые 250 мс; момент «строка видна» - начало опроса, поэтому цифры -
верхняя оценка с разрешением около 250 мс. Лаг по committed offset снимался раз в 5 с (завышает лаг на длину
интервала); лаг «опубликовано - записано» максимум 1315 сообщений. Ресурсы контейнеров - `docker stats` раз в 30 с.

## 3. Максимальная скорость одного экземпляра (backlog 300 000 событий, 9 партиций)

Топик наполнен до старта экземпляра, затем стартует Data Saver и разбирает очередь.

| Прогон | Всего | От первой записи | Интервал 10-90% | Запись пачки p50 / p99 |
|---|---|---|---|---|
| A (ранний, 2026-11-20 15:54) | 9113 соб/с (32,9 с) | 10 223 соб/с | 10 704 соб/с | 29 / 79 мс |
| B (повтор, 16:19) | 5531 соб/с (54,2 с) | 5928 соб/с | 6125 соб/с | 39 / 158 мс |

Разброс прогонов 1,75x при том же коде и стенде: на машине параллельно работали другие процессы (в том числе
сборки и тесты соседних задач), поэтому за оценку берём **нижнее значение: около 6000 соб/с** на один экземпляр.
Измерение с одним экземпляром, одной БД и без параллельной записи внутри экземпляра.

## 4. EXPLAIN (ANALYZE, BUFFERS) вставки 500 строк

Гипертаблица `ktm.events` заполнена 300 000 строк (один чанк). Вставка по структуре совпадает с `NpgsqlEventStore`
(`INSERT ... SELECT ... ORDER BY ... ON CONFLICT (source, source_event_id, occurred_at) DO NOTHING`), но строки
порождаются `generate_series`, а не `unnest` параметров; выполнялась в транзакции с откатом.

- Execution Time, 7 прогонов подряд (первый холодный): прогон A - 22,2; 20,4; 21,4; 20,5; 20,7; 22,3; 20,9 мс;
  прогон B - 24,7; 21,3; 20,0; 22,9; 23,2; 22,0; 22,5 мс.
- Planning Time около 0,2 мс. Узлы: `ModifyHypertable` -> `Insert on events`, арбитр конфликтов `ux_events_natural_key`,
  `Tuples Inserted: 500`, `Conflicting Tuples: 0`, `Buffers: shared hit=10059 dirtied=16 written=16`; сортировка и
  источник строк - около 1,6 мс. Из плана видно, что на источник строк и сортировку уходит около 1,6 мс из 20-25; остальное - вставка в чанк и проверка индекса (разбивка по индексам в плане не выводится).
- Сторона БД тратит около 20-25 мс на пачку; полное время записи пачки в сервисе (метрика
  `batch.duration`) 29-79 мс p50 (включает сетевой обмен, транзакцию, разбор параметров).

## 5. Вывод

- На стенде разработчика один экземпляр держит 500 соб/с без накопления лага: записано 500,9 соб/с, лаг не растёт,
  p99 задержки до строки в БД 1,4 с (верхняя оценка), максимум 2,9 с - при НФТ «не более 5 минут» от получения до
  профиля (в этом расчёте участвует только отрезок «Kafka -> журнал»).
- Максимальная скорость одного экземпляра: нижняя оценка около 6000 соб/с, верхняя около 10 700 соб/с.
  Запас к 500 соб/с - **от 12x до 21x**, то есть заметно выше порога 2x; задача на вариант `COPY` или параллельную
  запись внутри экземпляра **не заводится**.
- Масштабирование копиями возможно (до 9 партиций), но для 500 соб/с не требуется.

## 6. Ограничения замера

- Не dev-стенд: Docker Desktop на Windows (VM WSL2), один диск, нагрузка машины не изолирована; НФТ не подтверждены.
  Замер на `dev-backend`/`dev-data` (реальная сеть между Kafka, сервисом и БД, роль `ktm_app`, `Batch__*` из `.env`)
  делается отдельно, вместе с 9.2.
- Data Saver работает in-process в одном процессе с генератором и опросчиком задержки; сетевых хопов между сервисом и
  контейнерами нет, но есть между хостом и VM Docker.
- Один брокер Kafka, репликация 1; продуктивная конфигурация может отличаться.
- Задержка измерена опросом БД (разрешение около 250 мс, верхняя оценка); на устойчивом интервале исключены первые
  60 с и последние 10 с.
- Размер БД 300-750 тысяч строк (1 чанк) - существенно меньше месячного объёма (до 15 млн строк); поведение вставки на
  многочанковой и сжатой таблице не измерялось.
- Сжатие (политика 30 дней), `retention` и конкурирующие запросы на чтение во время записи не моделировались.
- Результат категории `Long` (2 минуты простоя БД) в протокол не входит: это задача 11.2.
