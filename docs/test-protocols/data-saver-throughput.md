# Протокол замера пропускной способности Data Saver (задачи 8.1, 8.2)

Статус: **заготовка. Числа будут сняты на этапе c/d (полный 15-минутный прогон, A/B, EXPLAIN) на свободной машине.**
Числа первого замера (2026-11-20) не сохранены файлом-источником и не воспроизводимы, поэтому в выводах не используются
(п. 7, справочно). Каждое число в таблицах ниже обязано ссылаться на файл выгрузки в
`docs/test-protocols/data/<дата>-<прогон>/`; пустая ячейка = «будет снято».

Требование: НФТ п. 7.1 - пиковая нагрузка не менее 500 событий/с, средняя не менее 100, задержка получения события
до отражения в профиле не более 5 минут.

> **Замер выполняется на локальном Docker машины разработчика, а не на dev-стенде. НФТ этот протокол не подтверждает:
> цифры - ориентир. Замер на dev (`dev-backend`/`dev-data`) - отдельный шаг, вместе с 9.2.**

## 2. Устойчивая нагрузка 500 соб/с, 15 минут (450 000 событий)

Источник: `docs/test-protocols/data/<дата>-full/perf-sustained.txt` (будет снят на этапе c).

Критерий устойчивой скорости: записано не менее **98%** цели (490 соб/с) на интервале от конца прогрева до
`T - 10 с`; допуск **95%** действует только для коротких (дымовых) прогонов длительностью менее 600 с
(`ShortRunSeconds`). Для 15-минутного прогона применяется 98%.

| Показатель | Результат | Строка источника |
|---|---|---|
| Опубликовано, соб/с; ошибок доставки | будет снято | `Generated` |
| Записано, устойчивый интервал, соб/с; по минутам | будет снято | `Steady interval`, `Per-minute` |
| Равномерность отправок (размер итерации публикатора, скорость по интервалам журнала) | будет снято | `Publisher uniformity` |
| Задержка «публикация -> строка в БД», устойчивый интервал: p50 / p95 / p99 / max | будет снято | `Latency publish` |
| Задержка, все события; не наблюдено | будет снято | `Latency all events` |
| Нагрузка монитора задержки: частота опроса, среднее число строк за опрос, длительность опроса | будет снято | `Latency poller load` |
| Лаг по committed offset (журнал раз в 1 с): первая / последняя треть / max | будет снято | `Lag by committed offsets` |
| Лаг по записи: первая / последняя треть / max | будет снято | `Lag by writes` |
| Хвост после окончания генерации | будет снято | `Drain after generation end` |
| Записей в БД до засева / после засева / после прогона; дублей ключа | будет снято | `ktm.events count(*)` |
| Пачки: число, размер, время записи p50 / p99 / max | будет снято | `Batches` |
| Записи лога Warning и выше; завершения процесса | будет снято | `Log records` |

Ресурсы (источник: строки `Test process` и `docker stats` в `perf-sustained.txt`; будут сняты): процесс теста,
контейнер Kafka, контейнер TimescaleDB.

Измерение:

- Журнал счётчиков (`written`, `sent`) и committed offsets ведётся **с одним периодом 1 с**; чтение committed
  занимает единицы миллисекунд (строка `Ledger period`), погрешность значения лага по committed - до 1 с публикации
  (около ±500 сообщений при 500 соб/с), по счётчикам записи - в пределах длительности опроса.
- Задержка «публикация -> строка в БД» получена курсорным чтением журнала (последний виденный `received_at`, читаются
  только новые строки, повторного чтения увиденного нет); опрос каждые 250 мс. Момент «строка видна» - начало опроса,
  погрешность до **±250 мс** плюс время запроса (строка `Latency poller load`).
- Утверждение «лаг определяется размером пачки и `MaxWaitMs`» **в протокол не входит**, пока не проверено: для проверки
  нужен прогон с другими `Batch__*` (команда в п. 8, прогон `batch`); после прогона вывод записывается по его данным
  либо не записывается вовсе.
- Слово «равномерно» относится только к тому, что показывает строка `Publisher uniformity` (на Windows `Task.Delay(2)`
  округляется до такта таймера около 15 мс, и отправка идёт пачками по несколько событий).

## 4. EXPLAIN (ANALYZE, BUFFERS) вставки 500 строк

Источник: `docs/test-protocols/data/<дата>-ab-A/explain-1.txt .. explain-7.txt` (будут сняты на этапе d).

Вставка выполняется под ролью `ktm_app` в БД с засевом 300 000 строк плюс 300 000 строк backlog (таблица после
разбора очереди), в транзакции с откатом. **Это не точный текст `NpgsqlEventStore.InsertEventsSql`:** строки
порождаются `generate_series`, а не `unnest` параметров, поэтому полученное время - **нижняя оценка** времени БД на
пачку (без разбора массивов параметров). Пока EXPLAIN не переснят реальным текстом `InsertEventsSql` с теми же
параметрами, не следует считать его оценкой полного пути записи. Сопоставление с `batch.duration` (запись пачки в
сервисе) допустимо только как ориентир.

| Execution Time, 7 прогонов подряд (первый холодный), мс | будет снято |

## 5. Вывод

Будет сформулирован по данным этапа c/d. Шаблон (подставляется только то, что подтверждено файлами выгрузки):

- устойчивая нагрузка: записано X соб/с при критерии не менее 98% цели, рост лага (по committed и по записи) -
  есть / нет, p99 задержки до строки в БД Y мс (с погрешностью ±250 мс) при НФТ «не более 5 минут» от получения до

- максимальная скорость: минимум из двух прогонов Z соб/с, запас к 500 соб/с = Z / 500 (если запас не ниже 2x,
  задача на `COPY` или параллельную запись внутри экземпляра не заводится);
- масштабирование копиями (до 9 партиций) **не проверялось** и в выводы не входит.

## 6. Ограничения замера

- Не dev-стенд: Docker Desktop на Windows (VM WSL2), один диск, нагрузка машины не изолирована; НФТ не подтверждены.
  Замер на `dev-backend`/`dev-data` (реальная сеть между Kafka, сервисом и БД, роль `ktm_app`, `Batch__*` из `.env`)
  делается отдельно, вместе с 9.2.
- **На хосте параллельно могут работать другие задачи** (сборки, тесты соседних ветвей, чужие контейнеры); тест это не
  изолирует. При каждом прогоне фиксируется, что ещё работало, и прогон повторяется при заметном разбросе. Результат
  без этой записи считается ориентиром.
- Data Saver работает in-process в одном процессе с генератором и опросчиком задержки; сетевых хопов между сервисом и
  контейнерами нет, но есть между хостом и VM Docker.
- Один брокер Kafka, репликация 1; продуктивная конфигурация может отличаться.
- Задержка измерена опросом БД (±250 мс плюс время запроса); на устойчивом интервале исключены прогрев и последние 10 с.
- Размер БД 300 000 строк засева плюс строки прогона (1-2 чанка) существенно меньше месячного объёма (до 15 млн
  строк); поведение вставки на многочанковой и сжатой таблице не измерялось.
- Сжатие (политика 30 дней), `retention` и конкурирующие запросы на чтение во время записи не моделировались.
- **Масштабирование копиями (несколько экземпляров в одной группе) не проверено**; утверждения о нём в протоколе
  допустимы только как следствие числа партиций, не как результат замера.
- EXPLAIN выполняется не по реальному тексту `InsertEventsSql` (см. п. 4), оценка нижняя.
- Результат категории `Long` (2 минуты простоя БД) в протокол не входит: это задача 11.2.

## 7. Справочно: первый замер 2026-11-20 (не воспроизводим)

Первый замер выполнялся до перехода на отдельную БД, курсорный монитор и журнал 1 с; файлы выгрузки не сохранены.
Числа из него **не используются в выводах**; приводятся лишь как порядок величин, чтобы заметить грубый разброс:
устойчивая запись около 500 соб/с без роста лага, p99 задержки около 1,4 с, максимум очереди порядка 5500-9100 соб/с
при разбросе между двумя прогонами 1,65x (параллельная нагрузка на машине), EXPLAIN вставки 500 строк около 20-25 мс.
Замечания ревью к первому замеру (объём БД зависел от порядка тестов, лаг по committed раз в 5 с, повторное чтение
журнала монитором, допуск 0,95 на длинном прогоне) устранены в тесте.

## 8. Команды этапа c/d

Предусловия: свободная машина (закрыть сборки и соседние тесты), Docker запущен; из корня репозитория. Тесты
пропускаются без `KTM_PERF_*`. Выгрузки пишутся в `docs/test-protocols/data/<дата UTC>-<KTM_PERF_RUN>/`.

```bash
# c) полный 15-минутный прогон (около 20 мин с засевом и подъёмом контейнеров; порог 98%, т.к. 900 с >= 600 с)
KTM_PERF_SECONDS=900 KTM_PERF_RUN=full dotnet test src/Ktm/tests/Ktm.DataSaver.IntegrationTests --filter "FullyQualifiedName~Sustained_load"
# c') проверка гипотезы про пачку (опционально): другой Batch, 300 с (порог 98% не нужен, <600 с -> 95%)
KTM_PERF_SECONDS=300 KTM_PERF_BATCH_MAXWAITMS=250 KTM_PERF_RUN=batch dotnet test src/Ktm/tests/Ktm.DataSaver.IntegrationTests --filter "FullyQualifiedName~Sustained_load"
# d) A/B + EXPLAIN: два одинаковых прогона (около 4-6 мин каждый)
KTM_PERF_CAPACITY=300000 KTM_PERF_RUN=ab-A dotnet test src/Ktm/tests/Ktm.DataSaver.IntegrationTests --filter "FullyQualifiedName~Backlog_drain"
KTM_PERF_CAPACITY=300000 KTM_PERF_RUN=ab-B dotnet test src/Ktm/tests/Ktm.DataSaver.IntegrationTests --filter "FullyQualifiedName~Backlog_drain"
```

После прогонов в этот документ вносятся числа с указанием файла-источника; п. 5 пишется по данным; п. 7 удаляется.
