# Протокол перф-проверки движка правил Data Saver (задача 6.5, ADR-0005 п. 2.13)

> **СТАТУС: ШАБЛОН. Полноценный замер НЕ выполнялся.** Выполнены только дымовые прогоны по 30 секунд (п. 3), проверяющие,
> что тесты работают. Они не подтверждают критерии и в выводы не входят. Таблицы п. 4 заполняются после замера, который
> запускается вручную по п. 6 на свободной машине, и сравниваются с базой `data-saver-throughput.md`.

## 1. Что проверяется

Тесты: `src/Ktm/tests/Ktm.DataSaver.IntegrationTests/Acceptance/RulesEnginePerfTests.cs`, категория `Perf`; без `KTM_PERF_RULES_RATE`
или `KTM_PERF_RULES_SECONDS` пропускаются (Skip с пояснением). Kafka и TimescaleDB в контейнерах, Data Saver in-process, топик на
9 партиций, настройки сервиса - умолчания продукта (как в базовом замере), опрос правил - по умолчанию.

Набор правил: 50 включённых правил на три источника и общие (сравнения, диапазоны трёхаргументным `<=`, вложенные
`and`/`or`/`!`), на сообщениях потока не срабатывают (вычисляются полностью, результат - ложь). Список строится в
`RulesEnginePerfTests.BuildRules`.

| Проверка | Тест | Критерий |
|---|---|---|
| (а) обычный поток, 50 правил, 500 соб/с | `Normal_stream_with_50_rules_reports_latency_and_no_lag_growth` | записано не менее 95 % цели на устойчивом интервале, лаг по committed не растёт, все события в журнале, задержка p50/p95/p99 не хуже базы `data-saver-throughput.md` (п. 2) в пределах погрешности |
| (б) 100 % отбраковка | `Full_rejection_with_50_rules_keeps_rate_on_rejected_publication` | `rules.rejected` держит не менее 95 % цели, журнал пуст, лаг не растёт, отброшено ровно столько, сколько отправлено |
| (в) стоимость `Evaluate` | `Evaluate_cost_per_message_with_50_rules_is_measured` | число записывается в протокол; порога в тесте нет (требуется решение лида по допустимой цене, см. п. 5) |

Что не равно базовому замеру: в тесте жёстче только допуск устойчивой скорости (95 % для всех длительностей, в базе 98 % для
прогонов от 600 с), нет засева 300 000 строк в таблицу, нет `docker stats`, CPU и записи Warning-лога. Для сравнения с базой при
необходимости прогнать оба теста с одинаковой длительностью и тем же засевом (`KTM_PERF_SEED` относится к базовому тесту).

## 3. Дымовые прогоны теста (не замер, 30 с, 500 соб/с)

Локальный Docker разработчика, 2026-11-23, 12 логических ЦП, .NET 10.0.13, дерево с незакоммиченными изменениями. Назначение -
показать, что тесты исполняются и считают; одиночные прогоны, статистики нет, к НФТ отношения не имеют.

| Показатель | (а) обычный поток | (б) 100 % отбраковка |
|---|---|---|
| Опубликовано, соб/с (факт) | 493,6 | 491,3 |
| Устойчивая запись в журнал, соб/с | 494,3 | 0 (журнал пуст) |
| Устойчивая публикация в `rejected` (`rules.rejected`), соб/с | 0 | 490,7 |
| Лаг по committed, среднее первой / последней трети, максимум | 462 / 345 / 654 | 488 / 415 / 665 |
| Задержка «публикация -> строка» p50 / p95 / p99 / max, мс | 777 / 1255 / 1386 / 1573 | не применимо |
| Не наблюдено опросчиком | 0 | не применимо |

(в) Evaluate: в двух дымовых запусках 10,65 и 9,11 мкс на сообщение (50 правил, по сообщению вычисляется 25 правил своего
источника и общих; ~0,36-0,43 мкс на правило). Это среднее по 60 000 вычислений без Kafka и БД, прогрев JIT выполнен.

Выгрузки этих прогонов в репозиторий не добавлены (писались во временный каталог).

## 5. Вывод (заполнить после замера)

_Не сделан._ Правило ADR п. 2.13: при заметной деградации относительно базы вернуть решение на пересмотр, а не принимать. Что считать
«заметной» деградацией, в задаче не определено: нужен порог от лида (например, p99 более чем на 20 % выше базы).

## 6. Команды прогонов

Предусловия: свободная машина, Docker запущен, из корня репозитория.

```bash
# (а) и (б), по 15 минут каждый (около 20 мин в сумме с подготовкой)
KTM_PERF_RULES_SECONDS=900 KTM_PERF_RUN=rules dotnet test src/Ktm/tests/Ktm.DataSaver.IntegrationTests --filter "FullyQualifiedName~Normal_stream_with_50_rules|FullyQualifiedName~Full_rejection_with_50_rules"
# (в) стоимость Evaluate
KTM_PERF_RULES_RATE=500 KTM_PERF_RUN=rules dotnet test src/Ktm/tests/Ktm.DataSaver.IntegrationTests --filter "FullyQualifiedName~Evaluate_cost_per_message"
```

## 7. Ограничения

- Задержка измеряется опросом БД раз в 250 мс (завышена на 0-250 мс плюс время запроса), как в базовом замере.
- Data Saver работает в одном процессе с генератором; один брокер Kafka; локальный Docker, не dev-стенд.
- (в) измеряет вычисление правил на разобранных телах без стадий формата и без `TraceFired`; стоимость в потоке (с разбором сообщения)
  входит в (а) и (б).
- Тест (б) использует одно общее правило с приоритетом 1: отбраковка происходит на первом правиле, остальные 50 не вычисляются.
  Стоимость 50 правил на «срабатывающем» потоке этим сценарием не измеряется (она ограничена сверху значением (в)).
