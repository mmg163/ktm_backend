# Формат сообщения события в Kafka (v1)

Единый контракт между адаптерами (СКУД, видео/CV, 1С:ДО) и Data Saver.
Схема: [`kafka-event.schema.json`](kafka-event.schema.json) (JSON Schema draft 2020-12).
Основание: `docs/05-источники-данных.md` п. 5.1 (единый внутренний формат, идемпотентность по ключу
«источник + ID события + timestamp», отклонение ошибочных данных). Формат утверждён.

Соответствие колонкам таблицы `events` - в согласовании в рамках задачи B3 (event store), в этом документе
не фиксируется.

## 1. Назначение и транспорт

- Один JSON-объект (UTF-8) = одно сообщение Kafka = одно событие.
- Адаптеры публикуют, Data Saver читает и пишет в неизменяемый журнал событий (`docs/03-архитектура.md`).
- Топики (утверждено): входящих - единый `ktm.events.raw` для всех источников (источник определяется полем
  `source` в теле, не именем топика), отклонённых - `ktm.events.rejected`.
- Рекомендация по ключу (не утверждена, уточняется в инфраструктурном change): ключ сообщения `{source}:{externalPersonId}` - события одного человека
  идут в одну партицию по порядку (нужно для хронологической обработки пропущенных событий CV, docs/05 п. 5.2).
  Ключ влияет на упорядочивание, не на идемпотентность.
- Заголовки Kafka семантики не несут; всё значимое - в теле.

## 2. Поля

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `schemaVersion` | integer | да | Версия формата, сейчас `1`. |
| `source` | string | да | `skud`, `cv`, `1c-do`. |
| `sourceEventId` | string (1..128) | да | ID события в источнике. СКУД - `EventId` из Орион Про строкой. CV и 1С:ДО - стабильный ID, детерминированно генерируемый адаптером (повтор события даёт тот же ID). |
| `occurredAt` | string date-time | да | Время события в источнике, только UTC (суффикс `Z`); время с офсетом отвергается. |
| `eventType` | string | да | Тип в словаре источника, `snake_case`; свободная строка, справочника нет. |
| `deviceId` | string / null | skud, cv - да; 1c-do - нет | Турникет/дверь/камера. Для 1С:ДО отсутствует или `null`. |
| `externalPersonId` | string | да | Идентификатор человека как в источнике (карта, табельный номер). К сотруднику его привязывает Процессор привязки (уровень 1), не адаптер. |
| `payload` | object | да | Прочие данные источника как есть. Без видео, изображений, биометрии; для CV - только признаки качества и ссылка на внешнее хранилище (docs/05 п. 5.4). |
| `correction` | object | нет | Только для корректирующего сообщения (п. 4). |

Рекомендуемые `eventType` (словарь расширяется без смены версии): `skud` - `access_granted`, `access_denied`;
`cv` - `presence_detected`, `absence_detected`; `1c-do` - `task_assigned`, `task_completed`, `task_overdue`,
`task_cancelled`.

Служебные поля (идентификатор события, время получения, признак доверия) адаптер не передаёт - их добавляет
Data Saver при приёме. Адаптеры не знают правил и коэффициентов доверия (docs/03).

## 3. Правила

**Идемпотентность.** Ключ события - `(source, sourceEventId, occurredAt)` (docs/05). Гарантия - уникальность на
уровне БД, а не код приложения; повторная доставка (at-least-once) дубликата не создаёт и ошибкой не считается.

**Корректировка.** Журнал неизменяем (docs/03), исправление - новое сообщение со своим `sourceEventId` и
необязательным объектом `correction`; исходное событие не меняется.
- `correction.correctsSourceEventId` и `correction.correctsOccurredAt` - ссылка на исходное по составному ключу;
  источник берётся из `source` самого сообщения (кросс-источниковые исправления не допускаются).
- `correction.reason` - причина (необязательна).
- `eventType` и `payload` корректирующего сообщения - уже исправленные значения.
- Если исходного события ещё нет (доставка не по порядку), сообщение не отбрасывается и партицию не блокирует.

**Неизвестная версия -> rejected.** Data Saver поддерживает явный набор версий (сейчас `{1}`). Сообщение с
неизвестным, отсутствующим или нечисловым `schemaVersion`, не прошедшее схему своей версии или не являющееся
JSON:
1. не попадает в журнал и не влияет на оценки;
2. публикуется в `ktm.events.rejected` с оригинальным телом и заголовками `ktm-reject-reason`
   (`unknown_schema_version` / `invalid_schema` / `malformed_json`), `ktm-reject-detail`, `ktm-source-topic`,
   `ktm-source-partition`, `ktm-source-offset`; для отбраковки, вызванной правилом (стадия вернула идентификатор
   правила), дополнительно необязательный `ktm-reject-rule-id` (см. ниже); для отбраковки по формату (три причины
   выше) заголовка нет;
3. offset фиксируется (отравленное сообщение не блокирует партицию);
4. пишется в лог ошибок и уведомляет администратора (docs/05 п. 5.1);
5. это технический инцидент интеграции, а не ухудшение оценки сотрудника.
Повторная обработка `rejected` после обновления Data Saver - ручная операция администратора.

**Заголовок `ktm-reject-rule-id`** (необязательный; добавлен аддитивно: любой потребитель `rejected` обязан
терпеть неизвестные заголовки):
- присутствует, только если отбраковавшая стадия вернула непустой идентификатор правила; для `malformed_json`,
  `unknown_schema_version`, `invalid_schema` и отбраковки портом C5 без правила отсутствует (пустого значения нет);
- значение - стабильный идентификатор правила (рекомендуемый формат `[A-Za-z0-9._:-]+`), UTF-8, без пробелов по краям,
  не длиннее 128 символов; более длинное значение усекается публикатором до 128 символов (отбраковка из-за него не
  теряется и партицию не блокирует);
- идентификатор - служебная метка правила, а не содержимое сообщения: стадия не должна класть в него данные из тела
  сообщения, персональные данные и текст ошибок;
- потребитель читает идентификатор только из `ktm-reject-rule-id` и не разбирает его из `ktm-reject-detail`. Для стадий,
  вернувших идентификатор (порт C5), `ktm-reject-detail` его не обязан содержать; для отбраковки движком правил (ниже)
  текст `ktm-reject-detail` по шаблону включает `rule_id` для чтения человеком - это не заменяет заголовок.

**Отбраковка правилом** (движок правил Data Saver, ADR-0005; необязательные аддитивные расширения контракта, `schemaVersion`
не меняется). Событие, прошедшее проверку формата, но подпавшее под включённое правило отбраковки, не пишется в журнал и
публикуется в тот же `ktm.events.rejected` с исходными ключом и телом и заголовками:
- `ktm-reject-reason` - код причины из правила (`[a-z][a-z0-9_]{0,63}`); три кода формата (`malformed_json`,
  `unknown_schema_version`, `invalid_schema`) и системный код `rule_eval_timeout` (ниже) правилам не принадлежат и
  использоваться ими не могут. Потребитель, не знающий значения, обрабатывает его как «прочее»;
- `ktm-reject-rule-id` - идентификатор правила (см. выше), присутствует всегда при отбраковке правилом;
- `ktm-reject-rule-name` - название правила, UTF-8, пробелы по краям убраны, не длиннее 256 символов (UTF-16 code units, как `string.Length`; усекается без разрыва суррогатной пары);
- `ktm-reject-rule-version` - версия правила (целое десятичное число), по которой вынесено решение;
- `ktm-reject-detail` - текст причины для человека, не длиннее 1024 символов (UTF-16 code units; усекается без разрыва суррогатной пары),
  по шаблону `Сработало правило «<name>» (<rule_id>, v<version>): <листья>`; `<листья>` - проверки, обеспечившие срабатывание, в виде
  `путь оператор` через `, ` (например `eventType ==`, `payload.confidence <=..<=`; под отрицанием `!` - с префиксом `!`); значения из
  сообщения и константы из условия в текст не попадают; формат `<листья>` не является контрактом для машинного разбора;
- `ktm-source-topic`, `ktm-source-partition`, `ktm-source-offset` - как всегда.
Потребитель отличает отбраковку правилом по наличию `ktm-reject-rule-id`.

**Системный код `rule_eval_timeout`** (оператор регулярного выражения движка правил; выдаётся только при включённом `regex`;
необязательное аддитивное расширение, `schemaVersion` не меняется). Если совпадение регулярного
выражения в правиле не уложилось в предел (`DataSaver__Rules__RegexTimeoutMs`, по умолчанию 200 мс), Data Saver не может определить,
подпадает ли сообщение под правило, и отбраковывает его, независимо от того, как записано правило (в том числе с отрицанием `!`):
- `ktm-reject-reason` = `rule_eval_timeout` - **технический отказ вычисления правила, а не свойство самого события**: сообщение может
  быть корректным, отказ вызван состоянием обработчика (пауза процесса, нехватка CPU) либо шаблоном правила. Потребитель не относит такое
  сообщение к браку данных сотрудника и не использует его для оценки; повторная обработка - ручная операция администратора (как выше);
- `ktm-reject-rule-id`, `ktm-reject-rule-name`, `ktm-reject-rule-version` - **правило, на котором вышло время** (не обязательно то, под
  которое сообщение подпало бы);
- `ktm-reject-detail` - текст вида `Вычисление правила «<name>» (<rule_id>, v<version>) прервано: превышен предел совпадения регулярного
  выражения (<N> мс)`: предел в миллисекундах; значения полей сообщения, шаблон и совпавший фрагмент в текст не попадают;
- остальные правила для сообщения не вычисляются (одно сообщение - одна запись в `rejected`); остальные заголовки - как у отбраковки правилом.
Потребитель отличает этот случай от отбраковки по содержимому по значению `ktm-reject-reason`.

**Потребители `ktm.events.rejected` и совместимость.** Потребитель топика не определён и не подтверждён, вопрос открыт (кому
сообщать - решит лид). Расширение аддитивно (новые необязательные заголовки `ktm-reject-rule-id`, `ktm-reject-rule-name`, `ktm-reject-rule-version`
и новые значения `ktm-reject-reason` - коды правил и системный `rule_eval_timeout`), `schemaVersion` не меняется. Любой потребитель обязан терпеть неизвестные заголовки
`ktm-reject-*` и неизвестные коды причин (обрабатывать как «прочее»). Статус оповещения: не отправлено. Для отбраковки правилом администратор не
уведомляется (в лог пишется предупреждение; п. 4 выше относится к отбраковке по формату). Это не оценка сотрудника, как и
отбраковка по формату. Повторная обработка - ручная операция администратора (как выше).

**Эволюция формата.**
- Необязательные поля (верхний уровень, `correction`, `payload`) и новые значения `eventType` - без смены
  `schemaVersion`; потребитель игнорирует неизвестные поля (`additionalProperties: true`).
- Добавление обязательного поля, удаление/переименование, смена типа или семантики - только новая
  `schemaVersion`; новая версия получает свой файл схемы, в переходный период Data Saver поддерживает обе.
- Новое значение `source` - расширение enum; требует релиза Data Saver до запуска адаптера (иначе - `rejected`),
  версия не меняется.

**Неизвестные типы событий.** Отбраковка по `eventType` не функция формата и схемы; это правило задачи C5
(внешняя зависимость, содержимое неизвестно). До C5 Data Saver по `eventType` не отбраковывает.

## 4. Принятые решения

| Решение | Почему |
|---|---|
| JSON, а не Avro/Protobuf со Schema Registry | docs/05 называет JSON; реестр - лишний компонент. Можно пересмотреть. |
| Версия `schemaVersion` в теле | Заголовок теряется при выгрузке/переигрывании; версия в имени топика размножает топики и ломает упорядочивание по человеку. |
| `correction` - объект, а не `correctsEventId` | Ключ события составной; объект несёт причину и расширяется без новых полей верхнего уровня. |
| Время только UTC | Единая шкала для всех источников, без неоднозначности часовых поясов. |
| `eventType` - свободная строка | Словарь источников растёт; справочник - вне формата (C5). |
| Адаптер не заполняет доверие, привязку к сотруднику | Уровни не смешиваются (docs/03). |
| `additionalProperties: true` | Добавление необязательных полей не ломает потребителей. |

## 5. Примеры (валидны по схеме)

СКУД, проход:

```json
{
  "schemaVersion": 1,
  "source": "skud",
  "sourceEventId": "48213377",
  "occurredAt": "2026-11-19T04:58:12Z",
  "eventType": "access_granted",
  "deviceId": "turnstile-01-entry",
  "externalPersonId": "card:0012345678",
  "payload": { "direction": "in", "zone": "main-gate", "orionEventCode": 28 }
}
```

Видео, сотрудник присутствует:

```json
{
  "schemaVersion": 1,
  "source": "cv",
  "sourceEventId": "cv-cam12-20261119-0001873",
  "occurredAt": "2026-11-19T05:12:40Z",
  "eventType": "presence_detected",
  "deviceId": "cam-12",
  "externalPersonId": "tab:5678",
  "payload": {
    "workplaceId": "wp-cnc-04",
    "confidence": 0.93,
    "frameQuality": "good",
    "evidenceUrl": "s3://cv-evidence/cam-12/2026-11-19/0001873"
  }
}
```

Видео, сотрудник отсутствует:

```json
{
  "schemaVersion": 1,
  "source": "cv",
  "sourceEventId": "cv-cam12-20261119-0001911",
  "occurredAt": "2026-11-19T06:47:05Z",
  "eventType": "absence_detected",
  "deviceId": "cam-12",
  "externalPersonId": "tab:5678",
  "payload": {
    "workplaceId": "wp-cnc-04",
    "confidence": 0.88,
    "absentSinceUtc": "2026-11-19T06:42:05Z",
    "evidenceUrl": "s3://cv-evidence/cam-12/2026-11-19/0001911"
  }
}
```

1С:ДО, просроченная задача (`deviceId` = `null`):

```json
{
  "schemaVersion": 1,
  "source": "1c-do",
  "sourceEventId": "task-000451-status-3",
  "occurredAt": "2026-11-18T15:00:00Z",
  "eventType": "task_overdue",
  "deviceId": null,
  "externalPersonId": "tab:5678",
  "payload": { "taskId": "000451", "status": "overdue", "dueAt": "2026-11-18T15:00:00Z" }
}
```

Корректирующее (СКУД: исправлен владелец карты):

```json
{
  "schemaVersion": 1,
  "source": "skud",
  "sourceEventId": "48213377-corr-1",
  "occurredAt": "2026-11-19T04:58:12Z",
  "eventType": "access_granted",
  "deviceId": "turnstile-01-entry",
  "externalPersonId": "card:0012345679",
  "payload": { "direction": "in", "zone": "main-gate", "orionEventCode": 28 },
  "correction": {
    "correctsSourceEventId": "48213377",
    "correctsOccurredAt": "2026-11-19T04:58:12Z",
    "reason": "В Орион Про исправлен владелец карты"
  }
}
```

## 6. Открытые вопросы

- Согласование формата с владельцем Data Saver; подтверждение авторами адаптеров СКУД, CV и 1С:ДО.
- Как CV определяет `externalPersonId` (если не может - поле станет nullable, это версия 2).
- Правило генерации `sourceEventId` для CV и 1С:ДО.
- Имена топиков, ключ сообщения, число партиций, срок хранения `rejected`.
- Нужны ли кросс-источниковые исправления.
- Содержимое правила C5 (отбраковка неизвестных `eventType`).
- Срок переходного периода при смене версии формата.
