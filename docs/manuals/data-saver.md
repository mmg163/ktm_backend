# Data Saver: руководство по эксплуатации

Сервис читает топик Kafka `ktm.events.raw` (группа `ktm-data-saver`), проверяет сообщения по схеме
`docs/api/kafka-event.schema.json` и пишет события пачками в таблицу `ktm.events` (и ссылки корректировок в
`ktm.event_corrections`). Offset коммитится только после COMMIT в БД. Сообщения, не прошедшие проверку формата, уходят в
`ktm.events.rejected`; туда же уходят сообщения, подпавшие под правила отбраковки из таблицы `ktm.rejection_rules` (п. 11).
Решения и обоснования - `docs/adr/0002-data-saver-ingestion.md` (далее ADR-0002) и
`docs/adr/0005-data-saver-rules-engine.md` (ADR-0005), формат сообщений - `docs/api/kafka-event-format.md`, правила
отбраковки - `docs/manuals/rules-engine.md`.

Пометка «уточнить» - то, что в коде или ADR однозначно не определено; до выяснения считать недоказанным.

## 1. Что нужно до запуска

1. **БД.** PostgreSQL с TimescaleDB, схема и роли созданы по `db/README.md` (`init/001_roles_and_extension.sql`, затем
   пароли ролей `ktm_migrator` и `ktm_app` заданы администратором). `init` - ручной шаг под суперпользователем.
   Миграции `db/migrations/V*.sql` накатывает контейнер `migrate` при `docker compose up` (п. 3); среди них `V002` (таблица
   правил отбраковки `ktm.rejection_rules`) и `V003` (выключенные примеры правил). Сервис работает под ролью `ktm_app`
   (`SELECT, INSERT` на журнал, только `SELECT` на `ktm.rejection_rules`), схему сам не создаёт и не мигрирует. Без `V002`
   сервис при `DataSaver__Rules__Enabled=true` не стартует (код выхода 78, п. 11).
2. **Kafka.** Топики созданы заранее (автосоздание выключено): `ktm.events.raw` (9 партиций, хранение 7 суток) и
   `ktm.events.rejected` (3 партиции, 30 суток) - `infra/kafka/README.md`. Если `ktm.events.raw` нет, сервис стартует, но
   `/health/ready` = 503 `no_partitions_assigned` (п. 5).
3. **Docker.** Образ собирается из корня репозитория (нужен `docs/api`, который встраивается в сборку):

   ```bash
   docker build -t ktm-data-saver .
   ```

## 2. Переменные окружения

Все настройки - переменные `DataSaver__<Секция>__<Имя>` (двойное подчёркивание - разделитель уровней). Источник истины -
`src/Ktm/Ktm.DataSaver/Configuration/DataSaverOptions.cs`, `src/Ktm/Ktm.DataSaver.Infrastructure/Kafka/KafkaOptions.cs`,
`src/Ktm/Ktm.DataSaver.Infrastructure/Postgres/PostgresOptions.cs`. Значения по умолчанию заданы в этих классах options и
проверяются при старте (ADR-0002, D-11); `appsettings.json` содержит только уровни логирования; шаблон окружения -
`deploy/data-saver/.env.example`. Ошибка в настройках - отказ запуска с сообщением, где названа
переменная (значения секретов в сообщения не попадают).

### Обязательные

| Переменная | Назначение |
|---|---|
| `DataSaver__Kafka__BootstrapServers` | адреса брокеров, `host:port[,host:port]` |
| `DataSaver__Postgres__Host` | хост БД |
| `DataSaver__Postgres__Database` | имя базы |
| `DataSaver__Postgres__Username` | роль (`ktm_app`) |
| `DataSaver__Postgres__PasswordFile` **или** `DataSaver__Postgres__Password` | пароль: ровно один из двух (оба или ни одного - отказ запуска); в проде и compose - только файл (Docker secret), завершающий перевод строки в файле отбрасывается |

### Kafka

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DataSaver__Kafka__Topic` | `ktm.events.raw` | входной топик |
| `DataSaver__Kafka__RejectedTopic` | `ktm.events.rejected` | топик отбракованных |
| `DataSaver__Kafka__GroupId` | `ktm-data-saver` | группа потребителей |
| `DataSaver__Kafka__ClientId` | не задан | `client.id` |
| `DataSaver__Kafka__GroupInstanceId` | не задан | `group.instance.id` (static membership), уникален на реплику, п. 4 |
| `DataSaver__Kafka__SessionTimeoutMs` | `45000` | session timeout группы |
| `DataSaver__Kafka__ProducerMessageTimeoutMs` | `30000` | предел подтверждения публикации в `rejected` |
| `DataSaver__Kafka__SecurityProtocol` | не задан (библиотека) | `PLAINTEXT`, `SSL`, `SASL_PLAINTEXT`, `SASL_SSL`; на dev - PLAINTEXT (ADR-0002, R-3) |
| `DataSaver__Kafka__SaslMechanism` | не задан | `PLAIN`, `SCRAM-SHA-256`, `SCRAM-SHA-512`, `GSSAPI`, `OAUTHBEARER` |
| `DataSaver__Kafka__SaslUsername` | не задан | пользователь SASL |
| `DataSaver__Kafka__SaslPasswordFile` / `DataSaver__Kafka__SaslPassword` | не задан | пароль SASL, взаимоисключающие; предпочтителен файл |

Без вашего участия фиксированы: чтение с `earliest` при отсутствии offset группы, автокоммит выключен, стратегия
распределения `cooperative-sticky`, автосоздание топиков выключено, producer `rejected` идемпотентный с `acks=all`.

### PostgreSQL

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DataSaver__Postgres__Port` | `5432` | порт |
| `DataSaver__Postgres__SslMode` | `Require` | `Disable`, `Prefer`, `Require`, `VerifyCA`, `VerifyFull`; `Disable` - только для локальной разработки |
| `DataSaver__Postgres__CommandTimeoutSeconds` | `10` | предел одной команды; запись пачки - три обращения к БД (начало транзакции, вставка, фиксация), каждое со своим пределом |
| `DataSaver__Postgres__ConnectTimeoutSeconds` | `15` | предел подключения |
| `DataSaver__Postgres__MinPoolSize` / `MaxPoolSize` | `1` / `10` | размер пула |
| `DataSaver__Postgres__KeepAliveSeconds` | `30` | keepalive |

### Приём, повторы, остановка, health

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DataSaver__Batch__MaxSize` | `500` | пачка закрывается по размеру... |
| `DataSaver__Batch__MaxWaitMs` | `1000` | ...или по времени от первого сообщения |
| `DataSaver__PollIntervalMs` | `500` | предел ожидания одного Consume (он же период опроса группы в паузе) |
| `DataSaver__Backoff__InitialMs` | `1000` | первая пауза повтора при сбое записи |
| `DataSaver__Backoff__MaxMs` | `30000` | потолок паузы (жёсткий, после джиттера) |
| `DataSaver__Backoff__Multiplier` | `2.0` | множитель (не меньше 1) |
| `DataSaver__Backoff__JitterFraction` | `0.2` | доля джиттера, 0..1 |
| `DataSaver__Shutdown__TimeoutSeconds` | `30` | предел дописывания пачки от сигнала остановки |
| `DataSaver__Health__Port` | `8080` | порт health-endpoint |
| `DataSaver__Health__LiveStaleSeconds` | `60` | через сколько без отметки цикла liveness = 503; должен быть строго больше `max(ceil(PollIntervalMs / 1000), Postgres__ConnectTimeoutSeconds + 3 * Postgres__CommandTimeoutSeconds, ceil(Kafka__ProducerMessageTimeoutMs / 1000))` (иначе отказ запуска, код 78): Consume, запись в БД и публикация в rejected - блокирующие ожидания, во время которых цикл не отмечается; между ними отметка есть, поэтому они не суммируются |

### Правила отбраковки

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DataSaver__Rules__Enabled` | `true` | `false` - стадия правил не регистрируется, таблица правил не читается (аварийное отключение без пересборки, перезапуск нужен) |
| `DataSaver__Rules__RefreshIntervalSeconds` | `60` | период опроса таблицы правил, целое 5..3600 с; изменение правила вступает в силу не позднее чем через этот интервал |
| `DataSaver__Rules__MaxRules` | `500` | предел числа применяемых правил: целое >= 1, верхней границы нет; считаются успешно скомпилированные включённые правила по порядку `priority`, `rule_id`, лишние не применяются, на каждое - Error в лог |

Неверное значение (`RefreshIntervalSeconds` вне 5..3600, `MaxRules` < 1) - отказ запуска, код 78. При `Enabled=false` значения
`RefreshIntervalSeconds` и `MaxRules` не проверяются. Подробности - п. 11.

### Коэффициенты доверия источников (временно, до появления хранилища настроек)

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DataSaver__Trust__Default` | `100` | коэффициент доверия по умолчанию, целое 0..100 |
| `DataSaver__Trust__Source__<source>` | - | переопределение для источника, например `DataSaver__Trust__Source__skud=80` |

Допустимые значения `<source>` - из enum `source` в `docs/api/kafka-event.schema.json`. Значение `<source>` в имени
переменной **не проверяется**: опечатка молча игнорируется, и для реального источника останется `Trust__Default`
(`EnvironmentSourceTrustProvider.cs:40-41`). Имена сверяйте вручную.

Шаблон: `deploy/data-saver/.env.example`. Реальный `.env` в git не попадает.

## 3. Запуск и остановка

Каталог `deploy/data-saver`:

```bash
cp .env.example .env        # подставить Kafka, хост и базу БД
mkdir -p secrets
umask 077
# пароль вводится скрыто; read и printf - встроенные команды bash, пароль не попадает в argv и историю
read -rs -p 'пароль ktm_app: ' P && printf '%s' "$P" > secrets/ktm_app_password; unset P; echo
read -rs -p 'пароль ktm_migrator: ' P && printf '%s' "$P" > secrets/ktm_migrator_password; unset P; echo
sudo chown 1654:1654 secrets/ktm_app_password secrets/ktm_migrator_password   # владелец - uid пользователя контейнера
chmod 0400 secrets/ktm_app_password secrets/ktm_migrator_password
docker compose up -d --build             # сначала migrate (разово), затем data-saver
docker compose logs migrate              # ход миграции; при ошибке data-saver не стартует
docker compose ps                        # STATUS должен стать "healthy" (это только liveness, см. ниже)
docker compose logs -f data-saver
```

Миграции: контейнер `migrate` (образ `postgres:16.16-alpine3.24`, около 420 МБ на диске; скрипт `deploy/data-saver/migrate/migrate.sh`)
выполняет `db/migrations/V*.sql` под `ktm_migrator` и завершается; `data-saver` стартует только после кода 0. Файлы идут по
возрастанию имени (имя вида `V<число>__<смысл>.sql`; номера не повторяются, а порядок имён совпадает с числовым: одиночный `V2` допустим, `V2` вместе с `V10` отвергается, поэтому
при росте числа цифр номера пишутся с ведущими нулями; строки с метакомандами psql (начинаются с `\`) отвергаются), один сеанс `psql` с `ON_ERROR_STOP=1` на файл; на время прогона удерживается
`pg_advisory_lock` (второй одновременный запуск ждёт до `MIGRATE_LOCK_TIMEOUT_SECONDS`, по умолчанию 120 с). Подключение - те же
`DataSaver__Postgres__Host/Port/Database/SslMode` (по умолчанию `Require`), пользователь всегда `ktm_migrator`, пароль - только
файл секрета `ktm_migrator_password` (подключён только к `migrate`, в `data-saver` его нет). Повторный запуск безопасен
(файлы идемпотентны).

Коды выхода `migrate`: `0` успех; `1` ошибка SQL, состава файлов (нет файлов, неверное имя, дубль или нарушение порядка номеров)
или подключения (в том числе `Require` при сервере без SSL, неверный пароль); `2` ошибка конфигурации или секрета (нет
переменной, неизвестный `SslMode`, файл пароля не читается или пуст); `3` таймаут блокировки или потеря сеанса блокировки.

Если `docker compose up -d` завершился ошибкой `migrate`: `data-saver` остаётся созданным, но не запущенным;
`docker compose logs migrate` показывает строку `apply <файл>` и ошибку `psql`. Исправить причину (применённый файл не правится -
новый `V00N`) и повторить `docker compose up -d`. Отдельный прогон: `docker compose run --rm migrate`.

Повторный `docker compose up -d` при уже запущенном стеке (проверено на Docker Compose v5.7.0): завершённый контейнер `migrate`
запускается заново (прогон идемпотентен, код 0), запущенный `data-saver` не пересоздаётся и не перезапускается, если его
конфигурация не менялась. Первый неидемпотентный `V`-файл требует пересмотра подхода (ADR-0004, раздел 5). `depends_on` не
действует при перезапуске контейнера демоном Docker (`restart: unless-stopped` после перезагрузки хоста): `data-saver` поднимется
без `migrate`, схема к этому времени уже накачена.

`secrets/` и `.env` в git и в контекст сборки образа не попадают (`.gitignore`, `.dockerignore`). Файл секрета должен быть
читаем из контейнера: процесс работает не от root (пользователь `app`, uid 1654), при недоступном файле сервис не стартует
(сообщение называет путь, не содержимое). Поэтому владелец файла - uid 1654 и права `0400`. Если `chown` невозможен,
допустима альтернатива `chmod 0444`, но **тогда пароль читает любой локальный пользователь хоста** - использовать только на
изолированном dev-хосте.

Признак успешного запуска: `GET /health/ready` отвечает 200 (`{"status":"ok","reason":null}`) - то есть выполнена первая
загрузка правил отбраковки (п. 11), consumer получил назначение партиций, брокер и БД отвечают. Статус `healthy` в `docker compose ps` для этого **недостаточен**: healthcheck
контейнера смотрит `/health/live` (п. 5), а он остаётся 200 и при недоступных БД и Kafka.

Проверка ready вручную (в образе нет curl); для liveness замените `ready` на `live`:

```bash
docker compose exec data-saver bash -c 'exec 3<>/dev/tcp/127.0.0.1/8080; printf "GET /health/ready HTTP/1.0\r\nHost: x\r\n\r\n" >&3; cat <&3'
```

**Остановка** - `docker compose stop` (SIGTERM). Сервис прекращает чтение, дописывает текущую пачку (запись в БД,
публикация отбракованных, commit offset), выходит из группы и завершается; код выхода 0. Предел - 
`DataSaver__Shutdown__TimeoutSeconds` (30 с) **от сигнала**; если БД недоступна и предел вышел, процесс выходит без
коммита, пачка придёт повторно (дубликатов в журнале не будет - их гасит уникальный ключ). Остановка посреди обработки и
`kill -9` данные не теряют и дубликатов не создают (ADR-0002, D-8).

`stop_grace_period` в `docker-compose.yml` задан 40 с = `Shutdown__TimeoutSeconds` (30) + запас host 5 с (решение лида Q3) +
ещё 5 с запаса. Значения связаны.
**При увеличении `Shutdown__TimeoutSeconds` увеличьте и `stop_grace_period`**, иначе Docker пошлёт SIGKILL раньше
предела (данные не теряются, но остановка перестаёт быть штатной).

Обновление версии: `docker compose up -d --build` (контейнер пересоздаётся с остановкой по правилам выше).

## 4. Масштабирование копиями

Несколько копий с одним `DataSaver__Kafka__GroupId`; партиции между ними делит Kafka, общего состояния и координации нет
(ADR-0002, D-9). Предел параллелизма - число партиций `ktm.events.raw` (9): копий больше 9 смысла не имеют.

- **Static membership** (`DataSaver__Kafka__GroupInstanceId`) необязателен. Если используется, значение должно быть
  **уникальным на каждую реплику** и стабильным между перезапусками реплики (например `data-saver-1`, `data-saver-2`):
  тогда перезапуск реплики в пределах `DataSaver__Kafka__SessionTimeoutMs` (45 с) не вызывает ребаланс. Одинаковый
  `GroupInstanceId` у двух живых реплик недопустим: одну из них брокер вытеснит. Как именно поведёт себя сервис при
  вытеснении (ошибка клиента, фатальная или нет) - **уточнить** по результатам интеграционного теста 7.7.
- Каждой реплике нужен свой `.env` (или переменная `GroupInstanceId`, переопределённая на реплику) и свой порт health,
  если реплики делят сетевой стек хоста.
- Как масштабировать через compose (`docker compose up --scale` не подходит при уникальном `GroupInstanceId` и общем
  `env_file`) - **уточнить**; штатный путь на сегодня - отдельные сервисы/проекты compose со своими `.env`.
- Реплика, которой не досталось партиций (копий больше партиций), по определению проверки не получает назначения и
  отвечает на ready 503 `no_partitions_assigned` - **уточнить** на стенде.

## 5. Health и что делать при `ready = 503`

Два маршрута на порту `DataSaver__Health__Port` (внутренняя сеть, без аутентификации; тело содержит только статус и
фиксированный код причины, без адресов и текстов ошибок):

- `GET /health/live` - 200, если цикл приёма отмечался не позже `Health__LiveStaleSeconds` назад. 503 при
  `consumer_fatal_error` (фатальная ошибка клиента Kafka, процесс при этом завершается) или `loop_stalled` (цикл завис).
  **Недоступность БД и Kafka liveness не роняет** (кроме `Commit`, см. ниже) - перезапуск их не лечит. Условие: каждое
  блокирующее ожидание (Consume - `PollIntervalMs`, запись в БД - `Connect + 3 x Command`, публикация в rejected) ограничено
  таймаутом, который строго меньше `Health__LiveStaleSeconds`; это проверяется при старте (см. описание
  `Health__LiveStaleSeconds` в п. 2). Допущение: `CommandTimeout` Npgsql действует на каждую из трёх команд записи отдельно
  (по документации Npgsql; на стенде не замерено, 10.16). Исключение: `Commit` offset в Kafka таймаута не имеет
  (решение Q1, п. 9): при зависшем брокере на `Commit` liveness может стать 503 `loop_stalled`.
- `GET /health/ready` - 200 только если выполнена первая загрузка правил отбраковки (при `DataSaver__Rules__Enabled=true`;
  пустая таблица - выполненная), consumer получил назначение партиций, состояние не `Degraded`, брокер Kafka
  отвечает на запрос метаданных, БД отвечает на `SELECT 1`. Проверки брокера и БД ограничены 2 с; результат пробы брокера
  кэшируется на 5 с.
- Пока первая загрузка правил не выполнена, `/health/live` возвращает 200 (цикл приёма намеренно не стартовал, перезапуск это
  не лечит), а `/health/ready` - 503 `rules_not_loaded`.

**Что видно в статусе контейнера.** Healthcheck в `docker-compose.yml` направлен на `/health/live` (дешёвая проверка без
обращения к брокеру и БД). Следствия:

- `unhealthy` в `docker compose ps` означает `loop_stalled` (цикл приёма завис) или `consumer_fatal_error`;
- недоступность БД и Kafka (`ready = 503`) в статусе контейнера **не видна**: контейнер остаётся `healthy`. Состояние ready
  смотреть напрямую (команда в п. 3, `... /health/ready`) или настроить внешний мониторинг на этот endpoint;
- Docker `unhealthy`-контейнер **сам не перезапускает**, а `restart: unless-stopped` реагирует только на выход процесса.
  При `loop_stalled` перезапускайте вручную: `docker compose restart data-saver` (данные не теряются, пачка придёт повторно).

Коды причин `ready = 503` (порядок проверки сверху вниз, возвращается первая сработавшая):

| `reason` | Что значит | Что делать |
|---|---|---|
| `rules_not_loaded` | правила отбраковки включены, но первая загрузка таблицы `ktm.rejection_rules` ещё не удалась (приём не начат, Kafka не читается). Проверяется первой. Не возникает при `DataSaver__Rules__Enabled=false` | если идёт старт - подождать; если держится: БД недоступна (в логе `Warning` «Rules are not loaded yet ...», повтор с backoff, не чаще раза в 10 минут на причину); нет таблицы или прав (`42P01`/`42501`) - процесс завершается кодом 78, а не висит в этом статусе: накатить `V002`, выдать `SELECT` роли `ktm_app` (п. 11) |
| `no_partitions_assigned` | consumer не получил партиций: идёт старт или ребаланс, **топика `ktm.events.raw` нет в кластере**, нет связи с брокером на старте | подождать ребаланс (до `SessionTimeoutMs`); проверить, что топик создан (`infra/kafka/README.md`), `BootstrapServers` верен, брокер доступен из контейнера; смотреть лог `Kafka client error` |
| `ingestion_degraded` | запись пачки или публикация в `rejected` не удалась: партиции на паузе, цикл повторяет **ту же** пачку с нарастающей паузой (1 с x 2^n, потолок 30 с). Данные не теряются | в логе искать `Error`/`Warning` цикла (классы ошибок: п. ниже); устранить причину - сервис восстановится сам, перезапуск не нужен |
| `broker_unavailable` | брокер не ответил на запрос метаданных за 2 с | проверить доступность `BootstrapServers`, сеть/UFW (на dev 9092 открыт для WireGuard и docker-сети, `infra/kafka/README.md`), состояние брокера |
| `database_unavailable` | БД не ответила на `SELECT 1` за 2 с | проверить доступность БД, пароль, `SslMode`, pg_hba; пока БД недоступна, цикл тоже в `Degraded` |

Классы ошибок записи (ADR-0002, D-7), по которым цикл уходит в `Degraded`:

- **временные** (разрыв соединения, таймаут команды, `57P01-57P03`, `53xxx`, `40001`, `40P01`, сбой публикации в Kafka) -
  пауза и повтор без ограничения числа попыток; восстановление автоматическое;
- **конфигурационные** (`42501` нет прав, `42P01` нет таблицы, ошибка аутентификации) - то же поведение, но на каждой
  попытке лог `Error` и сообщение `Administrator notification: fatal configuration/permission write error ...` (пока
  канала уведомлений нет, это только лог и счётчик); требуют вмешательства: права роли `ktm_app`, применённые миграции,
  пароль;
- **данные** (`22xxx`, `23xxx`) - решение за портом C6 (`IWriteFailureHandler`), который в этой версии не реализован;
  заглушка всегда повторяет пачку, то есть партиция блокируется, пока причина не устранена; данные остаются в Kafka
  (хранение 7 суток). Лог `Error` на каждой попытке.

Недоступность БД - технический сбой сервиса, а не ухудшение оценки сотрудника: по духу `docs/07`, п. 7.2 (при сбое
источника - технический инцидент, а не негативная оценка); прямого требования именно про недоступность БД в `docs/07`
нет - **уточнить**.

`ready = 503` (БД, Kafka, `ingestion_degraded`) в `docker compose ps` не отражается, см. выше; Docker перезапуск для него не
делает, и перезапуск не нужен (сервис восстанавливается сам).

## 6. Топик `ktm.events.rejected`

Сюда попадают сообщения, не прошедшие проверку формата, и сообщения, подпавшие под включённое правило отбраковки (п. 11).
Они не попадают в журнал и не влияют на оценки; это технический инцидент интеграции либо отбраковка по качеству данных, а не
ухудшение оценки сотрудника: offset таких сообщений коммитится, партицию они не блокируют. Тело - оригинальное, ключ сохраняется.

Заголовки (значения - UTF-8):

| Заголовок | Содержимое |
|---|---|
| `ktm-reject-reason` | отбраковка по формату: `malformed_json`, `unknown_schema_version`, `invalid_schema`; отбраковка правилом: `reason_code` правила (три кода формата правилам запрещены) |
| `ktm-reject-detail` | подробности причины (для правила: название, идентификатор, версия, пути и операции сработавших проверок, без значений из сообщения; до 1024 символов) |
| `ktm-source-topic`, `ktm-source-partition`, `ktm-source-offset` | координаты исходного сообщения |
| `ktm-reject-rule-id` | необязательный: идентификатор правила; **есть только при отбраковке правилом** (по нему отличают её от отбраковки формата) |
| `ktm-reject-rule-name` | необязательный: название правила, до 256 символов; только при отбраковке правилом |
| `ktm-reject-rule-version` | необязательный: версия правила, по которой принято решение; только при отбраковке правилом |

Чтение (пример для брокера из контейнера `apache/kafka`; путь к утилитам и способ доступа - **уточнить** на стенде):

```bash
kafka-console-consumer.sh --bootstrap-server <kafka-host>:9092 --topic ktm.events.rejected \
  --from-beginning --property print.headers=true --property print.key=true
```

Хранение - 30 суток. Что делать:

- `unknown_schema_version`: адаптер перешёл на версию формата, которую сервис ещё не поддерживает, - нужен релиз Data
  Saver (то же при новом значении `source`, `docs/api/kafka-event-format.md`, п. 3);
- `invalid_schema` / `malformed_json`: ошибка адаптера-источника, передать его владельцам вместе с `ktm-source-*`;
- есть `ktm-reject-rule-id`: сообщение отбраковано правилом (п. 11, `docs/manuals/rules-engine.md`); проверьте, что правило не слишком
  широкое; если событие нужно в журнале - выключите правило (`UPDATE ... SET enabled = false`) и повторите обработку вручную;
- повторная обработка после исправления - ручная операция администратора (автоматического повтора нет); потребитель
  `rejected` должен быть идемпотентен по `topic/partition/offset` исходного сообщения: при частичном сбое публикации
  пачки возможны дубли в `rejected` (принято, at-least-once).

В логе отбраковка по формату пишется с уровнем `Error` и полями `Topic`, `Partition`, `Offset`, `Source`, `SourceEventId` (для
неразобранного сообщения `Source` и `SourceEventId` = `null`, решение лида Q2); отбраковка правилом - с уровнем `Warning` (штатная
работа фильтра) и теми же полями плюс `RuleId`, `RuleVersion`, `ReasonCode`; для отбраковки правилом `IAdminNotifier` не
вызывается. Тело сообщения в лог не попадает.

## 7. Лаг группы и алерты

Сервис метрик наружу пока не отдаёт: метрики `System.Diagnostics.Metrics` (meter `Ktm.DataSaver`, инструменты
`ktm.datasaver.*`) создаются, но экспорт (Prometheus/OTel) и канал уведомления администратора - вне объёма этого этапа
(`tasks.md`, 10.5). Поэтому алерт на лаг настраивается **снаружи**, по состоянию группы в Kafka:

```bash
kafka-consumer-groups.sh --bootstrap-server <kafka-host>:9092 --describe --group ktm-data-saver
```

Столбец `LAG` по партициям `ktm.events.raw`. Алертить нужно:

- рост лага при `ready = 200` (сервис не успевает; решение - масштабирование копиями, п. 4, и замер из
  `docs/test-protocols/data-saver-throughput.md` - будет создан в задаче 8);
- ненулевой и растущий лаг при `ready = 503` / `ingestion_degraded` (сервис не пишет);
- жёсткий предел: сообщения в `ktm.events.raw` хранятся 7 суток, лаг в часах не должен приближаться к этому сроку (иначе
  непрочитанные сообщения будут удалены брокером).

Пороговые значения лага (число сообщений / время) в ТЗ и ADR не заданы - **уточнить** у лида.

## 8. Коды выхода процесса

| Код | Когда |
|---|---|
| `0` | штатная остановка по SIGTERM |
| `70` | фатальная ошибка клиента Kafka (`Error.IsFatal`): ретраи не помогают, процесс завершается после штатной остановки цикла; перед этим `/health/live` отвечает 503 `consumer_fatal_error`. Выход процесса перезапускает `restart: unless-stopped` |
| `1` | ошибка цикла приёма, перехваченная и залогированная (`DataSaverWorker.cs`, `catch (Exception)` в `ExecuteAsync`): лог `Critical` `Ingestion loop failed; the process is terminating`, затем процесс завершается этим кодом |
| `78` | ошибка конфигурации (`EX_CONFIG`): одна строка в stderr с именем настройки (например `DataSaver__Kafka__BootstrapServers is required.`), без стек-трейса и без значений секретов. Рестарт её не лечит: исправьте настройки; при `restart: unless-stopped` контейнер будет перезапускаться, пока их не исправят. Для правил отбраковки: неверное значение `DataSaver__Rules__*`; при первой загрузке правил таблицы `ktm.rejection_rules` нет (`42P01`, не накатана `V002`) или у `ktm_app` нет `SELECT` на неё (`42501`) |

При любом ненулевом выходе сначала смотрите лог последних строк `Critical` перед завершением.

## 9. Принятые решения лида (на которые опирается эксплуатация)

- **Q1.** Ограничение `Commit`/`Close`/`Flush` общим бюджетом остановки отложено: теоретически блокирующий `Commit` при
  зависшем брокере может удлинить остановку сверх `Shutdown__TimeoutSeconds`; тогда Docker остановит процесс по
  `stop_grace_period` (SIGKILL), данные не теряются, пачка придёт повторно.
- **Q2.** Для неразобранного сообщения `Source` и `SourceEventId` в логе отбраковки = `null`.
- **Q3.** `stop_grace_period` >= `Shutdown__TimeoutSeconds` + 5 с (запас host); в `docker-compose.yml` принято 40 с (30 + 5 + 5 запас).
- Прочие решения, на которые стоит оглянуться: `DataSaver__Postgres__SslMode` по умолчанию `Require`; потолок backoff
  жёсткий (30 с после джиттера); `Resume` партиций выполняется перед commit offset (ADR-0002, D-7).

## 10. Известные ограничения

- Содержимое проверок C5 и обработка ошибок данных C6 (в т.ч. `ktm.events.dlq`) - вне объёма этой версии (`tasks.md`,
  группа 10 архива `add-data-saver-core`). Отбраковка правилами идёт в тот же `ktm.events.rejected` (отдельного топика нет).
- Правила отбраковки (п. 11): аудита изменений правил нет (временное отступление от `docs/04-ролевая-модель.md` п. 4.2/4.4,
  принято лидом); перечитывание «по команде» не реализовано, только опрос; операции `in`, «пусто/заполнено», регулярное выражение
  и без учёта регистра отложены.
- Коэффициент доверия источника задаётся переменными окружения (п. 2) и применяется после перезапуска.
- Логи при недоступном Kafka: ошибки клиента (`Kafka client error`) и нативные сообщения librdkafka (в `ILogger`, не в
  stderr) идут с троттлингом - не чаще одной строки на причину в 30 с на тип сообщения. Объём в минуту на стенде после
  троттлинга не измерялся (**уточнить**); он ограничен числом различных причин, а не частотой попыток переподключения.
  Лог контейнера в `docker-compose.yml` ограничен `json-file`, `max-size: 10m`, `max-file: 3` (до 30 МБ): старые строки
  вытесняются, то есть более ранние `Critical`/`Error` могут пропасть из `docker compose logs` - при разборе инцидента
  снимайте лог сразу.

## 11. Правила отбраковки

Подробно - `docs/manuals/rules-engine.md` (что такое правило, синтаксис условия, SQL-команды для правок, примеры), решения - ADR-0005.
Здесь - то, что нужно оператору сервиса.

**Что это.** Стадия после проверки формата и C5 вычисляет для каждого сообщения включённые правила его источника и общие правила
из таблицы `ktm.rejection_rules`. Сработало первое по порядку (`priority`, затем `rule_id`) - событие не пишется в `ktm.events`, а
публикуется в `ktm.events.rejected` с исходным телом и заголовками `ktm-reject-*` (п. 6), в лог идёт `Warning`. Журнал
неизменяем, поэтому включённое правило необратимо влияет на то, что попадёт в журнал. Примеры из `V003` выключены; включать их можно
только после согласования критериев брака с владельцами источников.

**Настройки** `DataSaver__Rules__*` - п. 2 (`Enabled`, `RefreshIntervalSeconds`, `MaxRules`). Шаблон `.env.example` и compose не
менялись: у настроек есть умолчания.

**Как менять правила.** SQL-командой под ролью `ktm_migrator` (либо выданной администратором); сервис работает под `ktm_app` и
правил менять не может (только `SELECT`). Готовые команды: добавить, включить, изменить, выключить - `docs/manuals/rules-engine.md`, п. 5.
Изменение вступает в силу без перезапуска не позднее чем через `RefreshIntervalSeconds` (60 с по умолчанию, не меньше 5 с).
Перечитывание «по команде» не реализовано. Примеры из `V003` выключайте, а не удаляйте: удалённый пример вернётся при следующем
прогоне `migrate`.

**Порядок запуска.**

1. `migrate` накатывает `V002` и `V003` (п. 3).
2. `data-saver` стартует и **до начала чтения Kafka** выполняет первую загрузку правил. До её успеха `/health/ready` = 503
   с причиной `rules_not_loaded` (п. 5), сообщения не читаются: подписка ленивая (решено, реализовано) - consumer создаётся и
   подписывается после первой успешной загрузки, `Consume` и commit до неё не вызываются; `/health/live` при этом 200.
3. Результат первой загрузки:

| Состояние | Поведение |
|---|---|
| Таблица пуста или все правила выключены | штатно: набор без активных правил, запись `Info`, сервис готов, всё идёт в журнал |
| БД недоступна (таймаут, отказ соединения) | загрузка повторяется с нарастающей паузой (как `Backoff`), Kafka не читается, `ready` = 503 `rules_not_loaded`, причина в логе (`Warning` «Rules are not loaded yet ...», не чаще раза в 10 минут на причину) |
| Нет таблицы (`42P01`, не накатана `V002`) или нет прав (`42501`) | процесс завершается с кодом 78, сообщение без значений секретов; рестарт не лечит - накатите `V002`, выдайте `SELECT` роли `ktm_app` |
| Неверное значение `DataSaver__Rules__*` | код 78 |
| Есть ошибочное правило | старт продолжается, правило не применяется, `Error` с `RuleId`, растёт `rules.invalid` |

**Сбой БД правил во время работы.** После успешной первой загрузки сервис продолжает отбраковывать по **последнему валидному
набору**; в лог `Warning` «Rule reload failed, the previous rule set stays in effect ...» (не чаще раза в 10 минут на причину),
`ktm.datasaver.rules.reloads{result="failed"}` растёт, приём не прерывается; повтор - в штатный срок опроса. Ошибки `42P01`/`42501` после первой загрузки код выхода не дают. Устаревание набора
видно по `ktm.datasaver.rules.snapshot_age`; в готовность оно не входит.

**Ошибочное правило** (неверный оператор, путь, дата без зоны, перевёрнутый диапазон, неизвестный `source`, числовой литерал вне
`decimal`) выпадает из набора одно; остальные действуют; `Error` «Rejection rule is not applied: RuleId ..., RuleVersion ..., reason: ...»
повторяется не чаще раза в час на тройку `(rule_id, version, причина)`. Изменение любого столбца правила без увеличения `version`
даёт `Warning` «Rejection rule ... was changed without increasing version» (включая включение/выключение). Правка, превратившая рабочее правило в ошибочное, выключает его - брак снова пойдёт в журнал: следите за
`rules.invalid` и `Error` в логе после каждой правки.

**Аварийное отключение.** `DataSaver__Rules__Enabled=false` (перезапуск): ни стадия, ни загрузчик правил не регистрируются, таблица
не читается, `rules_not_loaded` не возникает, прочие `DataSaver__Rules__*` не проверяются, все события идут в журнал как до появления правил. Без перезапуска - `UPDATE ktm.rejection_rules SET enabled = false, version = version + 1 WHERE ...` на
нужное правило (`version + 1` и при выключении, иначе будет `Warning` «changed without increasing version») (вступит в силу в пределах интервала опроса).

**Метрики** (meter `Ktm.DataSaver`; экспорта наружу пока нет, п. 7):

| Метрика | Теги | Смысл |
|---|---|---|
| `ktm.datasaver.rules.rejected` | `source`, `rule_id` | отбраковано правилами (после подтверждённой публикации) |
| `ktm.datasaver.messages.rejected` | `reason` (для правила `rule_matched`) | общий счётчик отбракованных |
| `ktm.datasaver.rules.active` | - | применяемых правил в наборе (включённых и без ошибок) |
| `ktm.datasaver.rules.invalid` | - | включённых правил, не применённых из-за ошибки, в том числе сверх `MaxRules`; плюс строки таблицы, которые не удалось прочитать (повод для алерта) |
| `ktm.datasaver.rules.reloads` | `result` (`changed`/`unchanged`/`failed`), `trigger` (`startup`/`timer`; `signal` зарезервирован и сейчас не выдаётся) | попытки загрузки |
| `ktm.datasaver.rules.snapshot_age` | - | секунды с последней успешной проверки таблицы; до первой загрузки измерения нет |

**Чего нет.** Аудита изменений правил нет (временное отступление от `docs/04-ролевая-модель.md` п. 4.2/4.4, принято лидом): сервис
пишет в лог каждый применённый набор (добавлено/изменено/удалено, `version`); этого недостаточно для приёмки аудита. Операции `in`,
«пусто/заполнено», регулярное выражение и без учёта регистра отложены. Несколько копий сервиса читают таблицу независимо и в пределах
интервала опроса могут работать на разных наборах.
