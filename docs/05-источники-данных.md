# 5. Источники данных и интеграции

## 5.1. Общие требования ко всем источникам данных и интеграциям

Система должна быть читателем и интерпретатором данных из внешних источников. По
умолчанию Система не изменяет данные в системах-источниках, не заменяет их
функции и не является мастер-системой для кадрового учёта, графиков смен,
производственного планирования или бухгалтерских расчётов.

Каждый источник должен иметь назначение, уровень доверия, ограничения применения,
правила обработки сбоев и признаки, которые могут влиять на расчёт показателей.

### Устойчивость к сбоям

| Ситуация | Поведение Системы |
|---|---|
| Источник временно недоступен | Система продолжает работать с последними известными данными, повторяет попытки подключения с увеличивающимся интервалом (retry с backoff) |
| Источник отдал явно ошибочные данные | Событие отвергается, записывается в лог ошибок, отправляется уведомление администратору |
| Длительное отсутствие данных (> 2 часов) | Система генерирует предупреждение в дашборд администратора |
| Дублирование событий | Система должна быть идемпотентной: повторная доставка того же события не должна создавать дубликат (идентификация по составному ключу: источник + ID события + timestamp) |

### Дополнительные требования

- должен быть реализован единый внутренний формат события: все данные из любых
  источников приводятся к единому внутреннему формату перед сохранением в профиле
  сотрудника;
- интеграции должны поддерживать повторную доставку события без создания дублей;
- все события должны иметь идентификатор источника, время события, время
  получения, тип события, связанный объект и признак доверия;
- при недоступности источника Система продолжает работу с последними
  достоверными данными в пределах допустимого регламента;
- длительное отсутствие данных формирует технический кейс и уведомление
  администратора;
- Система должна иметь дашборд состояния интеграций: статус, время последнего
  обмена, количество событий, ошибки, задержки; администратор системы должен
  видеть дашборд состояния всех интеграций.

## 5.2. Источники данных и требования к интеграции

Интеграция обеспечивается со всеми информационными системами и источниками
данных Предприятия, перечисленными в настоящем ТЗ и фактически эксплуатируемыми
на дату начала работ.

| Источник | Что приходит в Систему | Требования к интеграции | Примечания |
|---|---|---|---|
| Модуль видеоаналитики Системы | Факт присутствия либо отсутствия сотрудника на рабочем месте, смена статуса | REST API (Система выступает как endpoint) или отправка в очередь (RabbitMQ/Kafka), формат данных: JSON | Если событие не приходит, Система считает, что сотрудник всё ещё находится в последнем известном статусе. При восстановлении связи — обработка пропущенных событий в хронологическом порядке |
| СКУД | Событие прохода через турникет или дверь, отказ в доступе (не та зона) | Постоянный стрим событий (WebSocket, TCP-сокет) или периодический опрос API СКУД (pull). Событие должно быть доставлено не позже чем через 10 секунд после прохода | Система должна фиксировать аномальные цепочки проходов (например, сотрудник за 5 минут отметился в двух разных концах завода — физически невозможно). Данные об отказах в доступе используются как индикатор попыток проникновения в запретные зоны и идут в тревожные отчёты службы безопасности |
| 1С:Документооборот | Список задач, висящих на сотруднике, статусы выполнения, просроченные задачи | REST API (Система опрашивает 1С) или выгрузка в промежуточную таблицу БД, формат данных: JSON или XML. Статус снимается по возможности в режиме online | 1С:ДО считается доверенным источником. Если задача не выполнена в срок, это фиксируется как объективный факт без права оспаривания (кроме случая, когда задача снята постановщиком — это приходит отдельным событием). Система должна понимать иерархию задач: если подзадача не выполнена, родительская задача тоже считается невыполненной |
| 1С:ERP | Нормативы выработки, фактическая выработка, простои | REST API или прямая выборка из БД 1С (read-only). Рекомендуется исследовать возможность интеграции, при которой данные в 1С:ERP заполняются на основе прямого опроса станков с ЧПУ | Система НЕ доверяет нормативам по умолчанию. Каждый норматив получает коэффициент доверия. Администратор может настраивать коэффициент доверия под каждый тип данных |

Дополнительно предусмотренные источники: PDM SolidWorks, iSecure Network,
кадровые справочники и иные согласованные источники, а также интеграционный
API для подключения новых источников в будущем.

## 5.3. Обработка конфликтов данных

При противоречии источников Система должна формировать в инциденте запрос на
проверку, а не делать автоматический негативный вывод. Примеры конфликтов:

- СКУД подтверждает вход, но видео не видит человека;
- 1С:ДО показывает просрочку, но есть подтверждённый простой оборудования;
- камера недоступна, но рабочее место подтверждено другими источниками.

## 5.4. Видеоаналитика и персональные данные

Система получает от системы видеонаблюдения видеопоток и регистрирует
фактические события и технические признаки. Обработка видеопотока, детекция
человека, позы или иных визуальных признаков (например, телефон или электронная
сигарета в руках) выполняется внешним или отдельным модулем видеоаналитики.

В Системе не хранятся видеоизображения, видеозаписи и биометрические шаблоны.
При этом необходимо предусмотреть возможность доступа к хранилищу из Системы по
специальной ссылке.
