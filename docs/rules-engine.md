# Правила отбраковки Data Saver

Документ для администратора и аналитика, который не читал код. По нему можно добавить, изменить и выключить правило, понять,
почему событие не попало в журнал, и найти его в `ktm.events.rejected`. Решения и обоснования -
`docs/adr/0005-data-saver-rules-engine.md` (далее ADR-0005); эксплуатация сервиса - `docs/manuals/data-saver.md`; формат
сообщения - `docs/api/kafka-event-format.md`.

Пометка «уточнить» - то, что на момент написания не подтверждено реализацией или стендом; до выяснения считать недоказанным.

## 0. Коротко

- Правило отвечает на вопрос «это сообщение - брак?». Если да, событие **не пишется в журнал** `ktm.events` и уходит в Kafka-топик
  `ktm.events.rejected` с исходным телом и пояснением.
- Правила лежат в таблице БД `ktm.rejection_rules`. Их меняют SQL-командой (см. раздел 5); перезапуск сервиса не нужен, изменение
  вступает в силу не позднее чем через минуту.
- Журнал событий неизменяем: попавшее в него убрать нельзя. Поэтому правило отбраковывает **до** записи, и включённое правило
  необратимо влияет на то, что окажется в журнале. Все примеры из поставки **выключены**; включать их можно только после
  согласования критериев брака с владельцами источников.
- Правило - это сигнал о качестве данных, а не оценка сотрудника. Отбракованное событие не влияет на оценки, санкций система не
  применяет.

## 1. Что такое правило и его столбцы

Правило - одна строка таблицы `ktm.rejection_rules`:

| Столбец | Обязателен | По умолчанию | Что хранит | Пример |
|---|---|---|---|---|
| `rule_id` | да | - | Уникальный идентификатор-слаг: латинские буквы, цифры и `. _ : -`, 1..128 символов. Попадает в заголовок, лог и метрику, поэтому по нему правило должно узнаваться без справочника | `skud-test-event` |
| `name` | да | - | Название для человека, 1..200 символов без учёта пробелов по краям (пробел-only название отвергается) | `СКУД: тестовое событие` |
| `description` | нет | `NULL` | Пояснение: что и зачем отбраковывает | `Пример: отбраковывает события СКУД с типом test_event.` |
| `source` | **да, без умолчания** | - | К какому источнику относится: `skud`, `cv`, `1c-do` или `*` (все источники) | `skud` |
| `condition` | да | - | Условие в виде JSON-объекта (синтаксис - раздел 3); размер ограничен базой: `pg_column_size` <= 16384 байт внутреннего представления `jsonb`, а не длина текста JSON (раздел 9) | `{"==": [{"var": "eventType"}, "test_event"]}` |
| `reason_code` | да | - | Код причины, уходит в заголовок `ktm-reject-reason`: строчные латинские буквы, цифры и `_`, начинается с буквы, до 64 символов. Нельзя `malformed_json`, `unknown_schema_version`, `invalid_schema` (они принадлежат проверке формата) | `test_event` |
| `enabled` | **да, без умолчания** | - | `true` - правило действует, `false` - нет | `false` |
| `priority` | нет | `100` | Порядок вычисления: меньше - раньше; 0..10000 | `100` |
| `version` | нет | `1` | Версия правила, 1..1 000 000. **Увеличивает автор** при правке условия или причины; попадает в заголовок `ktm-reject-rule-version` и в лог | `1` |

`source` и `enabled` намеренно без значения по умолчанию: пропущенное значение не должно ни сделать правило общим для всех
источников, ни включить необратимую отбраковку молча. `INSERT` без них база отклонит.

Форматы `rule_id`, `name` и `reason_code` (в том числе запрет трёх кодов формата) проверяются дважды: CHECK-ами базы при записи и
загрузчиком сервиса; значение, которое база не пропустила бы, сервис тоже отвергнет.

Какие значения допустимы в `source`, проверяет не база, а сервис при загрузке (новый источник добавляется релизом сервиса): опечатка
(`SKUD`, `scud`) не отклоняется `INSERT`-ом, но правило получит ошибку при загрузке и действовать не будет (раздел 8).

Аудита изменений нет: кто и когда менял правило, таблица не хранит (раздел 10). Есть только лог сервиса.

## 2. Место в обработке сообщения

```
сообщение из ktm.events.raw
   -> проверка формата (JSON, schemaVersion, схема v1)   не прошло -> rejected, причина malformed_json / unknown_schema_version / invalid_schema
   -> проверка C5 (содержательная)                       не прошло -> rejected (сейчас C5 принимает всё)
   -> правила отбраковки                                 сработало  -> rejected, причина = reason_code правила
   -> запись в ktm.events
```

- **Проверка формата - не правило и не настраивается.** Сообщение, не прошедшее формат, правил не видит: даже если условие правила
  «подошло бы», причина в `rejected` будет форматной, а заголовка `ktm-reject-rule-id` не будет.
- Правила применяются ко всем сообщениям, прошедшим формат, **включая корректирующие** (`correction`). Корректировка, попавшая
  под правило, остаётся в `rejected`, исправление при этом не применяется.
- Правила работают только с самим сообщением. Сотрудников, роли, смены и оценки они не знают (это уровни 2 и 3,
  `docs/03-архитектура.md`), в БД и внешние системы не обращаются.
- Для каждого сообщения вычисляются включённые правила **его источника** и правила со `source = '*'`; порядок - раздел 4.
  Сработало первое - остальные не вычисляются.

## 3. Синтаксис условия

Условие - JSON-объект в **нотации JsonLogic** (jsonlogic.com): каждый узел - объект ровно с одним ключом-оператором. Но принимается
только подмножество стандарта, а вычисляется оно **строже стандарта** (см. «Совместимость» ниже). Формальная схема записи -
`docs/api/rejection-condition.schema.json`.

### 3.1. Поле сообщения: `var` и путь

`{"var": "путь"}` берёт значение поля из тела сообщения **как оно пришло от адаптера** (не из колонок БД). Имена - как в
`docs/api/kafka-event-format.md`.

- Путь - сегменты через точку; сегмент: латинские буквы, цифры, `_`, `-`. Регистр значим. Длина пути до 256 символов.
- Первый сегмент - поле конверта v1: `schemaVersion`, `source`, `sourceEventId`, `occurredAt`, `eventType`, `deviceId`,
  `externalPersonId`, `payload`, `correction`. Другое верхнеуровневое имя - ошибка правила. Необязательные поля, которые адаптер
  добавил сверх формата, правилам недоступны.
- Внутри `payload` и `correction` структура свободна: `payload.confidence`, `payload.zone`, `payload.items.1.code`. Сегмент из
  цифр у массива - индекс элемента с нуля (`payload.items.1.code` - поле `code` второго элемента массива `items`), у объекта - обычное
  имя ключа.
- Нельзя: подстановки (`*`), фильтры, ключи с точкой, пустой путь (`""`), `a..b`, `a.`, `a[0]`, значение по умолчанию
  (`{"var": ["payload.x", 0]}`), путь-выражение. Всё это - ошибка правила.
- «Поля нет» - пути нет в теле. «`null`» - путь есть, значение JSON `null`. Это разные состояния.

**Ограничение.** Внутри `payload` и `correction` путь при загрузке проверяется только синтаксически: структура `payload` по
источникам в `docs/api` не зафиксирована. Опечатка в `payload.confidnce` не даст ошибки - поле просто «отсутствует», и правило
никогда не сработает. Опечатку в верхнем уровне (`eventTyp`) загрузчик поймает.

### 3.2. Сравнения

Во всех сравнениях ровно два операнда: один `{"var": ...}`, другой - литерал. Порядок любой: литерал слева читается зеркально
(`{"<": [5, {"var": "payload.x"}]}` означает `x > 5`). Два литерала, два `var`, три операнда (кроме диапазона) - ошибка правила.

| Оператор | Что значит | На каких типах | Если поля нет, `null` или тип другой |
|---|---|---|---|
| `==` | равно | строка (порядковое сравнение, регистр значим), число, `true`/`false`, `null` | ложь |
| `!=` | не равно: ровно отрицание `==` | те же | **истина** (ловушка, см. ниже) |
| `<` | меньше | число или дата-строка | ложь |
| `<=` | меньше или равно | число или дата-строка | ложь |
| `>` | больше | число или дата-строка | ложь |
| `>=` | больше или равно | число или дата-строка | ложь |

Правила типов:

- **Типы не приводятся.** `"5"` (строка) не равно `5` (число); строка `"0.3"` с числом `0.3` не сравнивается. Адаптер, нарушивший
  тип, не должен случайно «проходить» правило, - но и не будет им пойман: ошибки при этом нет, условие просто ложно.
- **Числа** сравниваются как десятичные (`decimal`): `1` равно `1.0`. Если **значение поля** в сообщении не помещается в десятичный
  тип, оно несравнимо: `==`, `<`, `<=`, `>`, `>=` и диапазон дают ложь, `!=` - истину. Если же **числовой литерал в самом условии**
  (в том числе граница диапазона) не помещается в `decimal`, это ошибка правила при загрузке: `числовой литерал вне диапазона decimal`
  (принятое решение лида, ADR-0005 п. 2.6: правило выпадает из набора, остальные действуют, растёт `rules.invalid`, пишется `Error`
  с `RuleId`).
- **Строки** в `==`/`!=` сравниваются порядково, без учёта культуры; `"Draft"` не равно `"draft"`. Литерал-строка до 1024 символов.
  Литералы для `==`/`!=`: строка, число, `true`/`false`, `null`; для `<`, `<=`, `>`, `>=` и границ диапазона: число или дата.
  Массив и объект литералами быть не могут.
- **`== null`** истинно, только если поле есть и равно JSON `null`. Для отсутствующего поля и для пустой строки - ложь.

**Даты.** Если литерал в `<`, `<=`, `>`, `>=` (и в границах диапазона) - строка, это дата в формате RFC 3339 **с обязательной
зоной** (`Z` или смещение): `"2026-01-01T00:00:00Z"`, `"2026-01-01T03:00:00+03:00"`. Поле тоже должно быть строкой с такой датой;
сравнение идёт по моменту времени в UTC, так что `"2025-12-31T23:00:00+00:00"` раньше `"2026-01-01T00:00:00Z"`. Литерал без
зоны (`"2026-01-01"`) или не дата - ошибка правила при загрузке. Поле не строка или не разбирается как дата - сравнение ложно, ошибки
нет. Произвольные строки операциями порядка не сравниваются. (Поле `occurredAt` по формату v1 всегда в UTC.)

Разбор даты строгий: `ГГГГ-ММ-ДДTчч:мм:сс`, необязательная дробная часть (значимы 7 знаков), затем `Z` либо `±чч:мм`; `T` и `Z` допустимы
и строчными. Секунды 0..59 (`:60` не принимается), смещение не более `±14:00`, дата должна существовать (`2026-02-30` - не дата).
Литерал, не прошедший такой разбор, - ошибка правила; такое же значение поля - просто ложь.

#### Ловушка `!=` на отсутствующем поле

`!=` - строгое отрицание `==`. Поэтому `{"!=": [{"var": "payload.zone"}, "A"]}` срабатывает **и на сообщениях, где `payload.zone`
вообще нет**. Отсутствие поля - это «не равно» любому значению.

Как обойти в первой итерации:

- Перечислить допустимые значения положительно и отсечь остальные другим способом: правило должно ловить то, что вы *знаете* как
  брак (`==`), а не «всё, кроме»;
- для чисел и дат добавить лист, который у отсутствующего поля ложен: `{"and": [{"!=": [{"var": "payload.count"}, 0]}, {">=": [{"var": "payload.count"}, -1000000]}]}`
  (второй лист ложен, если поля нет, поэтому `and` на сообщении без `payload.count` не срабатывает);
- для строк надёжного способа исключить отсутствие сейчас нет: нужен оператор «пусто/заполнено», он отложен (раздел 10) и стоит первым в
  очереди расширений.

### 3.3. Диапазон: трёхаргументный `<=`

`{"<=": [нижняя, {"var": "путь"}, верхняя]}` означает `нижняя <= поле <= верхняя` и **включает обе границы**. `var` - строго
посередине. Нижняя и верхняя - либо обе числа, либо обе даты (с зоной); нижняя не больше верхней (вырожденный `[5, var, 5]`
допустим и истинен для 5).

Пример `{"<=": [0.2, {"var": "payload.confidence"}, 0.8]}`:

| `payload.confidence` | Результат |
|---|---|
| `0.2` | истина (ровно на нижней границе) |
| `0.5` | истина |
| `0.8` | истина (ровно на верхней границе) |
| `0.19` | ложь |
| `0.81` | ложь |
| `"0.5"` (строка), `null`, поля нет | ложь |

Ошибка правила: нижняя больше верхней, число и дата вперемешку, дата без зоны, `var` не посередине, не литерал в границе. Трёхаргументные
`<`, `>`, `>=` (в стандарте JsonLogic `<` с тремя аргументами - исключающий диапазон) **не принимаются**. Исключающий диапазон
записывается через `and` с `>` и `<`.

«Вне диапазона»: `or(<, >)` - не срабатывает на отсутствующем поле; `{"!": диапазон}` - срабатывает и на нём.

### 3.4. `and`, `or`, `!`

| Узел | Запись | Смысл |
|---|---|---|
| И | `{"and": [узел, узел, ...]}` | **логическое** И (не побитовое): истинно, если истинны все; вычисляется до первого ложного. Массив непустой |
| ИЛИ | `{"or": [узел, узел, ...]}` | **логическое** ИЛИ (не побитовое): истинно, если истинен хотя бы один; до первого истинного. Массив непустой |
| НЕ | `{"!": узел}` или `{"!": [узел]}` | отрицание результата узла |

Результат узла всегда «истина» или «ложь»; «неизвестного» нет: отсутствие поля - просто ложь листа. Вложенность - любая в пределах
лимитов (раздел 9).

Зачем нужен `!`: он выражает «поля нет **или** оно вне порога». `{"!": {">=": [x, 0.5]}}` истинно и на отсутствующем поле, а
`{"<": [x, 0.5]}` - нет.

Пример вложенности (видео: слишком низкая уверенность либо значение выше 1 у источника `cv`):

```json
{"or": [
  {"<": [{"var": "payload.confidence"}, 0.3]},
  {"and": [
    {"==": [{"var": "source"}, "cv"]},
    {">": [{"var": "payload.confidence"}, 1]}
  ]}
]}
```

Любой другой ключ (`in`, `missing`, `if`, `+`, `map`, `cat`, `!!`, `regex`, `all`, `any` ...) - ошибка правила «оператор не
поддерживается»: неподдерживаемое не должно молча превращаться в «всегда ложь».

### 3.5. Соответствие нотации JsonLogic и совместимость

| Операция из постановки | Оператор JsonLogic | Есть в стандарте | В первой итерации |
|---|---|---|---|
| равно | `==` (с приведением типов) / `===` (строгий) | да | `==`, у нас строгий (как `===`) |
| не равно | `!=` / `!==` | да | `!=`, у нас строгий (как `!==`) |
| больше, меньше, не больше, не меньше | `>`, `<`, `<=`, `>=` | да | да |
| между (включительно) | `{"<=": [a, x, b]}` (трёхаргументный; `<` - исключающий) | да | да, только `<=` |
| И, ИЛИ | `and`, `or` (в стандарте возвращают значение, а не булево) | да | да (у нас булево) |
| НЕ | `!` | да | да |
| поле, вложенное поле | `var` с точечным путём (`payload.items.1.code`) | да | да, только строка-путь |
| входит в список | `in`: `{"in": [{"var": "f"}, [...]]}` | да | отложено |
| содержит (подстрока / элемент массива) | `in` с обратным порядком: `{"in": ["sub", {"var": "f"}]}` | да (тот же оператор) | отложено |
| пусто / отсутствует | `missing`: `{"missing": "f"}` (только отсутствие ключа; `""` и `[]` он «не пустыми» не считает) | да, но смысл уже нашего «пусто» | отложено |
| заполнено | `{"!": {"missing": "f"}}` | да (через `!`) | отложено |
| регулярное выражение (частичное совпадение) | - | **нет**, будет собственный оператор | отложено |
| без учёта регистра | - | нет | отложено |

**Запись совместима со стандартом, семантика - строже.** Правило, перенесённое в стороннюю JsonLogic-библиотеку, без доработки
может вести себя иначе: `==` у нас как `===`, а отсутствующее поле в `<`, `<=`, `>`, `>=` не срабатывает (в эталонной
реализации `null < 0.5` истинно). Это известная цена выбора: запись стандартная, вычислитель собственный.

## 4. Источник, приоритет и порядок

- `source = 'skud' | 'cv' | '1c-do'` - правило применяется только к событиям этого источника. `source = '*'` - ко всем.
- Для сообщения берутся включённые правила его источника и общие (`*`), в порядке `priority` по возрастанию, при равенстве - по
  `rule_id` по возрастанию (порядковое сравнение).
- **Если сработали два правила**, в `rejected` уйдёт **одна** запись - от первого по порядку. Остальные не вычисляются: одно
  сообщение - одна запись и один счёт в метриках. Администратор, выключив сработавшее правило, увидит следующее.
- Выключенные (`enabled = false`) правила не применяются.

Пример порядка при одинаковом `priority = 100` (включены все примеры из раздела 7) для события `skud`: `common-test-flag`, затем
`skud-stale-event`, затем `skud-test-event`. Чтобы правило проверялось раньше других - уменьшите `priority`.

## 5. Как добавить, изменить, выключить правило

Правила меняет администратор БД SQL-командой. Подключаться нужно под ролью **`ktm_migrator`** (владелец схемы `ktm`, пароль есть
только у контейнера `migrate` и у администратора) либо под ролью, которую администратор выдаст отдельно. Роль `ktm_app`, под которой
работает сервис, на таблицу правил имеет **только `SELECT`**: компрометация Data Saver не позволяет скрыть отбраковку.

```bash
# пароль вводится по запросу или берётся из PGPASSFILE, в команде и в истории его быть не должно
psql -U ktm_migrator -h <host> -d ktm_revisor
```

### 5.1. Посмотреть текущий набор

```sql
SELECT rule_id, source, enabled, priority, version, reason_code
FROM ktm.rejection_rules
ORDER BY priority, rule_id;
```

### 5.2. Добавить правило

Рекомендуемый порядок: вставить **выключенным**, проверить условие (5.5), затем включить.

```sql
INSERT INTO ktm.rejection_rules
    (rule_id, name, description, source, condition, reason_code, enabled, priority, version)
VALUES
    ('cv-zero-confidence',
     'Видео: нулевая уверенность',
     'Отбраковывает события видеоаналитики с payload.confidence = 0.',
     'cv',
     '{"==": [{"var": "payload.confidence"}, 0]}'::jsonb,
     'zero_confidence',
     false, 100, 1);
```

`source` и `enabled` указывать обязательно. Условие - строка JSON с приведением `::jsonb`; внутри SQL-строки одинарные кавычки
удваиваются (`''`), поэтому в условии используйте двойные кавычки JSON.

### 5.3. Включить, изменить, выключить

```sql
-- включить (version увеличивается: включение - значимое изменение, попадёт в заголовок и лог;
-- без увеличения сервис напишет предупреждение «изменено без увеличения version»)
UPDATE ktm.rejection_rules
SET enabled = true, version = version + 1
WHERE rule_id = 'cv-zero-confidence';

-- изменить условие или причину: ОБЯЗАТЕЛЬНО увеличить version
UPDATE ktm.rejection_rules
SET condition = '{"<=": [0, {"var": "payload.confidence"}, 0.05]}'::jsonb,
    version = version + 1
WHERE rule_id = 'cv-zero-confidence';

-- выключить (version тоже увеличить, иначе будет Warning ChangedWithoutVersionIncrease)
UPDATE ktm.rejection_rules
SET enabled = false,
    version = version + 1
WHERE rule_id = 'cv-zero-confidence';
```

Если нужно изменить несколько правил согласованно, делайте это в одной транзакции (`BEGIN; ... COMMIT;`): сервис читает только
закоммиченное и не увидит полуприменённый набор.

`version` ведёт автор вручную: триггера нет. Если изменить правило и забыть увеличить `version`, правило применится, но
в `ktm-reject-rule-version` останется старая версия, а сервис напишет в лог предупреждение «изменено без увеличения version»
(раздел 6.2, 8). Предупреждение срабатывает на изменение **любого** столбца, кроме самого `version`: условия, причины, `source`,
`priority`, названия, описания и `enabled` (включение или выключение без `version + 1` тоже даст предупреждение, поэтому `version = version + 1` нужен и при выключении). Сравнение идёт
между двумя последовательными наборами в памяти одного экземпляра сервиса: после перезапуска предыдущего набора нет, и первое
чтение предупреждений не даёт; уменьшение `version` предупреждения не даёт.

### 5.4. Удалять или выключать

**Выключайте, а не удаляйте** примеры из поставки: файл `V003` идёт через `INSERT ... ON CONFLICT (rule_id) DO NOTHING` и при каждом
прогоне контейнера `migrate` (а он выполняется при каждом `docker compose up`) вернёт удалённый пример - выключенным, но вернёт.
Изменённые вручную примеры повторный прогон не затирает. Свои правила удалять можно (`DELETE`), но аудита нет: историю правки
потом не восстановить, поэтому рекомендуется тоже выключать.

### 5.5. Как быстро вступает в силу и как проверить условие

- Сервис перечитывает таблицу **опросом**: по умолчанию раз в 60 секунд (`DataSaver__Rules__RefreshIntervalSeconds`, допустимо
  5..3600). Изменение вступает в силу не позднее чем через интервал и действует на сообщения, начатые обработкой после замены
  набора. Для быстрого применения можно поставить 5 с (цена - один небольшой `SELECT` раз в 5 с на экземпляр).
- Несколько экземпляров сервиса читают таблицу независимо и в пределах интервала могут работать на разных наборах.
- **Перечитывание «по команде» не реализовано** (только опрос; раздел 10).
- Ретроактивной отбраковки нет: уже записанное в журнал не меняется; отбракованное автоматически назад в обработку не
  возвращается.

**Как проверить условие до `UPDATE`.** База проверяет только то, что `condition` - JSON-объект размером до 16 КиБ (по `pg_column_size`, раздел 9); грамматику проверяет сервис
при загрузке (ошибка видна в логе спустя до минуты, а не при записи). Поэтому:

1. Сверьте условие со схемой `docs/api/rejection-condition.schema.json` (JSON Schema 2020-12): редактором с поддержкой схем либо
   валидатором, например `ajv-cli` (`ajv validate --spec=draft2020 -s docs/api/rejection-condition.schema.json -d условие.json`;
   команда не проверялась на стенде, уточнить). Схема ловит неверную форму (два литерала, пустой `and`, неизвестный оператор, трёхаргументный
   `<`, неверный первый сегмент пути). Она **не ловит**: дату без зоны, нижнюю границу больше верхней, смешение чисел и дат в
   диапазоне, глубину больше 8 и больше 64 узлов, опечатку внутри `payload`.
2. Выключенные правила сервис **не проверяет** (черновики допустимы), поэтому «вставить выключенным и посмотреть лог» ошибку не покажет.
   Проверка на сообщении - только включением: на тестовом стенде включите правило, подайте образец сообщения, убедитесь, что оно
   оказалось в `ktm.events.rejected` (или не оказалось, если должно пройти), а в логе нет `Error` с `RuleId` правила. Готовой
   утилиты «проверить правило на сухую» нет. На рабочей системе включайте правило с узким условием и сразу следите за логом и
   топиком `rejected`; при ошибке - `UPDATE ... SET enabled = false`.

## 6. Что видно при отбраковке

### 6.1. В топике `ktm.events.rejected`

Тело и ключ - исходные, байт в байт. Заголовки (значения - UTF-8):

| Заголовок | Значение для отбраковки правилом |
|---|---|
| `ktm-reject-reason` | `reason_code` правила |
| `ktm-reject-rule-id` | `rule_id`; **по его наличию потребитель отличает отбраковку правилом от отбраковки формата** |
| `ktm-reject-rule-name` | название правила, до 256 символов |
| `ktm-reject-rule-version` | `version` правила, по которой принято решение |
| `ktm-reject-detail` | текст причины для человека, до 1024 символов |
| `ktm-source-topic`, `ktm-source-partition`, `ktm-source-offset` | координаты исходного сообщения |

Текст `ktm-reject-detail` строится по шаблону `Сработало правило «<name>» (<rule_id>, v<version>): <листья>`, где `<листья>` -
проверки (листья условия), обеспечившие срабатывание, через `, `. **Значений из сообщения и констант из условия в нём нет**:
персональные данные в заголовки не попадают. `rule_id` в тексте дублируется для чтения человеком; программно его надо брать из
`ktm-reject-rule-id`, а не разбирать из `detail`.

Как строится `<листья>` (по реальному выводу, повторный проход по уже сработавшему условию):

- лист записывается как `путь оператор`: `eventType ==`, `payload.confidence >=`, `occurredAt <`; при литерале слева оператор
  записывается зеркально (`{"<": [5, {"var": "x"}]}` даёт `x >`); диапазон - `payload.confidence <=..<=`;
- `and` - все его листья; `or` - листья **всех** истинных операндов (не только первого);
- `!` - листья, **ложные** внутри отрицаемого узла, с префиксом `!`: `{"!": {">=": [x, 0.5]}}` даёт `!payload.x >=`. Каждый
  вложенный уровень `!` добавляет ещё один `!` (`!!`), независимо от чётности отрицаний;
- одинаковые строки в списке встречаются один раз, порядок - как в условии;
- если список пуст, суффикс `: ...` опускается; весь текст усекается до 1024 символов без разрыва суррогатной пары.

Названия правил и `rule_id` - данные администратора, а не сообщения; в `detail` попадает название целиком (в заголовок
`ktm-reject-rule-name` - не более 256 символов, по краям пробелы убираются).

Пример (правило `skud-test-event`):

```
ktm-reject-reason:        test_event
ktm-reject-rule-id:       skud-test-event
ktm-reject-rule-name:     СКУД: тестовое событие
ktm-reject-rule-version:  1
ktm-reject-detail:        Сработало правило «СКУД: тестовое событие» (skud-test-event, v1): eventType ==
ktm-source-topic:         ktm.events.raw
ktm-source-partition:     3
ktm-source-offset:        10452
```

Чтение - командой из `docs/manuals/data-saver.md`, п. 6. Формат контракта - `docs/api/kafka-event-format.md`, п. 3.
Потребитель, не знающий значения `ktm-reject-reason`, обрабатывает его как «прочее». Повторная обработка - ручная операция
администратора (автоматического повтора нет); потребитель должен быть идемпотентен по `topic/partition/offset`.

### 6.2. В логе

Каждое срабатывание - `Warning` (не `Error`: это штатная работа фильтра, а не поломка интеграции) с полями `RuleId`, `RuleVersion`,
`ReasonCode`, `Source`, `SourceEventId`, `Topic`, `Partition`, `Offset`; тела сообщения в логе нет. Администратор по этому случаю
**не уведомляется**. Остальные записи - при загрузке набора. Тексты ниже - шаблоны из кода (на английском; значения подставляются
вместо `{...}`, поля пишутся структурно, так что по ним можно фильтровать):

```
Warning  Message rejected by rule: {RuleId} {RuleVersion} {ReasonCode} {Source} {SourceEventId} {Topic} {Partition} {Offset}
         (пример значений: skud-test-event 1 test_event skud 48213377 ktm.events.raw 3 10452; пишется после подтверждения публикации)
Info     Rejection rule set applied: revision {Revision}, {RuleCount} active rules, {InvalidCount} invalid; added [{Added}], changed [{Changed}], removed [{Removed}]
         (пример: revision a1b2c3d4e5f6, 5 active rules, 1 invalid; added [], changed [cv-zero-confidence@2], removed [])
Info     Rejection rule set applied: revision {Revision}, no enabled rules, {InvalidCount} invalid; added [{Added}], changed [{Changed}], removed [{Removed}]
         (шаблон для набора без включённых правил)
Warning  Rejection rule {RuleId} was changed without increasing version (version {RuleVersion})
Error    Rejection rule is not applied: RuleId {RuleId}, RuleVersion {RuleVersion}, reason: {Reason}
         (пример reason: condition: нижняя граница диапазона больше верхней; у нескольких ошибок одного правила - через "; ")
Warning  Rules are not loaded yet, ingestion waits for the first load; retry in {Delay}. Reason: {Reason}; repeats suppressed: {Suppressed}
Warning  Rule reload failed, the previous rule set stays in effect; next attempt in {Delay}. Reason: {Reason}; repeats suppressed: {Suppressed}
Critical Rules cannot be loaded, the service is not started: {Reason}   (нет таблицы или прав на первой загрузке, код выхода 78)
Critical Rule refresh loop failed; the process is terminating   (дефект загрузчика; код выхода 1)
```

Пояснения:

- ревизия - первые 12 символов SHA-256 прочитанной выборки; элементы списков - `rule_id@version`. Запись «no enabled rules» пишется,
  когда в наборе нет ни применяемых, ни ошибочных правил (таблица пуста либо все выключены);
- список `changed` включает и правила, у которых изменилась только `version`; списки строятся по всем строкам таблицы, включая
  выключенные;
- «Rejection rule is not applied» повторяется в логе не чаще раза в час на тройку `(rule_id, version, причина)`: первое сообщение
  пишется сразу после загрузки, затем напоминание раз в час, пока ошибочное включённое правило остаётся в таблице (проверка идёт
  на каждом опросе, в том числе когда таблица не менялась). Перезапуск сервиса сбрасывает счётчик;
- «Rules are not loaded yet» и «Rule reload failed» - не чаще раза в 10 минут на причину (класс сбоя и его текст, например
  `SQLSTATE 08006`); подавленные повторы считаются в `repeats suppressed`. Текст причины не содержит строки подключения.

### 6.3. В метриках

Метрики `System.Diagnostics.Metrics`, meter `Ktm.DataSaver` (экспорта наружу пока нет, `docs/manuals/data-saver.md`, п. 7):

| Метрика | Тип | Теги | Смысл |
|---|---|---|---|
| `ktm.datasaver.rules.rejected` | счётчик | `source` (`skud`/`cv`/`1c-do`), `rule_id` | отбраковано правилами; считается после подтверждённой публикации. «По источникам и по правилам» - срезы этой метрики |
| `ktm.datasaver.messages.rejected` | счётчик | `reason` | общий счётчик отбракованных; для правила `reason = rule_matched` (фиксированное значение, не `reason_code`) |
| `ktm.datasaver.rules.active` | gauge | - | применяемых правил в текущем наборе (включённых и без ошибок); обновляется при смене набора |
| `ktm.datasaver.rules.invalid` | gauge | - | включённых правил, не применённых из-за ошибки (в том числе сверх `MaxRules`), плюс строки таблицы, которые адаптер не смог прочитать (повод для алерта) |
| `ktm.datasaver.rules.reloads` | счётчик | `result` (`changed`/`unchanged`/`failed`), `trigger` (`startup`/`timer`/`signal`) | попытки загрузки; `signal` зарезервировано под будущий `IRuleChangeSignal`, сейчас не выдаётся (сигнала нет) |
| `ktm.datasaver.rules.snapshot_age` | gauge, секунды | - | время с последней успешной проверки таблицы (`unchanged` - тоже успешная проверка); до первой успешной загрузки измерения нет |

При `DataSaver__Rules__Enabled=false` загрузчик и стадия не создаются: счётчики правил не растут, `active` и `invalid` равны 0,
у `snapshot_age` измерений нет.

## 7. Готовые примеры

Миграция `db/migrations/V003__rejection_rules_examples.sql` создаёт шесть правил, **все выключены**. Это иллюстрация формата, а не
бизнес-критерии брака: реальные критерии у предприятия не получены, структура `payload` по источникам не зафиксирована. Имена
полей `payload.status`, `payload.isTest` - условные.

| `rule_id` | `source` | Условие | Что отбраковывает | `reason_code` |
|---|---|---|---|---|
| `skud-test-event` | `skud` | `{"==": [{"var": "eventType"}, "test_event"]}` | события СКУД с типом `test_event` | `test_event` |
| `skud-stale-event` | `skud` | `{"<": [{"var": "occurredAt"}, "2020-01-01T00:00:00Z"]}` | события СКУД с временем раньше 2020-01-01 UTC | `stale_event` |
| `cv-low-confidence` | `cv` | `{"<=": [0, {"var": "payload.confidence"}, 0.3]}` | уверенность от 0 до 0.3 **включительно** (диапазон) | `low_confidence` |
| `cv-confidence-out-of-range` | `cv` | `{"or": [{"<": [{"var": "payload.confidence"}, 0]}, {">": [{"var": "payload.confidence"}, 1]}]}` | уверенность меньше 0 или больше 1 | `confidence_out_of_range` |
| `1c-do-draft-document` | `1c-do` | `{"==": [{"var": "payload.status"}, "draft"]}` | события 1С:ДО со статусом `draft` | `draft_document` |
| `common-test-flag` | `*` | `{"==": [{"var": "payload.isTest"}, true]}` | события любого источника с `payload.isTest = true` | `test_flag` |

У всех `priority = 100`, `version = 1`; названия и описания - в миграции. Что произойдёт на конкретных сообщениях:

- `skud-test-event`: `{"source":"skud","eventType":"test_event",...}` - отбраковано; `eventType = "access_granted"` - проходит.
  Событие `cv` с `eventType = "test_event"` правилом не затрагивается (оно для `skud`).
- `skud-stale-event`: `occurredAt = "2019-12-31T23:59:59Z"` - отбраковано; `"2020-01-01T00:00:00Z"` - проходит (строго меньше).
  Внимание: загрузка исторических данных за период до 2020 года будет отбракована целиком.
- `cv-low-confidence`: `payload.confidence` 0, 0.3 - отбраковано (границы включены); 0.31 и `-0.1` - проходят; строка `"0.2"` и
  отсутствующее поле - проходят.
- `cv-confidence-out-of-range`: `-0.1` и `1.2` - отбраковано; `0`, `1`, поле отсутствует - проходят. С `cv-low-confidence`
  не пересекается.
- `1c-do-draft-document`: `payload.status = "draft"` - отбраковано; `"Draft"` и отсутствующее поле - проходят (регистр значим,
  отсутствие не срабатывает).
- `common-test-flag`: `payload.isTest = true` - отбраковано у любого источника; строка `"true"` и `1` - проходят (типы не приводятся).

Как включить пример (после согласования критериев):

```sql
UPDATE ktm.rejection_rules
SET enabled = true, version = version + 1
WHERE rule_id = 'skud-test-event';
```

## 8. Типичные ошибки и реакция сервиса

Условие ошибочного правила **при загрузке** отбрасывает это правило из набора; остальные продолжают работать, сервис не падает. В лог
идёт `Error` с `RuleId`, `RuleVersion` и причиной вида `<путь по дереву>: <причина>`, например `condition.or[1]: оператор "in" не
поддерживается`; растёт gauge `ktm.datasaver.rules.invalid`. Исправленное правило вступает в силу со следующим опросом.

| Ошибка | Когда видна | Что делает сервис |
|---|---|---|
| Неподдерживаемый оператор (`in`, `missing`, `regex`, `if`, `+`, `all`/`any`...) | при загрузке | правило не применяется, Error в лог |
| Два ключа в узле, пустой объект, пустой `and`/`or` | при загрузке | то же |
| Неверная форма операндов: два литерала, два `var`, `var` со значением по умолчанию, три операнда не у `<=` | при загрузке | то же |
| Неверный путь: неизвестное верхнеуровневое поле (`unknownField`), `a..b`, `a.`, `*` | при загрузке | то же |
| Дата без зоны (`"2026-01-01"`) или не дата в операции порядка | при загрузке | то же |
| Диапазон с перевёрнутыми границами; число и дата вперемешку; `var` не посередине | при загрузке | то же |
| Глубина больше 8, больше 64 узлов, строка-литерал длиннее 1024, путь длиннее 256 символов, числовой литерал вне `decimal` | при загрузке | то же |
| `source` с неверным значением (`SKUD`, `scud`) | при загрузке (БД такое примет) | правило не применяется, Error в лог |
| `source` или `enabled` не указаны в `INSERT` | сразу, ошибка БД | строка не добавлена |
| `reason_code` из трёх кодов формата, `rule_id` с пробелом, `priority` вне 0..10000, `version` вне 1..1 000 000, `condition` не объект | сразу, ошибка БД (CHECK) | строка не добавлена |
| Забыт `version` при правке | не ошибка | правило действует, Warning «изменено без увеличения version», в `ktm-reject-rule-version` старая версия |
| Превышение `MaxRules` (по умолчанию 500) | при загрузке | применяются первые `MaxRules` **успешно скомпилированных** включённых правил по порядку (`priority`, `rule_id`); ошибочное правило место не занимает; каждое лишнее правило не применяется и даёт свой Error (его условие при этом не проверяется) |
| Тип в условии не тот (`"5"` вместо `5`, строка вместо числа) | **не видна** | правило применяется и просто не срабатывает; ошибки нет |
| Опечатка в пути внутри `payload` | **не видна** | то же: поле «отсутствует», правило не срабатывает |
| Слишком широкое правило | по росту `rules.rejected` | в `rejected` уходит поток; выключите правило `UPDATE`-ом |

Риск: правка, превратившая рабочее правило в ошибочное, **выключает его**: брак снова пойдёт в журнал. Прежняя версия правила не
сохраняется. Следите за `rules.invalid` и за `Error` в логе после каждой правки.

Сбой чтения таблицы (БД недоступна, таймаут) после успешной загрузки: действует **последний валидный набор**, `Warning` в лог,
`rules.reloads{result="failed"}` растёт, приём не прерывается. Если БД недоступна при старте - сервис не читает Kafka и не готов,
повторяет загрузку; нет таблицы (не накатана `V002`) или прав (`42P01`/`42501`) на первой загрузке - процесс завершается с кодом 78.
Пока набор не загружен, `/health/ready` отвечает 503 с причиной `rules_not_loaded` (`docs/manuals/data-saver.md`, п. 5), а
`/health/live` остаётся 200: приём намеренно не начат, перезапуск это не лечит.

**Аварийное отключение.** `DataSaver__Rules__Enabled=false` (нужен перезапуск): загрузчик и стадия правил не регистрируются, таблица не
читается, `/health/ready` причину `rules_not_loaded` не выдаёт, значения прочих `DataSaver__Rules__*` не проверяются; все события
идут в журнал. Значение, не разбирающееся как `true`/`false`, правила не отключает (об ошибке сообщит проверка настроек при старте).

## 9. Ограничения и лимиты

| Что | Лимит |
|---|---|
| Правил в наборе (`DataSaver__Rules__MaxRules`) | по умолчанию 500; допустимо любое целое >= 1, верхней границы нет (лишние не применяются, Error на каждое) |
| Размер `condition` | 16384 байт по `pg_column_size(condition)` (CHECK в БД): это размер внутреннего двоичного представления `jsonb` (может быть сжат), не длина JSON-текста; сервис размер не проверяет |
| Длина пути `var` | 256 символов |
| Глубина вложенности | 8 |
| Узлов-операторов в условии | 64 |
| Литерал-строка | 1024 символа |
| `rule_id` | 1..128 символов, `[A-Za-z0-9._:-]` |
| `name` | 1..200 символов без пробелов по краям; в заголовок усекается до 256 (из-за ограничения 200 усечение на практике не происходит) |
| `reason_code` | `[a-z][a-z0-9_]{0,63}`, не один из `malformed_json`, `unknown_schema_version`, `invalid_schema` |
| `ktm-reject-detail` | 1024 символа |
| Интервал опроса | 5..3600 с, по умолчанию 60 |
| Первое сработавшее правило | единственная причина в `rejected` |

Прочее: правила видят только поля конверта v1 и `payload`/`correction`; значения из сообщения не попадают в заголовки и лог;
правила не обращаются к БД и внешним данным; сравнения без арифметики и без ссылок одного поля на другое.

## 10. Что отложено и чего нет

Намеренно не входит в первую итерацию (решения лида 2026-11-23; ADR-0005 п. 2.4, 5, 9). Архитектура отложенное **допускает**:
операторы добавляются в реестр отдельным классом без правки узлов `and`/`or`/`!`, стадии и источника правил.

- **Операции:** «входит в список» (`in`), «содержит» (`in` в обратном порядке), «пусто / заполнено» (`missing`-подобный), регулярное
  выражение, сравнение без учёта регистра. Пока правило с ними - ошибка «оператор не поддерживается». Поэтому сейчас **не
  выражается** типовое условие вида «`externalPersonId` пуст ИЛИ `deviceId` начинается с `TEST-`»: `== null` ловит только явный
  JSON `null`, но не пустую строку и не отсутствие поля. Первыми в очереди расширений - «пусто/заполнено» (оно же снимет ловушку
  `!=`) и регулярное выражение.
- **Перечитывание «по команде»:** не реализовано. Только опрос (раз в 60 с по умолчанию, не быстрее 5 с). Шов под `LISTEN/NOTIFY`
  оставлен, но не используется; лид признал его ненужным в этой итерации.
- **Аудит изменений правил, триггер версии, `NOTIFY`:** отложены. **Аудита изменений правил нет** - это временное отступление от
  `docs/04-ролевая-модель.md` п. 4.2/4.4 («изменение правила попадает в аудит»), принятое лидом. Что есть вместо: сервис пишет в лог
  каждый применённый набор (что добавлено, изменено, удалено, с `version`), срабатывание несёт `version`. Этого недостаточно для приёмки
  аудита: нет субъекта («кто») и лог не неизменяем. **Триггер возврата обвязки БД** (триггер версии, таблица и триггер аудита,
  `LISTEN/NOTIFY`, отдельная роль-редактор): появление первого реального правила либо потребность в аудите.
- **REST API и интерфейс управления правилами, уведомления администратору, проверка правила «на сухую» утилитой:** не входят.
- **Относительное время и арифметика в условиях** («старше суток»): не поддерживаются.

**Почему не используется готовая JsonLogic-библиотека** (подробно - ADR-0005 п. 2.2 и 3.1): `JsonLogic` (json-everything) по
лицензии бинарного релиза не проходит требование «только MIT/Apache/BSD»; `JsonLogic.Net` заброшена и тянет уязвимую зависимость;
`Corvus.Text.Json.JsonLogic` лицензионно допустима, но приносит свой тип JSON вместо используемого в сервисе. Главное: стандартная
семантика нестрогая (приведение типов, `null < 0.5` истинно), и поверх любой библиотеки сравнения пришлось бы переопределять. Поэтому
запись совместима со стандартом, а проверка и вычисление собственные; при необходимости арифметики вопрос пересматривается отдельным ADR.
