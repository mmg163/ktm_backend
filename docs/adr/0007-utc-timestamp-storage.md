# ADR-0007. UTC в колонках timestamp without time zone

- Статус: принят по прямому требованию пользователя от 2026-11-26: «без таймзоны, просто в utc».
- Дата: 2026-11-26.
- Область: журнал `ktm.events`, `ktm.event_corrections`; уточняет ADR-0001/0002 и схему B3. Стек и внешние контракты сохраняются.

## Контекст

Первоначальная V001 использует `timestamptz`. Пользователь требует физический тип без часового пояса, содержащий
календарное представление UTC. Все пять временных колонок обязательны, значений по умолчанию у них нет.
`events.occurred_at` — измерение TimescaleDB; есть уникальные индексы и сжатые чанки. Переписывать V001 нельзя
(ADR-0004): миграции выполняются повторно и должны поддерживать существующую непустую базу.

## Решение

1. Итоговый тип `timestamp without time zone`, семантика всегда UTC:
   `events.occurred_at`, `events.received_at`, `event_corrections.correction_occurred_at`,
   `event_corrections.original_occurred_at`, `event_corrections.corrected_at`.
2. Новая forward-миграция V005 изменяет каждую колонку только при исходном типе `timestamptz`:
   `ALTER COLUMN ... TYPE timestamp without time zone USING ... AT TIME ZONE 'UTC'`.
   Простое приведение типа без `AT TIME ZONE` запрещено: результат зависел бы от timezone сессии.
   Дополнительно миграция сохраняет `current_setting('TimeZone')` и временно задаёт
   `set_config('TimeZone', 'UTC', true)`. Это необходимо для проверки существующих границ чанков TimescaleDB
   во время переписывания: старые CHECK-ограничения содержат timestamptz и до пересоздания могут сравниваться
   с новым timestamp через неявное приведение. Одного `USING ... AT TIME ZONE 'UTC'` для этого недостаточно.
   На успешном выходе прежняя timezone явно восстанавливается через `set_config('TimeZone', saved, true)`, в том числе
   при запуске внутри внешней транзакции. При ошибке изменения атомарного DO-блока откатываются.
   При повторном применении V005 завершает работу без преобразований и операций с чанками.
3. Переход выполняется атомарно под `ktm_migrator`, с блокировкой обеих таблиц. Сжатые чанки предварительно
   распаковываются; после изменения типов снова сжимаются именно те чанки, которые были сжаты до перехода.
   Состав данных, идентификаторы событий, естественные ключи, точность микросекунд, права и триггеры неизменяемости
   сохраняются. Политика сжатия и её расписание сохраняются; прямые изменения каталогов TimescaleDB запрещены.
   Реализация должна проверяться на закреплённой версии TimescaleDB 2.32.1, включая непустой сжатый чанк.
4. Npgsql передаёт явный `NpgsqlDbType.Timestamp` (для массива — `Array | Timestamp`). Значение строится как
   `DateTime.SpecifyKind(value.UtcDateTime, DateTimeKind.Unspecified)`: сначала нормализация в UTC, затем удаление
   только метки Kind для протокола timestamp. Исходный offset не превращается в сдвиг записанного UTC-времени.
5. При чтении Npgsql возвращает `DateTime` с `Unspecified`. Для доменной модели:
   `new DateTimeOffset(DateTime.SpecifyKind(value, DateTimeKind.Utc))`.
   Конструктор `new DateTimeOffset(value)` без явного UTC и `value.ToUniversalTime()` для Unspecified запрещены:
   они зависят от timezone машины. Альтернатива для SQL-проекции — `column AT TIME ZONE 'UTC'`, после которой
   допустимо читать `DateTimeOffset`. Сейчас production-чтения дат журнала нет; существующие проверки чтения
   адаптируются к новому типу.
6. В SQL границы выборок задаются `TIMESTAMP '2026-11-01 00:00:00'` с UTC-семантикой. Не смешивать timestamp
   и timestamptz неявно. Для будущего default текущего времени использовать `(CURRENT_TIMESTAMP AT TIME ZONE 'UTC')`;
   текущие колонки остаются без defaults. Сессии сервиса остаются `TimeZone=UTC` как дополнительная защита,
   корректность записи не зависит от timezone сессии, а миграция сама устанавливает и затем восстанавливает её,
   не требуя определённого исходного значения.
7. В коде и API остаются UTC `DateTimeOffset`, `TimeProvider.GetUtcNow()` и RFC 3339 с `Z`.
   `Time:UtcOffsetMinutes` — фиксированное смещение только для вычислений местной календарной даты, когда оно требуется
   бизнес-логике. Оно не прибавляется к хранимым timestamp, Kafka-времени, аудитным моментам и техническим интервалам.
   Произвольные JSON-строки внутри исходного payload не преобразуются.

## Альтернативы

- Оставить `timestamptz` и UTC-сессии: технически обеспечивает UTC-моменты, но не соответствует уточнённому требованию
  о физическом типе без зоны.
- Исправить V001: не обновляет существующую базу и нарушает правило неизменяемых применённых миграций.
- Пересоздать журнал и скопировать данные: не требуется для поддерживаемого изменения типа, увеличивает риск потери
  прав, индексов и настроек TimescaleDB.

## Последствия и эксплуатация

- Новый writer и V005 поставляются совместно. Перед накатом остановить старые экземпляры Data Saver и другие writers;
  после успешного наката запускать новую версию. Смешанная работа старого writer и новой схемы не поддерживается.
- Изменение типа и распаковка/повторное сжатие требуют окна обслуживания, места на несжатые данные и WAL.
  Перед накатом на рабочую базу нужна актуальная резервная копия. Размер и длительность оцениваются по данным среды.
  Ошибка внутри миграции откатывает её транзакцию; исходные миграции не выполняют обратное изменение типов.
- PK, UQ, индексы и ограничения чанков должны сохранять UTC-ключи. Нет UPDATE/DELETE журнала от приложения;
  преобразование представления колонки выполняет DDL от владельца, без удаления строк и без обхода триггеров.
- Сам тип timestamp не содержит признака UTC. Каждый внешний SQL-writer обязан соблюдать соглашение; наличие или
  отсутствие суффикса в клиентском отображении больше не определяет семантику колонки.
- Новые тесты по просьбе пользователя не добавляются; допустимы адаптация существующих проверок и ручная проверка
  перехода из V001..V004 с разными timezone сессии и уже сжатыми данными.

## Основания совместимости TimescaleDB

Официальная [документация операций hypertable](https://www.tigerdata.com/docs/learn/hypertables/optimize-data-in-hypertables)
допускает изменение типа временного измерения на timestamp. В
[исходнике TimescaleDB 2.32.1](https://github.com/timescale/timescaledb/blob/2.32.1/src/process_utility.c)
проверка `AT_AlterColumnType` требует отсутствия сжатых чанков; обработчик `process_alter_column_type_end`
обновляет тип измерения и пересоздаёт его ограничения чанков. Это основание выбранного перехода; проверка
на закреплённом образе обязательна перед поставкой.

При фактическом прогоне V005 на 2.32.1 из сессии `Pacific/Honolulu` событие ровно на UTC-границе чанка
выявило нарушение старого CHECK во время ALTER с явным USING. Это подтверждает необходимость локальной UTC-настройки
из пункта 2. Повторная проверка должна включать данные перед границей и на границе, сжатые чанки, повторный запуск
V005 и восстановление исходной timezone как при отдельном вызове, так и внутри внешней транзакции.
