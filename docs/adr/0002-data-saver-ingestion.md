# ADR-0002. Data Saver: приём событий из Kafka в журнал (батчи, идемпотентность, offset, сбои)

- Статус: принят (утверждено лидом проекта, 2026-11-20)
- Дата: 2026-11-20
- Область: сервис Data Saver (уровень 1), `openspec/changes/add-data-saver-core`
- Связанные документы: `docs/03-архитектура.md` п. 3.2, `docs/05-источники-данных.md` п. 5.1,
  `docs/07-нефункциональные-требования.md` п. 7.1-7.2, `docs/api/kafka-event-format.md`,
  `docs/design/Схема_БД_ER.md`, `infra/kafka/README.md`; ADR-0001, ADR-0003, ADR-0004.

## 1. Контекст

Data Saver - единственный писатель в `ktm.events` / `ktm.event_corrections`. Ограничения:

- пик 500 событий/с, 100 в среднем, 15 млн в месяц; событие в профиле не позже 5 минут от получения
  (`docs/07`, п. 7.1). Доля Data Saver в этих 5 минутах должна быть секундами;
- повторная доставка не создаёт дубль, гарантия - в схеме БД (`UNIQUE (source, source_event_id, occurred_at)`);
- журнал неизменяем: у роли `ktm_app` только `SELECT, INSERT`;
- сбой БД не должен приводить к потере событий; ошибочное сообщение не должно блокировать партицию;
- несколько копий сервиса работают параллельно, партиции делит Kafka;
- Kafka: единый входящий топик `ktm.events.raw` (все источники; 9 партиций, хранение 7 суток), один брокер,
  `ktm.events.rejected` и `ktm.events.dlq` (30 суток).

## 2. Решения

### D-1. Транспорт и подписка

Data Saver - consumer в группе `ktm-data-saver` (настраиваемо), подписка на один топик `ktm.events.raw`
(имя настраиваемо, `Kafka__Topic`). Один поток чтения на экземпляр, одно сообщение Kafka = одно событие. `auto.offset.reset=earliest`
(на первом запуске ничего не пропускаем; дубли гасит БД), `partition.assignment.strategy=cooperative-sticky`,
`enable.auto.commit=false`, `enable.auto.offset.store=false`. Источник события определяется полем `source` в теле,
а не именем топика; новый источник не требует нового топика, но новый `source` всё равно требует релиза Data Saver
(`kafka-event-format.md` п. 3). Предел параллелизма определяется числом партиций одного топика (9).

### D-2. Запись: Npgsql + `unnest`, а не EF Core

Одна транзакция на пачку, один `NpgsqlBatch` из двух команд (ReadCommitted):

```sql
-- 1. события (все сообщения пачки, включая корректирующие: см. D-4)
INSERT INTO ktm.events (event_id, source, source_event_id, occurred_at, received_at, event_type,
                        device_id, external_person_id, trust, payload, schema_version)
SELECT * FROM unnest(@event_id::uuid[], @source::text[], @source_event_id::text[], @occurred_at::timestamptz[],
                     @received_at::timestamptz[], @event_type::text[], @device_id::text[],
                     @external_person_id::text[], @trust::smallint[], @payload::jsonb[], @schema_version::smallint[])
ON CONFLICT (source, source_event_id, occurred_at) DO NOTHING;

-- 2. привязки корректировок (только для сообщений с полем correction)
INSERT INTO ktm.event_corrections (source, correction_source_event_id, correction_occurred_at, correction_event_id,
                                   original_source, original_source_event_id, original_occurred_at,
                                   original_event_id, reason, actor, corrected_at)
SELECT c.source, c.source_event_id, c.occurred_at, e.event_id,
       c.source, c.orig_source_event_id, c.orig_occurred_at, o.event_id, c.reason, c.source, c.received_at
FROM unnest(@c_source::text[], @c_source_event_id::text[], @c_occurred_at::timestamptz[],
            @c_orig_source_event_id::text[], @c_orig_occurred_at::timestamptz[], @c_reason::text[],
            @c_received_at::timestamptz[])
     AS c(source, source_event_id, occurred_at, orig_source_event_id, orig_occurred_at, reason, received_at)
JOIN ktm.events e ON e.source = c.source AND e.source_event_id = c.source_event_id AND e.occurred_at = c.occurred_at
LEFT JOIN ktm.events o ON o.source = c.source AND o.source_event_id = c.orig_source_event_id
                      AND o.occurred_at = c.orig_occurred_at
ON CONFLICT (source, correction_source_event_id, correction_occurred_at) DO NOTHING;
```

Почему `unnest`: один параметр-массив на колонку, не зависит от лимита параметров (65535), один round-trip, количество
реально вставленных строк - результат команды (`дублей = событий в пачке - вставлено`). Строки пачки сортируются по
`(source, source_event_id, occurred_at)`, чтобы два экземпляра с пересекающимися ключами брали блокировки в одном
порядке и не получали взаимоблокировку.

`COPY` во временную таблицу + `INSERT ... SELECT ... ON CONFLICT` быстрее на больших пачках, но это три команды и
временная таблица на транзакцию; переходим на него только если замер (`task 8.x`) не покажет запас по NFR.

**EF Core: оценка.** Почему не EF Core для записи пачки - по существу:

- `SaveChanges` при `AddRange` формирует `INSERT` по строкам (пакетируются в один round-trip, но без `ON CONFLICT`);
  дубль по `ux_events_natural_key` обрывает всю транзакцию (`23505`), а идемпотентность здесь - штатный путь, а не
  исключение (повторная доставка, 10 дублей из 100 в критерии приёмки). Перехват и повтор «по одной строке» ломает
  пропускную способность и порядок блокировок.
- Штатного `INSERT ... ON CONFLICT DO NOTHING` в EF Core нет. Варианты: `EFCore.BulkExtensions`/`linq2db` - сторонняя
  зависимость на критичном пути (по ADR-0001 любой пакет вне перечня - отдельное решение); `Database.ExecuteSqlRaw`
  с `unnest` через соединение EF возможен, но тогда EF даёт только соединение и транзакцию, а трекинг, модель и LINQ не
  используются - выигрыша над Npgsql нет, а `DbContext` добавляет зависимость и накладные расходы.
- `ktm_app` имеет только `SELECT, INSERT`; трекинг изменений Data Saver не нужен (сущности не читаются и не меняются).
- Узкое место - число round-trip и обработка конфликта, а не маппинг; `NpgsqlBatch` + `unnest` решает его двумя
  командами в одной транзакции.

**Рекомендация сохраняется: Npgsql на горячем пути.** Рассмотренная альтернатива - «`DbContext` только для схемы/миграций +
Npgsql для вставки» - отклонена для Data Saver: схема журнала целиком состоит из Timescale-специфичного SQL, и миграции
ведутся SQL-скриптами (ADR-0004), так что EF Core как инструмент миграций Data Saver не нужен и не используется. Если
позже REST API получит CRUD-таблицы на EF Core, выбор инструмента миграций для них - отдельный ADR; на данные журнала и
Data Saver это не влияет. Сторонний bulk-пакет можно пересмотреть, только если замер (`tasks.md` 8.x) покажет, что
`unnest`/`COPY` не даёт запаса к 500 соб/с (маловероятно).

### D-3. Ключ идемпотентности и отображение сообщения на колонки

Ключ - `(source, sourceEventId, occurredAt)`: `ux_events_natural_key` в схеме B3. Идемпотентность держит БД; код
приложения дубли не фильтрует (кроме счётчика). Отображение (в `kafka-event-format.md` его нет, фиксируем здесь):

| Колонка `ktm.events` | Значение |
|---|---|
| `event_id` | `Guid.CreateVersion7()` на строку (упорядочен по времени - лучше локальность индекса); при конфликте отбрасывается |
| `source`, `source_event_id`, `event_type`, `device_id`, `external_person_id`, `schema_version` | из сообщения как есть (`deviceId: null` или отсутствует -> `NULL`) |
| `occurred_at` | `occurredAt`, UTC, **усечён до микросекунд** (точность `timestamptz`); усечение детерминировано, чтобы повтор давал тот же ключ |
| `received_at` | момент закрытия пачки по `TimeProvider`, один на пачку, при повторе записи той же пачки не пересчитывается |
| `trust` | порт `ISourceTrustProvider` (см. G-3); значение на момент приёма |
| `payload` | **исходное тело сообщения целиком** (jsonb), как требует схема B3 |

Тело с символом `\u0000` Postgres в `jsonb` не принимает (ошибка 22P05 на всю пачку), поэтому такое сообщение
отбраковывается на стадии разбора (ADR-0003) и в пачку не попадает. Так же отбраковываются остальные тела, несовместимые
с `jsonb` (ADR-0003, п. 2.2): непарные суррогаты и числа с экспонентой вне диапазона `numeric` (до 131072 цифр целой
части и 16383 дробной; проверено на PostgreSQL 16) - иначе одно такое сообщение роняет всю пачку.

### D-4. Корректирующие сообщения

Сообщение с объектом `correction` сохраняется **двумя записями в одной транзакции**, как задано схемой B3
(`Схема_БД_ER.md` п. 3): обычная строка в `events` (исправленные `eventType`/`payload` со своим `sourceEventId`) и
строка в `event_corrections`. Исходное событие не читается и не меняется; если его нет, строка всё равно пишется с
`original_event_id = NULL`, связь по `(source, original_source_event_id, original_occurred_at)`. Идентификатор
`correction_event_id` берётся **выборкой из `events` по натуральному ключу корректирующего события** (join в команде 2),
а не из сгенерированного uuid: иначе при повторной доставке он не совпал бы с сохранённым и сломал
`ux_event_corrections_event_id`. `actor` = `source`, `corrected_at` = `received_at`. Корректирующее сообщение, ссылающееся
само на себя (тот же `sourceEventId` и `occurredAt`), отбраковывается как `invalid_schema`.

**Расхождение с постановкой задачи - см. G-1.** Реализуется вариант B3; требуется подтверждение.

### D-5. Пакетирование

Пачка закрывается по первому из условий: накоплено `Batch__MaxSize` сообщений (по умолчанию 500) или прошло
`Batch__MaxWaitMs` (по умолчанию 1000 мс) с момента получения первого сообщения пачки. Время - через `TimeProvider`.
Ожидаемая задержка до записи при малой нагрузке - около `MaxWaitMs` плюс время записи; критерий приёмки «в БД за секунды»
выполняется при значениях по умолчанию. В пачку входят сообщения разных партиций и топиков. Худший объём памяти пачки:
`MaxSize` x 64 КиБ (предел размера, `Схема_БД_ER.md` п. 7.5) = 32 МиБ.

### D-6. Модель коммита offset и семантика доставки

At-least-once + идемпотентная запись = эффект «ровно один раз» в журнале. Порядок на пачку, строго:

1. закрыть пачку, разобрать и классифицировать сообщения (ADR-0003): события, корректировки, отбракованные;
2. транзакция БД (D-2) -> **COMMIT**;
3. опубликовать отбракованные в `ktm.events.rejected` (ADR-0003), дождаться подтверждений (идемпотентный producer, `acks=all`);
4. **только после 2 и 3** - синхронный `consumer.Commit(offsets)`: по каждой партиции `последний offset пачки + 1`.

В расчёт offset входят **все** сообщения пачки, включая отбракованные (иначе отравленное сообщение блокирует партицию,
`kafka-event-format.md` п. 3), поэтому трекер offset принадлежит пачке, а не списку записанных событий. Автокоммит и
`StoreOffset` не используются. Сбой между шагами 2 и 4 даёт повторную доставку, которую гасит ключ; повтор отбракованных
в `rejected` при сбое между 3 и 4 - осознанный дубль (повторная публикация безопасна, потребитель `rejected` -
администратор). Тот же дубль возможен и при частичном сбое публикации пачки: часть сообщений уже подтверждена брокером,
публикация упала, пачка повторяется целиком и переопубликует уже подтверждённые - это осознанный at-least-once, дедупликация
в `rejected` не вводится (потребитель - администратор, идемпотентен по `topic/partition/offset` исходного сообщения). Ошибка `Commit` (потеря партиции при ребалансировке) логируется и не роняет сервис.

### D-7. Недоступность БД: классификация, backoff, pause/resume

Ошибки записи делятся на три класса (классификатор - чистая функция в `Core`, тестируется без БД):

| Класс | Примеры | Действие |
|---|---|---|
| Transient | недоступность/разрыв соединения, таймаут команды, `57P01-57P03`, `53xxx` (ресурсы), `40001`, `40P01`, сбой публикации в Kafka | пауза и повтор **той же пачки** без ограничения числа попыток |
| Fatal-config | `42501` (нет прав), `42P01` (нет таблицы), ошибка аутентификации | как Transient (ничего не теряем), но с логом уровня Error на каждой попытке и `ready = false`; не «отбраковка» |
| Data | `22xxx`, `23xxx` (CHECK/NOT NULL) | вызов порта `IWriteFailureHandler` (C6); стратегия до C6 - см. ADR-0003 |

При Transient/Fatal-config сервис: (1) переводит состояние в `Degraded` (readiness = 503); (2) вызывает
`consumer.Pause(consumer.Assignment)`; (3) **продолжает вызывать `Consume` с коротким таймаутом**, пока ждёт: опрос нужен,
чтобы не превысить `max.poll.interval.ms` и не вылететь из группы (на паузе `Consume` сообщений не возвращает);
(4) повторяет запись той же пачки после паузы `min(Initial x 2^n, Max)` с джиттером (по умолчанию 1 с, множитель 2,
потолок 30 с, джиттер +-20 %, настраиваемо); (5) после успешной записи и публикации отбракованных - `Resume`, затем commit offset (порядок реализации; счётчик попыток
сбрасывается). Порядок «Resume до commit» принят осознанно: commit не влияет на безопасность чтения (позиция чтения
консьюмера не зависит от закоммиченного offset), а пауза не должна затягиваться на время синхронного `Commit`. Сбой commit
после `Resume` безопасен: повторная доставка гасится ключом (D-6).
Новые партиции, назначенные во время `Degraded`, ставятся на паузу сразу в обработчике назначения. Контракт порта C6 (`IWriteFailureHandler`, класс Data): `DeadLetter(items)` возвращается
**только после durable-сохранения этих сообщений** (подтверждённая публикация в DLQ / запись в хранилище); только после
этого цикл коммитит их offset. `Retry` блокирует партицию: лог Error на каждой попытке, `Degraded`, backoff как выше.
Данные при этом остаются в Kafka (хранение 7 суток, см. риск R-1), в памяти держится одна пачка.

Недоступность БД - технический сбой Data Saver, оценок сотрудников не касается (`docs/07`, п. 7.2).

### D-8. Остановка и ребалансировка

- **Graceful shutdown** (SIGTERM / `StopAsync`): прекратить `Consume`, дописать текущую пачку по порядку D-6, закоммитить
  offset, `consumer.Close()` (выход из группы), сбросить producer. `Shutdown__TimeoutSeconds`
  отсчитывается **от сигнала stop** (не от начала дописывания) и ограничивает все in-flight операции: запись, публикацию
  отбракованных, `Commit`, `Close`. Если остановка пришла во время backoff, делается **одна немедленная** попытка записи
  без ожидания паузы; неудача - выход без коммита. Предел - `Shutdown__TimeoutSeconds` (по умолчанию 30;
  `HostOptions.ShutdownTimeout` выставляется не меньше). Если БД недоступна и предел вышел - выход **без** коммита:
  ничего не теряется, пачка придёт повторно. `stop_grace_period` контейнера не меньше `Shutdown__TimeoutSeconds` + запас host (`ShutdownOptions.HostMarginSeconds`, 5 с): иначе SIGKILL придёт раньше предела host (данные не теряются, но остановка перестаёт быть штатной).
- **Ребалансировка**: при отзыве/потере партиций сообщения этих партиций удаляются из пачки без записи (их заново прочитает
  новый владелец с последнего закоммиченного offset, дубли гасит БД). Блокирующей записи внутри обработчика нет: он
  выполняется на потоке опроса, а БД может быть недоступна.
- **Аварийное завершение** (kill -9): повторная доставка с последнего закоммиченного offset; дублей в БД нет.

### D-8а. Контракты портов цикла

- `IMessageSource`: `Consume` блокируется не дольше переданного таймаута и возвращает «нет сообщения» по его истечении;
  `TakeAssignmentChanges` вызывается только из потока цикла (изменения назначений накапливаются адаптером и отдаются
  циклу, обработчики librdkafka не мутируют состояние цикла); `Pause/Resume` толерантны к отозванным партициям (не
  бросают, игнорируют отсутствующие); нефатальные ошибки брокера поглощаются адаптером (лог + метрика), наружу идут только
  фатальные.
- `IRejectionPublisher`: предел ожидания один блокирующий вызов - `Kafka__ProducerMessageTimeoutMs` (`message.timeout.ms`
  producer, умолчание 30 с); отдельного таймаута в адаптере нет. Истечение - Failure (Transient): цикл уходит в backoff,
  пачка повторяется. Во время самого ожидания heartbeat не отмечается, поэтому `ProducerMessageTimeoutMs` участвует в
  правиле согласованности `Health__LiveStaleSeconds` (D-11).
- `IEventStore.WriteAsync`: атомарна на пачку (одна транзакция D-2): либо записана вся пачка, либо ничего.

### D-9. Масштабирование

Несколько копий с одним `group.id`; партиции делит Kafka. Состояния между копиями нет; координации не нужно.
Предел параллелизма = число партиций (9). Параллелизм внутри экземпляра не вводится (один поток
чтения и записи): упрощает учёт offset; вводится по результатам замера, если один экземпляр не даёт запаса к 500 соб/с.
Число партиций `ktm.events.raw` (9) выбрано равным прежнему суммарному (3 источника x 3); увеличивается вручную
(`infra/kafka/README.md`), уменьшить нельзя - менять до появления данных.

### D-10. Health

Отдельный минимальный Kestrel в том же процессе (`Health__Port`, по умолчанию 8080), только два маршрута без
аутентификации (внутренняя сеть), без чувствительных данных в ответе:

- `GET /health/live` - 200, если цикл обработки отметился (`heartbeat`) не позже `Health__LiveStaleSeconds` (60 с) назад
  (heartbeat обновляется и в состоянии `Degraded`); 503 при зависшем цикле или фатальной ошибке consumer
  (`IsFatal`) - тогда процесс завершается с ненулевым кодом. **Недоступность БД liveness не роняет** (перезапуск не лечит).
- `GET /health/ready` - 200 только если consumer подписан и получил назначение, состояние не `Degraded`, и брокер Kafka доступен
  (активная проверка связи - запрос метаданных с пределом 2 с, результат кэшируется на 5 с, вне потока цикла; наличие назначения в
  памяти клиента доступность брокера не доказывает; в ответе - код `broker_unavailable` без адресов); иначе 503 с телом `{ "status": "...", "reason": "..." }`.
  Отсутствие топика в кластере - не сбой проверки: брокер ответил, значит доступен; недоступность топика проявляется как
  `no_partitions_assigned`, а не `broker_unavailable`.

### D-11. Конфигурация (только окружение)

Секции `DataSaver__*`; значения по умолчанию живут в классах options (`DataSaverOptions`, `KafkaOptions`,
`PostgresOptions`) и проверяются при старте (`ValidateOnStart`); шаблон окружения - `deploy/data-saver/.env.example`;
`appsettings.json` содержит только настройки логирования. Причина: единый источник значений по умолчанию и валидация
рядом с ними (значение и его допустимый диапазон не расходятся между файлами). Секреты - из окружения или из файла
(`...__PasswordFile` / `*_FILE`). Обязательные без значения по умолчанию: `DataSaver__Kafka__BootstrapServers`,
`DataSaver__Postgres__Host`, `DataSaver__Postgres__Database`, `DataSaver__Postgres__Username`,
`DataSaver__Postgres__Password` (или `PasswordFile`). Необязательные: `Kafka__GroupId` (`ktm-data-saver`),
`Kafka__Topic` (`ktm.events.raw`), `Kafka__RejectedTopic` (`ktm.events.rejected`), `Kafka__GroupInstanceId` (статическое членство),
`Kafka__SecurityProtocol`/`Sasl*` (на dev - PLAINTEXT, см. R-3), `Batch__MaxSize`, `Batch__MaxWaitMs`,
`Backoff__InitialMs|MaxMs|Multiplier|JitterFraction`, `Postgres__CommandTimeoutSeconds`, `Shutdown__TimeoutSeconds`,
`Health__Port`, `Health__LiveStaleSeconds`. Ошибка конфигурации - отказ запуска с понятным сообщением (без значений
секретов), одна строка в stderr и код выхода 78 (`EX_CONFIG`) - в том числе для конфликта `SaslPassword`/`SaslPasswordFile` и
нечитаемого файла секрета. Согласованность: `Health__LiveStaleSeconds` строго больше
`max(ceil(PollIntervalMs / 1000), Postgres__ConnectTimeoutSeconds + 3 * Postgres__CommandTimeoutSeconds, ceil(Kafka__ProducerMessageTimeoutMs / 1000))`:
одно ожидание Consume (до `PollIntervalMs`), запись в БД (подключение и три команды: начало транзакции, вставка, фиксация; `CommandTimeout` Npgsql действует на каждую отдельно - по документации, замер 10.16; умолчание `CommandTimeoutSeconds` = 10, итого 15 + 30 = 45 < 60) и публикация в rejected - блокирующие ожидания без отметки heartbeat;
отметка ставится в начале итерации, после Consume (с учётом дожидания периода опроса) и после записи/публикации, поэтому длительности
не суммируются и худший разрыв - максимум из трёх. Валидатор проверяет только три перечисленных ожидания. Вне правила и без проверки при старте остаются `Commit` offset (без предела, 10.9) и `IWriteFailureHandler` (10.14): на них liveness может стать 503 `loop_stalled`. Нарушение самого правила - отказ запуска. Шаблон `deploy/data-saver/.env.example` с заглушками в репозитории; `.env` в `.gitignore`.

### D-12. Тестовая стратегия

- **Unit (без контейнеров)**: батчер (размер/время, `FakeTimeProvider`), политика backoff, трекер offset (включая
  отбракованные), классификатор ошибок записи, разбор и валидация (все примеры из `kafka-event-format.md` как valid-кейсы),
  конечный автомат цикла на fake-портах (нет commit до успеха записи; pause/resume; flush при shutdown).
- **Интеграционные (Testcontainers)**: `apache/kafka` (KRaft, как на dev) и `timescale/timescaledb:*-pg16` (как в B3);
  схема применяется теми же файлами `db/init` и `db/migrations`, что и в средах (ADR-0004); приложение подключается ролью
  `ktm_app` - тем самым проверяется достаточность прав `SELECT, INSERT`. Топик и группа уникальны на тест
  (`ktm.events.raw.t<guid>` через `Kafka__Topic`), контейнеры общие на коллекцию. Сценарии 1:1 с критериями приёмки
  (см. `tasks.md`, группа 7). Тесты запускаются локально (Docker на машине есть); вопрос запуска в CI открыт отдельно.
- **Сбой БД**: остановка/запуск контейнера Postgres с **фиксированным host-портом** (иначе после рестарта порт меняется);
  длительность простоя параметризуется: 15 с в обычном прогоне, 2 минуты - в категории `Long`.
- **Замер**: категория `Perf` (исключена из обычного прогона), результат в `docs/test-protocols/`.
- Запуск - по `$run-tests`; фильтр обычного прогона `Category!=Perf&Category!=Long`.

## 3. Альтернативы

- **Запись по одному событию / EF Core `SaveChanges`**: на 500 соб/с с 4 индексами и hypertable упирается в число
  round-trip и транзакций; обработка конфликта строк по одной. Отклонено (D-2, см. «EF Core: оценка»).
- **Автокоммит offset**: при сбое записи после автокоммита событие потеряно. Нарушает «ничего не терять». Отклонено.
- **Коммит offset до записи (at-most-once)**: то же. Отклонено.
- **Exactly-once Kafka transactions / хранение offset в БД**: обязательны только при неидемпотентной записи; здесь
  идемпотентность гарантирует схема, а offset в БД добавил бы вторую точку правды. Отклонено.
- **Блокирующий retry без `Pause` и опроса**: консьюмер вылетает из группы по `max.poll.interval.ms`, начинается шторм
  ребалансировок. Отклонено.
- **Пауза без продолжения опроса (`Thread.Sleep`)**: то же.
- **Параллельная запись по партициям внутри экземпляра**: усложняет учёт offset; отложено до замера.
- **Выбрасывать сообщения после N неудачных попыток записи**: нарушает «ничего не терять»; допустимо только через C6 и только для
  класса Data.
- **Попытка исправить `correction_event_id` в приложении (SELECT затем INSERT отдельными командами)**: гонка между
  экземплярами; единый `INSERT ... SELECT` в транзакции проще и атомарнее.

## 4. Последствия

- Журнал в `ktm.events` содержит и корректирующие строки как обычные события: уровень 2 обязан определять действующую
  версию через `event_corrections` и не считать исходное событие и исправление дважды (риск R-4, передать в ЧТЗ уровня 2).
- Идемпотентность держится на неизменности `occurredAt` при повторной отправке адаптером (G-6).
- `ktm_app` достаточно `SELECT, INSERT`; никаких `UPDATE` в запросах Data Saver нет (проверяется интеграционным тестом
  под этой ролью).
- Уровни не нарушаются: Data Saver не читает правил и оценок; привязка к сотруднику не выполняется (уровень 1,
  Процессор привязки - отдельная задача).
- В Data Saver не попадают и не сохраняются видео/биометрия: `payload` сохраняется как получено, проверка отсутствия таких
  данных остаётся на контракте и на адаптере (Data Saver в payload не заглядывает, кроме предела размера тела и проверок совместимости с jsonb).

## 6. Риски

- **R-1.** Один брокер, `replication.factor=1`, хранение 7 суток: потеря диска брокера теряет неприёмные события; простой БД
  дольше 7 суток теряет хвост. Нужен алерт на лаг группы `ktm-data-saver` (мониторинг `dev-infra`). Закрывается в прод-контуре
  (3 брокера, `add-infrastructure-topology`).
- **R-2.** Пропускная способность на dev (БД и Kafka на одной ВМ `dev-data`, 4 vCPU) НФТ не подтверждает
  (`add-infrastructure-topology`: dev исключён из приёмки НФТ). Замер на dev - ориентир, приёмочный - на целевом контуре.
- **R-3.** Kafka на dev - PLAINTEXT без аутентификации; `docs/07` п. 7.3 требует шифрование каналов - в прод-контуре.
  Конфигурация Data Saver поддерживает SASL/TLS, включить - работа инфраструктуры.
- **R-4.** Двойной учёт исходного и исправляющего события на уровне 2 (см. раздел 4).
- **R-5.** Отсутствие проверки допустимого окна `occurredAt` (G-8) до C5.
- **R-6.** Скрипт миграции пишется в этом change по DDL черновика (`Схема_БД_ER.md` п. 9, ADR-0004); расхождение с замыслом
  владельца схемы снимается ревью и тестами идемпотентности и прав (`tasks.md` 4A.2). Единый файл `db/migrations/` - источник
  истины и для сред, и для тестов.
