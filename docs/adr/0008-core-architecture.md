# ADR-0008. Архитектура ядра и каркас solution

- **Статус** — принят. Лид проекта утвердил ADR 2026-11-27 сообщением «Утверждаю».
- **Дата** — 2026-11-27.
- **Область** — CORE-01, `src/Ktm/Ktm.sln`, композиция хостов, границы модулей и доступ к данным.

## Контекст

Data Saver уже записывает события в PostgreSQL и использует Kafka для приёма, отбраковки, DLQ и повторной обработки. В solution есть отдельный шаблон `Ktm.Api`. Ядру нужны общие границы для REST, справочников, авторизации, привязки событий и интерпретации. По ТЗ Data Saver и привязка относятся к уровню 1, интерпретация и расчёт — к уровню 2.

Основания решения — [дизайн CORE-01](../../openspec/changes/add-core-architecture/design.md), [архитектура по ТЗ](../03-архитектура.md), [ролевая модель](../04-ролевая-модель.md) и [нефункциональные требования](../07-нефункциональные-требования.md).

## Решение

### Хосты и развёртывание

- `Ktm.Api` — отдельный процесс публичного REST API. Он подключает прикладные сервисы для HTTP и не запускает фоновые обработчики.
- `Ktm.HostedServices` — единый исполняемый проект для Data Saver, Binding и Interpretation. Конфигурация выбирает обработчики при старте. Отключённые модули не регистрируют зависимости, не валидируют собственные настройки и не запускают клиентов.
- Действующий Compose-сервис `data-saver` выбирает только Data Saver. Сохраняются путь и имя сервиса, разовая задача `migrate` как условие старта, роль `ktm_app`, параметры `DataSaver__*`, служебные HTTP-маршруты health и повторной обработки, её UI и действующие контракты Kafka. Локально можно включить все три модуля или запускать экземпляры того же образа с разными наборами обработчиков.

### Модули и зависимости

Для каждого модуля используются сборки `Ktm.<Module>.Application` и `Ktm.<Module>.Infrastructure`. `Ktm.DataSaver.Core` переходит в `Ktm.DataSaver.Application`. Входная точка прежнего `Ktm.DataSaver` переносится в `Ktm.HostedServices`.

| Модуль | Ответственность |
|---|---|
| DataSaver | Приём, техническая отбраковка, запись событий и корректировок. |
| Directory | Справочники и производственные роли сотрудников. |
| Identity | Учётные записи, роли доступа, назначения и прикладные порты аутентификации и областей видимости. |
| Binding | Привязки событий и записи обогащения. |
| Interpretation | Бизнес-правила интерпретации, расчёты и производные результаты. |

Зависимости направлены от хостов к Infrastructure и Application компонуемых модулей. Infrastructure реализует порты своего Application и работает с опубликованными контрактами данных. Application использует `Ktm.Shared` и нейтральные абстракции. Ссылки Application на другие модули, ASP.NET Core, EF Core, Npgsql и Kafka запрещены. `Ktm.Shared` содержит общие типы, соглашения о времени, ошибки и контракты опций и не зависит от модулей, хостинга и хранения. Привязка и проверка конфигурации и преобразование ошибок в HTTP-ответы остаются на границах.

### EventStore и порядок доставки

Data Saver записывает неизменяемые `ktm.events` и связанные корректировки. Binding получает из EventStore зарегистрированные события, читает справочные данные через собственный порт и пишет отдельные обогащения со ссылками на журнал. Interpretation читает через свой порт EventStore опубликованные обогащения и связанные исходные события и сохраняет результаты. Каждый обработчик ведёт свой сохранённый курсор. Межмодульный обмен идёт через опубликованные данные и порты, без прямых вызовов между обработчиками. Kafka подключает только Data Saver.

Для последующей реализации предусмотрен ссылочный поток с числовой позицией и ключом журнала `(event_id, occurred_at)`. Watermark по `received_at` пропускает поздно зафиксированные записи. Обычная sequence также выделяет значения до фиксации транзакции.

1. В транзакции Data Saver после вставки событий и корректировок публикуются ссылки только на фактически добавленные события. Позиции выделяются диапазоном на пачку через транзакционный счётчик под блокировкой строки, удерживаемой до фиксации. Более высокая позиция становится видимой после публикации предыдущих.
2. Binding и Interpretation читают ограниченные страницы по позиции. Обработчик фиксирует результат и сдвиг своего курсора в одной транзакции. Binding публикует ссылку на сохранённое обогащение в той же транзакции с эквивалентным порядком для входа Interpretation. Для одного курсора в момент времени работает одна транзакция.
3. Позиция задаёт порядок доставки, а `occurred_at` — бизнес-время. Повторы, поздние корректировки, отставание и восстановление проверяются при реализации обработчиков.

Открытый вопрос для изменения EventStore — обработать весь накопленный журнал, начать с согласованной границы или выполнить управляемый перенос по диапазонам. Реализация должна покрыть записи, поступающие во время переключения.

### База данных и миграции

- Хосты используют общую PostgreSQL 16 с TimescaleDB и схемой `ktm`. Для CRUD-конфигурации используется EF Core с Npgsql. Модуль с CRUD-моделью регистрирует scoped `DbContext` в своей Infrastructure, явно отображает собственные таблицы, схему, ключи и типы времени. Контекст живёт в области HTTP-запроса или операции. `NpgsqlDataSource` переиспользуется для данного набора настроек подключения и роли. Для горячего пути Data Saver и будущих пакетных чтений потока применяется прямой Npgsql.
- DDL выполняет `ktm_migrator` в разовой задаче по [ADR-0004](0004-db-migrations.md). Миграции — идемпотентные SQL-файлы в `db/migrations` с первого свободного номера, сейчас `V006`. Хосты не вызывают EF-миграции или автоматическое создание схемы. Применённые скрипты сохраняются.
- Для API, Binding и Interpretation администратор подготавливает отдельные прикладные роли и выдаёт гранты по таблицам и операциям. Потребители получают только чтение опубликованных данных. Запись ограничена данными, которыми владеет компонент. `ktm_app` сохраняет права Data Saver. Существующие default privileges выдают ему `SELECT, INSERT` на новые таблицы, поэтому лишние права нужно отзывать в той же миграции или изменить default grant с проверкой прежних прав.

### Конфигурация и общие правила

- Настройки приходят из окружения с `__` между секциями. В `appsettings.json` допустимы несекретные значения по умолчанию. `ValidateOnStart` проверяет хост и включённые модули до начала работы. Новый секрет задаётся значением или связанной переменной `*_FILE`. Если указаны оба источника, отсутствует обязательная настройка или файл недоступен, запуск завершается с ненулевым кодом и диагностикой без значений секретов. Существующие ключи и правила Data Saver, включая `PasswordFile`, сохраняются.
- Используются `TimeProvider` и UTC `DateTimeOffset`, HTTP передаёт UTC с `Z`. Чтение и запись временных полей журнала явно отображают UTC в `timestamp without time zone` по [ADR-0007](0007-utc-timestamp-storage.md). Идентификаторы записей — UUID.
- Структурные логи указывают компонент и операцию. Метрики через `System.Diagnostics.Metrics` используют метки с ограниченным числом значений. Для будущих обработчиков измеряются очередь, отставание, время обработки и повторы. Диагностика исключает секреты и тела событий. Публичный REST преобразует прикладные ошибки в Problem Details с идентификатором трассировки.
- Авторизация ограничивает выборки по роли, подразделению, зоне и полномочиям. Действия подлежат аудиту. Интеграция с корпоративным AD/LDAP при наличии и MFA для критических ролей относятся к реализации Identity. Выбор корпоративного поставщика остаётся открытым.

## Альтернативы

- Общий процесс API и фоновой обработки связывает перезапуски и зависимости. Исполняемый проект на каждый обработчик увеличивает число точек композиции и артефактов поставки.
- Общий `DbContext` и единая прикладная роль увеличивают связанность модулей и объединяют их доступ. Модульные контексты и отдельные права сохраняют границы при общем PostgreSQL.
- Inbox с поэлементным подтверждением устраняет общий счётчик, но меняет контракт курсора. Kafka для Binding и Interpretation создаёт отдельный транспортный контракт доступности журнала и обогащений.

## Последствия и приёмка

- Этот ADR уточняет раздел о структуре solution в [ADR-0001](0001-backend-stack.md). Прежние имена и граф `Ktm.DataSaver` и `Ktm.DataSaver.Core` заменяются композициями и ссылками, описанными выше. Указание об общей роли `ktm_app` для Data Saver и публичного API заменяется минимальными ролями по компонентам. EF Core используется для CRUD без применения EF-миграций. .NET, центральные версии пакетов, xUnit v2 и технологический стек сохраняются.
- CORE-01 поставляет каркас. Циклы обработки Binding и Interpretation, таблицы потоков и курсоров, перенос истории, Identity и токены, CRUD-эндпоинты и EmployeeMatcher реализуются последующими изменениями. При реализации потока нужно подтвердить 500 событий/с, сквозную задержку до пяти минут, корректность при поздней фиксации, откате и перезапуске.
- Приёмка требует утверждения ADR лидом проекта, сборки всего solution с `TreatWarningsAsErrors`, регрессионного прогона Data Saver и запуска проектов `Ktm.Binding.Tests`, `Ktm.Interpretation.Tests`, `Ktm.Directory.Tests`, `Ktm.Identity.Tests` и `Ktm.Api.IntegrationTests`. Reviewer сверяет прямые и транзитивные ссылки с этим ADR.
- `src/README.md` описывает сборку, тесты и запуск через локальный Docker Compose с PostgreSQL/TimescaleDB и Kafka KRaft. Подготовка ролей и расширения предшествует разовой миграции, а хосты запускаются после её успешного завершения. Проверка проводится на свежей БД под прикладными ролями и включает действующий режим Data Saver.
