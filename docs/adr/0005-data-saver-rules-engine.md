## 0. Что изменилось в редакции 3 и почему

Лид пересмотрел решение ред. 2: источник правил - **таблица БД в урезанном варианте** («как полноценная, но без обвязки»), а не
JSON-файл. Причины: трудоёмкость сопоставима (одна миграция и один `SELECT` против файлового источника, watcher-а, доставки
каталога в контейнер, встроенного набора и режимов запуска без файла), а доставка файла в контейнер и «запасной режим» при его
отсутствии - отдельный источник эксплуатационных проблем (inotify в Docker, атомарная запись, расхождение копий); БД у сервиса уже
есть, права и миграции отработаны (ADR-0004).

| Ред. 2 (JSON-файл) | Ред. 3 (таблица БД, урезанная) |
|---|---|
| Файл правил, схема файла, `FileRuleSource`, `FileSystemWatcher`, каталог в compose, `OnStartupError`, встроенный набор, `fallback_active` | **Убраны.** Правила - строки таблицы `ktm.rejection_rules`; `NpgsqlRuleSource` читает её опросом |
| Схема `docs/api/rejection-rules.schema.json` описывает файл | Схема описывает **только поле `condition`**: `docs/api/rejection-condition.schema.json`; структура правила - колонки таблицы |
| Нет миграций | Одна миграция схемы `V002__rejection_rules.sql` (таблица, CHECK-и, права: `ktm_app` только `SELECT`) и отдельная `V003__rejection_rules_examples.sql` с выключенными примерами |
| Хэш файла как ревизия | Хэш содержимого выборки как ревизия (непрозрачная строка порта) |
| Старт без файла - встроенный набор | Пустая таблица - штатно (пустой набор, Info); БД недоступна на первой загрузке - повтор с backoff, Kafka не читается, не готов; код 78 - на неверные настройки и ошибку доступа к таблице (`42P01`/`42501`) |
| «По команде»: watcher | **Отступление:** в первой итерации только опрос (по умолчанию раз в 60 с, 5..3600); команда отложена, шов `IRuleChangeSignal` оставлен под будущий `NOTIFY` (п. 2.10, 5) |
| Аудит: лог и git файла | Аудита нет: **временное отступление от `docs/04` п. 4.2/4.4, принято лидом**; триггер возврата обвязки БД (аудит, `NOTIFY`, триггер версии) - первое реальное правило либо потребность в аудите (приложение A) |

Неизменно с ред. 2 (не пересматривается): нотация условий в стиле JsonLogic (`and`/`or`/`!`/`var`, `==`, `!=`, `<`, `<=`, `>`, `>=`,
диапазон - трёхаргументный `<=`, обе границы включительно) и собственный вычислитель без библиотеки (п. 2.2, 2.4); строгая семантика
типов, отсутствующее поле не срабатывает, `!=` - строгое отрицание `==` (п. 2.6); отложенные операции (`in`, `missing`-подобный,
сравнение без учёта регистра; регэксп - см. раздел 0.1) с реестром операций; порты `IRuleSource`/`IRuleChangeSignal`; контракт `rejected` (п. 2.9); метрики
(п. 2.12); два уровня ошибок (ошибочное правило выпадает одно; сбой чтения источника - последний валидный снимок); `not` (`!`) оставлен.

## 0.1. Дополнение 1: оператор `regex` (решение лида, 2026-11-23)

Лид решил реализовать регулярное выражение в составе этого change (раньше - «отложено», п. 2.7 ред. 3), а не отдельным change.
Синтаксис задан лидом: бинарная форма как у сравнений, `{"regex": [{"var": "поле"}, "шаблон"]}`. Критерии готовности лида: работают
все операции, включая регэксп; на каждую операцию - тест; ошибочное правило (в том числе невалидный регэксп) не ломает сервис, не
применяется, пишется в лог (Error, `RuleId`, причина, без содержимого сообщений). Что решено при проработке (подробно - п. 2.7):

| Вопрос | Решение | Где |
|---|---|---|
| Сопоставление | по части строки (`Regex.IsMatch`); якоря задаёт автор; поле не строка или отсутствует - ложь | п. 2.6, 2.7 |
| Движок | BCL `System.Text.RegularExpressions` (встроенный, отдельной лицензии и пакета нет), `NonBacktracking \| CultureInvariant`, компиляция при загрузке правила | п. 2.7 |
| Невалидный шаблон / неподдерживаемая конструкция | ошибка загрузки правила (правило выпадает, остальные работают, Error с `RuleId`) | п. 2.7 |
| Без учёта регистра | **нового оператора и флага нет**: встроенный в шаблон `(?i)` (проверено на `NonBacktracking`); сравнение `==`/`in` без учёта регистра по-прежнему отложено | п. 2.7 |
| Лимиты | шаблон 1..512 символов; до 8 regex-узлов на правило; до `MaxRegexNodes` (64) на набор; узел `regex` считается и в лимите 64 узлов правила | п. 2.7, 2.10 |
| Таймаут совпадения | `RegexTimeoutMs` (**200 мс**, 1..1000) как второй рубеж; **не «не совпало»**: сообщение **отбраковывается** (в `ktm.events.rejected`) с системным кодом причины `rule_eval_timeout`, независимо от формы правила (с `!` и без); остальные правила не вычисляются. Решение лида 2026-11-23 вместо варианта «правило на сообщении не применяется, сообщение идёт в журнал» | п. 2.7 |
| Системный код причины | `rule_eval_timeout` принадлежит системе, как три кода формата: автор правила использовать его не может (отказ в загрузчике; CHECK `V002` не меняется - файл уже применён на dev) | п. 2.3, 2.7, 2.9 |
| Наблюдаемость отказа | `rules.eval_errors{kind="regex_timeout", rule_id}` на каждый таймаут и Warning не чаще раза в 10 минут на правило; без отдельного наблюдателя, через обычный путь отбраковки (`RejectionInfo`) | п. 2.7, 2.12 |
| Миграция примера | отдельный новый файл `V004__rejection_rules_examples_regex.sql` (`V003` уже выкачена на dev и не правится) | п. 2.3 |

## 1. Контекст

Адаптеры могут прислать формально корректное сообщение, которое по смыслу мусор: тестовые события, записи без нужных данных,
служебные значения. Критерии у каждого источника свои и меняются, поэтому зашивать их в код нельзя (инвариант «правила
настраиваются через API/хранилище»). Журнал неизменяем: попавшее в `ktm.events` удалить нельзя, поэтому отбраковка обязана
происходить до записи, а отбракованное не должно теряться (`docs/05` п. 5.1: ошибочные данные - в лог и в `rejected`).

Что уже есть в `add-data-saver-core` (архив `openspec/changes/archive/2026-11-22-add-data-saver-core`; проверено по коду, не по документам):

- Конвейер `FormatStage` (JSON, `schemaVersion`, JSON Schema v1 с обязательными полями, размер, jsonb-совместимость, UTC) ->
  `IIngestionStage[]` (сейчас только `EventValidationStage`/C5, принимает всё) -> пачка -> запись + публикация `rejected` -> commit.
- `RejectionInfo(Kind, Reason, Detail, RuleId, TargetTopic)`; `RejectionKind.Rule` зарезервирован; публикатор пишет заголовки
  `ktm-reject-reason`, `ktm-reject-detail`, `ktm-source-*` и необязательный `ktm-reject-rule-id` (усечение до 128).
- Отбраковка по формату (пункт 4 задачи) реализована полностью: `malformed_json`, `unknown_schema_version`, `invalid_schema`,
  в `rejected` с кодом причины. Дельта этого change по пункту 4 - только порядок стадий и документация (п. 2.11).
- Метрика `ktm.datasaver.messages.rejected{reason}`; `ObservedRejectionPublisher` логирует каждую отбраковку на уровне Error.
- `ISchemaValidator` (`Core/Decoding`, библиотека `LateApexEarlySpeed.Json.Schema`, BSD-3-Clause, ADR-0001) - проверка JSON Schema
  2020-12 за интерфейсом; сейчас привязан к схеме события.
- Опции `DataSaver__*` с проверкой при старте, `StartupErrors` (код выхода 78 на конфигурационные ошибки).
- Расширений БД для правил нет; `ktm_app` имеет по умолчанию `SELECT, INSERT` на новые таблицы схемы `ktm`
  (`db/init/001_roles_and_extension.sql`, `ALTER DEFAULT PRIVILEGES`). Явный `GRANT USAGE ON SCHEMA public TO ktm_migrator`
  (PR #10) на этот ADR не влияет: `V002`/`V003` не используют объекты схемы `public`.
- Миграции накатывает контейнер `migrate` (ADR-0004 п. 5, `openspec/specs/data-saver/schema-migration`): `V002`/`V003`
  обязаны соответствовать шаблону имени, не содержать метакоманд `psql` и быть идемпотентными; в `db/migrations` сейчас только
  `V001`, номера `V002`/`V003` свободны. Порядок выкладки и проверки на dev - `docs/test-protocols/data-saver-deployment-dev.md`.

Границы уровней (ADR-0003 п. 1): правила Data Saver - только правила качества данных над самим сообщением. Ссылка на
сотрудника, роль, смену, оценку недопустима: язык условий оперирует исключительно полями сообщения, обращений к БД и
внешним данным в нём нет.

## 2. Решение

### 2.1. Где живёт код и шов `IRuleSource`

- `Ktm.DataSaver.Core/Rules` - модель правила (`RuleDefinition`), разбор и компиляция условия (`System.Text.Json` из BCL; реестр
  операций - новая операция добавляется классом и регистрацией, не правкой узлов и стадии), снимок набора правил,
  `RuleRejectionStage : IIngestionStage`, порты `IRuleSource` и `IRuleChangeSignal`. Core не знает Kafka, Npgsql и файловую
  систему (ADR-0001, граница сборок).
- `Ktm.DataSaver.Infrastructure/Postgres` - `NpgsqlRuleSource` (чтение таблицы, хэш выборки как ревизия); метрики правил - в
  `DataSaverMetrics`.
- `Ktm.DataSaver/Hosting` - `RuleRefreshService` (первая загрузка и фоновое обновление снимка по таймеру; не знает, какой источник
  за портом). Решение лида: остаётся в Host, а не в Infrastructure, потому что использует `StartupErrors` (код выхода 78;
  `internal` в `Ktm.DataSaver`, `Ktm.DataSaver/StartupErrors.cs`) и относится к общему хост-слою (порядок регистрации
  hosted-сервисов, запуск цикла приёма после первой загрузки; `DataSaverWorker` - `public sealed class` того же проекта);
  вынос в Infrastructure потребовал бы открыть `StartupErrors` наружу ради одного сервиса.
- Новые NuGet-пакеты не нужны: BCL (`System.Text.Json`, `System.Security.Cryptography`, `System.Text.RegularExpressions` - Доп. 1)
  и уже подключённые Npgsql и `LateApexEarlySpeed.Json.Schema` (последняя - только в тестах сверки схемы условия и компилятора, п. 2.13).
  Лицензия `System.Text.RegularExpressions`: часть среды выполнения .NET (MIT), отдельного пакета нет; библиотека уже используется
  в `ConditionCompiler` (проверка `rule_id`/`reason_code`).
- Доп. 1: в `Core/Rules` добавляются `RegexOperator` (оператор реестра), `RegexPolicy` (таймаут, пределы) и внутреннее исключение
  `RuleEvaluationAbortedException` (вид отказа и предел таймаута): лист бросает его, `And`/`Or`/`Not` пропускают, стадия перехватывает
  **на уровне правила** и возвращает обычную отбраковку (п. 2.7). Отдельного порта-наблюдателя нет: стадия остаётся чистой функцией без
  побочных эффектов (ADR-0003 п. 2.1 не меняется), метрика и лог отказа выдаются там же, где остальные метрики и логи отбраковки правилом, -
  в `ObservedRejectionPublisher` (`Infrastructure/Observability`) после подтверждённой публикации. Публичные типы `IngestionVerdict`,
  `RejectionInfo`, `RejectionKind` не меняются.

**Порт - шов под отложенную обвязку БД.**

```
interface IRuleSource {
    // previousRevision - ревизия последнего применённого набора (null на первой загрузке).
    // Возвращает Unchanged, если источник может дёшево доказать отсутствие изменений, либо новый набор.
    // Бросает RuleSourceException(kind: Unavailable | Invalid) при невозможности получить пригодный набор.
    ValueTask<RuleSourceResult> ReadAsync(string? previousRevision, CancellationToken ct);
}
record RuleSourceResult(bool Unchanged, string Revision, IReadOnlyList<RuleDefinition> Rules, IReadOnlyList<RuleProblem> Problems);
record RuleDefinition(string Id, string Name, string? Description, string? Source /* null = все */, bool Enabled,
                      int Priority, int Version, string ReasonCode, JsonElement Condition);
record RuleProblem(string? RuleId, string Location, string Message);   // ошибка отдельного правила, найденная источником
interface IRuleChangeSignal { IAsyncEnumerable<RuleChangeHint> WatchAsync(CancellationToken ct); }   // ускоритель, необязателен
```

- `RuleDefinition` не содержит имён колонок: условие - `JsonElement`, поля - в терминах модели. Движок (компилятор условий,
  снимок, стадия, метрики, вывод в `rejected`) знает только `RuleDefinition`; `NpgsqlRuleSource` отображает колонки `rule_id` ->
  `Id`, `source = '*'` -> `Source = null` и т. д.
- Ревизия - непрозрачная строка (для БД - SHA-256 упорядоченной выборки); движок лишь сравнивает её на равенство.
- Невозможность прочитать источник - `RuleSourceException`; ошибка отдельной строки (не разобралась) - `RuleProblem`: поведение
  «ошибочное правило не применяется, остальные работают» одинаково для любого источника.
- `IRuleChangeSignal` в первой итерации **не реализуется**: порт заведён, чтобы позже подключить `LISTEN/NOTIFY` (приложение A)
  без правок движка; `RuleRefreshService` принимает необязательный сигнал и ведёт общий `Channel` с таймером (когда реализации нет,
  работает только таймер).

Стадия остаётся чистой функцией без побочных эффектов (ADR-0003 п. 2.1): читает текущий снимок из памяти (`volatile`-ссылка,
замена целиком), в БД не ходит, тело не меняет. Публикацию, лог и метрики по вердикту делает существующий путь
(`ObservedRejectionPublisher`), поэтому offset отбракованного продвигается так же, как у записанного.

### 2.2. Формат условий: собственный DSL (A) против JsonLogic (B) и обёртки над ним (C)

Лид попросил оценить JsonLogic (jsonlogic.com) как формат и движок; затем сузил набор операций первой итерации до
`<`, `>`, `<=`, `>=`, `==`, `!=`, И, ИЛИ и `between` (п. 2.4). Сравнение переделано под суженный набор: ниже оценён именно он, а не
полный список из первоначальной задачи. Лицензии бинарных релизов проверены по nuspec на nuget.org 2026-11-23 (не по README).

**Соответствие JsonLogic требованиям первой итерации.**

| Требование | JsonLogic (jsonlogic.com/operations.html) | Вывод |
|---|---|---|
| `<`, `>`, `<=`, `>=` | есть, но операторы приводят типы; в эталонной реализации (`json-logic-js`) это операторы JS: отсутствующее поле (`var` -> `null`) в `null < 0.5` равно 0 и даёт **истину**; в .NET-библиотеках поведение зависит от реализации | правило «поле отсутствует - не срабатывает» нарушается; нужна проверка типов и `null` перед сравнением, то есть своя семантика |
| `==`, `!=` | `==`/`!=` приводят типы (`1 == "1"`), строгие - `===`/`!==` | нужен запрет нестрогих либо переопределение; запрос лида - именно `==`/`!=` без приведения |
| `between` | есть как три аргумента: `{"<": [a, x, b]}` - границы **исключающие**, `{"<=": [a, x, b]}` - **включающие** | покрывает; решение лида (включающие) = тройной `<=`; но запись `[a, x, b]` с переменной в середине нечитаема, схема её не проверит |
| И, ИЛИ, НЕ | `and`, `or`, `!`; `and`/`or` возвращают **значение** последнего вычисленного операнда, а не булево | подходит с оговоркой: итог нужно приводить к булеву по «истинности» JsonLogic (`0`, `""`, `[]` ложны) |
| вложенные поля | `var` с точкой и числовыми индексами | подходит; но путь у `var` может быть **выражением** (`{"var": {"cat": [...]}}`), первый сегмент статически не проверить |
| даты | операторов дат нет; строки сравниваются по правилам реализации (лексикографически или через приведение к числу -> `NaN`) | сравнение по моменту времени, обязательная зона - своё |
| ограничение выразительности | есть арифметика, `map`/`filter`/`reduce`, `cat`, `substr`, `if`, `log` | нужен белый список операторов на загрузке, иначе правило вычислимо произвольной сложности |

**Библиотеки .NET** (nuspec, 2026-11-23):

| Пакет | Лицензия бинарного релиза | Поддержка | Совместимость с `net10.0` | Замечания | Решение |
|---|---|---|---|---|---|

**Три варианта (пересчитано под суженный набор и решения лида).**

- **(A) Собственный DSL с именованными полями** (`{"field": ..., "op": ..., "value": ...}`). Строгая семантика, точная JSON Schema,
  без зависимостей. Минус: нестандартная запись.
- **(B) JsonLogic как есть (библиотека).** Синтаксически покрывает все операции, но: `null < 0.5` истинно (отсутствующее поле
  отбраковывает событие - необратимо), `==` нестрогое, даты не определены, пути динамические, белого списка операторов нет. Из
  библиотек по лицензии допустима одна (Corvus), и она приносит чужой JSON-стек. **Как есть - не подходит.**
- **(C) JsonLogic-нотация + собственные валидатор и вычислитель, без библиотеки.** Запись операторов и `var` как в стандарте,
  но принимается только белый список операторов и форм, проверяются пути, типы, лимиты; вычисление строгое.

**Решение лида (2026-11-23, ред. 2; в ред. 3 не пересматривается): C без библиотеки.** Конструктора условий на фронте не будет, поэтому совместимость нужна не ради
внешних инструментов, а чтобы при желании можно было перейти на библиотеку; пересчёт рекомендации под это решение: затраты
почти равны A (валидатор и вычислитель нужны в любом случае), запись становится стандартной, схема условия остаётся достаточно
точной (форма операндов проверяется через `prefixItems`/`contains`). Принятые ограничения: (1) совместимость по **записи**, а не
по семантике: наши `==`, `!=`, `<`... строже стандартных (п. 2.4), поэтому при переходе на библиотеку сравнения придётся
переопределить; (2) допускается только подмножество стандарта; (3) запись длиннее, чем у A.

**Триггер пересмотра:** арифметика/функции в условиях, либо решение перейти на библиотеку (тогда отдельный ADR: выбор библиотеки
по лицензии, переопределение сравнений, перенос проверок).

### 2.3. Хранилище правил: таблица `ktm.rejection_rules` (урезанная)

Условие - **JSONB-дерево** (п. 2.4), остальное - обычные колонки. Файлы миграций (ADR-0004; правила файлов: идемпотентно, без
метакоманд `psql`, предусловие `current_user = 'ktm_migrator'` как в `V001`, применяются `ktm_migrator`):

- `db/migrations/V002__rejection_rules.sql` - таблица, CHECK-и, права;
- `db/migrations/V004__rejection_rules_examples_regex.sql` (Доп. 1) - два выключенных примера на `regex` для `skud`
  (`skud-test-device`: `deviceId` ~ `^TEST-`; `skud-blank-person`: `externalPersonId` пустая или из пробелов). **Новый файл, а не правка
  `V003`**: `V003` уже применена на dev-стенде, правка применённого файла миграции запрещена (ADR-0004: «уже применённый файл не правится:
  изменение схемы - новый файл `V00N`»). Та же форма, что у `V003`: `INSERT ... ON CONFLICT (rule_id) DO NOTHING`, предусловие `current_user = 'ktm_migrator'`,
  одна строка `condition` на правило (формат строки читает тест примеров); следствия те же (удалённый пример вернётся при `migrate`:
  выключать, не удалять). Номер `V004` ранее резервировался под возврат обвязки БД (приложение A) - та миграция получит следующий
  свободный номер.
- `db/migrations/V003__rejection_rules_examples.sql` - выключенные примеры для `skud`, `cv`, `1c-do` и общего. Отдельный файл
  (решение teamlead): изменение набора примеров не правит файл со схемой; метатест «каждый `V*.sql` дважды» (ADR-0004 п. 5)
  проходит благодаря `INSERT ... ON CONFLICT (rule_id) DO NOTHING`. Следствие: **удалённый пример вернётся при следующем
  прогоне `migrate`**, поэтому правило выключают (`enabled = false`), а не удаляют (описано в `docs/manuals/rules-engine.md`); изменённые
  вручную примеры повторный прогон не затирает.

```sql
CREATE TABLE IF NOT EXISTS ktm.rejection_rules (
    rule_id      text    NOT NULL,
    name         text    NOT NULL,
    description  text    NULL,
    source       text    NOT NULL,                 -- 'skud' | 'cv' | '1c-do' | '*' (все источники); без умолчания
    condition    jsonb   NOT NULL,
    reason_code  text    NOT NULL,
    enabled      boolean NOT NULL,                 -- без умолчания: правило не включается молча
    priority     integer NOT NULL DEFAULT 100,
    version      integer NOT NULL DEFAULT 1,       -- простая колонка: при правке условия или причины её увеличивает автор
    CONSTRAINT pk_rejection_rules PRIMARY KEY (rule_id),
    CONSTRAINT ck_rejection_rules_id      CHECK (rule_id ~ '^[A-Za-z0-9._:-]{1,128}$'),   -- формат ktm-reject-rule-id
    CONSTRAINT ck_rejection_rules_name    CHECK (length(btrim(name)) BETWEEN 1 AND 200),
    CONSTRAINT ck_rejection_rules_source  CHECK (length(source) BETWEEN 1 AND 32),
    CONSTRAINT ck_rejection_rules_cond    CHECK (jsonb_typeof(condition) = 'object' AND octet_length(condition::text) <= 16384),
    CONSTRAINT ck_rejection_rules_reason  CHECK (reason_code ~ '^[a-z][a-z0-9_]{0,63}$'
                                                 AND reason_code NOT IN ('malformed_json','unknown_schema_version','invalid_schema')),
    CONSTRAINT ck_rejection_rules_prio    CHECK (priority BETWEEN 0 AND 10000),
    CONSTRAINT ck_rejection_rules_version CHECK (version BETWEEN 1 AND 1000000)
);
REVOKE ALL ON ktm.rejection_rules FROM PUBLIC, ktm_app;
GRANT SELECT ON ktm.rejection_rules TO ktm_app;
```

Обоснование:

- `rule_id` - текстовый слаг (`skud-test-event`), а не `uuid`/`serial`: он попадает в заголовок, лог и метрику, и человек должен
  узнавать его без справочника; формат совпадает с контрактом `ktm-reject-rule-id`.
- `source = '*'` - «все источники» (не `NULL`): ключ без умолчания, чтобы пропущенное значение не сделало правило общим.
  Допустимость значения (`skud`, `cv`, `1c-do`, `*`) проверяет загрузчик, а не БД: новый источник добавляется релизом Data Saver
  (kafka-event-format.md п. 3), CHECK в БД потребовал бы миграции на каждый источник.
- `enabled` без умолчания: опечатка или пропуск не должны включить необратимую отбраковку молча.
- `reason_code` - код для `ktm-reject-reason`; три кода формата зарезервированы CHECK-ом, чтобы правило не могло выдать брак за ошибку формата.
  **Доп. 1: четвёртый системный код `rule_eval_timeout`** (отказ вычисления по таймауту регэкспа, п. 2.7) тоже не принадлежит автору
  правил. `V002` уже применена на dev (протокол `docs/test-protocols/data-saver-rules-engine.md`), применённый файл не правится
  (ADR-0004), поэтому CHECK остаётся с тремя кодами, а запрет выполняет **загрузчик**: `ConditionCompiler` (проверка `reason_code`, куда уже
  входят три кода формата) добавляет `RejectReasons.RuleEvalTimeout` в перечень зарезервированных; правило с этим кодом ошибочно
  (Error с `RuleId`, не применяется, `rules.invalid`), как любое другое ошибочное. Ручной `INSERT` с этим кодом БД примет - как и любую
  ошибку условия (п. 5), - но он не вступит в действие, поэтому ни подмены системной причины, ни неоднозначности в `rejected` не возникает.
  Почему не миграция `ALTER ... CHECK`: DDL на живой таблице с `DROP`/`ADD CONSTRAINT` ради защиты, которую и так даёт загрузчик (единственный
  путь правила в действие); два источника правды о списке кодов (CHECK и код) расходились бы при каждом новом системном коде; правки идут под
  доверенной ролью `ktm_migrator`, а не от недоверенного ввода. Если потребуется защита в БД - отдельная миграция со следующим свободным
  номером (`ALTER TABLE ... DROP CONSTRAINT IF EXISTS ...; ADD CONSTRAINT ... NOT VALID`), без изменений движка. `rejection-condition.schema.json`
  описывает только условие, `reason_code` в схеме нет.
- `priority` - детерминированный порядок вычисления (п. 2.8); меньше = раньше.
- `version` - простая колонка (решение лида: без триггера): автор увеличивает её при правке условия или причины. Уходит в
  `ktm-reject-rule-version`. Мягкая защита: сервис пишет Warning, если содержимое правила изменилось, а `version` прежняя (п. 2.10).
- Лимит размера условия 16 КиБ - **логическая** длина (решение лида 2026-11-23): `octet_length(condition::text) <= 16384`, то есть
  байты нормализованного текста `jsonb` (после `:` и `,` стоит пробел, ключи упорядочены базой), а не размер хранения
  (`pg_column_size` не используется: он зависит от внутреннего представления и сжатия). Единица - UTF-8 байт при условии, что
  **база данных создана в кодировке UTF8** (требование развёртывания, `db/README.md`): `octet_length` считает байты в кодировке
  сервера. Решение: `octet_length` и требование UTF8. Альтернатива `convert_to(condition::text, 'UTF8')` допустима и снимает
  требование кодировки; рассматривается при необходимости (сейчас не вводим: при UTF8-базе результат тот же, а ограничение проще).
  Компилятор повторяет проверку: он считает UTF-8 байты `GetRawText()` переданного `JsonElement`. **Предусловие компилятора:**
  условие передано в jsonb-форме (текст из БД: так его и читает `NpgsqlRuleSource`, единственный производственный источник).
  Для произвольно отформатированного JSON (без пробелов после `:` и `,`, либо с лишними) мера компилятора может быть меньше
  или больше меры БД; такой ввод в производственном пути не встречается, а в тестах границу задают текстом в jsonb-форме.
  Рабочий смысл: БД - страховка и единственный авторитет по размеру при записи, компилятор - ошибка правила с понятным текстом
  при чтении (если CHECK снят или обойдён). Согласованность мер на ASCII-границе закреплена интеграционным тестом: условие ровно в 16384 байта
  jsonb-текста принимается и БД, и компилятором (`NpgsqlRuleSourceTests`). Для многобайтовых символов совпадение мер держится на
  UTF8-кодировке БД (требование развёртывания) и отдельным тестом не закреплено. Грамматику и лимиты глубины/узлов проверяет
  компилятор (второй источник правды в PL/pgSQL не заводим; CHECK проверяет только тип и размер текста условия).
- `created_at`/`updated_at`/`updated_by` не заводятся: без триггера они врали бы (отложено вместе с обвязкой, приложение A).

**JSON Schema условия** `docs/api/rejection-condition.schema.json` (`$id`: `https://ktm.local/schemas/rejection-condition/v1.json`)
описывает только `condition`: документ и подсказка для редактора. Рантайм-проверка условия - собственный компилятор; тесты сверяют
схему и компилятор на образцах (п. 2.13) и проверяют, что примеры `V003` проходят и то, и другое.

**Права.** Явно, а не полагаясь на `ALTER DEFAULT PRIVILEGES` (по умолчанию `ktm_app` получил бы `INSERT`): `REVOKE ALL FROM PUBLIC,
ktm_app`, затем `GRANT SELECT TO ktm_app`. Data Saver правила только читает: компрометация сервиса не позволяет изменить критерии
отбраковки. Менять правила может `ktm_migrator` (владелец схемы; пароль выдаётся только контейнеру `migrate`, см. compose) либо
роль, которую администратор выдаст отдельно; отдельную роль `db/init` не создаёт (init - ручной шаг суперпользователя). Это
операционный процесс до появления API (вопрос владельца таблицы при REST API на EF Core - отдельный ADR, ADR-0004 п. 3).

**Как меняют правила.** Обычными SQL-командами (`INSERT`, `UPDATE ... SET enabled = ..., version = version + 1`) под ролью с правами;
изменение вступает в силу не позже интервала опроса (п. 2.10). Готовые команды - `docs/manuals/rules-engine.md`.

### 2.4. Язык условий (запись в нотации JsonLogic, вычислитель собственный)

**Решения лида 2026-11-23.** (1) Первая итерация - только `<`, `>`, `<=`, `>=`, `==`, `!=`, И, ИЛИ, НЕ и `between`; остальные операции из
первоначальной задачи отложены, но из архитектуры не исключены. **Доп. 1 (тот же день): к ним добавлен `regex`** (п. 2.7). (2) Запись условия максимально совместима с JsonLogic
(операторы-ключи, `var` с точечным путём, `between` как трёхаргументный `<=`), чтобы при желании можно было перейти на
библиотеку; вычислитель и проверка - собственные (п. 2.2).

Узел условия - JSON-объект ровно с одним ключом-оператором.

| Узел | Запись | Смысл |
|---|---|---|
| И | `{"and": [узел, ...]}` | **логическое** И (не побитовое); истинно, если истинны все; до первого ложного; массив непустой |
| ИЛИ | `{"or": [узел, ...]}` | **логическое** ИЛИ (не побитовое); истинно, если истинен хотя бы один; до первого истинного; массив непустой |
| НЕ | `{"!": узел}` (допустимо `{"!": [узел]}`, как в JsonLogic) | отрицание результата узла |
| Сравнение | `{"<оп>": [операнд, операнд]}`, `<оп>` из `==`, `!=`, `<`, `<=`, `>`, `>=` | ровно два операнда: один `{"var": "путь"}`, другой - литерал; порядок любой (`[литерал, var]` читается зеркально: `{"<": [5, {"var":"x"}]}` = `x > 5`) |
| Диапазон | `{"<=": [нижняя, {"var": "путь"}, верхняя]}` | три операнда, `var` посередине: `нижняя <= поле <= верхняя`, **обе границы включительно** (решение лида) |
| Регулярное выражение (Доп. 1) | `{"regex": [{"var": "путь"}, "шаблон"]}` | ровно два операнда **в фиксированном порядке**: первый `var`, второй - строковый литерал-шаблон (1..512 символов); истинно, если шаблон находит совпадение **в любой части** строки-поля (`Regex.IsMatch`); подробно - п. 2.6, 2.7 |

Переменная - только `{"var": "путь"}` со строкой-путём (п. 2.5); форма с значением по умолчанию `{"var": ["путь", 0]}`, пустой путь
и путь-выражение - ошибка правила. Литерал - строка (до 1024 символов), число, `true`/`false`, `null` (для `==`/`!=`); для `<`, `<=`, `>`, `>=` и
границ диапазона - число либо строка-дата (п. 2.6); для `regex` - только непустая строка до 512 символов (п. 2.7). Любой другой ключ узла (`if`, `+`, `map`, `cat`, `in`, `missing`, `!!` и т. д.) -
ошибка правила «оператор не поддерживается»: неподдерживаемое не должно молча превращаться в «всегда ложь».
Трёхаргументные `<`, `>`, `>=` (в JsonLogic: `<` - исключающий диапазон) в первой итерации не принимаются: ошибка правила.
Исключающий диапазон записывается через `and` с `<` и `>`; «вне диапазона» - `or(<, >)` или `{"!": диапазон}` (отличие - п. 2.6).

Вложенность произвольная в пределах лимитов: глубина до 8, узлов-операторов до 64, длина условия до 16 КиБ (16384 байта нормализованного jsonb-текста `condition::text` в UTF8-базе; предусловие компилятора - jsonb-форма входа, п. 2.3).

Пример (видео: слишком низкая уверенность либо значение вне допустимого диапазона):

```json
{"or": [
  {"<": [{"var": "payload.confidence"}, 0.3]},
  {"and": [
    {"==": [{"var": "source"}, "cv"]},
    {">": [{"var": "payload.confidence"}, 1]}
  ]}
]}
```

**Строгость отличается от стандарта, запись - нет.** `==`/`!=` у нас ведут себя как `===`/`!==` JsonLogic (без приведения типов);
`<`, `<=`, `>`, `>=` на отсутствующем поле, `null` и несовпадении типов дают ложь (в эталонной реализации `null < 0.5` истинно).
Поэтому правило, перенесённое в стороннюю библиотеку, без переопределения сравнений может вести себя иначе: это известная цена
совместимости по записи (п. 2.2); при переходе на библиотеку (допустима лицензионно только `Corvus.Text.Json.JsonLogic`, где пользовательские
операторы приоритетнее встроенных) сравнения переопределяются нашими.

**«НЕ» - нужен ли.** Решение лида: оставить (`!`). Он выражает то, чего иначе нет: «поле отсутствует **или** вне порога»
(`{"!": {">=": [x, 0.5]}}` истинно и на отсутствующем поле, а `{"<": [x, 0.5]}` - нет).

**Соответствие операций задачи оператору JsonLogic** (нотация записи; «в стандарте» - в спецификации jsonlogic.com):

| Операция из задачи | Оператор JsonLogic | В стандарте | В первой итерации |
|---|---|---|---|
| равно | `==` (приводит типы) / `===` (строгий) | да | `==`, у нас строгий (как `===`) |
| не равно | `!=` / `!==` | да | `!=`, у нас строгий (как `!==`) |
| больше, меньше, не больше, не меньше | `>`, `<`, `<=`, `>=` | да | да |
| между (включительно) | `{"<=": [a, x, b]}` (трёхаргументный; `<` - исключающий) | да | да, только `<=` |
| И, ИЛИ | `and`, `or` (возвращают значение, а не булево) | да | да (у нас булево) |
| НЕ | `!` | да | да |
| поле, вложенное поле | `var` с точечным путём (`payload.items.1.code`) | да | да, только строка-путь |
| входит в список | `in`: `{"in": [{"var": "f"}, [..]]}` | да | отложено |
| содержит (подстрока / элемент массива) | `in` с обратным порядком: `{"in": ["sub", {"var": "f"}]}` | да (тот же оператор) | отложено |
| пусто/отсутствует | `missing`: `{"missing": "f"}` (только отсутствие ключа; `""` и `[]` он «не пустыми» не считает) | да, но смысл уже нашего «пусто» | отложено |
| заполнено | `{"!": {"missing": "f"}}` | да (через `!`) | отложено |
| регулярное выражение (частичное совпадение) | - | **нет**, собственный оператор `regex` | **да (Доп. 1)**, только `NonBacktracking`, п. 2.7 |
| без учёта регистра | - | нет | для `regex` - встроенный в шаблон `(?i)` (отдельного оператора нет, п. 2.7); для `==`/`in` отложено |

Отложенные операции добавляются в реестр операций тем же способом (классом и регистрацией, без правок стадии, порта источника,
узлов `and`/`or`/`!`) - так добавлен и `regex` (Доп. 1); их запись в условии будет JsonLogic-совместимой там, где оператор есть в
стандарте (`in`, `missing`), и собственным оператором там, где нет (`regex`). Пока правило с отложенным оператором - ошибка «оператор не
поддерживается». Проработанная семантика (для будущей реализации): `in`-список - равенство по правилам `==` одному из элементов (до 1000);
`in`-содержит - подстрока в поле-строке (порядковое) или элемент поле-массива, равный значению; `is_empty` - отсутствует, `null`, пустая
или пробельная строка, пустой массив/объект (`missing` в стандарте уже этого не покрывает - нужна собственная семантика или оператор
`is_empty`); регэксп - п. 2.7.

Следствие отсрочки (с учётом Доп. 1): пример задачи («`externalPersonId` пуст ИЛИ `deviceId` ~ `^TEST-.*`») выражается, кроме случая
«поле **отсутствует**»: `{"or": [{"==": [{"var": "externalPersonId"}, null]}, {"regex": [{"var": "externalPersonId"}, "^\\s*\\z"]},
{"regex": [{"var": "deviceId"}, "^TEST-"]}]}` ловит JSON `null`, пустую и пробельную строку и `TEST-`-устройства; отсутствие поля без
`missing`-подобного оператора не выражается (`== null` ловит только явный JSON `null`). Примеры `V003` построены на операциях первой
итерации, `V004` - на `regex` (п. 2.3, 9).

### 2.5. Модель путей к полям

- Путь адресует поле **тела сообщения как оно получено** (`ParsedEvent.Body`): не колонки БД и не нормализованные значения.
  Поэтому `externalPersonId` и `payload.accessFlags` - имена из `kafka-event-format.md`, а не из схемы БД.
- Грамматика (как у `var` в JsonLogic): `сегмент ("." сегмент)*`, сегмент = `[A-Za-z0-9_-]+`. Регистр значим. Сегмент из цифр, применённый
  к массиву, - индекс элемента (с нуля): `payload.items.1.code`; применённый к объекту - имя свойства. Подстановок (`*`), фильтров
  и ключей с точкой нет: нужно будет - расширение грамматики без смены формата условия.
- Первый сегмент проверяется при загрузке по списку полей конверта v1: `schemaVersion`, `source`, `sourceEventId`,
  `occurredAt`, `eventType`, `deviceId`, `externalPersonId`, `payload`, `correction`. Неизвестное верхнеуровневое имя -
  ошибка правила («поле указано верно»). Внутри `payload` и `correction` структура свободна (в `docs/api` её нет), поэтому
  путь внутри них при загрузке проверяется только синтаксически; опечатка в пути внутри `payload` даёт «поле отсутствует»,
  а не ошибку загрузки. Это ограничение фиксируется в `docs/manuals/rules-engine.md`; смягчающее средство - примеры и проверка
  правила на реальном сообщении (`docs/manuals/rules-engine.md`, раздел «Как проверить»).
- Верхнеуровневые поля вне списка v1 (адаптер добавил необязательное поле, `additionalProperties: true`) правилам недоступны;
  при смене `schemaVersion` список расширяется вместе со схемой.
- Поле «отсутствует» = пути нет в теле; «`null`» = путь есть, значение JSON `null`.

### 2.6. Семантика операций (без неявных приведений)

Типы значений поля: строка, число, булево, `null`, объект, массив, отсутствует. Никаких приведений между типами
(`"5"` не равно `5`): адаптер, нарушающий тип, не должен случайно «проходить» правило.

- **Строки:** `==`/`!=` - порядковое сравнение (ordinal, без культуры, регистр значим).
- **Числа:** сравнение как `decimal` (`1` равно `1.0`); **значение поля** в сообщении, не помещающееся в `decimal`,
  несравнимо: `==` и `<`, `<=`, `>`, `>=`, `between` дают ложь, `!=` - истину. **Числовой литерал в условии правила** вне
  диапазона `decimal` (в том числе граница `between`) - ошибка загрузки этого правила: оно выпадает из набора, остальные
  действуют, `rules.invalid` растёт, пишется `Error` с `RuleId`. Принятое решение лида («таких чисел не будет»), не спорный пункт.
- **Даты:** при `value`-строке в `<`, `<=`, `>`, `>=` и в границах `between` оба операнда разбираются как RFC 3339 / ISO-8601
  с обязательным указанием зоны (`Z` или смещение) и сравниваются как момент времени (UTC). Значение правила без зоны или не
  дата - ошибка правила при загрузке; поле, не строка или не разбирается как дата - сравнение ложно. `value`-число
  требует поля-числа; смешение типов - ложь. Произвольные строки операциями порядка не сравниваются.
- **`between`:** `value` - массив ровно из двух элементов одного вида (два числа либо две даты), нижняя не больше верхней, иначе
  ошибка правила. Истинно при `нижняя <= поле <= верхняя` (**обе границы включительно**): поле, равное границе, в диапазоне;
  вне диапазона, другого типа, `null`, отсутствующее - ложь. Тесты: на нижнюю границу, на верхнюю, внутри, ниже, выше,
  числа и даты, отсутствующее поле, смешение видов в правиле.
- **Отсутствует / `null` / несовпадение типов:** `==`, `<`, `<=`, `>`, `>=`, `between` дают **ложь** (правило не срабатывает
  на данных, которых нет). `!=` - строгое отрицание `==`, то есть `==`+`not`: отсутствующее поле «не равно» любому значению.
  Это сознательно, чтобы `!=` и `not(==)` не расходились; предупреждение в `docs/manuals/rules-engine.md`: `payload.x != "a"` сработает
  и на сообщениях без `payload.x`. Исключить отсутствие сейчас можно только другим листом (например `payload.x >= ...`
  для чисел); полноценно - после добавления `is_empty`/`missing`-подобного оператора (отложено, п. 2.4; первые в очереди расширений).
- **`== null`:** истинно, если путь присутствует и значение - JSON `null`; для отсутствующего поля ложно.
- **`regex` (Доп. 1):** истинно, только если значение поля - **строка** и шаблон находит в ней совпадение в любой части
  (`Regex.IsMatch`; полное совпадение - якорями `^`...`\z` в шаблоне). Число, булево, `null`, объект, массив и отсутствующее поле -
  **ложь** (приведения нет: число `12345` не совпадёт с `^\d+$`, нужно строковое поле). Как остальные листья, `regex` не вычисляется в
  «неизвестно»: внутри `!` ложь листа даёт истину (`{"!": {"regex": [x, "^A"]}}` истинно и на сообщении без `x`, как `!=`; идиома
  «поле есть, строка и не подходит» - п. 2.7). Единственное исключение из «лист = истина/ложь» - таймаут совпадения
  (п. 2.7): он прерывает вычисление и ведёт к отбраковке сообщения, а не даёт ложь листа.
- **И/ИЛИ:** вычисление коротким замыканием; **НЕ** - отрицание результата узла. Узел вычисляется в два значения (истина/ложь),
  трёхзначной логики нет: «неизвестное» не существует, отсутствие поля - просто ложь листа.

Семантика отложенных операций (`contains`, `in`, `is_empty`, `is_not_empty`) - проработана в п. 2.4 и в приложении A
не дублируется; при добавлении повторить принцип: отсутствующее/`null`/другой тип - ложь, кроме `is_empty`.

### 2.7. Оператор `regex` (Доп. 1: включён в объём решением лида; ранее «отложено вместе с `matches`»)

Запись и форма - п. 2.4 (`{"regex": [{"var": "путь"}, "шаблон"]}`), семантика типов - п. 2.6. Здесь - безопасность на горячем пути
(500 соб/с, `docs/07`), лимиты, ошибки загрузки, отказы вычисления.

**Порядок операндов фиксирован: `[var, шаблон]`.** В отличие от сравнений зеркальной формы нет: «шаблон слева» читается неоднозначно
(что к чему применяется), а перепутанные операнды должны быть ошибкой, а не тихо работающим правилом. Шаблон - только строковый
литерал (шаблон из поля сообщения, `var` вторым операндом - ошибка). Пустой шаблон - ошибка (пустая ячейка не должна давать «совпадает со
всем»); «поле есть и является строкой» выражается явно: `{"regex": [{"var": "x"}, "^"]}`.

**Движок и компиляция.** `System.Text.RegularExpressions` (встроенная часть .NET, отдельного пакета и лицензии нет). Шаблон
компилируется **один раз при сборке снимка** (загрузка правила), а не на сообщение: `new Regex(шаблон, RegexOptions.NonBacktracking |
RegexOptions.CultureInvariant, matchTimeout)`; готовый `Regex` неизменяем и потокобезопасен, лежит в узле условия. Режим
`NonBacktracking` даёт время совпадения, линейное по длине входа, поэтому катастрофический откат (ReDoS: `^(a+)+$`) невозможен по
построению; `matchTimeout` - второй рубеж. Параметры `RegexOptions` из правила не берутся (никаких флагов в записи условия).
Проверено на .NET 10 (`10.0.402`) скриптом-пробой teamlead (не артефакт репозитория): `(?i)` работает; `$` без `Multiline` совпадает и перед
завершающим `\n`, `\z` - нет; `^(a+)+$` на 40 `a` и `!` под `NonBacktracking` завершается за единицы мс, а тот же шаблон с откатом по тому же
входу (34 `a`) уходит в таймаут; 1000 вычислений `^TEST-\d+\z` на строке 64 КиБ - менее 1 мс суммарно, шаблон без якоря - около 0,2 мс на строку 64 КиБ.

**Ошибка загрузки правила (правило не применяется, остальные работают, `rules.invalid`, Error с `RuleId`).** Каждая - отдельный текст
`<путь узла>.regex[<n>]: <причина>` (формат п. 2.4/Р-5), **в текст не копируются ни шаблон целиком, ни `Message` исключения .NET**
(английский текст с шаблоном; причина формируется нами, для разбора - код `RegexParseError` и позиция `Offset`):

| Причина | Источник |
|---|---|
| операнд не строка / пустая строка / длиннее 512 символов (UTF-16) | разбор операндов |
| первый операнд не `var`, второй не строковый литерал (в том числе зеркальная форма, шаблон-`var`) | разбор операндов |
| синтаксическая ошибка шаблона (`RegexParseException`: код и позиция) | конструктор `Regex` |
| конструкция не поддерживается `NonBacktracking` (просмотр вперёд/назад, обратные ссылки, атомарные группы, условные конструкции, балансирующие группы, `\G`) или автомат слишком велик (`NotSupportedException`, например `(a{1000}){1000}`) | конструктор `Regex` |
| превышен лимит regex-узлов правила (8) или набора (`MaxRegexNodes`) | компилятор, построитель снимка |
| любое иное нефатальное исключение конструктора (например, чрезмерная вложенность) | конструктор `Regex` (перехват, кроме `OutOfMemoryException`) |

Нефатальность проверена пробой: `NotSupportedException` для перечисленных конструкций и для больших счётчиков повторений (встроенный
предел автомата), `RegexParseException` для синтаксиса; `RegexOptions.RightToLeft`/`ECMAScript` недоступны, так как флаги не принимаются.
Компилятор по-прежнему **ничего не бросает** (контракт `ConditionCompiler`): конструктор `Regex` обёрнут перехватом.

**Без учёта регистра - без нового оператора и флага.** Решение: автор пишет `(?i)` в начале шаблона (`(?i)^test-`); поддержка в режиме
`NonBacktracking` проверена, регистр сворачивается по `CultureInvariant` (не по культуре процесса). Основание: минимальная
поверхность (нет `iregex`, нет третьего операнда-флага, нет второго ключа в реестре и схеме), нет расхождения между «флагом» и
записью шаблона; цена - автору нужно знать синтаксис `(?i)` (в руководстве - раздел с примерами). Сравнение без учёта регистра для `==`/`in` остаётся отложенным; точное
равенство без учёта регистра выражается так: `(?i)^значение\z`. Альтернативы - п. 3.2.

**Лимиты.** Шаблон 1..512 символов; не более **8** regex-узлов в правиле; не более `DataSaver__Rules__MaxRegexNodes` (по умолчанию
64, допустимо 1..1000) в наборе включённых и корректных правил. Правило, на котором лимит набора исчерпан (правила идут в порядке
п. 2.8), ошибочно: не применяется, Error с `RuleId`, `rules.invalid` (остальные правила - без `regex` и с меньшим числом узлов - не
страдают). Узел `regex` - обычный лист и учитывается в лимите 64 узлов и глубине 8 правила наравне с сравнением; размер условия 16 КиБ
считается по тексту JSON, где `\` записан как `\\` (учтено в руководстве). Обоснование цифр: на строке 64 КиБ один узел - до 0,2 мс, на типичных
значениях (идентификаторы, коды, до 1 КиБ) - единицы микросекунд; 64 узла на наборе на типичных полях дают сотни микросекунд на сообщение, то есть
доли ядра на 500 соб/с; худший случай (все 64 узла на 64 КиБ-строке каждого сообщения) нереалистичен для потока, но фиксируется замером (п. 2.13) и риском R-11.

**Таймаут совпадения - отбраковка с системным кодом (решение лида 2026-11-23).** Если `Regex.IsMatch` бросает `RegexMatchTimeoutException`
(`DataSaver__Rules__RegexTimeoutMs`, по умолчанию **200**, допустимо 1..1000; при `NonBacktracking` практически недостижим, но возможен при
паузе GC/нехватке CPU), результат листа неизвестен, и принимать «ложь» нельзя: внутри `!` она превратилась бы в истину и дала бы
**случайную** отбраковку по правилу, которое на самом деле ничего не проверило. Поэтому лист бросает внутреннее
`RuleEvaluationAbortedException(kind = regex_timeout, предел)`, `And`/`Or`/`Not` его не перехватывают, а `RuleRejectionStage` перехватывает
**на уровне правила** и **отбраковывает сообщение сразу**: независимо от формы правила (с `!` и без) и от того, сработало бы оно на самом
деле, возвращается `Reject(RejectionInfo{Kind = Rule, Reason = "rule_eval_timeout", RuleId, RuleName, RuleVersion, Detail})` (идентификация
правила - того, на котором вышло время); остальные правила не вычисляются (одно сообщение - не больше одного таймаута: поток приёма не ждёт N раз по предел).
Правило, стоящее раньше и сработавшее штатно, останавливает вычисление раньше (п. 2.8): таймаут возможен только на первом необработанном
правиле. Любое иное исключение вычислителя по-прежнему проходит наверх (ADR-0003 п. 2.1 не меняется: перехватывается только типизированный
ожидаемый отказ вычисления, а не дефект кода).

Почему отбраковка, а не «правило не применено, сообщение в журнал» (прежняя редакция Доп. 1): журнал неизменяем, мусор, попавший в него из-за
паузы, не удалить, тогда как отбракованное сохранено в `rejected` вместе с исходным телом и ключом и может быть обработано повторно вручную
(kafka-event-format.md п. 3); правило, которое не смогло проверить, не должно молча пропускать. Цена: при длительной паузе (GC, нехватка CPU)
часть полезных сообщений уйдёт в `rejected` с кодом `rule_eval_timeout` до повторной ручной обработки (риск R-13). Код `rule_eval_timeout` -
**технический отказ вычисления, а не свойство события**: потребитель не относит его к качеству данных сотрудника, оценку он не ухудшает
(инвариант «сбой системы не ухудшает оценку»; автоматических санкций нет).

Что в заголовках: `ktm-reject-reason` = `rule_eval_timeout`; `ktm-reject-rule-id`/`-rule-name`/`-rule-version` - правило, на котором вышло
время; `ktm-reject-detail` по шаблону `Вычисление правила «<name>» (<rule_id>, v<version>) прервано: превышен предел совпадения регулярного
выражения (<N> мс)`, где `<N>` - предел из исключения (`RegexMatchTimeoutException.MatchTimeout` - тот, с которым собран `Regex`); ни значения
поля, ни шаблона, ни совпавшего фрагмента, ни перечня листьев в тексте нет. Усечение до 1024 - как у остальных `detail`.

Наблюдаемость (на обычном пути отбраковки, без отдельного наблюдателя; выдаётся `ObservedRejectionPublisher` после подтверждённой публикации,
п. 2.9, 2.12): счётчики `rules.rejected{source, rule_id}` (событие отбраковано правилом), `messages.rejected{reason="rule_eval_timeout"}` и
`rules.eval_errors{kind="regex_timeout", rule_id}` - на **каждый** таймаут; Warning о таймауте **заменяет** обычный Warning отбраковки правилом
для таких сообщений (иначе пауза в 500 соб/с дала бы 500 записей в секунду) и пишется не чаще раза в 10 минут на правило (`LogThrottle`, ключ
`rule_id`; при следующей записи - число подавленных) с полями `RuleId`, `RuleVersion`, `Source`, `SourceEventId`, `Topic`, `Partition`,
`Offset`, `TimeoutMs` (из `RegexPolicy`), `Suppressed`, без тела и значений полей. `IAdminNotifier` не вызывается (как для остальных отбраковок
правилом). Алерт - на ненулевой прирост `rules.eval_errors`.

Трассировка листьев сработавшего правила (п. 2.9) вычисляет правило повторно; если **повторный проход** отменён таймаутом, отбраковка по
правилу (с его `reason_code`) **уже** решена первым проходом и сохраняется, `detail` строится без перечня листьев. Такой таймаут отдельно не
считается и в `rules.eval_errors` не попадает (допущение: первый проход на тех же данных уложился в предел, второй - только при паузе процесса;
возможное расширение - необязательный признак в `RejectionInfo`, не требуется для приёмки).

**Что в `ktm-reject-detail`.** Лист описывается как `путь regex` (например `deviceId regex`, под `!` - `!deviceId regex`); ни значение поля,
ни совпавший фрагмент, ни шаблон в заголовок не попадают (п. 2.9). В лог при отбраковке правилом - то же, что у остальных правил.

**Якоря и экранирование - ответственность автора** (в руководстве, с примерами): частичное совпадение по умолчанию (`TEST` найдёт
`MY-TEST-1`); `$` совпадает и перед завершающим `\n` (для строгого конца - `\z`); в JSON обратная косая записывается `\\`
(`"^\\d+\\z"`), в SQL-строке без `E''` и при `standard_conforming_strings = on` её удваивать повторно не нужно; `.` не совпадает с `\n`
(для многострочного текста - `(?s)`); `^`/`$` по строкам - `(?m)`.

**Ввод.** Входная строка ограничена размером сообщения (64 КиБ, ADR-0003 п. 2.2); `GetString()` на значение поля выделяет строку на
каждое вычисление, и при замере 2.13 это учитывается (если аллокации заметны - буфер из `ArrayPool` вместо `GetString()`, без
смены контракта). Отдельного предела длины поля нет; вводится, если замер покажет превышение NFR на реалистичных данных (R-11).

Сторонние библиотеки регулярных выражений не подключаются.

### 2.8. Порядок вычисления и что в `rejected` при нескольких правилах

- Для сообщения берутся включённые правила с `source`, равным источнику события, и `source: "*"`, порядок - `priority` по
  возрастанию, при равенстве - `rule_id` по возрастанию (порядковое сравнение). Порядок фиксируется при построении
  снимка; индекс «источник -> массив правил» также строится при загрузке, на сообщение аллокаций нет.
- Вычисление останавливается на **первом** сработавшем правиле: оно и попадает в `rejected`, остальные не вычисляются.
  Одно сообщение - одна запись в `rejected`, один счёт в метрике. Альтернатива (вычислять все и сообщать список) отклонена:
  дороже на горячем пути, усложняет контракт заголовков, а администратору для диагностики достаточно того, что
  сообщение отбраковано одним правилом; выключив его, он увидит следующее.
- Стадия стоит **после** `FormatStage` и `EventValidationStage` (C5): правила не видят сообщений, не прошедших формат; решение C5
  приоритетнее. Правила применяются ко всем разобранным сообщениям, включая корректирующие (`correction`) (принято по
  умолчанию, подтвердить у лида: отбракованная правилом корректировка остаётся в `rejected`, не теряется, но исправление
  не будет применено).

### 2.9. Формат отбраковки правилом в `ktm.events.rejected`

Топик прежний, тело и ключ - исходные байты (контракт п. 3 не меняется). Заголовки:

| Заголовок | Значение для отбраковки правилом |
|---|---|
| `ktm-reject-reason` | `reason_code` правила (`[a-z][a-z0-9_]{0,63}`); три кода формата и системный `rule_eval_timeout` правилам запрещены (последний выставляет сама система при таймауте, п. 2.7) |
| `ktm-reject-detail` | текст причины для человека, до 1024 символов (UTF-16 code units, усекается без разрыва суррогатной пары; шаблон текста - ниже) |
| `ktm-reject-rule-id` | `rule_id` (заголовок уже реализован) |
| `ktm-reject-rule-name` | **новый, необязательный**: название правила, UTF-8, до 256 символов (UTF-16 code units) |
| `ktm-reject-rule-version` | **новый, необязательный**: `version` правила, десятичное число |
| `ktm-source-topic`, `-partition`, `-offset` | как у остальных |

Потребитель отличает отбраковку правилом по наличию `ktm-reject-rule-id`; значения `ktm-reject-reason`, неизвестные
потребителю, он обрабатывает как «прочее» (неизвестные значения причин - аддитивное расширение). Все добавленные заголовки
- необязательные и аддитивные: версия формата `schemaVersion` не меняется; любой потребитель `rejected` обязан терпеть
неизвестные заголовки `ktm-reject-*` и неизвестные коды причин. Потребитель топика не определён (решение лида), поэтому
утверждений о его текущем поведении здесь нет. Изменение вносится в `docs/api/kafka-event-format.md` п. 3 этим же change.

Текст `ktm-reject-detail` формируется по шаблону `Сработало правило «<name>» (<rule_id>, v<version>): <листья>`, где
`<листья>` - перечень сработавших проверок в виде `путь операция` в порядке условия (например `source ==, payload.confidence >`;
у `or` - листья всех истинных операндов, у `!` - ложные листья отрицаемого узла с префиксом `!`, по одному на уровень вложенности;
одинаковые строки не повторяются; пустой список - без суффикса `: ...`), **без значений из сообщения**: детали не должны утекать в заголовок как данные (kafka-event-format.md п. 3 о
`ktm-reject-rule-id`; персональные данные в лог и заголовки не кладутся). Значения из условия правила (администраторские
константы) в текст допустимы, но на этапе не включаются: достаточно пути и операции. Для листьев берётся повторное
вычисление правила с трассировкой, выполняемое только когда правило уже сработало. Лист `regex` описывается как `путь regex`
(Доп. 1: шаблон в текст не включается; если повторный проход отменён таймаутом - `detail` без перечня листьев, п. 2.7).
Отбраковка по таймауту совпадения (п. 2.7) - тот же набор заголовков с `ktm-reject-reason = rule_eval_timeout`, правилом, на котором вышло
время, и собственным текстом `ktm-reject-detail` (предел в мс, без значений, шаблона и листьев).

Лог: `LogWarning` (не Error, как у формата: это штатная работа фильтра, а не поломка интеграции) с именованными полями
`Topic`, `Partition`, `Offset`, `Source`, `SourceEventId`, `RuleId`, `RuleVersion`, `ReasonCode`; тело сообщения не логируется.
Запись выполняется после подтверждения публикации (как у формата) - `ObservedRejectionPublisher`. Канал оповещения
администратора (`IAdminNotifier`) для правил **не вызывается** (требование задачи: уведомления не делаем).

Продвижение offset и порядок «публикация -> commit» не меняются (ADR-0002 D-6).

### 2.10. Загрузка и перезагрузка: опрос таблицы

В сервисе держится снимок: неизменяемый объект (правила, индекс по источникам, список ошибочных правил, ревизия), ссылка на
который заменяется атомарно; стадия берёт ссылку один раз на сообщение. `NpgsqlRuleSource` выполняет
`SELECT rule_id, name, description, source, condition, reason_code, enabled, priority, version FROM ktm.rejection_rules
ORDER BY priority, rule_id` под `ktm_app` (читаются **все** строки, включая выключенные: набор мал, а выключенные нужны для
журнала изменений и счёта `rules.active`); результат хэшируется (SHA-256 канонической записи строк) и сравнивается с ревизией
текущего снимка: совпало - `Unchanged`, разбор и компиляция не выполняются.

**Порядок старта и Kafka-подписка.** Решение лида: подписка ленивая. `RuleRefreshService` делает первую загрузку до старта цикла
приёма, а Kafka consumer создаётся и подписывается на топики только после первой успешной загрузки правил (при
`Rules__Enabled=false` - сразу при старте цикла). До этого группа в Kafka не присоединяется, `Consume` и commit не вызываются.
Реализовано в этом change.

**Триггер перезагрузки - только таймер.** `DataSaver__Rules__RefreshIntervalSeconds` (по умолчанию 60, допустимо 5..3600): изменение
вступает в силу не позже чем через интервал. Нагрузка: один небольшой `SELECT` (до `MaxRules` строк, десятки КиБ) за интервал на
экземпляр. Тик не пересекается с предыдущим (последовательная загрузка).

**Отступление от исходной постановки: «по команде».** Исходная задача требовала перечитывание «раз в минуту и по команде». В ред. 3 «по
команде» **не реализуется**: без `LISTEN/NOTIFY` (убран вместе с триггерами и выделенным соединением) остаются сигнал процессу (SIGHUP
- нет в Windows, на стенде - `docker kill -s HUP`, второй шаг помимо правки данных) и админ-эндпоинт (неаутентифицированная
операция на порту health - новая поверхность атаки, п. «Альтернативы»). Оба дороже, чем стоит первая итерация. Принято: только опрос;
чтобы изменение вступало в силу быстро, администратор может поставить `RefreshIntervalSeconds = 5` (стоимость - один небольшой
`SELECT` раз в 5 с). Шов `IRuleChangeSignal` оставлен: `NOTIFY` подключается без правок движка (приложение A). **Требует
подтверждения лида.**

**Первая загрузка (до цикла приёма).** Порядок регистрации hosted-сервисов: загрузка правил -> `DataSaverWorker`.

| Состояние на старте | Поведение |
|---|---|
| Таблица пуста | штатно: пустой набор, Info «правил нет»; готовность не страдает |
| Все правила выключены | штатно: набор без активных правил, Info |
| БД недоступна (таймаут, отказ соединения) | **повтор с backoff** (`BackoffPolicy`) пока не получится или не остановят host; Kafka не читается, `/health/ready` = 503 с кодом `rules_not_loaded` (проверяется первым, до `no_partitions_assigned` и `broker_unavailable`), `/health/live` = 200 (цикл приёма не запущен по замыслу, перезапуск не лечит); причина в логе (Warning, `LogThrottle`) |
| Нет таблицы (`42P01`) или нет прав (`42501`) | **код выхода 78** (ошибка конфигурации: не накатана `V002` либо не выдан `SELECT`), сообщение без значений секретов |
| Неверные настройки `DataSaver__Rules__*` | код выхода 78 (проверка при старте) |
| Ошибочное правило (`condition` не разобралось и т. п.) | старт продолжается, правило не в наборе, Error в лог, `rules.invalid` |

Оговорка к ADR-0002 D-10 (live/ready): таблица выше **уточняет** D-10 на период до первой загрузки правил: до неё liveness не
проверяет отметки цикла приёма (200, если нет фатальной ошибки consumer), а readiness возвращает `rules_not_loaded`; после первой
загрузки действуют правила D-10 без изменений (`Health/HealthEvaluator.cs`).

Обоснование повтора при недоступной БД: писать в необратимый журнал мусор «в открытую» хуже, чем подождать, а БД правил - та же БД
журнала, без неё запись всё равно невозможна; поведение совпадает с прочими зависимостями Data Saver (БД, брокер). Устаревание снимка
наблюдается метрикой `ktm.datasaver.rules.snapshot_age`; в готовность не входит (потеря связи на минуты не должна останавливать приём,
пока работает запись).

**Результат загрузки.**

- Хэш совпал - `unchanged`, ничего не меняется (`reloads{result="unchanged"}`).
- Новый набор - собирается снимок (ошибочные правила отбрасываются, остальные компилируются), ссылка заменяется атомарно, в лог Info:
  ревизия (первые 12 символов хэша), число правил, список добавленных/изменённых/удалённых `rule_id` с `version`. Если у правила
  изменилось содержимое (хэш канонической записи), а `version` прежняя - Warning «правило изменено без увеличения version».
- Сбой чтения (БД недоступна, таймаут, ошибка запроса) после успешной первой загрузки - **последний валидный снимок** продолжает
  действовать, Warning в лог (`LogThrottle`: повтор той же причины не чаще раза в 10 минут), `reloads{result="failed"}`; повтор в
  штатный срок. `42P01`/`42501` после первой загрузки код выхода не дают (обрабатываются как недоступность источника).
- Ошибочное правило: Error с `RuleId`, `RuleVersion` и текстом причины (без значений из сообщений - их при загрузке нет); повтор той же
  `(rule_id, version, причина)` не чаще раза в час (`LogThrottle`); `rules.invalid` растёт. Исправленное правило вступает в силу в
  следующем снимке. Всё-или-ничего на уровне набора отвергнуто: одно плохое правило не должно выключать остальные. Известный риск (R-3):
  правка, превратившая рабочее правило в ошибочное, выключает его - брак снова пойдёт в журнал; страхуется gauge `rules.invalid` и
  Error в логе. «Последняя валидная версия этого правила» отклонена: скрывает ошибку правки и усложняет модель снимка.
- Выключенные правила (`enabled = false`) компилятором не проверяются (черновики допустимы); проверка условия выключенных правил -
  в тесте примеров `V003` и `V004`. Следствие для `regex`: шаблон выключенного правила тоже не компилируется, поэтому его корректность
  видна только после включения (безопасно: невалидное включённое правило не применяется и пишет Error).

Что уже записано, повторно не проверяется: изменение правила действует на сообщения, начатые обработкой после замены
снимка; ретроактивной отбраковки нет (журнал неизменяем), отбракованное правилом автоматически назад в обработку
не возвращается (повтор `rejected` - ручная операция, kafka-event-format.md п. 3).

Настройки (`DataSaver__Rules__*`, проверка при старте, как у прочих опций): `Enabled` (по умолчанию `true`; `false` - стадия не
регистрируется и таблица не читается, аварийное отключение без пересборки), `RefreshIntervalSeconds` (60, 5..3600), `MaxRules` (500:
если включённых правил больше, загружаются первые `MaxRules` по порядку п. 2.8, остальные не применяются, Error в лог - ограничение
объёма вычислений и кардинальности метрик, п. 2.12). Доп. 1 (регэксп, п. 2.7): `RegexTimeoutMs` (200, 1..1000) - таймаут совпадения (по его истечении сообщение отбраковывается, п. 2.7),
мс; `MaxRegexNodes` (64, 1..1000) - предел regex-узлов в наборе. Проверка при старте как у прочих (неверное значение -> код 78); при
`Enabled=false` не проверяются. Изменение требует перезапуска (регэкспы компилируются со своим таймаутом при сборке снимка; смена настройки без
перезапуска не поддерживается).

### 2.11. Базовая проверка формата (пункт 4 задачи) - дельта

Реализована в `add-data-saver-core` и соответствует задаче (корректный JSON, известная версия, обязательные поля по схеме v1
- `required` в `kafka-event.schema.json`, - с отбраковкой в `rejected` и кодом причины). Дельта этого change:

- порядок стадий закрепляется тестом: сообщение, не прошедшее формат, не попадает в движок правил (правило, которое «сработало
  бы» на нём, не вычисляется, причина остаётся форматной);
- в `docs/manuals/rules-engine.md` описан порядок «формат -> C5 -> правила» и то, что проверка формата - не правило и не
  настраивается;
- существующие тесты формата не дублируются.

### 2.12. Метрики

Инструменты в существующем `Meter` `Ktm.DataSaver` (`DataSaverMetrics`), единицы `{message}` и т. д. в стиле текущих:

| Метрика | Тип | Теги | Смысл |
|---|---|---|---|
| `ktm.datasaver.rules.rejected` | counter | `source` (`skud`/`cv`/`1c-do`), `rule_id` | отбраковано правилами (считается после подтверждённой публикации); Доп. 1: включает отбраковку по таймауту на этом правиле (набор тегов не меняется, чтобы не менять ряды уже выложенной метрики; таймауты отделяются через `messages.rejected{reason="rule_eval_timeout"}` и `rules.eval_errors`) |
| `ktm.datasaver.messages.rejected` | counter (есть) | `reason` | для отбраковки правилом тег `reason` = `rule_matched` (фиксированное значение), а не `reason_code`: иначе кардинальность определяется администратором; Доп. 1: для отбраковки по таймауту - `rule_eval_timeout` (системный код, значение фиксировано в коде, не задаётся автором) |
| `ktm.datasaver.rules.active` | gauge | - | включённых правил в текущем снимке |
| `ktm.datasaver.rules.invalid` | gauge | - | включённых правил, не применённых из-за ошибки (повод для алерта) |
| `ktm.datasaver.rules.reloads` | counter | `result` (`changed`/`unchanged`/`failed`), `trigger` (`timer`/`startup`) | попытки загрузки (`watcher`/`notify` добавятся с `IRuleChangeSignal`) |
| `ktm.datasaver.rules.snapshot_age` | gauge, `s` | - | время с последней успешной проверки таблицы (`unchanged` тоже успешная проверка: «не менялось» не равно «устарело») |

Доп. 1: к таблице добавляется счётчик `ktm.datasaver.rules.eval_errors` (теги `kind` - пока одно значение `regex_timeout`, и `rule_id` - только из
загруженного снимка, как у `rules.rejected`): вычисление правила прервано таймаутом, сообщение отбраковано (п. 2.7). Растёт на каждый таймаут (а не
раз в окно лога), после подтверждённой публикации отбраковки (как `rules.rejected`; повтор пачки при сбое публикации не удваивает счёт).
Алерт - на ненулевой прирост. Кардинальность - не больше `MaxRules` рядов на значение `kind`. Таймаут повторного прохода трассировки (п. 2.7) не считается.

Кардинальность: `source` - три значения (из схемы v1; отбракованное по формату сюда не попадает, у него источник не разобран);
`rule_id` берётся только из загруженного снимка (не из данных сообщения), а число правил ограничено `MaxRules = 500`;
максимум рядов `rules.rejected` = 3 × 500 + 500 (общие правила считаются по источнику события) при реалистичных единицах
- десятках правил. Тегов, зависящих от содержимого сообщений (`deviceId`, значения полей, `reason_code` свободного вида), нет.
«Считаем отбракованные по источникам и по правилам» (C7) выполняется срезами одной метрики `rules.rejected`.
Экспорт (Prometheus/OTel) по-прежнему вне объёма (core 10.5): метрики читаются так же, как существующие.

### 2.13. Тесты и NFR

- Тесты на каждый оператор первой итерации (`==`, `!=`, `<`, `<=`, `>`, `>=`, диапазон: обе границы, внутри, ниже, выше) и на каждый узел
  (`and`, `or`, `!`), на пути, семантику отсутствия/типов, даты, компилятор (каждая причина ошибки правила), порядок правил,
  перезагрузку опросом, недоступность БД правил (первая загрузка и после неё), права ролей; интеграционный тест 100/95/5 и тест
  перезагрузки без рестарта (`UPDATE` таблицы) - в `tasks.md`. Правило с ошибкой не применяется и пишется в лог - тест сохраняется
  (неизвестный оператор, неверный путь, диапазон с перевёрнутыми границами, **невалидный регэксп** - Доп. 1).
- Доп. 1, регэксп: тест на каждую ветвь оператора (совпадение в части строки; якоря; `(?i)`; поле не строка/отсутствует/`null`/число/
  объект/массив; `regex` под `!`, `and`, `or`; трассировка листа без значений), на каждую причину ошибки загрузки (пустой, длинный, не
  строка, зеркальная форма, синтаксис, просмотр/обратная ссылка/атомарная группа, большой счётчик повторений, лимиты правила и набора),
  на безопасность (`^(a+)+$` на враждебном входе завершается быстро; таймаут отбраковывает событие с кодом `rule_eval_timeout` и заголовками правила - и в форме с `!`, и без; остальные правила после него не вычисляются; запрещён ли код правилам), на
  счётчик и лог (без значений сообщения), интеграционный тест «невалидный regex не ломает сервис, Error с `RuleId`, `rules.invalid`»;
  сверка схемы условия и компилятора на образцах `regex`; примеры `V004` проходят и то, и другое. Перф: набор с regex-узлами (п. 2.7, R-11).
- Соответствие схемы `docs/api/rejection-condition.schema.json` и компилятора проверяется тестом на образцах (одни и те же
  допустимые и недопустимые условия; расхождения по семантике, которую схема выразить не может, перечислены в тесте как исключения):
  схема - второе описание грамматики, и без такой сверки оно разойдётся с кодом. Примеры `V003` проходят и схему, и компилятор.
- NFR (`docs/07`: 500 событий/с в пике): стадия работает с готовым снимком в памяти без обращений к БД и без аллокаций на
  сообщение сверх необходимых; затраты на сообщение - обход нескольких десятков узлов. Перф-проверка (категория `Perf`, как
  существующие) на 50 включённых правилах подтверждает, что нагрузка 500 соб/с не ухудшает задержку «Kafka -> журнал»
  относительно замера `docs/test-protocols/data-saver-throughput.md`; результат записывается в протокол. Если замер покажет
  заметную деградацию, решение пересматривается (кеширование разбора путей, ограничение `MaxRules`), а не принимается.
  Опрос раз в минуту (небольшой `SELECT` и SHA-256) на горячий путь не влияет: выполняется в фоновой задаче.

### 3.2. Прочие

- **Условие как SQL-фрагмент/выражение или DSL-строка.** Собственный парсер, худшие сообщения об ошибках, риск исполнения
  произвольного кода. JSON-дерево парсится стандартным разбором, проверяется структурно.
- **Нормализованная таблица условий (узлы строками с `parent_id`).** Любая правка дерева - несколько строк и транзакция, вложенность
  неудобна в SQL. JSONB хранит правило целиком в одной строке.
- **Правила в файле (редакция 2 этого ADR).** Отменено решением лида: доставка файла в контейнер, `FileSystemWatcher` в Docker,
  атомарная запись и режимы запуска без файла - трудоёмкость, сопоставимая с урезанной БД, при худших эксплуатационных свойствах.
- **Регэксп с бэктрекингом и только таймаут** (для `regex`). Таймаут не защищает ресурсы потока обработки: пока идёт
  совпадение, партиция стоит. `NonBacktracking` даёт гарантию, таймаут - страховка (п. 2.7). Цена выбора: недоступны просмотр
  вперёд/назад и обратные ссылки (для фильтра качества данных не требуются; при появлении потребности - пересмотр ADR, а не флаг).
- **Отдельный оператор `iregex` либо флаг (третий операнд `"i"`).** Дублирует встроенный в шаблон `(?i)`, расширяет реестр, схему и
  документ на ключ/форму, которые ничего не добавляют по выразительности. Отклонено (п. 2.7). Вернуться - если авторы будут массово
  забывать `(?i)`.
- **Сопоставление всей строкой (как `Regex.IsMatch` с неявными якорями).** Расходится с ожиданием лида («как `Regex.IsMatch`») и
  с привычным смыслом оператора; полное совпадение выражается `^...\z`. Отклонено.
- **Таймаут как «ложь листа».** Под `!`/`!=`-подобными конструкциями превращает отказ вычисления в **случайную** отбраковку по условию, которое
  ничего не проверило, а без `!` - в молчаливый пропуск; отклонено: отказ вычисления должен быть явным (п. 2.7).
- **Таймаут: «правило на сообщении не применяется, сообщение идёт в журнал»** (прежняя редакция Доп. 1, отменена решением лида 2026-11-23). Отказ
  открытый: при паузе процесса или нехватке CPU мусор попадает в неизменяемый журнал, откуда его не убрать, и это же правило молча перестаёт
  защищать; требовало отдельного порта-наблюдателя `IRuleEvaluationObserver` для метрики и лога (побочный канал помимо вердикта). Выбрана
  отбраковка с системным кодом: сообщение сохранено в `rejected` и восстановимо, отказ виден в потоке отбраковок.
- **Отдельный `RejectionKind.RuleTimeout` и/или поле в `IngestionVerdict`.** Не нужны: `Kind = Rule` с системным `Reason` несёт всё нужное
  (заголовки правила, публикация, продвижение offset); новое значение enum тихо попало бы в ветку «по формату» кода, проверяющего
  `Kind == Rule`. Публичные типы не меняются.
- **CHECK `V002` с четвёртым кодом (`ALTER`/правка применённого файла).** Правка запрещена (ADR-0004), `ALTER` не нужен: запрет в загрузчике
  достаточен (п. 2.3).
- **Зеркальная форма `[шаблон, var]` и шаблон из поля сообщения.** Двусмысленно; шаблон из данных - внешний ввод в компилятор регэкспов на
  горячем пути. Отклонено.
- **Пакет `RE2`/`Re2.Net` и иные сторонние движки.** Нативные зависимости и лишняя лицензионная проверка при готовом встроенном
  линейном движке. Отклонено.
- **Новый номер правки `V003` вместо `V004`.** Правка применённого файла запрещена (ADR-0004); пример - в новом файле (п. 2.3).
- **Отбраковка отдельным сервисом/топиком до Data Saver.** ADR-0003 п. 3: дополнительный сервис и задержка без выигрыша.
- **Отдельный топик `ktm.events.rule-rejected`** (рекомендация ADR-0003). Лид задал `ktm.events.rejected`; различие внутри топика -
  заголовок `ktm-reject-rule-id`. Цена: потребитель `rejected` получает и технические инциденты, и отбраковку по правилам в одном потоке.
- **REST API правил сейчас.** Требует аутентификации и ролевой модели в Data Saver (которого нет) или отдельного API-сервиса;
  объём не этого этапа (в задаче: «UI управления - позже»). Временный путь - SQL под ролью-владельцем.
- **Перезагрузка «по команде» сейчас: сигнал (SIGHUP), админ-эндпоинт `POST /admin/rules/reload`, `LISTEN/NOTIFY`.** SIGHUP: нет в
  Windows, второй шаг помимо правки данных. Эндпоинт: Data Saver не имеет аутентификации, неаутентифицированная операция на порту
  health - новая поверхность атаки. `NOTIFY`: триггер и выделенное соединение - обвязка, из первой итерации убрана (приложение A).
- **Применение набора «всё или ничего» на уровне правил** (одно ошибочное правило - снимок не обновляется) - п. 2.10.

## 4. Влияние на контракты и схему данных

- **Kafka (`docs/api/kafka-event-format.md` п. 3)**: два новых необязательных заголовка (`ktm-reject-rule-name`,
  `ktm-reject-rule-version`); новые значения `ktm-reject-reason` (коды правил; Доп. 1: системный `rule_eval_timeout`, п. 2.7); уточнение: для отбраковки правилом нет
  оповещения администратора. Схема `kafka-event.schema.json` не меняется. Аддитивно; потребитель `rejected` не определён,
  кому сообщать - решит лид (согласование - задача 7.2).
- **Контракт условия**: `docs/api/rejection-condition.schema.json` (нотация условия v1). Доп. 1: схема получает новый вариант узла `regex`
  (`prefixItems: [var, строка 1..512]`) и обновлённое описание; изменение аддитивное (допустимых до этого условий не отвергает), версия `v1`
  и `$id` не меняются. Схема не выражает: корректность синтаксиса шаблона, поддержку `NonBacktracking`, лимиты правила/набора (проверяет
  компилятор; перечислено в тесте сверки как документированные расхождения).
- **HTTP API**: не затрагивается (в Data Saver только health).
- **БД**: одна новая таблица `ktm.rejection_rules` схемы `ktm`, миграции `V002` (схема, права), `V003` (выключенные примеры) и
  `V004` (Доп. 1: два выключенных примера на `regex`); `ktm_app` получает `SELECT` на таблицу правил; журнал событий не меняется;
  схема таблицы (CHECK-и) для `regex` не меняется.
- **Метрики**: новый счётчик `rules.eval_errors` (п. 2.12) и новое значение тега `messages.rejected{reason="rule_eval_timeout"}` - аддитивно.
- **Публичные типы Data Saver**: `IngestionVerdict`, `RejectionInfo`, `RejectionKind` не меняются (п. 2.1, 2.7); добавляется константа
  `RejectReasons.RuleEvalTimeout` (внутренняя модель `Core/Model`).
- **Конфигурация**: `DataSaver__Rules__*` (п. 2.10; Доп. 1: `RegexTimeoutMs`, `MaxRegexNodes`), `src/README.md` и руководство `docs/manuals/data-saver.md`. Изменений compose,
  `.env.example` и `Dockerfile` не требуется (`DataSaver__Rules__*` имеют умолчания).

## 5. Последствия

- Конвейер и цикл не меняются: регистрируется ещё одна `IIngestionStage`; изменения публикатора и метрик аддитивны.
- Первое включённое правило начинает необратимо менять то, что попадает в журнал: ошибочное правило-фильтр «съедает» события в
  `rejected`. Смягчения: примеры в `V003` выключены (п. 9), понятный `detail`, предупреждение в лог на каждое срабатывание, метрика
  по правилам, повторная обработка `rejected` вручную возможна (тело и ключ исходные).
- **Отступление от исходной постановки: «по команде».** Только опрос (п. 2.10). Подтвердить у лида (раздел 9, п. 2).
- **Аудита изменений правил нет** (`docs/04` п. 4.2/4.4: «Все изменения настроек должны фиксироваться в журнале аудита»; «создание,
  редактирование и удаление ... правил» - категория аудита). Что есть вместо: сервис пишет в лог каждый применённый набор (что
  добавлено/изменено/удалено, `version`), срабатывание правила несёт `version`; `version` ведёт автор вручную. Этого **недостаточно** для
  приёмки аудита: нет субъекта («кто»), лог не неизменяем. **Принято лидом как временное отступление.** **Триггер возврата обвязки БД
  (приложение A: триггер версии, таблица и триггер аудита, `LISTEN/NOTIFY`): появление первого реального правила либо потребность в аудите.**
- Доп. 1: шаблон регэкспа - ввод администратора, а не сообщения; ReDoS закрыт движком (`NonBacktracking`), а не соглашением; ошибка шаблона
  видна при ближайшей загрузке (Error + `rules.invalid`), а не при записи (как и прочие ошибки условия). Слишком широкий шаблон
  (`TEST` без якорей) отбракует больше задуманного - необратимо для журнала; смягчение прежнее (примеры выключены, `detail`, лог, метрика, `rejected`
  хранит исходное). Таймаут совпадения ведёт к отбраковке с кодом `rule_eval_timeout` (сообщение сохранено в `rejected`, заметно: `rules.eval_errors`, Warning); при
  длительной паузе процесса часть корректных сообщений уйдёт в `rejected` до ручной повторной обработки (R-13).
- `ktm_app` не может менять правила: компрометация Data Saver не позволяет скрыть отбраковку.
- Ручной `INSERT/UPDATE` правила с ошибкой в условии не отвергается БД (CHECK проверяет только тип и размер jsonb): ошибка видна в
  логе и метрике после ближайшей загрузки (до интервала опроса), а не при записи. Допустимо: грамматику проверяет код с тестами и
  понятными сообщениями; дублировать её в PL/pgSQL - второй источник правды; JSON Schema в редакторе и CI - ранняя проверка.
- Правки правил идут под `ktm_migrator`: роль с правами DDL используется для DML (временно; отдельная роль-редактор - с обвязкой).
- Несколько экземпляров Data Saver читают таблицу независимо; на краткое время (до интервала опроса) могут работать на разных
  наборах (R-7).
- Тесты и протоколы этого change - `tasks.md`.

## 6. Триггеры пересмотра

- **Появление первого реального правила либо потребности в аудите** (решение лида), REST API правил / UI: вернуть отложенную
  обвязку БД (приложение A): триггер версии, таблицу и триггер аудита с субъектом-пользователем, `LISTEN/NOTIFY` как `IRuleChangeSignal`,
  отдельную роль-редактор; владелец таблицы при REST API - отдельный ADR (ADR-0004, «Триггеры пересмотра»). Движок не меняется.
- Нужна арифметика/функции в условиях, ссылки между полями, относительное время («старше суток») - расширение языка либо CEL/Corvus (п. 3.1).
- Реальные критерии потребовали отложенных операций (`in`, `missing`-подобный, `==`/`in` без учёта регистра) - добавить реестром операций
  (п. 2.4), без смены нотации; в первую очередь `is_empty`/`is_not_empty` (исключение отсутствующих полей при `!=`/`!regex`).
- Доп. 1: нужны просмотр вперёд/назад или обратные ссылки в шаблонах - пересмотр ADR (отказ от `NonBacktracking` возвращает поверхность
  ReDoS и требует иной защиты); замер показал превышение NFR на наборе с regex-узлами - предел длины поля, уменьшение `MaxRegexNodes`.
- Нужна «команда» перезагрузки быстрее минуты - `NOTIFY` (приложение A) либо уменьшение интервала (минимум 5 с).
- Нужен «список сработавших правил» или статистика пересечений - переход на вычисление всех правил.
- Деградация NFR на реальном наборе правил (п. 2.13) - оптимизация вычисления или перенос в отдельный сервис (ADR-0003 п. 3).
- pgbouncer в режиме `transaction` перед БД не влияет на опрос; важен только при возврате `LISTEN`.

## 8. Риски

- R-1. Данные для проверки правил: нет реального потока адаптеров на стенде (адаптеры - внешняя зависимость): критерии «что
  считать браком» у предприятия не получены. Примеры в `V003` - иллюстрация формата, не бизнес-решение; включать их на стенде можно
  только после согласования критериев с владельцами источников.
- R-2. Нет перечня полей `payload` по источникам в `docs/api`: опечатки в путях внутри `payload` не ловятся при загрузке (п. 2.5).
- R-3. Правка, делающая правило ошибочным, выключает фильтр (п. 2.10); защита - алерт на `rules.invalid` (канал алертов вне объёма).
- R-4. Нет аудита изменений правил (п. 5): отступление от `docs/04`, принято лидом как временное. Закрывается возвратом обвязки БД.
- R-5. Нет «команды» перезагрузки: задержка до интервала опроса (п. 2.10); смягчение - интервал 5 с.
- R-6. Рост журнала `rejected`: слишком широкое правило отправит в `rejected` весь поток (до 500 соб/с). Замер в перф-проверке на
  100 % отбраковки.
- R-7. Согласованность экземпляров в пределах интервала опроса; допустимо.
- R-8. Имена операторов и форма условия - стабильный контракт нотации v1; переименование - миграция данных.
- R-9. Правки идут под `ktm_migrator` без аудита; ограничение процесса (п. 2.3, 5).
- R-10. Версия правила (`version`) ведётся вручную: забытый инкремент не ломает работу, но искажает `ktm-reject-rule-version`;
  смягчение - Warning сервиса (п. 2.10).
- R-11 (Доп. 1). Стоимость `regex` на горячем пути: линейна по длине поля; на строке 64 КиБ - до 0,2 мс на узел (проба); худший случай
  `MaxRegexNodes` узлов на крупном поле каждого сообщения превысил бы бюджет 500 соб/с. Смягчение: типичные поля короткие, лимиты п. 2.7,
  замер на реалистичном и на предельном вводе (tasks 9.8); при превышении - предел длины поля для `regex` (длиннее: отказ вычисления
  `kind="input_too_long"` по тому же пути, что таймаут; какой код причины и отбраковка ли - решает teamlead по замеру) и/или меньший `MaxRegexNodes`.
  Решение принимается по замеру, а не принимается вслепую.
- R-12 (Доп. 1). Ошибки авторов шаблонов: пропущенные якоря (частичное совпадение), `$` перед `\n`, одинарная `\` в JSON, `!regex` на
  отсутствующем поле. Смягчение: руководство с примерами и «ловушками», выключенные примеры `V004`, Error при невалидном шаблоне.
- R-13 (Доп. 1). Таймаут совпадения (200 мс) отбраковывает сообщение: при длительной паузе процесса (GC, нехватка CPU, троттлинг контейнера) часть
  корректных сообщений уйдёт в `rejected` с `rule_eval_timeout` и не попадёт в журнал, пока их не обработают повторно вручную. Не потеря данных
  (тело и ключ в `rejected`), но задержка до разбора и нагрузка на оператора. Смягчение: `NonBacktracking` делает таймаут практически
  недостижимым без паузы; предел 200 мс (запас на пики); сообщение отбраковывается не более чем одним таймаутом (остальные правила не
  вычисляются), поэтому поток не ждёт N × предел; `rules.eval_errors` (алерт на прирост) и Warning с `Suppressed`. Неизмеримое: частота таймаутов на
  реальной нагрузке неизвестна до стенда (9.10). Потребитель должен трактовать `rule_eval_timeout` как технический отказ, а не как брак события.
- R-14 (Доп. 1). Запрет кода `rule_eval_timeout` для авторов правил держит загрузчик, а не БД (п. 2.3): ручной `INSERT` с этим кодом БД примет,
  правило будет ошибочным (Error, `rules.invalid`) и не вступит в действие. Закрывается отдельной миграцией с `ALTER ... CHECK` по решению лида.

### A.1. Таблица, версия и аудит триггерами, права, оповещение (ред. 1, п. 2.2)

Условие - **JSONB-дерево с жёсткой схемой** (п. 2.3), остальное - обычные колонки. Файлы миграций (ADR-0004, правила файлов
те же: идемпотентно, без метакоманд, применяется `ktm_migrator`):

- `db/migrations/V002__rejection_rules.sql` - схема (таблицы, триггеры, права);
- `db/migrations/V003__rejection_rules_examples.sql` - примеры правил для `skud`, `cv`, `1c-do` и общего. Данные вынесены
  в отдельный файл, чтобы изменение набора примеров не правило файл со схемой.

```sql
CREATE TABLE IF NOT EXISTS ktm.rejection_rules (
    rule_id      text        NOT NULL,
    name         text        NOT NULL,
    description  text        NULL,
    source       text        NULL,                  -- NULL = все источники
    condition    jsonb       NOT NULL,
    reason_code  text        NOT NULL,
    enabled      boolean     NOT NULL DEFAULT true,
    priority     integer     NOT NULL DEFAULT 100,
    version      integer     NOT NULL DEFAULT 1,    -- растёт триггером при каждом UPDATE
    created_at   timestamptz NOT NULL DEFAULT now(),
    updated_at   timestamptz NOT NULL DEFAULT now(),
    updated_by   text        NOT NULL DEFAULT session_user,
    CONSTRAINT pk_rejection_rules PRIMARY KEY (rule_id),
    CONSTRAINT ck_rejection_rules_id      CHECK (rule_id ~ '^[A-Za-z0-9._:-]{1,128}$'),   -- формат ktm-reject-rule-id
    CONSTRAINT ck_rejection_rules_name    CHECK (length(btrim(name)) BETWEEN 1 AND 200),
    CONSTRAINT ck_rejection_rules_source  CHECK (source IS NULL OR length(source) BETWEEN 1 AND 32),
    CONSTRAINT ck_rejection_rules_cond    CHECK (jsonb_typeof(condition) = 'object' AND octet_length(condition::text) <= 16384),
    CONSTRAINT ck_rejection_rules_reason  CHECK (reason_code ~ '^[a-z][a-z0-9_]{0,63}$'
                                                 AND reason_code NOT IN ('malformed_json','unknown_schema_version','invalid_schema')),
    CONSTRAINT ck_rejection_rules_prio    CHECK (priority BETWEEN 0 AND 10000)
);
```

Обоснование колонок:

- `rule_id` - текстовый ключ-слаг (`skud-test-device`), а не `uuid`/`serial`: он попадает в заголовок, лог и метрику, и человек
  должен узнавать его без справочника; формат совпадает с контрактом `ktm-reject-rule-id`.
- `source IS NULL` = «все источники». Допустимость значения (`skud`, `cv`, `1c-do`) проверяет загрузчик, а не БД: новый
  источник добавляется релизом Data Saver (kafka-event-format.md п. 3), CHECK в БД потребовал бы миграции на каждый источник.
- `reason_code` - код, который уходит в `ktm-reject-reason`. Три кода формата зарезервированы CHECK-ом, чтобы правило не могло
  выдать брак за ошибку формата.
- `priority` - детерминированный порядок вычисления (п. 2.7); меньше = раньше.
- `version` и `updated_*` ведёт триггер, вручную их не правят; `version` уходит в заголовок `ktm-reject-rule-version`
  (зарезервирован ADR-0003 п. 2.4).
- Лимит размера условия 16 КиБ (страховка БД; логическая длина `octet_length(condition::text)`, как в п. 2.3 ред. 3; единица - UTF-8 байт при
  обязательной UTF8-кодировке БД; `convert_to(condition::text,'UTF8')` допустима как альтернатива, снимающая требование кодировки, сейчас не используется; лимиты разбора - п. 2.3).

**Аудит (инвариант «изменение правила попадает в аудит»).** Таблица `ktm.rejection_rule_audit`
(`audit_id bigint generated always as identity`, `rule_id`, `action` (`insert`/`update`/`delete`), `old_row jsonb`,
`new_row jsonb`, `changed_at timestamptz default now()`, `changed_by text default session_user`) заполняется триггером
`AFTER INSERT OR UPDATE OR DELETE ... FOR EACH ROW` на `rejection_rules`; неизменяема теми же триггерами
`ktm.forbid_modify()`, что и журнал (UPDATE/DELETE/TRUNCATE). Пока нет REST API, «пользователь» = роль БД, под которой
выполнен SQL (`session_user`). Когда появится API с аутентификацией пользователей (отдельный change), он дополнит аудит
своим субъектом, схема аудита расширяется колонкой, а не заменяется.

**Права.** Явно, а не полагаясь на `ALTER DEFAULT PRIVILEGES` (по умолчанию `ktm_app` получил бы `INSERT`):
`REVOKE ALL ... FROM PUBLIC, ktm_app` на обе таблицы, затем `GRANT SELECT ON ktm.rejection_rules TO ktm_app`;
к `rejection_rule_audit` у `ktm_app` доступа нет. Data Saver правила только читает: он не может ни изменить критерии
отбраковки, ни стереть аудит. Менять правила может `ktm_migrator` (владелец схемы) или роль, которую администратор выдаст
отдельно; отдельную роль `ktm_rules_admin` `db/init` не создаёт (init - ручной шаг суперпользователя, расширять его ради
временного пути нерационально). Вопрос владения таблицей при появлении REST API на EF Core решается отдельным ADR, как и
оговорено в ADR-0004 п. 3 и «Триггерах пересмотра»: до тех пор схемой `ktm` управляют SQL-файлы.

**Оповещение об изменении.** Statement-level триггер `AFTER INSERT OR UPDATE OR DELETE OR TRUNCATE` вызывает
`pg_notify('ktm_rejection_rules_changed', '')` (п. 2.6). `NOTIFY` доставляется при COMMIT, поэтому сервис никогда не увидит
полуприменённое изменение.

Миграции идемпотентны (`IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION`, триггеры через `DO`-блоки с проверкой `pg_trigger`;
примеры - `INSERT ... ON CONFLICT (rule_id) DO NOTHING`), поэтому проходят метатест «каждый `V*.sql` дважды» (ADR-0004 п. 5).
Следствие повторных прогонов `migrate`: **удалённый пример появится снова**; правило выключают (`enabled = false`), а не
удаляют (описано в `docs/manuals/rules-engine.md`). Изменённые вручную примеры повторный прогон не затирает (`DO NOTHING`).

### A.2. Загрузка по `LISTEN/NOTIFY` (ред. 1, п. 2.9)

Источник истины - таблица. В сервисе держится снимок: неизменяемый объект (правила, индекс по источникам, список ошибочных
правил), ссылка на который заменяется атомарно; стадия берёт ссылку один раз на сообщение.

**Триггеры перезагрузки:**

1. **Периодически** - `DataSaver__Rules__RefreshIntervalSeconds` (по умолчанию 60, допустимо 5..3600). Это гарантированный
   нижний предел: изменение вступит в силу не позже чем через интервал.
2. **По команде - `LISTEN/NOTIFY` PostgreSQL.** Триггер на таблице (п. 2.2) шлёт `NOTIFY ktm_rejection_rules_changed` при
   коммите любого изменения; сервис держит одно выделенное соединение (`ktm_app`, `LISTEN`; права сверх `CONNECT`
   не нужны), на уведомление перечитывает таблицу не чаще раза в секунду (склейка пачки уведомлений). Администратору
   «команда» ничего не стоит: достаточно выполнить обычный `UPDATE` (изменение вступает в силу за ~1-2 с); без правки
   данных - `SELECT pg_notify('ktm_rejection_rules_changed', '')`. Если соединение `LISTEN` потеряно, сервис
   переподключается с backoff и перечитывает таблицу; пока его нет, работает периодическое чтение (п. 1), поэтому `NOTIFY` -
   ускорение, а не единственный механизм.

**Почему не другие варианты** (рекомендация - NOTIFY + опрос):

- *Сигнал (SIGHUP).* Проще по коду, но: на dev-стенде процесс - контейнер на Linux (`docker kill -s HUP`), у разработчика на
  Windows сигнала нет; администратору БД, правящему правило, нужен ещё и доступ к хосту сервиса; изменение и команда
  - два шага, которые легко разделить забывчивостью. Отклонено.
- *Админ-эндпоинт `POST /admin/rules/reload` на порту health.* В Data Saver нет аутентификации; открывать на порту,
  который читает оркестратор, неаутентифицированную операцию - новая поверхность атаки, а делать авторизацию ради одной
  кнопки - объём не этого этапа. Отклонено; вернуться, когда появится общий API с ролевой моделью (`docs/04`).
- *Только опрос.* Удовлетворяет «раз в минуту», но не «по команде». Отклонено как недостаточное.
- *Debezium/CDC и т. п.* Несоразмерно.

Ограничения и последствия `LISTEN`: нужно постоянное соединение вне пула (`NpgsqlConnection`, `KeepAlive`, один экземпляр на
процесс); не работает через pgbouncer в режиме `transaction` (на стенде прямое подключение; при его смене остаётся
опрос - сервис не ломается); одно соединение на экземпляр Data Saver приемлемо.

**Проверка корректности при загрузке.** Каждое включённое правило компилируется отдельно: структура условия по п. 2.3,
пути (п. 2.4), типы значений и допустимость операций, дата-значения, регэксп (п. 2.6), лимиты, допустимость `source`
(`skud`, `cv`, `1c-do` или `NULL`). Ошибочное правило **не попадает в снимок** (применение «всё или ничего» ко всей
таблице отвергнуто: одно плохое правило не должно выключать остальные), в лог пишется Error с `RuleId`, `RuleVersion`
и текстом ошибки (без значений из сообщений - их при загрузке нет), счётчик/gauge ошибочных правил растёт. Повтор той же
ошибки того же `(rule_id, version)` в логе ограничивается `LogThrottle` (раз в час), чтобы минутный цикл не заливал лог.
Когда правило исправлено, оно вступает в силу в следующем снимке. Отключённые правила (`enabled = false`) не проверяются.
Известный риск (разбирается в `docs/manuals/rules-engine.md` и риске R-3 design): правка, превратившая рабочее правило в ошибочное,
выключает его - брак снова пойдёт в журнал; страхуется gauge `ktm.datasaver.rules.invalid` для алерта. Оставление «последней
валидной версии этого правила» отклонено: скрывает ошибку правки, усложняет модель снимка и расходится с требованием
«ошибочное правило не применяется».

**Недоступность БД правил.** Сервис держит **последний валидный снимок** и продолжает отбраковывать по нему. Неудачное
чтение: Warning в лог (`LogThrottle`), метрика `ktm.datasaver.rules.reloads{result="failed"}`, повтор в штатный срок опроса
(с backoff по `BackoffPolicy` не нужен: интервал и так минутный). Если снимка ещё нет (первая загрузка не удалась), сервис
**не начинает читать Kafka** и не готов (`/health/ready` = не готов, причина в логе): писать в необратимый журнал мусор «в
открытую» хуже, чем подождать, а БД правил - та же БД журнала, без неё запись всё равно невозможна. Первая загрузка выполняется
до старта цикла приёма (порядок регистрации hosted-сервисов: загрузка правил -> `DataSaverWorker`); ошибка доступа к таблице
(нет прав, нет таблицы - `42P01`/`42501`) на первой загрузке - конфигурационная ошибка (код выхода 78, как у ошибок настроек).
Устаревание снимка наблюдается метрикой `ktm.datasaver.rules.snapshot_age`; в готовность не входит (потеря связи
с БД правил на минуты не должна останавливать приём, пока работает запись).

Что уже записано, повторно не проверяется: изменение правила действует на сообщения, начатые обработкой после замены
снимка; ретроактивной отбраковки нет (журнал неизменяем), отбракованное правилом автоматически назад в обработку
не возвращается (повтор `rejected` - ручная операция, kafka-event-format.md п. 3).

Настройки (`DataSaver__Rules__*`, проверка при старте, как у прочих опций): `Enabled` (по умолчанию `true`; `false` -
стадия не регистрируется и таблица не читается, аварийное отключение без пересборки), `RefreshIntervalSeconds` (60),
`ListenEnabled` (`true`), `RegexTimeoutMs` (200, 1..1000), `MaxRules` (500).
`MaxRules`: если включённых правил больше, загружаются первые `MaxRules` по порядку п. 2.7, остальные не применяются, Error в
лог - ограничение объёма вычислений и кардинальности метрик (п. 2.11).
