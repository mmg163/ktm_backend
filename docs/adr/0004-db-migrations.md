# ADR-0004. Миграции БД журнала событий: идемпотентные SQL-скрипты

- Статус: принят (утверждено лидом проекта, 2026-11-20); дополнен 2026-11-21 (раздел 5, решение лида, `openspec/changes/add-data-saver-migrate-job`)
- Дата: 2026-11-20
- Область: схема `ktm` (журнал событий), `openspec/changes/add-data-saver-core`
- Связанные документы: `docs/design/Схема_БД_ER.md` (п. 6-9), ADR-0001, ADR-0002.
- Изменения: раздел 5 (автоматический накат разовым контейнером) заменяет п. 4, второй абзац «оператор следит за порядком сам»; остальное решение (разделы 2-4) в силе.

## 1. Контекст

Готового скрипта миграции в репозитории нет: есть только справочный DDL (`Схема_БД_ER.md` п. 9). Владелец схемы скрипт
отдельно не поставит, поэтому его делает этот change. Требования схемы к миграциям (п. 6-8):

- применяются ролью `ktm_migrator`, приложения под `ktm_app` (`SELECT, INSERT`) миграции не применяют;
- идемпотентны на пустой БД: двукратный запуск - оба раза код 0, схема не меняется;
- содержимое почти целиком специфично для TimescaleDB: `create_hypertable`, `ALTER TABLE ... SET (timescaledb.compress...)`,
  `add_compression_policy`, триггер неизменяемости, `REVOKE/GRANT`, `DO`-блоки для проверки роли и расширения;
- интеграционные тесты должны применять тот же файл, что и среды, иначе тесты проверяют не ту схему (риск R-3/R-6).

## 2. Решение

**Версионируемые SQL-скрипты в репозитории, без EF Core migrations.**

```
db/init/001_roles_and_extension.sql     суперпользователь, один раз: роли ktm_migrator/ktm_app, схема ktm, CREATE EXTENSION timescaledb
db/migrations/V001__event_journal.sql   под ktm_migrator: events, event_corrections, hypertable, индексы, триггер, компрессия, права
db/migrations/V002__...                 следующие изменения схемы (по одному файлу, имя - порядковый номер + смысл)
db/README.md                            порядок применения, команда psql, проверка идемпотентности
```

Правила файлов:

- каждый файл идемпотентен сам по себе (`IF NOT EXISTS`, `if_not_exists => TRUE`, `DO`-блоки); таблицы истории применённых
  версий нет - порядок задаёт имя файла, повторный прогон безопасен;
- только простой SQL: без метакоманд `psql` (`\i`, `\set`), без `CREATE INDEX CONCURRENTLY`, чтобы один и тот же файл
  выполнялся и через `psql -v ON_ERROR_STOP=1`, и через Npgsql в тестах;
- уже применённый файл не правится: изменение схемы - новый файл `V00N`;
- применение в средах: `psql -v ON_ERROR_STOP=1 -f` по порядку под `ktm_migrator` (в compose-развёртывании - контейнером `migrate`, раздел 5); `db/init` - администратор.

Тесты: фикстура Testcontainers (`timescale/timescaledb:*-pg16`) выполняет `db/init/*.sql` под суперпользователем и
`db/migrations/V*.sql` под `ktm_migrator`, читая файлы из репозитория (не копии); отдельный тест применяет миграции
дважды и сравнивает схему (`pg_dump --schema-only` или выборка из `information_schema`/`pg_indexes`/`timescaledb_information`).

## 3. Альтернативы

- **EF Core migrations + `migrationBuilder.Sql(...)`.** Отклонено: (1) EF-модель журнала не нужна, так как Data
  Saver работает через Npgsql (ADR-0002, D-2), поэтому модель была бы нужна только ради миграций, а файл миграции состоял бы
  из `Sql("...")` на 100 % содержимого (hypertable, компрессия, триггер, гранты) - оболочка без пользы; (2) приложение с EF
  Core получило бы зависимость и привилегии DDL, а политика схемы - миграции только под `ktm_migrator`; (3) идемпотентность
  «дважды без ошибок» в EF обеспечивается таблицей истории, а не самим скриптом - расхождение с критерием схемы п. 8; (4) ручная
  правка снапшота модели при изменениях Timescale-объектов, о которых EF не знает. Вернуться к вопросу можно, когда появится
  REST API с CRUD-таблицами (правила, роли, инциденты) на EF Core: тогда отдельным ADR решается, чьи это таблицы и кто их
  мигрирует. Смешивать два инструмента на одной схеме `ktm` без такого решения нельзя.
- **Flyway/DbUp/Liquibase.** Дают таблицу истории и раннер, но это новая зависимость или внешний инструмент ради двух файлов;
  вернуться, если файлов станет много и понадобится учёт применённых версий.
- **Хранить скрипт в `docs/design/`.** Документ - справочный; исполняемый артефакт должен лежать вне `docs/`.

## 4. Последствия

- Задача по созданию `db/` включена в `tasks.md` (группа 4A, до записи в БД и интеграционных тестов); из открытых вопросов пункт
  «где скрипт B3» снят.
- Учёта применённых версий нет; порядок и полноту наката обеспечивает разовый контейнер `migrate` (раздел 5), а не оператор. Допустимо, пока все файлы идемпотентны.
- Любое изменение `Схема_БД_ER.md` п. 9 после появления `db/migrations/` вносится новым скриптом; п. 9 остаётся справочным
  и должен получить ссылку на `db/`.
- Расхождение между DDL в документе и файлом выявляется ревью; источник истины - файл в `db/migrations/`.
- Версия TimescaleDB: скрипты проверены на 2.32.1; 2.31 (значение из первых черновиков схемы) не проверялась и блокером не
  является. Образ для тестов фиксируется тегом (`timescale/timescaledb:2.32.1-pg16`), а не `latest`; на стенде предприятия
  с другой версией прогон проверок `db/README.md` повторяется до приёмки.
- Пароли ролей `db/init` не задаёт и в репозиторий не кладёт: администратор задаёт их отдельно (`db/README.md`).
- `db/init` не меняет владельца существующей схемы `ktm` (при несовпадении владельца завершается ошибкой), чтобы повторный
  запуск не передавал владение молча.
- Отступления от первоначального DDL (нет `REVOKE ALL ON DATABASE`, на `public` только `REVOKE CREATE`, защита от `TRUNCATE`
  и её пределы) зафиксированы в `Схема_БД_ER.md` п. 5.
- `V001` ещё не применялась ни в одной среде (ветка не влита), поэтому до слияния её допустимо править на месте; правило
  «применённый файл не правится» действует с момента первого применения вне стенда разработки.

## 5. Дополнение 2026-11-21: автоматический накат разовым контейнером `migrate`

### Контекст

Ручной накат (п. 4) допускает старт Data Saver на немигрированной базе (конфигурационная ошибка записи `42P01`, бесконечный
повтор), на частично применённых файлах и одновременный накат с двух машин. Со вторым `V`-файлом риск растёт.

### Решение

Расширение п. 2, а не замена: файлы, их правила и роли не меняются; меняется исполнитель.

- В `deploy/data-saver/compose.yml` добавляется разовый сервис `migrate` (`restart: "no"`): образ официальный
  `postgres:16-alpine` с фиксированным тегом (лицензия PostgreSQL License, бесплатно; нужен только `psql` 16), скрипт-обёртка
  `deploy/data-saver/migrate/migrate.sh` и `db/` монтируются только на чтение. Собственного образа нет.
- `data-saver` стартует после `migrate` (`depends_on: condition: service_completed_successfully`) и остаётся под `ktm_app`
  без DDL.
- Скрипт: файлы `V*.sql` по возрастанию имени; один сеанс `psql` на файл с `-v ON_ERROR_STOP=1`; на весь прогон
  `pg_advisory_lock` (ключ `hashtextextended('ktm:schema-migration', 0)`; сначала `pg_try_advisory_lock`, при занятости -
  ожидание под `lock_timeout`, живость проверяется запросом) в отдельном сеансе-держателе (метакоманды `psql` - только в обёртке, в `V`-файлах по-прежнему нет); при
  ошибке - ненулевой код, сервис не стартует, причина в `docker compose logs migrate`.
- Пароль `ktm_migrator` - только файл Docker secret `secrets/ktm_migrator_password` (`chown 1654:1654`, `0400`, как у
  `ktm_app`); в `.env`, образ сервиса, argv и окружение не попадает (скрипт строит `PGPASSFILE` в tmpfs). Хост, порт, база и
  `SslMode` (по умолчанию `Require`) - те же переменные `DataSaver__Postgres__*`, пользователь всегда `ktm_migrator`.
- Не автоматизируется и остаётся ручным шагом администратора под суперпользователем: `db/init`, роли, расширение
  `timescaledb`, схема `ktm`, пароли ролей.
- Имена файлов `V<1-9 цифр>__<смысл>.sql` (ASCII), порядок по номеру обязан совпадать с порядком по имени (нужны
  ведущие нули: `V002`, `V010`). Образ `postgres:16.16-alpine3.24`. Коды выхода: 1 - SQL, состав, подключение; 2 -
  конфигурация; 3 - таймаут блокировки, потеря сеанса.
- Подробности и проверки - `openspec/changes/add-data-saver-migrate-job` (design, spec, tasks).

### Альтернативы

- **Накат при старте Data Saver.** Отклонено: нужен DDL у `ktm_app`, нарушаются ADR-0001 (стр. 24: приложения не применяют
  миграции при старте и работают под `ktm_app`) и принцип минимальных прав `docs/04-ролевая-модель.md`; ослабляется защита
  неизменяемости журнала.
- **Остаться на ручном накате.** Отклонено лидом: развёртывание должно быть воспроизводимым.
- **Flyway/DbUp сразу.** Отложено: триггер ниже.
- **Образ `timescale/timescaledb` как клиент; собственный образ `alpine` + `apk add`.** Отклонено: лишний серверный образ со
  смешанной лицензией либо лишняя сборка ради выигрыша в размере.

### Триггеры пересмотра (сохраняются)

- Первый неидемпотентный `V`-файл (повторный запуск меняет схему или данные либо падает) - вводится таблица истории
  применённых версий и готовый инструмент (DbUp или Flyway Community); до этого такой файл не добавляется. Это условие
  охраняется тестом, прогоняющим каждый `V*.sql` дважды (задача 2.3 change).
- Появление EF Core-таблиц конфигурации (REST API) - отдельное решение о владельце схемы (см. раздел 3).

### Последствия

- `docker compose up` требует секрет `ktm_migrator_password`; администратор задаёт пароль роли (`db/README.md`).
- Прогоняются все файлы при каждом запуске (истории нет); приемлемо при единицах файлов.
- `depends_on` не действует при перезапуске контейнеров демоном Docker; схема к тому времени уже накачена.
- Пароль роли-владельца схемы лежит на `dev-backend` файлом `0400` (Docker secret, как у `ktm_app`, подключён только к
  `migrate`): расширение поверхности риска, решение лида проекта (2026-11-21).
- Автотестов немного (двукратный прогон, неверный SQL, метатест идемпотентности); порядок, параллельный накат, `SslMode` и
  секрет проверяются вручную один раз (`docs/test-protocols/data-saver-migrate-job.md`). `SslMode=Verify*` и сертификаты вне
  объёма.
- Проверка: двукратный запуск `migrate` - код 0 и неизменный `pg_dump --schema-only -n ktm`.
