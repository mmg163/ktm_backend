# ADR-0003. Data Saver: конвейер стадий, отбраковка и точка расширения под движок правил

- Статус: принят (утверждено лидом проекта, 2026-11-20)
- Дата: 2026-11-20
- Область: Data Saver, `openspec/changes/add-data-saver-core`; расширение под правила отбраковки - **вне объёма**,
  но точка расширения закладывается сейчас
- Связанные документы: `docs/03-архитектура.md` п. 3.2 («Валидатор и фильтр»), `docs/05-источники-данных.md` п. 5.1,
  `docs/api/kafka-event-format.md` п. 3, ADR-0002

## 1. Контекст

Между чтением из Kafka и записью в журнал нужны шаги, которые решают «писать / не писать»:

1. **Формат** (обязателен по `kafka-event-format.md` п. 3): не JSON, неизвестная `schemaVersion`, не прошло схему ->
   `ktm.events.rejected`, offset фиксируется.
2. **C5** - проверка событий (внешняя зависимость, содержимое неизвестно; до неё отбраковки по `eventType` нет).
3. **C6** - обработка ошибок записи (внешняя зависимость).
4. **Будущее:** движок правил отбраковки: событие, подпавшее под правило, в БД не пишется, а уходит в отдельный топик с
   указанием сработавшего правила.

Все четыре должны вставать в конвейер без переделки цикла чтения/записи/commit. Главный риск - учёт offset:
отбракованное сообщение обязано продвигать offset так же, как записанное.

Граница уровней: `docs/03` п. 3.2 относит «Валидатор и фильтр» к уровню 1 (отбраковка ошибочных, дублирующихся, неполных
записей), а правила интерпретации (роли, смены, оценки) - к уровню 2. Инвариант проекта: уровень 1 не знает о правилах и
оценках. Поэтому будущие правила Data Saver допустимы **только как правила качества данных**.

## 2. Решение

### 2.1. Конвейер

```
Consume -> Decode (JSON + schemaVersion + схема v1)             [встроено, обязательная стадия]
        -> IIngestionStage[] (по порядку регистрации):
              EventValidationStage   -> порт IEventValidator (C5), по умолчанию принимает всё
              (будущее) RuleRejectionStage -> движок правил      [ВНЕ ОБЪЁМА]
        -> Classify (событие | корректировка)
        -> Batch -> Write (БД, D-2 ADR-0002) + Publish rejects -> Commit offset
```

Каждое сообщение после стадий получает вердикт: `Accept` или `Reject(RejectionInfo)`. `RejectionInfo` содержит
`Kind` (`Format` | `Validation` | зарезервировано `Rule`), `Reason`, `Detail`, `RuleId` (необязателен) и
`TargetTopic` (необязателен; по умолчанию `ktm.events.rejected`). Стадия `IIngestionStage` - чистая функция
«сообщение -> вердикт» без побочных эффектов (публикует и пишет не она, а пачка), поэтому отбраковка не может
«забыть» offset: пачка хранит все сообщения с вердиктами и считает offset по всем (ADR-0002, D-6).

Ограничения на стадии (чтобы расширение не нарушало NFR и инварианты):
- стадия не обращается к БД журнала синхронно на каждое сообщение (иначе сбой БД блокирует разбор); данные для правил
  - из кэша «последняя известная конфигурация» с обновлением в фоне;
- стадия не меняет тело сообщения (журнал хранит сообщение как получено);
- исключение внутри стадии не превращается в отбраковку: иначе дефект кода молча уводит события в `rejected`. Оно
  трактуется как сбой обработки пачки (класс Fatal-config: повтор, `Degraded`, лог Error), событие не теряется.

### 2.2. Отбраковка по формату (в объёме)

Заголовки и причины - строго по `kafka-event-format.md` п. 3: `ktm-reject-reason` (`unknown_schema_version`,
`invalid_schema`, `malformed_json`), `ktm-reject-detail`, `ktm-source-topic`, `ktm-source-partition`,
`ktm-source-offset`; тело и ключ - исходные. Дополнительные случаи Data Saver (размер > 64 КиБ, `\u0000`, ссылка
корректировки на саму себя, `occurredAt` не UTC) используют `invalid_schema` с пояснением в `detail` (новая причина
изменила бы контракт, ADR-0002 G-5). Публикация - идемпотентный producer, `acks=all`, до commit offset.
Также: лог ошибки уровня Error и вызов порта `IAdminNotifier` (по умолчанию - только лог и счётчик; канал уведомлений -
вне объёма, `docs/05` п. 5.1). Отбраковка - технический инцидент интеграции, оценок сотрудника не касается.

Проверка схемы - по `docs/api/kafka-event.schema.json`, подключённому в проект как встроенный ресурс (одна копия правды;
JSON Schema draft 2020-12; проверка `format: date-time` включается явно - по умолчанию это аннотация).

### 2.3. Порты C5 и C6 (в объёме - только контракт и заглушка)

- `IEventValidator.Validate(ParsedEvent) -> ValidationResult { Accept | Reject(reason, detail) }` (C5). Заглушка -
  `AcceptAllEventValidator`. Содержимое правила (неизвестные `eventType`, окно `occurredAt`) - в C5.
- `IWriteFailureHandler.HandleAsync(WriteFailureContext) -> WriteFailureDecision { Retry | DeadLetter(items) }` (C6),
  вызывается **только для класса Data** (ADR-0002, D-7). Заглушка - `BlockingWriteFailureHandler`: решение `Retry`
  (пауза, `Degraded`, лог Error на каждой попытке). Заглушка ничего не теряет и ничего не пропускает, но блокирует
  партицию до устранения причины; это сознательный «безопасный по умолчанию» выбор до появления C6. Топик
  `ktm.events.dlq` заглушка не использует.

### 2.4. Движок правил отбраковки (ВНЕ ОБЪЁМА; закладывается интерфейс)

Что фиксируется сейчас, чтобы позже не менять конвейер:

1. `Reject` с `Kind = Rule`, `RuleId`, `TargetTopic` уже есть в модели `RejectionInfo`; публикатор отбраковок маршрутизирует по
   `TargetTopic`, а не по константе.
2. Отбракованное правилом сообщение **не пишется в БД**, offset продвигается наравне с записанными (по построению D-6).
3. Рекомендация для будущего change: отдельный топик (например `ktm.events.rule-rejected`) и заголовки
   `ktm-reject-reason=rule_matched`, `ktm-reject-rule-id`, `ktm-reject-rule-version` плюс стандартные `ktm-source-*`;
   отдельный топик, потому что это не технический инцидент интеграции и у него другой получатель. Новый топик создаётся
   ansible-ролью `infra/kafka`; новая причина - изменение контракта `kafka-event-format.md` (согласуется с адаптерами).
4. Правила хранятся в БД и меняются через API с записью в аудит (инвариант «правила настраиваются через API/хранилище»,
   «изменение правила попадает в аудит»), версионируются; в стадии - снимок конфигурации (п. 2.1, ограничение 1).
5. Правила допустимы только как проверки качества данных над самим сообщением (поля, формат, допустимые значения,
   плотность). Любая ссылка на сотрудника, роль, смену, оценку - нарушение границы уровней и в Data Saver недопустима.

## 3. Альтернативы

- **Отбраковка прямо в цикле чтения (`if`-ы).** Быстро, но каждое новое правило ломает учёт offset и тесты цикла. Отклонено.
- **Отбраковка после записи (запись всё, потом помечать).** Нарушает требование «не пишется в БД»; журнал неизменяем,
  отмена невозможна. Отклонено.
- **Отдельный сервис-фильтр между адаптерами и Data Saver.** Дополнительный сервис, дополнительный топик, лишняя задержка;
  без выигрыша для объёма 500 соб/с. Можно пересмотреть, если правила станут тяжёлыми.
- **Ошибка стадии = отбраковка.** Дефект кода молча уводит события в `rejected`. Отклонено (п. 2.1).
- **Сразу писать `dlq` для ошибок записи (до C6).** Содержимое политики C6 неизвестно; решать за неё нельзя.

## 4. Последствия

- Цикл Data Saver не знает, какие стадии подключены; добавление стадии - регистрация в DI и тесты стадии.
- Тесты конвейера (в объёме): «отбракованное сообщение продвигает offset», «пачка из одних отбракованных коммитит offset без
  обращения к БД», «ошибка публикации rejected не коммитит offset». Они же защищают будущее расширение.
- C5 и C6 подключаются заменой реализации порта; Data Saver не перекомпилируется в части цикла.
- Открыт вопрос: нужен ли пользователю вариант C6 «по умолчанию в `dlq` после N попыток» вместо блокировки (решает C6).
