# 4. Ролевая модель доступа

## 4.1. Общие принципы

- конфиденциальность персональных данных и оценок;
- минимальные необходимые привилегии;
- разделение обязанностей и исключение конфликтов интересов;
- аудируемость действий пользователей;
- обезличивание данных в сводных отчётах, если персонализация не требуется для
  решения задачи;
- ограничение доступа руководителя рамками своих подразделений и подчинённых
  структур.

## 4.2. Основные роли

| Роль | Основные права |
|---|---|
| Собственник / топ-менеджмент | Просмотр агрегированных дашбордов, зон риска, эффекта внедрения и сводных отчётов без избыточной персонализации. Персональные данные доступны только при наличии служебной необходимости и прав |
| Начальник цеха / руководитель подразделения | Просмотр состояния своего подразделения, инцидентов, причин отклонений и рекомендуемых действий |
| Мастер смены | Подтверждение производственного контекста, работа с инцидентами смены, комментарии и закрытие причин |
| Служба безопасности | Работа с событиями доступа, зонами ограниченного доступа, внештатными входами и режимными инцидентами |
| Кадровая служба | Просмотр базовых кадровых сведений, участие в регламентных процедурах без самостоятельного изменения расчётных оценок |
| Администратор Системы | Настройка справочников, ролей, правил, источников и мониторинг технического состояния |
| IT-администратор | Контроль доступности интеграций, технических сбоев и инфраструктурных событий |
| Аналитик | Просмотр агрегированных и разрешённых детальных данных без права принятия управленческих решений |

Администратор Системы не должен иметь права незаметно изменять расчётные
значения, историю событий или аудиторские записи. Все изменения настроек должны
фиксироваться в журнале аудита.

## 4.3. Разграничение доступа на уровне данных

Система должна автоматически ограничивать доступ к данным по подразделению,
роли, зоне ответственности и назначенным полномочиям. Руководитель подразделения
видит данные своего подразделения и вложенных подразделений, если это
предусмотрено организационной структурой.

## 4.4. Аудит действий пользователей

| Категория | Действия, подлежащие аудиту |
|---|---|
| Вход в систему | Успешный вход, неудачная попытка, выход, блокировка учётной записи |
| Просмотр данных | Открытие дашборда, просмотр профиля сотрудника, просмотр кейса, формирование отчёта |
| Изменение настроек | Создание, редактирование и удаление ролей, правил, источников, коэффициентов доверия |
| Работа с инцидентами | Назначение ответственного, изменение статуса, добавление комментария, подтверждение, оспаривание, закрытие |
| Экспорт | Выгрузка отчётов в PDF, Excel, CSV |
| Администрирование | Изменение прав доступа, создание пользователей, настройка интеграций, калибровка справочников |

## 4.5. Запрещённые сочетания ролей

- Администратор Системы и топ-менеджмент в одном пользовательском аккаунте;
- Администратор Системы и служба безопасности без отдельного утверждения;
- Руководитель подразделения и кадровая служба при возможности влияния на профили
  сотрудников;
- Аналитик и руководитель подразделения, если это нарушает независимость
  аналитики.
